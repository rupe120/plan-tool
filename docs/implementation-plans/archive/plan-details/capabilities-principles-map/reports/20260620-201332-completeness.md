The chosen mitigation is the option most vulnerable to the risk it answers.
- MEDIUM `[honesty-check-placement]`: Part C houses a repo-wide, plan-independent check (CAPABILITIES.md vs CLI surface vs MISSION.md) inside `review.collect_smell_findings`, which is invoked per single named plan from `validate` (`collect_smell_findings(plan, ctx.repo_root, plan_name=args.name)`) and the per-plan completeness layer. The capability check never reads `plan`, so it re-emits identical repo-wide findings once per plan and attributes them to whatever plan happens to be validated — noise that scales with plan count and misleads on ownership.
- MEDIUM `[baseline-restamp-on-drift]`: Part B fingerprints `CAPABILITIES.md` itself as fingerprint input (c) yet the drift→Claude pass edits `CAPABILITIES.md`, and the acceptance criterion re-stamps the baseline only "after a **clean** reconcile". After a drift run rewrites `CAPABILITIES.md`, its content no longer matches the baseline, so every subsequent `reconcile-mission` re-detects drift and never converges — unlike `reconcile-plan --refresh`, whose drift gate keys on the *code* fingerprint it never edits.
- MEDIUM `[cli-surface-fingerprint-input]`: Part B says the baseline fingerprints "the CLI surface … content-hash, the way completeness reports carry a `code_fingerprint`", but `compute_code_fingerprint` hashes *file contents* of `step.files`, whereas the CLI surface is argparse introspection (`cli_reference._subparsers_action`/`_alias_map` over `_choices_actions`) with no backing file to hash. The cited mechanism cannot fingerprint the subcommand/flag inventory as written.
- MEDIUM `[drift-surface-attribution]`: Part B promises to "re-reconcile only the changed surfaces" on drift across three heterogeneous inputs (MISSION.md, the CLI surface, `CAPABILITIES.md`), but never defines how a drifted surface maps to a scoped reconcile action — what the Claude pass does differently when only MISSION drifts (re-fit principle refs) vs only the CLI surface drifts (re-fit surfaces) vs `CAPABILITIES.md` was hand-edited. Without that mapping "only the changed surfaces" is unoperationalized.
- HIGH `[convergence-loop-non-plan-target]`: Part B asserts the drift→Claude pass "output lands as advisory findings and under `--iterate` converges (gates → `apply_finding` → re-audit)," but that loop (`convergence.py`, `auto_reconcile.run_auto_reconcile_on_drift`) is built around `Plan` objects and edits plan/detail prose; `reconcile-mission` must instead apply edits to `CAPABILITIES.md`, which is not a plan and has no `apply_finding` path or apply-eligible source. The plan reuses plan-centric convergence machinery for a non-plan target without establishing it can act there.
- MEDIUM `[alias-subcommand-enumeration]`: Part C's orphan-subcommand check must enumerate the subcommand set the way `cli_reference` does — over `action._choices_actions` (primary names only) — or it will treat command aliases as distinct subcommands and flag them as uncatalogued. `reconcile-plan`, `verify-all`, and `reconcile-plan-walk` carry real aliases (`reconcile`/`review`, `reconcile-all`/`review-all`/`verify`, `reconcile-walk`/`review-walk`), so a naive `action.choices` walk yields false orphans.
