- HIGH `[idempotent-rollback-replay]` [confidence: limited]: The eligibility predicate and the idempotent-replay guarantee contradict each other, and nothing in the plan resolves the conflict. Architecture states the eligibility check is "a closed predicate over four independently-triggerable conditions: the accepted head names exactly the root version, no candidate admission exists, no pending generation is recorded, and no roadmap seed state with `status: "current"` is tracked" and that "any one violated condition is a refusal, not a partial rollback." But `accepted-head.json` is a single selector file (`roadmap_versions.py:accepted_head_path`, `load_accepted_head`) that a successful rollback clears — and `load_accepted_head` returns `None` both when the roadmap was never enrolled and after a prior rollback already cleared it, so the two states are indistinguishable by that file alone. That means on a replay call, condition 1 ("accepted head names exactly the root version") is false for the same reason it would be false for "never enrolled" — yet step 1's own stated intent requires the opposite: "idempotent replay can tell 'already rolled back' apart from 'never enrolled.'" The Acceptance criteria likewise require "a repeated call with the same named target version id recomputes the identical receipt address and gets `EVIDENCE_EXISTING` rather than writing a second receipt or erroring," and Architecture places the receipt write "before clearing the selector" — i.e., downstream of the same eligibility gate that a replay cannot pass. Nothing in the plan says a replay takes a different path (e.g., checking for an existing receipt before, or instead of, re-evaluating condition 1); as written, a literal implementation of the stated eligibility check would refuse a replay with an ordinary "not eligible" error rather than the promised idempotent "already rolled back" report.
  - Fix: State explicitly how the rollback route recognizes an already-completed rollback for the named target version id — for example, by checking for an existing receipt at the computed content address before (or instead of) re-evaluating the "accepted head names the root" condition — so a second call is routed to the idempotent "already rolled back" outcome rather than falling into the same refusal path as "never enrolled."
- MEDIUM `[rollback-receipt-content-address]` [confidence: limited]: The "confirmed-intent marker" that Architecture names as one of the three inputs to the receipt's content address is never defined, and the two readings produce different behavior. Architecture says the address is "derived only from stable identifying facts — the roadmap slug, the target root's version id, and the confirmed-intent marker — never from the rollback timestamp," while the same section separately says the CLI confirmation "names the exact target root version id rather than a bare yes/no." If "confirmed-intent marker" means a fixed literal constant (the pattern `roadmap_escalation.py`'s `EscalationReceipt` already uses via its constant `feedback_state: "open"` semantic field, folded into `semantic_id`), the address is stable across replays as intended. If it is instead read as derived from the operator's own confirmation input — plausible since the plan describes confirmation as "naming" the version id, and no other candidate value is given for the marker — two calls with differently-formatted (but equally valid) confirmations, or confirmations issued by different operators, would compute different addresses, silently breaking the very replay-idempotence property the plan requires elsewhere.
  - Fix: Define the confirmed-intent marker as a fixed literal value, not any operator-supplied or call-specific text, so the three named inputs necessarily reproduce the same address on every call for the same (slug, target version id) pair.
- MEDIUM `[receipt-mechanism-citation]` [confidence: limited]: The References section misattributes `receipt_worktree_for_plans_dir` to `roadmap_escalation.py`: "Check whether the existing git-committed receipt mechanism in `roadmap_escalation.py` (`build_receipt`/`render_receipt`/`receipt_worktree_for_plans_dir`) already fits before adding a second receipt implementation." `build_receipt` and `render_receipt` do live in `roadmap_escalation.py`, but `receipt_worktree_for_plans_dir` is defined in `roadmap_escalation_run.py`. This doesn't change the plan's conclusion (it still correctly rejects the escalation receipt shape in favor of `publish_evidence`), but a reader chasing this citation during `detail` will look in the wrong file.
  - Fix: Correct the module name in the References citation to `roadmap_escalation_run.py` for `receipt_worktree_for_plans_dir`.
