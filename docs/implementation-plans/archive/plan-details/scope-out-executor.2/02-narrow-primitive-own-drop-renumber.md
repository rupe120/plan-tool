# Step 2 — Add the narrow primitive: own drop-renumber + `depends_on` repair + detail migrate/archive + CURRENT cursor, with dry-run preview and apply-or-rollback

## Summary

Adds the structural half of scope-out to `plan_tool/scope_out.py` (the leaf step 1 created): a deterministic `compute_narrow(...)` that builds a **dry-run preview** of the narrowed plan (drop the carved step, renumber survivors to a contiguous `1..N-1`, repair every `depends_on` edge, plan the downstream detail-file renames + the carved step's archive, promote a post-drop runnable survivor to CURRENT only when dropping the plan's sole CURRENT, and complete the top-level plan when all committed survivors are DONE and no CURRENT is promoted), plus an `apply_narrow(...)` that commits that preview **all-or-nothing with rollback**. The primitive writes its **own** drop-renumber (there is no survivor to fold onto, so `create._apply_step_merge` does not fit) and owns an explicit downstream detail-file journal for rename/archive side effects; `detail._migrate_downstream_details_after_merge` is not called unless wrapped in a snapshot/restore layer that treats every helper side effect as rollback-managed. The most important decision is that `compute_narrow` *detects* the structural blockers (non-canonical step numbering, inbound dependent on the carved step, a downstream non-PENDING step that would renumber, an empty-plan result, a missing step) and `apply_narrow` refuses to touch disk when any are present — but the **policy** layer (seed-first sequencing, opt-in flag, TTY confirm, the `EscalateResult`-style return) stays in step 3. On green, `tests/test_scope_out.py` proves the preview math (renumber/repair/cursor/status) is correct and deterministic, the blockers fire on the unsafe shapes, and a forced mid-apply failure rolls back to the exact pre-narrow state.

## Why

The convergence diagnostic recommends carving a spinning region out of a plan, and step 1 added the pure seed renderer, but nothing yet *narrows the plan*. No existing executor drops a step: `detail.split_step` is one→many and `detail.merge_steps` (via `create._apply_step_merge`) folds many→**one survivor** and repoints dependents to it. A drop has **no survivor to repoint to**, so reusing the merge renumber would corrupt the graph silently — the dropped id gets reused by a different step with no validation crash. This step builds the narrow as its own primitive with explicit `depends_on` repair, a re-established run cursor, and dry-run-then-apply-or-rollback atomicity, so step 3 can wrap it with seed-first ordering and the safety policy without re-deriving any plan-graph mechanics.

## Implementation

### `plan_tool/scope_out.py` — the narrow primitive

**Foundational logic of this step:** *drop one step from a plan and re-canonicalize the remaining graph (ids `1..N-1`, repaired `depends_on`, migrated detail files, and a fresh CURRENT only when dropping the plan's sole CURRENT leaves a post-drop runnable survivor) atomically, refusing rather than corrupting when the carve is unsafe.*

#### Public surface

- **`NarrowBlocker`** — frozen dataclass; one structural reason a carve cannot proceed.
  - `kind: str` — one of `"step-missing"`, `"empty-plan"`, `"non-canonical-numbering"`, `"inbound-dependent"`, `"downstream-orphan"`.
  - `step_ids: list[int]` — the offending survivor ids (e.g. the steps that `depends_on` the carved step; the non-PENDING downstream steps). Empty for `step-missing` / `empty-plan` / `non-canonical-numbering`.
  - `message: str` — a one-line operator-facing explanation.
  - These are **facts about the plan graph**, not policy. Step 3 maps `kind` → its `EscalateResult`-style `outcome` (`unsafe` / `empty-plan` / `step-missing`) and owns the opt-in/TTY decision — see Deferred.

- **`NarrowPreview`** — frozen dataclass; the dry-run plan, mirroring `detail.MergeResult`'s preview fields (`renumber`, `new_plan`) so the two read alike.
  - `carved_id: int` — the step being dropped.
  - `source_plan_path: Path` and `source_frontmatter_hash: str` — the source-plan provenance captured from the same parse snapshot as the `Plan` object being narrowed, so apply can refuse a stale preview before touching disk instead of reparsing a changed graph.
  - `blockers: list[NarrowBlocker]` — empty ⇒ safe to apply. Non-empty ⇒ `apply_narrow` refuses.
  - `new_steps: list[Step]` — the survivors after drop + renumber + `depends_on` repair + CURRENT promotion (the exact `steps:` the narrowed `Plan` will carry). Empty when carving the last total survivor; the `empty-plan` blocker can also fire with `new_steps` non-empty when the survivors are all parked (no committed step remains) — see the empty-plan guard below.
  - `narrowed_plan: Plan | None` — the complete narrowed `Plan` object to pass to `write_plan`, carrying the source plan's metadata/provenance fields plus `new_steps`, `new_plan_status`, and the **pruned `features:` registry** (see the registry-prune rule below); `None` when blockers prevent constructing a valid narrowed plan.
  - `renumber: list[tuple[int, int]]` — `(old_id, new_id)` for every survivor whose id changed (old `id > carved_id` shifts down by one; old `id < carved_id` unchanged), matching `MergeResult.renumber`'s shape.
  - `new_plan: list[tuple[int, str, list[int]]]` — `(new_id, title, depends_on)` triples for a cheap human/preview render, as `MergeResult.new_plan` does.
  - `detail_renames: list[tuple[Path, Path]]` — `(old_detail_path, new_detail_path)` for each downstream survivor whose `NN-` prefix changes.
  - `archive_detail: Path | None` — the carved step's own detail file to archive, resolved from `Step.detail` first and canonical fallback second, or `None` when the carved step was never detailed (no file on disk).
  - `new_current_id: int | None` — the survivor (new id) to promote to CURRENT after dropping the plan's sole CURRENT, or `None` when no promotion applies.
  - `new_plan_status: PlanStatus` — the top-level status to persist; set to `completed` when `new_current_id is None` and every committed survivor is DONE, otherwise preserve the source plan's status.

- **`NarrowResult`** — frozen dataclass; what `apply_narrow` actually committed (`carved_id`, `renumber`, `new_current_id`, `new_plan_status`, `archived: Path | None`, `migrated: list[Path]`). Lets step 3 and tests assert the applied outcome without re-reading disk.

- **`compute_narrow(plan: Plan, *, carved_id: int, plan_path: Path, repo_root: Path, source_frontmatter_hash: str) -> NarrowPreview`** — pure computation, **no disk mutation**. The caller must pass `source_frontmatter_hash` captured from the exact parse snapshot that produced `plan`; `compute_narrow` stores that provenance in the preview and does **not** re-read the plan frontmatter from disk. Reads plan structure and resolves the carved detail path from `carved_step.detail` first (`repo_root / carved_step.detail`), falling back to `detail.derive_detail_path(plan_path, plan, carved_step)` only when the step has no `detail:` pointer and the canonical file exists; touches the filesystem only to test whether the carved step's resolved detail file exists (to decide `archive_detail`). Builds `new_steps`, the complete `narrowed_plan`, `renumber`, `new_plan`, the file-op lists, the cursor pick, and `blockers`.

- **`apply_narrow(plan_path: Path, preview: NarrowPreview, *, repo_root: Path) -> NarrowResult`** — commits `preview` all-or-nothing by writing `preview.narrowed_plan`, not by reparsing or rebuilding the graph. Raises (and rolls back) if `preview.blockers` is non-empty, if `preview.narrowed_plan is None`, or if the current plan frontmatter no longer matches `preview.source_frontmatter_hash` — the hard invariant that the graph is never corrupted, independent of step 3's policy gate.

#### Drop-renumber + `depends_on` repair (own logic, not a merge reuse)

- **Refuse non-canonical input before building the preview.** The drop math is valid only when the source plan's step ids are already contiguous, unique, and position-ordered (`1..N` in list order), matching the precondition `detail.split_step` / `detail.merge_steps` enforce before id-based detail migration. `schema.Plan._validate_graph` rejects duplicate/dangling/cyclic graphs but does **not** reject non-contiguous ids, so `compute_narrow` must detect any gap or out-of-order id and return a `non-canonical-numbering` blocker without producing a renumber/detail preview that `apply_narrow` could commit.
- **Build the old→new id map first.** Survivors keep their declared order; assign new ids `1..N-1`. Concretely: `new_id = old_id` when `old_id < carved_id`, `new_id = old_id - 1` when `old_id > carved_id`. This is one private helper returning `dict[int, int]` over the survivor ids (carved id excluded). It is the single source for both the step renumber and the `depends_on` remap — do **not** re-derive the shift in two places.
- **Repair every `depends_on`.** For each survivor, map each dependency id through the old→new map. A dependency equal to `carved_id` cannot be mapped — that survivor is an **inbound dependent**, recorded as an `inbound-dependent` blocker (do not silently drop the edge, which would reuse the freed id under a different step). Drop self-edges and de-dupe, mirroring `create._apply_step_merge`'s edge hygiene, but **without** any repoint-to-survivor step (there is no survivor).
- **Do not reuse `create._apply_step_merge`.** It collapses `merge_ids` onto `min(merge_ids)` and repoints dependents to that survivor — a drop has no survivor, so its repoint branch is wrong here. State this in the module so a future reader does not "simplify" the narrow into a one-member merge.
- **Prune the `features:` registry — a drop has no survivor to fold tags onto.** Unlike `merge_steps` (which folds `merged_features` onto the survivor), a drop deletes the carved step outright, so any registry feature the carved step solely implemented would otherwise stay registered-but-unimplemented in `narrowed_plan` (step 1 carries those tags into the seed, but the source registry must shed them — seed decision `carved-step-features-disposition`). `compute_narrow` recomputes the narrowed plan's `features:` registry as the source registry minus any entry no surviving step still tags, preserving the step→feature ownership invariant (no dangling registry tag). `write_plan`/`model_validate` does not reject an unimplemented registry entry, so this prune is the only guard against silent registry drift.
- **Empty-plan guard keys on the committed survivors, not the total count.** `schema.Plan` carries a `scope` dimension (`committed`/`deferred`/`wont_do`) and the cursor/completion rules already filter on it (`committed_steps`, `next_runnable_step`, `all_steps_done`). So zero total survivors is not the only dead-plan shape: carving the last **committed** survivor while **parked** (`deferred`/`wont_do`) steps remain leaves a plan that still satisfies `schema.Plan`'s `min_length=1` yet has no committed step — no CURRENT is promotable, `all_steps_done` returns `False` (it requires committed steps), and `new_plan_status` stays `in_progress`: a permanently dead plan, the exact rot the guard exists to prevent. `compute_narrow` therefore fires the `empty-plan` blocker whenever the post-drop survivor set has **no committed step** (`schema.Plan.committed_steps` would be empty), covering both the zero-survivor shape and the committed-empty/parked-only shape, and never constructs a committed-empty `narrowed_plan`.

#### Detail-file migration + archive (owned rollback journal)

- **Downstream renames — own the explicit file-op journal.** A drop shifts every downstream id down by exactly one, identical to a two-into-one merge's downstream shift, but `detail._migrate_downstream_details_after_merge` performs hidden archival/rename side effects without returning an operation journal. `compute_narrow` therefore records every `(old_detail_path, new_detail_path)` pair in `detail_renames`: resolve each downstream survivor's source detail path from `Step.detail` first (`repo_root / step.detail`), then fall back for unpointed survivors to the canonical existing file via `detail.find_unreferenced_detail_for_step(plan_path, plan, step)`, and only record a rename when that resolved source exists. Use `detail._DETAIL_ID_PREFIX_RE` to rewrite the resolved file's `NN-` prefix and store the resulting pairs in the preview, so canonical files that exist without a frontmatter `detail:` pointer are not stranded under stale ids after drop-renumber. `apply_narrow` drives the moves from `preview.detail_renames` directly, applies them in ascending old-id order, checks every destination before moving, pushes the reverse rename onto the journal before any later operation can fail, and raises on destination collision instead of archiving or overwriting implicitly. The only expected occupied destination is the carved detail itself (for example, carved `02-build.md` and downstream `03-build.md` renaming to `02-build.md`): in that case, archive the carved detail first under the same rollback journal, then perform the downstream rename into the freed path. Unrelated destination collisions still refuse before any overwrite. If an implementation chooses to call `_migrate_downstream_details_after_merge` anyway, it must first snapshot the affected detail tree and restore that snapshot on any exception so every helper side effect is rollback-managed; otherwise the helper is out of bounds for this primitive. Because a drop shifts every downstream id down by one, each new path is the prior step's still-occupied slot, so a descending (or unordered) apply clobbers a not-yet-vacated file; pin `detail_renames` to ascending old-id order so each source frees its destination before the next move needs it.
- **Carved step's own detail → archive.** Mirror `merge_steps`, which archives folded-away files, but make scope-out's carved archive strict rather than best-effort. `compute_narrow` distinguishes the clean no-op case (`archive_detail is None`, because no carved detail exists) from the apply case (`archive_detail` points at an existing carved detail). The resolved carved-detail path is `repo_root / carved_step.detail` when `Step.detail` is set, preserving noncanonical but authoritative pointers after title edits or slug drift; only unpointed steps use `detail.derive_detail_path(...)` as a canonical fallback. When `archive_detail` is set, `apply_narrow` must archive that exact file under the sibling `archive/` directory with a UTC-timestamp suffix and verify the move succeeded; if the archive helper returns no destination, the source remains, or the archived destination is missing, raise so the apply journal rolls back. Its body is already captured in the step-1 seed, so archive (not delete) preserves history.

#### Re-establish the CURRENT cursor

- **The narrow must set its own cursor.** Dropping a run-started (typically CURRENT) step can leave a DONE+PENDING mix with no CURRENT, which `run` cannot resume from. `create._seed_initial_step_status` does **not** help — it promotes only when *all* steps are PENDING (it early-returns on any non-PENDING step), and the launcher's promotion fires only after a step completes.
- **Rule:** only when the carved step is the plan's sole CURRENT, run the post-drop survivor set through the same runnable-step rule as `Plan.next_runnable_step()`: promote the **first committed PENDING survivor whose dependencies are all DONE** (in id order) to `StepStatus.CURRENT` and record its new id in `new_current_id`. Carving a non-CURRENT step must preserve the existing cursor state, including an existing no-cursor state; do not create a new CURRENT merely because no survivor is already CURRENT. When no such runnable survivor exists after dropping the sole CURRENT, set `new_current_id = None` and promote nothing — blocked or parked pending work must not be made current before its prerequisites. If `new_current_id is None` because the committed survivor set is all DONE, set the narrowed plan's top-level status to `PlanStatus.COMPLETED`; a no-cursor all-DONE plan left `in_progress` is not complete under existing sweep semantics. Apply the promotion and status update to the preview so the persisted plan carries them.

#### Atomicity: dry-run preview, then apply-or-rollback

- **Compute fully in memory before any write**, exactly as `merge_steps(dry_run=True)` returns its preview. `compute_narrow` produces the complete `NarrowPreview`; nothing on disk changes during compute.
- **`apply_narrow` runs a reversible journal.** `write_plan` (`plan_tool/parser.py`) is a plain `write_text`, not atomic, and the detail renames are several `os.rename` calls — so the primitive owns its own all-or-nothing. Record an inverse for each op as it runs, then on any exception unwind the journal LIFO:
  - snapshot the plan file's original bytes and verify its current frontmatter still matches `preview.source_frontmatter_hash` before any detail-file move;
  - if `preview.archive_detail` is also a planned downstream rename destination, archive the carved detail first with strict success checks (reverse = move it back from `archive/`; archive failure raises and triggers rollback) so that expected destination is freed under the same journal;
  - perform each `detail_renames` move **in ascending old-id order** (the non-clobber invariant above), guarding each destination against a pre-existing file other than the already-archived carved-detail destination, pushing the reverse rename onto the journal;
  - archive the carved detail with strict success checks when it was not already archived to free a downstream destination (reverse = move it back from `archive/`; archive failure raises and triggers rollback);
  - write `preview.narrowed_plan` last via `write_plan` (not a temp-write + `os.replace`) — `write_plan`'s `p.write_text(...)` is *not* atomic, so the all-or-nothing guarantee comes solely from the byte-snapshot LIFO rollback above, not from the write itself; calling `write_plan` directly preserves its compare-and-swap provenance (keyed on `str(p.resolve())`), which a temp-path `os.replace` would bypass. Do not assume `write_plan` is atomic;
  - if any step raises, replay the journal in reverse and re-raise, leaving the pre-narrow state restored (plan frontmatter + every detail file back in place).
- **Refuse before touching disk** when `preview.blockers` is non-empty: `apply_narrow` raises a typed error naming the blockers and writes nothing. This keeps "never corrupt the graph" true regardless of how step 3's caller behaves.

## Acceptance criteria

- `compute_narrow(plan, carved_id=N, plan_path=..., repo_root=..., source_frontmatter_hash=...)` returns a frozen `NarrowPreview` and performs no plan/detail mutation (only a read to decide `archive_detail`); the supplied `Plan` and `source_frontmatter_hash` must come from the same parse snapshot.
- `preview.narrowed_plan` is the complete `Plan` object to persist, preserving the source plan's metadata/provenance fields while carrying the validated narrowed steps/status; `preview.source_frontmatter_hash` is the caller-supplied hash from that same parse snapshot and lets `apply_narrow` reject stale previews before touching disk.
- `preview.narrowed_plan`'s `features:` registry drops any feature the carved step solely implemented (no surviving step still tags it) and retains every feature a survivor still tags, so the narrowed plan carries no dangling registry entry.
- `preview.renumber` shifts only ids greater than `carved_id` down by one; `preview.new_steps` has contiguous ids `1..N-1` with `depends_on` remapped through the same map.
- Non-canonical step numbering produces a `non-canonical-numbering` blocker before preview/apply; a surviving step depending on the carved step produces an `inbound-dependent` blocker; a downstream non-PENDING step produces a `downstream-orphan` blocker; carving the only survivor — or the last committed survivor while only parked (`deferred`/`wont_do`) steps remain — produces an `empty-plan` blocker, so `compute_narrow` never constructs a committed-empty `narrowed_plan`; a missing id produces a `step-missing` blocker.
- Carving the plan's sole CURRENT step promotes the first committed PENDING survivor whose dependencies are all DONE to CURRENT (`new_current_id` set); carving a non-CURRENT step preserves the existing cursor state, including an existing no-cursor state; when no post-drop runnable pending survivor exists after dropping the sole CURRENT, `new_current_id is None`; when the committed survivor set is all DONE, the top-level plan status is set to `completed`.
- `apply_narrow` on a blocker-free preview first verifies the on-disk frontmatter still matches the preview's source provenance, then renames downstream detail files to their new prefix through an explicit rollback-managed journal, archives the carved step's resolved detail file under `archive/`, and writes `preview.narrowed_plan`; when the carved detail is also a downstream rename destination, it archives that carved detail first under the same journal so the expected destination is free; if the preview is stale, an unrelated downstream detail destination collides, or an existing carved detail cannot be archived, it raises and rolls back; on a preview with blockers it raises and writes nothing.
- Forcing a mid-apply failure rolls back to the exact pre-narrow plan frontmatter and detail-file layout.
- `compute_narrow` is deterministic — two calls on the same plan return equal previews.
- `tests/test_scope_out.py` passes under `uv run pytest tests/test_scope_out.py -q`.
