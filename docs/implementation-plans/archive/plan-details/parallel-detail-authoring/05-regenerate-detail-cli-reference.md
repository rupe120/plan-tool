## Why

Steps 3 and 4 add the `--jobs N` flag and its conflict guard to the `detail` subparser in `plan_tool/cli/authoring.py`, and step 2 makes `generate_detail`'s authoring shell-out run concurrently when `jobs > 1`. Two docs now lag the code. First, `docs/cli/detail.md` is a generated reference that mirrors the live argparse surface; once `--jobs` exists in the parser, the committed reference is stale, and `tests/cli/test_cli_reference.py:TestCliReferenceDrift` fails until it's regenerated. Second, `TESTING.md`'s backend-seam table tells the next contributor how `generate_detail`'s `invoker=` seam is exercised, but it doesn't yet say that seam now fires from several worker threads at once — a fact a test author needs so they don't assume the seam is only ever called serially. This step lands both so the plan ships with accurate, non-drifting docs.

## Implementation

**Regenerate `docs/cli/detail.md` — don't hand-edit it.**
- The file is **generated**, not authored. `plan_tool/cli_reference.py` walks the assembled parser from `plan_tool.cli.build_parser` and renders one Markdown file per subcommand; the argparse parser is the single source of truth for flags, defaults, choices, and `help=` text. See the module docstring in `plan_tool/cli_reference.py` and `CLAUDE.md`'s `docs/cli/` reference line.
- Produce the new file by running `python -m plan_tool.cli_reference --write` **after steps 3 and 4 are merged** (the flag and its guard must already be in the `detail` subparser). The command rewrites every `docs/cli/<command>.md`; only `detail.md` should change in this plan's diff.
- Do **not** type the `--jobs` row or the usage-line edit by hand. The flag's wording is owned by step 3's `p_detail.add_argument("--jobs", ..., help=...)` call — restating it here would just drift from that `help=` string. If the regenerated row reads wrong, fix the `help=` text in step 3's file, not this generated output.
- **Constraint — depends_on 2 and 4.** The reference must be regenerated against the final parser, so this step runs after step 4 (which transitively includes step 3's flag). Regenerating earlier would either miss the flag or capture a half-wired help string.

**Add the concurrent-seam note to `TESTING.md`.**
- The seam table already carries the `detail.py → generate_detail(invoker=...)` row (default `shell_detail_invoker`, neutralize by passing `invoker=lambda p: ...`). Keep that row as the seam-override recipe — the override mechanism is unchanged by concurrency.
- Add one short note (a sentence or a bullet near the table or in the **Real-backend subprocess gate** paragraph) stating: under `--jobs > 1`, `generate_detail` calls that same `invoker=` seam from several `ThreadPoolExecutor` worker threads at once; a test that forgets to override `invoker=` therefore leaks **concurrent** real-backend shell-outs, and the autouse conftest gate (`backend.registered_binaries()`) still catches every such leak because it fires per-spawn regardless of thread. The neutralization recipe is identical — override the one `invoker=` seam and all workers use the fake.
- Name the **second** seam too: when the foundational-logic sweep is wired, `run_foundational_logic_sweep` runs inside the worker through a *distinct* `foundational_invoker` seam, so under `--jobs > 1` that seam is also driven concurrently. It is OFF by default (no production caller wires it), so the leak surface is bounded to eval harnesses — but list `foundational_invoker` alongside `shell_detail_invoker` as a concurrently-exercised seam so the neutralization table is complete and a sweep-enabled test overrides both.
- Keep it terse and don't re-specify step 2's concurrency mechanics (the worker boundary, the guard, the ordered flush). Reference that `--jobs > 1` is the concurrent path and point the reader at the `detail` command; step 2 owns the mechanics. This matches the project rule to cite the owning step, not restate its internals.
- The plan's `## Testing` section already asks for this exact note ("Note in TESTING.md that the `invoker=` seam (`shell_detail_invoker`) is now exercised concurrently; the conftest real-`claude` gate and the neutralization table must keep holding").

**Foundational change of this step:** keep two generated/maintained docs in sync with the now-landed `--jobs` surface. There is no production code path here and nothing to consolidate — the `docs/cli/<name>.md` generation is already centralized in `plan_tool/cli_reference.py` (one generator for every command), and the seam recipes already live in one `TESTING.md` table.
