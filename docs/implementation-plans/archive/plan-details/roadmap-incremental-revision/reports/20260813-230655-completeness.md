- CRITICAL `[revision-publication-atomicity]`: Step 8 (`Publish revisions all at once…`), Architecture, Risks, Testing, and the atomic-publication criterion promise that the complete collection set changes together or no canonical artifact changes. At HEAD, `plan_tool/fileio.atomic_write_text` and `plan_tool.roadmap._write_artifact` replace one path at a time, while `plan_tool.roadmap_view.load_roadmap` reads the four artifacts separately; staging and rollback cannot prevent a reader, or a process stop between replacements, from seeing a mixed revision.
  - Fix: define one publish snapshot and recovery rule that every reader uses for canonical artifacts, seed state, and the session record, or narrow the guarantee to a feasible failure scope
- HIGH `[prose-isolation]`: Step 5 (`Parse and render … replace-prose … patches`) and step 6 (`Merge allowlisted patches … preserve … prose byte`) must satisfy the Overview, Problem statement, Testing, and first acceptance criterion that unrelated prose never enters backend input or the write set. At HEAD, `plan_tool.roadmap_artifacts._split_frontmatter` and `_render` treat each artifact body as one string, and `plan_tool.roadmap_gates.check_inventory_has_prose` only checks that an ID occurs somewhere; no row owns a prose span, so `replace-prose` can rewrite unrelated text or cannot safely update prose required for an added or changed row.
  - Fix: define a stable, machine-checkable prose boundary and scoped operation policy that preserves all non-target prose bytes across steps 5 and 6
- MEDIUM `[revision-session-record-lifecycle]`: Architecture says “Each session records” inputs, outputs, validation, and deferred work; steps 3, 8, 9, and 11 define the record, publish it, and show the latest outcome, but the acceptance criterion guarantees recording only for a successful session. The plan never chooses whether an invoke, parse, gate, or checkpoint failure writes or replaces a durable record, so “latest” can mean either the latest attempted session or latest published revision and can conflict with the no-change failure guarantee.
  - Fix: define the session-record lifecycle for every outcome, its transaction and Git boundary, and which outcome step 11 presents as latest
- HIGH `[feedback-selection-addressing]`: Architecture’s selected “stable feedback row ids,” step 4 (`Reject invalid feedback selections …`), step 10 (`Add explicit --revise-feedback selection …`), Testing, and the selection acceptance criterion never define one unambiguous selector. `ROADMAP_FORMAT.md` permits artifact-target feedback with no `row_id`, keeps feedback local to its artifact, and `plan_tool.roadmap_view.build_feedback_index` preserves same-id rows from different artifacts, so the plan leaves the target collection, eligible state, and promised “incompatible” multi-row policy open.
  - Fix: define an artifact-qualified feedback selector, artifact-target root, open-state eligibility, and compatibility rule for multiple dependency closures, then use that same record for the previewed write set and tests.
- HIGH `[affected-plan-staleness]`: Architecture, Input, step 4 (`…minimal collection dependency order`), step 8 (`mark only affected plans stale`), the staleness acceptance criterion, and Deferred require a per-plan stale set but never define how it is derived. At HEAD, `plan_tool.roadmap._invalidate_roadmap_seeds` invalidates every entry, while `PlanRow.component_ids` and the existing gates do not choose which plan drafts become stale after a row, prose, or removal change; deleted plan rows make the omission especially visible.
  - Fix: define a conservative plan-impact traversal from selected feedback and allowed changes through roadmap relations, including artifact-wide prose and added or removed plans, and test the exact stale and unchanged seed-state entries.
- HIGH `[dependent-removal-authorization]`: Architecture’s dependent-collection requests, steps 4 (`…dependency order`), 5 (`remove-row`), 6 (`create cited removals`), and 9 (`Run one bounded patch request per dependent collection`) allow a selected row to lead to a removal in a dependent collection. `ROADMAP_FORMAT.md` says feedback is local to its artifact, and `plan_tool.roadmap_gates.check_design_row_continuity` accepts a new removal only when it cites an `open` feedback row from that artifact’s predecessor; a selected domain feedback row therefore cannot authorize a needed component or plan removal.
  - Fix: define that removal authority stays within the selected feedback’s collection and that the planner rejects or defers any dependency path needing a separate collection’s reviewer feedback.
- HIGH `[selected-feedback-lifecycle]`: Architecture, step 4’s selection validation, step 5’s `respond-feedback` operation, step 6’s review-state preservation, step 9, Testing, and the acceptance criteria never say how a successful session disposes of each selected feedback row. At HEAD, `FeedbackState` and `plan_tool.roadmap_gates.check_feedback_integrity` permit only `open` → `awaiting-review` with a response, while the plan can also be read to leave selected rows open or alter unavailable review states.
  - Fix: define eligible selected states and require each selected open row either to receive exactly one valid awaiting-review response on publication or to fail before publication, with that result recorded and tested.
- HIGH `[revision-snapshot-isolation]`: Architecture’s transaction and preservation guarantees, steps 4, 6, 7, 8, and 9, and the no-unselected-write acceptance criterion do not establish a snapshot precondition or shared writer fence. At HEAD, `plan_tool.roadmap.run_roadmap` and `_write_artifact` have no locking or version check, so two targeted revisions—or a targeted revision and `--from-stage`—can start from one snapshot and silently overwrite each other’s valid changes.
  - Fix: define a mutation fence shared by targeted and broad roadmap writers that serializes publication or rejects and replans changed inputs, with interleaving tests.
