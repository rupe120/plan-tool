plan-tool · value walkthrough

When the Plan
Wouldn't Converge

The audit kept finding correctness bugs — labeled HIGH, run after run, all in the same place. The fix wasn't another patch. It was admitting the plan was the wrong shape.

A real session · the escalate-structural-findings-to-split plan

plan-tool turns an idea into a plan, audits it against the code before any implementation, then iterates to convergence. This session is what happens when iteration alone can't get there.
the trigger

Eight audits. Same region. New HIGHs each time.

Each completeness-audit --iterate run reported converged / no-blocking-findings — then a fresh manual re-run surfaced more correctness findings, all clustered on one step:

midapply-verdict-convergence-routing · HIGH recommendation-report-surfacing phase-b-recommendation-emission · HIGH create-trigger2-recommendation-emission create-trigger2-proposal-unusable recurring-unattended-trigger2-cost

Six anchors, three audit rounds, one step. The count never trended down.

The anchor slugs are stable across re-audits, so a finding that comes back is recognizable. These all name the same step-5 region under different framings.
the tell

Each fix spawned the next finding

run 6 → "the bridge's Recommendation is never surfaced…"
run 7 → "…now the recommendation=None case is silently dropped…"
run 8 → "…now it re-emits a duplicate recommendation every iteration."

Three runs, three fixes, three new holes — in the same patch. That's not convergence. That's whack-a-mole.

Whack-a-mole is the signature of fighting a plan's shape, not its prose.

The give-away: the findings weren't independent. Each was a consequence of the previous fix's mechanics. A loop that's converging produces fewer, smaller findings — not a fresh sibling each pass.
the value moment

The author didn't hit apply a ninth time

"The audit continues to find correctness bugs being labeled high. Is there a flaw in the design that's hard to pin down — or does the design need to be broken into smaller parts?"

Every prior round asked "how do I close this finding?" This question asked "why does this region keep generating them?"

The tool surfaced the symptom. The right move was to stop and diagnose the cause.

the diagnosis

A structural edit jammed into a prose loop

The convergence loop applies prose edits idempotently: collect → apply → re-collect → repeat. Every invariant assumes apply never changes step identity.

Step 5 made it apply a split — which renumbers step ids mid-iteration. So all six findings were one bug, refracted:

stale captured ids · re-collection re-derives the same finding · the per-step summary already emitted · partial edits need revert-first

Seven symptoms, one cause: a structure-mutating operation forced through a prose-mutating loop.

Because the two convergence loops had different topologies — create's outer while, detail's nested for-loops — every rule had to be written twice with different mechanics. That doubled the surface area for the audit to find a hole in. That's why it felt un-pin-downable.
the proof — machine-readable code, one grep

Half the complexity defended dead code

The plan called create's mid-apply split its "live structural trigger." Was it reachable? One grep settled it:

APPLY_ELIGIBLE_SOURCES = frozenset({
    "body-completeness", "detail-body", "plan-correctness",
    "reconcile", "detail-reconcile", "run-reconcile", "claude",
})   # ← create only ever dispatches PROSE-fill findings to apply_finding

For create's trigger to fire, Claude would have to be mid-apply on a "fill in this prose" finding and decide the only fix is a step split. The plan never named that scenario — because there isn't one.

The most bug-dense part of the plan was wiring a path production never takes.

the deeper flaw

apply can only add prose

apply_finding edits text. It can fix under-specification — it can never delete a concern, drop dead wiring, or re-decompose.

So every fix grew the plan, which fed the next audit more surface. The plan got more complex each pass, not more correct.

no-blocking-findings ≠ sound
It means "nothing left the loop is allowed to auto-touch." A plan whose remaining problems are all structural reports converged prematurely.
the fix

Re-decompose: seed → regenerate

before — one over-packed step

- id: 5            # complexity: high
  files: [create.py, detail.py]
  # trigger-1 + trigger-2
  # refactor + feature
  # break-out + dedup + revert
  # + create-side dead wiring

after — a clean 9-step spine

1 refactor · predicate
2 feature  · render recs
…
6 feature  · trigger-1 surface
7 feature  · in-loop contract
8 feature  · review-walk
# create-side trigger → deferred

The refactor split from the feature. Trigger-1 isolated from trigger-2. The hostile in-loop renumbering contract got its own step. Dead wiring deferred, not hardened. The fresh small steps converge — each is small enough for the editor to finish.

the kicker

The blind spot became the next feature

Every loop the tool has converges content. None converges step boundaries — they're decided once, by create, at the moment of least information, then frozen.

That gap is now BACKLOG #57 — a decomposition convergence loop:
detect non-convergence → fork the recommendation → re-split one step vs. re-seed the plan. Seed already written.

Diagnosing the failure produced the capability that would catch it automatically next time.

The pieces compose: the granularity advisor is the static detector, escalate_to_split is the localized executor, #57 is the loop that ties them. The manual re-seed we just did is the escape hatch #57 would surface.
why this is the demo

Coherent plans, efficient to implement

  • Non-convergence is a signal — the audit's persistence pointed at a design flaw, not a typo.
  • It reviews shape, not just words — the failure was a mis-decomposition no prose edit could fix.
  • Machine-readable truth is cheap — "is this branch dead?" was a one-line grep.
  • Seed / plan separation — the fix was a seed rewrite + regenerate, not surgery on a frozen plan.
  • Small, single-concern steps — the regenerated spine is one you can build without fighting it.

The tool's best moment isn't writing the plan —
it's making you fix the plan's shape before you build it.
