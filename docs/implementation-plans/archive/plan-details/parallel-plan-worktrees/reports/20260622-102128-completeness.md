### Correctness (run these first)

_Verified: file paths resolve, dependencies are coherent, and the plan's stated concepts are internally sound._

- HIGH `[prune-deregistered-clone-enumeration]`: `worktree prune` (step 4) and the acceptance criterion "prune drops workspaces (both kinds) for archived/deregistered/missing plans" rest on the stateless per-slug path derivation, which the Architecture itself defines as deriving the path *from the slug* in the manifest. A *deregistered* plan's slug is gone from the manifest, so derivation cannot enumerate its workspace; the plan's own caveat concedes "worktrees can still be recovered via git's own registry; clones cannot." Thus prune can reach a deregistered/archived **worktree** (via `git worktree list`) but is structurally unable to find a deregistered **clone** — making the "both kinds" criterion undeliverable for clones.
- MEDIUM `[clone-branch-creation]`: step 1 (`clone_repo(repo, path, *, branch)`) and step 3 inherit the Architecture's claim that "the branch is created+checked-out by the worktree-add itself (`-b`)" and that "`create_and_checkout_branch` is deliberately not reused here — it switches the main tree, which the worktree-add then cannot co-checkout." That rationale is worktree-only: a `--clone` produces an *independent* repo with no main-tree co-checkout conflict, so a plain `git clone -b <newbranch>` fails when the branch does not yet exist in the source, and the plan never specifies how the clone lands on a new plan branch.
- HIGH `[start-point-resolution]`: `worktree add` (step 3, via step 1 `worktree_add(..., start_point=)`) fixes the new branch's start-point as "the resolved default branch's HEAD," but `gitcommit.py:default_branch` returns `None` when neither `PLAN_TOOL_DEFAULT_BRANCH` nor `origin/HEAD` is set — the normal state of a local-only repo with no remote. The plan never defines the start-point when `default_branch` is `None`, so `git worktree add -b <branch> <path> <start>` would receive an empty/None start-point and fail cryptically — defeating the goal that bare `worktree add <plan>` "just works" under default config.
- MEDIUM `[branch-resolution-fallback]`: The branch-resolution precedence (Architecture / branch-resolution criterion) clause (3) routes "branch-awareness OFF *or no configured prefixes*" to the slug-derived fallback, which correctly dodges `derive_branch`'s `prefixes[0]` indexing an empty prefix list — but the plan never states that the ON-with-empty-prefixes case must take the fallback rather than calling `derive_branch`, leaving the one path that would raise unguarded in prose.
