The Risk asks the plan to "decide explicitly whether this console-level exposure is acceptable... or must be gated," but no step makes that call, so the Testing criterion's "verbose terminal output" either silently excludes `--debug` (leaving a real exposure path unverified) or is unsatisfiable as written.
  - Fix: pick one of the two stated options for `--debug` (accept the exposure, matching `run`'s existing risk, or gate it until redaction covers all three parsers) and reword the Testing criterion to say explicitly whether `--debug` output is inside or outside its secret-fixture check.
- MEDIUM `[step2-relocation-plus-exception-net]`: Step 2 ("Move the streaming Popen runner out of launcher.py into a shared module") bundles a behavior-preserving relocation with genuinely new behavior in one code step — its own intent text says "two distinct things happen in this step, not one": the move is byte-compatible with `run`'s current behavior, and a new kill-on-any-exception net around `proc.wait()` is "layered on top of the moved code rather than part of the move." This is exactly the mixed-step pattern (restructuring + new behavior in one code step). The plan bundles them so the net lands no later than the extraction, avoiding a Ctrl-C-orphans-the-child window before step 5, but `depends_on` ordering across two type-pure steps gives the identical timing guarantee without merging them.
  - Fix: split step 2 into a pure-move step (relocate `_run_streaming_once`, byte-identical to `run`'s current behavior, its own test) and a follow-on step adding the kill-on-any-exception net for both lanes, joined by `depends_on`, retargeting every current dependent of step 2 onto the new second step.
- HIGH `[batch-transport-argv-override-drift]`: Step 5 (`Run batch claude calls through the shared runner instead of subprocess.run`) routes `claude_invoke` through the same shared runner `_run_streaming_once` uses, which builds its command line from `backend.streaming_transport(prompt)`. `claude_invoke` today builds its command line from `backend.batch_transport(prompt)` instead, and a project can configure those two differently: `plan_tool/backend_config.py`'s `BackendOverride` carries separate `extra_batch_argv` and `extra_streaming_argv` lists read from `.plan-tool/backends.json`, and `docs/design-plans/BACKEND_SELECTION.md`'s own example sets `"extra_streaming_argv": ["--reasoning", "high"]` specifically so only the long-running `run` calls get the higher reasoning effort, not batch calls. The plan's own Intent states "`claude_invoke`'s `(rc, stdout)` contract and all existing roadmap/detail/audit parsing and gate logic are unchanged," but if the shared runner always calls `streaming_transport`, every one of the seven `claude_invoke` callers — including `roadmap`, the plan's stated initial rollout target — would silently start receiving the streaming extra args instead of the batch ones on any project using this feature. The divergence is invisible on the three built-in backends (their `batch_argv` and `streaming_argv` happen to be textually identical today), so step 1's characterization tests won't catch it unless they specifically exercise a `backends.json` override, and it is named nowhere in Architecture's single "allowed behavior changes" list, in Risks, or in Out of scope.
  - Fix: give the shared runner (step 2) an explicit transport-selector call-contract parameter, mirroring step 3's `enforce_configured_timeout` flag, so `claude_invoke`'s call site keeps building argv from `batch_transport` while `run`'s call sites keep using `streaming_transport`, and add this behavior-preservation point to Architecture's allowed-behavior-changes list.
- HIGH `[apply-finding-interrupt-scope-shared-walk]`: Step 7 says its `apply_finding` wiring is "scoped narrowly to the `plan-tool run` CLI verb's own call sites," but `run --reconcile` reaches `apply_finding` through `cli/reconcile.py`'s `_cmd_run_reconcile` → `walk_recommendations` → `review_actions._build_review_action_fn`'s `_dispatch_apply_finding` — the exact same shared function that `completeness-audit --iterate`, `review --walk`, and `data_contract_cmd.py` all use, and that Out of scope separately names as excluded ("the interactive review apply walk"). No step gives `apply_finding`/`walk_recommendations`/`_dispatch_apply_finding` any parameter that would let it tell a `run --reconcile` call apart from a `completeness-audit --iterate` call — they are literally the same function call with the same shape. Architecture's observer-wiring bullet ("`apply_finding` adapt their `run_logger` into one directly — step 7 is where this adapter is built") and Out of scope's caller list describe two mechanisms that cannot both be true without something new.
  - Fix: name the concrete gate that lets step 7's new interrupt/backend-event wiring distinguish a `run --reconcile` walk from every other caller of `walk_recommendations`/`apply_finding` (e.g., an explicit caller-scoped flag threaded from `_cmd_run_reconcile` through the shared action function), and make Architecture's wiring bullet and Out of scope's caller list state that same mechanism rather than asserting the boundary as if `apply_finding` already knows its caller.
- HIGH `[tool-input-secret-redaction-mechanism]`: Testing requires "a known secret fixture never reaches JSONL or verbose terminal output," and steps 6 and 9 both call their change "redaction," but at HEAD `_summarize_tool_input` (`plan_tool/backend.py`) does no content-level scrubbing — its `Bash` branch returns `str(inp.get("command", ""))[:200]` verbatim, so a secret embedded in a shell command (e.g. an inline auth header) reaches `tool_input_summary` untouched today. The plan never says what content rule "baseline redaction" (step 6) actually adds to that function — only that codex's and cursor's own `tool_call` producers get suppressed with a marker until step 9 extends "the same pass" to them. Without a stated scrubbing rule, it's unclear the plan can satisfy its own Testing bullet, and it's unclear what "the same pass" even means for codex/cursor, whose producers hand back pre-formatted strings ("path (kind), path (kind)", raw command text) rather than the `(tool_name, dict)` shape `_summarize_tool_input` expects.
  - Fix: state the actual redaction rule `_summarize_tool_input` gains — what in a command/path/pattern value gets scrubbed and how — and confirm that rule, not just which field is chosen, is what makes the secret-fixture test pass; have step 9 name whether codex/cursor route through `_summarize_tool_input` itself (needs input reshaping) or a shared scrubbing helper both call.
- MEDIUM `[step8-inflight-scope-boundary]`: Architecture draws a line between the global, unconditional silence kill (every one of the seven `claude_invoke` callers) and the narrower JSONL heartbeat/spawn/stream-event trail (only callers with an open `RunLogWriter` — `annotate.py`, `jira.py`, and `create.py`'s slug-generation call are excluded) — but it never says which side of that line `in-flight.json` sits on, and step 8's title ("Keep in-flight.json current for the whole life of a call") doesn't resolve it either.   - Fix: extend the same sink-scoped boundary Architecture already draws for the JSONL trail to say explicitly whether `in-flight.json` follows it, and have step 8 confirm the three no-sink callers produce no snapshot rather than leaving that implied by an unstated code fact.
