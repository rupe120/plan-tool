# Step 2 — Move the confirmed brief rebind write after publication recovery, and wire the revision checkpoint into every roadmap run

<!-- plan-tool:detail-format-version: 1 -->

## Summary

`_run_roadmap` in `plan_tool/roadmap.py` writes `source.json` for a confirmed brief rebind (the `confirm_brief_rebind` branch, before `parse_carried_decisions`) before it ever calls `recover_roadmap_publication`. This step moves that write to run only after recovery succeeds, so recovery always resolves any dangling publication journal before this run makes its own first write. It then wires step 1's checkpoint module (`plan_tool/roadmap_revision_checkpoint.py`) into `_run_roadmap`: capture or continue a checkpoint right after recovery, verify a tracked file's current bytes against the checkpoint before writing it, update the checkpoint after each write actually lands, and discard the checkpoint only when the run reaches a completed outcome. A run refused before `recover_roadmap_publication` runs — an unconfirmed refused brief, or a `from_stage` error — creates no checkpoint; every later preflight refusal or exception (a malformed carried-decisions block, a rejected artifact deletion, a stage load/predecessor failure, a stage gate failure) leaves an already-captured or already-continued checkpoint in place, even though none of those write a tracked file themselves. `publish_stage_artifact`, `publish_roadmap_generation`, and `recover_roadmap_publication` themselves keep their current signatures and behavior; all of the new logic sits in `roadmap.py` around the existing call sites.

## Why

`_run_roadmap` holds the roadmap writer lock for its whole run and, today, has no record of what the roadmap looked like before the run started. Step 1 built that record in isolation; nothing calls it yet. Wiring it in here is what actually gives an interrupted, exhausted, or crashed run something to restore to in step 3.

The wiring has one real precondition: the checkpoint's captured "pre-run" bytes and its ongoing "last written" bytes are only trustworthy once `recover_roadmap_publication` has resolved any dangling journal from an earlier crash — reading a file mid-recovery would capture a transient value, not the roadmap's real last-committed state. At `HEAD` this already holds for every stage publish and for the plain (non-rebind) admission paths, because `recover_roadmap_publication` already runs before the stage loop. It does **not** hold for the confirmed-rebind write: `_write_brief_source` in the `confirm_brief_rebind` branch runs immediately after computing `admission`, well before `recover_roadmap_publication` is even called (`plan_tool/roadmap.py:_run_roadmap`, the `if (admission.startswith("refused-") and ... and confirm_brief_rebind):` block). A crash between that write and recovery would leave the checkpoint capturing bytes recovery had not yet settled. This step closes that one exception so every tracked write in a run, the rebind write included, happens after recovery — matching the plan's Architecture section ("recover_roadmap_publication always runs first").

## Implementation

**The reorder.** `_run_roadmap` computes `admission` (`"initial"` / `"matched"` / `"refused-legacy"` / `"refused-changed"`) from the recorded vs. current brief digest, then, in the `confirm_brief_rebind` branch, writes the new baseline immediately and only afterward calls `parse_carried_decisions` and `recover_roadmap_publication`. Move the actual `_write_brief_source` call (and the `admission = "accepted-rebind"` / `baseline_rebound = True` transitions and the `roadmap_source_admission` log call that go with it) to run **after** `recover_roadmap_publication` succeeds. Move `recover_roadmap_publication`'s own call earlier too, to before `parse_carried_decisions` (its position relative to `reject_direct_artifact_deletions` is what stays unchanged), so it becomes unconditional for every surviving admission (not just reached after `parse_carried_decisions` succeeds). Concretely:

- Compute whether this run *would* rebind (the same condition as today: `admission.startswith("refused-")` and `recorded_brief_source is not None` and `brief_path is not None` and `confirm_brief_rebind`) without performing the write yet.
- When that condition is false and `admission` is still refused, keep today's behavior exactly: log the refusal and raise `RoadmapError` before reaching `recover_roadmap_publication` at all. `test_unconfirmed_same_path_changed_digest_refuses_before_recovery_or_writes` and its legacy-record sibling pin `recovery_calls == []` for this path — nothing here may call recovery for a plain, unconfirmed refusal.
- Otherwise, call `recover_roadmap_publication` unconditionally (matched, initial, and pending-rebind all reach it now). A failure here raises a plain `RoadmapError`/`RoadmapWriterGuardError`-derived error with no `_rebind_failure_error` wrap — nothing has been written yet at this point in the new order, so `baseline_rebound` cannot be `True` here (see the test-roster note below).
- Capture-or-continue the checkpoint (next bullet) once recovery succeeds.
- For a `"matched"` or `"initial"` admission (this run is not pending a rebind), log `roadmap_source_admission` here, at exactly the point the existing single call site logs it today — right after `admission` is finalized, unchanged in position and content for these two dispositions. This is the same call the pending-rebind bullet below fires for `"accepted-rebind"`; between the two, every admission value still logs exactly once, matching `test_rebind_confirmation_is_noop_for_initial_recording` (disposition `"initial"`) and `test_feedback_free_reentry_uses_the_recorded_brief_without_a_backend_call` (disposition `"matched"`), both of which must keep passing unchanged.
- If this run is pending a rebind, verify and write `source.json` here (after capture-or-continue, before `parse_carried_decisions`), update the checkpoint's `source.json` entry, and only then set `admission = "accepted-rebind"`, `baseline_rebound = True`, and log `roadmap_source_admission`. This keeps `parse_carried_decisions` positioned exactly where it is today relative to the write — after it — so a malformed carried-decisions block still fails with `baseline_rebound` already `True` for a pending-rebind run, matching `test_rebind_malformed_carried_block_keeps_accepted_baseline_context`'s existing expectation unchanged.
- `reject_direct_artifact_deletions` and everything below it keeps its current position and its current `if baseline_rebound: raise _rebind_failure_error(...)` wrapping, unchanged.

**Checkpoint capture-or-continue.** Right after `recover_roadmap_publication` succeeds, and before any write this run might make (the rebind write included — this is the "one call site, no forking" point the plan's step title asks for): call `load_checkpoint(plans_dir, slug)`. If it returns `None`, this is a fresh lineage — call `capture_checkpoint(plans_dir, slug)` and `write_checkpoint(plans_dir, slug, checkpoint)`; `capture_checkpoint` reads current, already-post-recovery bytes directly, so a fresh capture already reflects whatever recovery just settled. If it returns an existing checkpoint, an earlier failed run in the same lineage already left one — keep it as-is and use it as the run's working checkpoint value; never call `capture_checkpoint` again in that case, since doing so would overwrite `pre_run_bytes` with today's bytes and lose the "state before the first failed run" the plan's Architecture section requires.

**The one reconciliation this step performs: when `admission == "matched"`** (the run already re-read `source.json` via `_resolve_brief_path`/`read_recorded_brief_source` before this point, and its digest already equals `current_brief_digest`, so its content is settled and not about to be rewritten this run), if `source.json`'s current bytes differ from the checkpoint's `last_written_bytes` for that entry, adopt current bytes into `last_written_bytes` — this is the one crash-recovery case that matters for `source.json`: an earlier attempt in this lineage wrote it and crashed before its own bookkeeping landed, and `admission == "matched"` is a proof this reflects the tool's own settled write rather than a hand edit, since a hand edit would make `recorded_brief_source.brief_digest` diverge from `current_brief_digest` and produce a `"refused-*"` admission instead. This is deliberately the *only* reconciliation this step performs — it needs no knowledge of any other roadmap writer or journal kind, unlike a mechanism that would peek and reconcile against a dangling `PendingGeneration` journal (out of scope; see Deferred and the plan's own Risks section for why). Recommended: do the capture-or-continue-and-reconcile step unconditionally for every run, whether or not it turns out to write anything. A run that ends up making zero writes (e.g. a feedback-free re-gate reaching `OUTCOME_COMPLETED_NO_CHANGE`) still discards the checkpoint at the end (see below), so the observable result — no checkpoint after a completed run — is identical to lazily capturing on first write, and it avoids threading a "have we captured yet" flag through every branch that could turn out to be the first write. Wrap the capture/continue/reconcile calls (and their `write_checkpoint`) in a `try`/`except OSError` that raises a `RoadmapEnvironmentalError`, consistent with the other filesystem-touching preflight steps in this function; log the failure with a new `run_logger.roadmap_preflight_failed(check=...)` name (e.g. `"revision_checkpoint"`) rather than reusing `"brief_source"` or `"publication_recovery"`, since it is neither.

**Verify-before-write, update-after-write.** At each of the three points `_run_roadmap` writes a tracked file, add a check immediately before the write and an update immediately after it commits:

- **The (now-deferred) confirmed-rebind `_write_brief_source` call.** Before writing, read `brief_source_path(plans_dir, slug)`'s current bytes (`None` on `FileNotFoundError`, mirroring the same convention step 1's `capture_checkpoint` uses) and compare against the checkpoint's stored `last_written_bytes` for that path's relative-path entry. A match proceeds normally. A mismatch here is always a genuine outside change — refuse the run before writing, raising a `RoadmapError` (or a small subclass of it defined in this module) that names the file. **This branch is reached only when `admission.startswith("refused-")`, which itself requires `recorded_brief_source.brief_digest != current_brief_digest` — a crash-recovered write (current bytes already equal to what this write would produce) is impossible to see here, because it would already have made `admission == "matched"` upstream and skipped this whole branch instead.** The checkpoint-side half of that same crash-recovery case is handled once, earlier, in the "Checkpoint capture-or-continue" step's `admission == "matched"` reconciliation — not duplicated here. After the write commits, call `with_last_written` with the freshly-written bytes and persist with `write_checkpoint`.
- **The second `_write_brief_source` call** (the initial-recording write later in the stage loop, gated on `record_brief_source`, distinct from the rebind branch — this one already runs after recovery today and needs no reordering, only the same verify/update wrapping and the same reasoning: a mismatch here is always genuine, for the identical reason above).
- **The `publish_stage_artifact` call in the stage loop.** This call commits three members atomically (artifact, baseline, `seed-state.json`). Verify all three current-vs-last-written before calling it, and update all three after it returns successfully — treat it as one unit, the same way `publish_roadmap_generation` treats its own members as one unit. Use `stage.artifact_path(plans_dir, slug)`, `baseline_path(roadmap_dir(plans_dir, slug), stage.artifact_key)`, and `seed_state_path(roadmap_dir(plans_dir, slug))` to name the three paths — the same helpers `_publication_members` already uses internally, so nothing here needs to guess at `publish_stage_artifact`'s internals. Since `publish_stage_artifact` does not return the bytes it wrote, read each of the three paths back from disk after it returns to get the values for `with_last_written` — this is also already the pattern the stage loop uses for the artifact itself (`admit_stage_artifact` re-reads the just-published file at the line right after). **This call site has no equivalent crash-recovery reconciliation.** The `source.json` sites get one because `admission == "matched"` is a proof, already computed by this run's own ordinary preflight, that current bytes reflect this tool's own settled write rather than an outside change. Nothing analogous is available here without extra work: whether a stage's freshly-rendered content already matches what is on disk is exactly `_publication_members`' own internal comparison, not something this call site can cheaply ask in advance without duplicating that derivation. So a crash strictly between this call returning and this bullet's own `with_last_written` update remains an accepted, explicitly-named residual (see Risks and Deferred) rather than a gap this step closes; it is a narrow, purely-local, no-model-call window, unlike the recovery-ordering gap the rest of this step exists to close.

A mismatch refusal raised inside the stage loop's per-stage block is already covered by the existing `_rebind_stage_failure_context(baseline_rebound=..., slug=..., stage=...)` context manager wrapping that block — as long as the raised type is `RoadmapError` or `RoadmapArtifactError`, it is wrapped with the "accepted the recorded brief's current baseline before stage N failed" message for free when `baseline_rebound` is `True`, with no new wrapping code needed at the new check site.

**Discard on completion.** `_run_roadmap` already computes `is_successful_roadmap_outcome(result.outcome)` once, right before `lifecycle.complete(...)` and the function's single normal `return result` (the `outcome in {OUTCOME_COMPLETED, OUTCOME_COMPLETED_NO_CHANGE}` check). Call `discard_checkpoint(plans_dir, slug)` there, gated on that same condition. This one site is reached both by a genuinely completed run and by a completed-no-change run (`reentered_without_write and not written`), so it covers "including a no-change run" without a second call site. It is not reached by the two early `return result` sites for `OUTCOME_STAGE_INVALID` (raised from `_load_and_regate_below` / `_load_predecessors` failures) or by any exception that escapes the function — both leave the checkpoint in place, which is exactly the "a checkpoint that still exists means the run did not complete" invariant.

**What does not change.** `publish_stage_artifact`, `publish_roadmap_generation`, `recover_roadmap_publication`, and `reject_direct_artifact_deletions` keep their current signatures, bodies, and journal-cleanup behavior — every new check and update in this step reads bytes back from disk or from the checkpoint object in `roadmap.py`, around those calls, not inside `roadmap_revision_publish.py`. The checkpoint file lives under the same `roadmap_dir(plans_dir, slug)` the whole run already holds the writer lock for, so no separate locking is needed for its reads or writes.

## Acceptance criteria

- The confirmed-rebind `_write_brief_source` call runs only after `recover_roadmap_publication` has returned successfully, for every roadmap run — matching `test_confirmed_rebind_write_happens_after_publication_recovery`.
- `recover_roadmap_publication` still never runs for a plain, unconfirmed refused-brief admission — `recovery_calls == []` still holds for `test_unconfirmed_same_path_changed_digest_refuses_before_recovery_or_writes` and its legacy-record sibling.
- A fresh run (no existing checkpoint) captures one via `capture_checkpoint` right after recovery; a run continuing an existing checkpoint's lineage keeps that checkpoint's `pre_run_bytes` unchanged.
- Before each of the three write actions (confirmed-rebind write, initial-recording write, stage publish), the file(s) about to be written are checked against the checkpoint's `last_written_bytes`; a mismatch refuses the run before writing, raising a `RoadmapError`-family exception, and the file's on-disk bytes are unchanged afterward.
- After each of those write actions commits, the checkpoint's `last_written_bytes` for every file that action touched is updated and persisted.
- `discard_checkpoint` runs exactly when `is_successful_roadmap_outcome(result.outcome)` is `True`, covering both `OUTCOME_COMPLETED` and `OUTCOME_COMPLETED_NO_CHANGE`; a `stage-invalid` or `stage-exhausted` outcome, or any exception escaping `_run_roadmap`, leaves the checkpoint in place.
- A run that raises before `recover_roadmap_publication` is reached creates no checkpoint file; a refusal or exception raised after that point (including `parse_carried_decisions`, `reject_direct_artifact_deletions`, `_load_and_regate_below`, and `_load_predecessors` failures) leaves an already-captured or already-continued checkpoint in place, even though the run wrote nothing itself.
- A fresh checkpoint capture reads current, already-post-recovery bytes, so it never needs a separate reconciliation step even when recovery just silently completed a dangling journal; a *continuing* checkpoint performs no reconciliation against any dangling journal at all (accepted residual; see Risks and Deferred).
- A run whose `admission` resolves to `"matched"` reconciles a stale `source.json` checkpoint entry to current on-disk bytes as part of capture-or-continue, before either `_write_brief_source` call site is reached; a `"refused-*"` admission (a genuine divergence) never triggers this reconciliation, since it requires the digests to already agree.
- `roadmap_source_admission` logs exactly once per run, for every admission value, including `"matched"` and `"initial"` under the new call order.
- A crash strictly between `publish_stage_artifact` committing and this step's own checkpoint update for its three members is an accepted, explicitly-named residual (not closed by this step) — pinned by a test, not silently absent.
- `publish_stage_artifact`, `publish_roadmap_generation`, `recover_roadmap_publication`, and `reject_direct_artifact_deletions` are unchanged (same signatures, same bodies).
- `.gitignore` ignores the checkpoint's on-disk filename.
- `uv run pytest tests/test_roadmap.py -q` and the full suite (`uv run pytest tests/ -q -n auto`) pass.

## Applicable guardrails

The plan's `## Scope guardrails` bind this step on several points:

- "No automatic restore, and no restore offered on anything but an explicit command" — this step ships no restore or apply path; it only captures, verifies, updates, and discards the checkpoint around the run's existing writes.
- "No new persisted state except the checkpoint" — the only new on-disk artifact this step causes to appear is the checkpoint file step 1 already defined; nothing else is added.
- "No change to enrollment, candidates, review seals, promotion, or the `.roadmap-versions/` namespace" — this step touches only `_run_roadmap` / `run_roadmap`, not `enroll_roadmap_root`, `enroll_roadmap_baselines`, or `plan_tool/roadmap_versions.py`.
- "Eligibility never reads run logs" — every check this step adds compares on-disk bytes against the checkpoint's own recorded values; none of it reads `.plan-tool/runs/`.
- "No change to `--revise-feedback`, `--materialize`, `--enroll-baselines`, or `--enroll-version`" — this step's files are `plan_tool/roadmap.py` and `tests/test_roadmap.py`, and its edits are scoped to `_run_roadmap`; the other writer entry points in that file are untouched.

## Deferred

- The restore runner and its case matrix (no checkpoint, enrolled, matches last-written, matches pre-run, anything else) — step 3.
- CLI flags, exit-code mapping, and the restore-command message at `cmd_roadmap`'s four non-completion paths — steps 4 and 5.
- A `RoadmapRevisionCheckpointError` escaping from `load_checkpoint` on a corrupted or malformed on-disk checkpoint file is left to propagate uncaught, the same as other genuinely-corrupted-tool-state errors do today — this step only adds handling for the *content-mismatch* refusal it itself raises, not for recovering from a damaged checkpoint file.
- Tracking an eleventh inventory file, or changing which files the checkpoint tracks — step 1's inventory is fixed to the plan's stated ten files; the plan's own top-level Deferred note covers widening it if `detail` or a later step finds a write outside it.
- Adding a `.gitignore` entry for the pending-publication journal (`.roadmap-publication-pending.json`) — unrelated to this checkpoint and not part of this plan.
- Reconciling a continuing checkpoint against a dangling `PendingGeneration` journal at all — for `publish_stage_artifact`'s own three-member write, or for any other roadmap writer sharing `recover_roadmap_publication`'s journal (a crashed root enrollment, review-seal promotion, baseline enrollment, or a feedback/structural-revision publish). An earlier version of this step built exactly this reconciliation across five rounds of audit convergence before it was cut: closing the own-writer case would require duplicating `_publication_members`'s internal baseline/seed-state derivation outside `roadmap_revision_publish.py`, and closing the cross-writer case requires reasoning about another writer's state, which the plan's own `## Deferred` section (carried from the seed) routes to a follow-up backlog item (`BACKLOG.md` #395) instead of in-plan scope. A run hitting either window refuses as "changed since the failed run"; an operator resolves it the same way as any other genuine outside change to a tracked file — by hand, or by accepting the refusal and starting a fresh revision.
