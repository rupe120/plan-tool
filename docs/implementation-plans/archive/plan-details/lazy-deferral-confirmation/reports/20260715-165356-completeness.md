- MEDIUM `[create-gate-interactive-decline]`: Step 2 (`02-replace-whole-tree-confirm-walk`)'s deferral-only gate mechanism contradicts its own prose on the interactive-decline branch: the Implementation says "prompt to confirm each proposed deferral and, on confirm, sign it off," but the concrete mechanism it commits to — "pass only the deferral node ids and `sign_off=interactive`" to `review_concept_scope` — signs off *every* passed deferral whenever the session is interactive, with no described path for the operator declining a proposed deferral at the prompt. So an interactive operator who rejects a proposed deferral would get it signed off anyway, and the design never names what a declined deferral becomes (dropped, or left `unreviewed` like the `-y` path).
- MEDIUM `[detail-materialize-narrowed-record]`: Step 4 (`04-materialize-new-deferral-detail-shared`) assumes "either the record is absent (re-bootstrap) or a record exists and the target node is already present" — its derive-on-absent path fires only when `concept_tree is None`. But step 2 (`02-replace-whole-tree-confirm-walk`) **narrows** create's persisted record to `defer`/`wont_do` nodes only ("Narrow the returned tree to the deferral nodes … contain only the defer/wont_do nodes"). So on a plan where create already recorded a carried-in deferral, detail loads a record holding *only* that one defer node — every section concept is absent. `_format_concept_scope_block` then lists no proposable node (the narrowed record has no `""`/`include` node to show), so the model cannot name a new concept to defer, and if it does, `parse_structured_detail_response` rejects the *entire response* on `node is None` (`detail.py:1687`). Detail's stated ability to "materialize the deferral its own shared-find routing proposes" silently dies on any plan that already carries a narrowed record.
