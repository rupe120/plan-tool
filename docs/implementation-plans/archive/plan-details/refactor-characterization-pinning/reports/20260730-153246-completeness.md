The plan also never relates it to the shipped plan-level `test_command` (`plan_tool/schema.py`, documented in `PLAN_FORMAT.md`, run with `shell=True` at `repo_root`) or says what the check does when the field is absent, which is every plan that exists today.
- HIGH `[gitcommit-layering]`: Step 3 (`Add the throwaway pre-change sandbox…`) creates the top-level module `plan_tool/characterization_check.py` driving `plan_tool/cli/gitcommit.py`'s worktree primitives, and steps 6–7 wire that module into `plan_tool/launcher.py` — but importing anything from the `plan_tool.cli` package runs `plan_tool/cli/__init__.py`, which does `from plan_tool.cli import app as app`, and `cli/app.py` imports `plan_tool.launcher` at module top, so a module-top import of the primitives from a module launcher imports is a circular import. No top-level module imports `plan_tool.cli` at module scope today; `plan_tool/capability_catalog.py` defers `from plan_tool.cli import build_parser` into a function body and says in its docstring that this is to avoid the cycle. The plan's "no new git plumbing" fence forbids moving the primitives but never names this constraint or which way out is allowed.
- HIGH `[detection-guarantee]`: The acceptance criterion "A test suite written to match post-refactor output is **flagged**" promises detection the mechanism cannot deliver. A refactor step is behavior-preserving, so a test written *after* the change still describes the same behavior and passes against pre-change source — the check stays silent unless the test touches a symbol the refactor created or renamed, or the "refactor" actually changed behavior. What the re-run really proves is that the tests describe pre-change behavior; it catches behavior-changing refactor steps and tests coupled to new structure, not every after-written suite.
- MEDIUM `[sandbox-environment]`: The mechanism's step "Run **only those files** there" never says how the throwaway worktree gets an environment to run tests in. `.venv` is gitignored, so a fresh worktree carries no interpreter environment or installed dependencies; this repo's own suites run as `uv run pytest …`, which in a bare worktree resolves and builds an environment before a single test executes. The worktree-cost risk prices only `git worktree add` — "~200–500 ms plus disk" — so both the cost estimate and the "can the check even conclude" question rest on an unstated assumption.
- MEDIUM `[skip-vs-flag-principle]`: The Architecture principle "every case where the check cannot draw a sound conclusion must *skip and say why*, never emit a finding" contradicts the Risks entry "False alarms on tests that legitimately need new fixtures. Mitigation: advisory-only, and the finding text must state that a new-fixture dependency is a plausible benign cause." A red run in the sandbox looks identical whether the cause is a post-hoc test or a fixture that does not exist pre-change, so the design cannot skip that case — it emits a finding with a caveat, which is what the principle forbids.
- MEDIUM `[uncollectable-vs-failing]`: The criterion "A test file that cannot be *collected* pre-change is **flagged**, with the uncollectable case distinguished from the failing case in the message" rests on pytest's exit-code table and `--collect-only` (both cited in References), but step 2 makes the test command a per-plan configurable value, and an arbitrary shell command returns non-zero for both a collection error and a test failure. The plan never says how the two are told apart once the runner is not necessarily pytest.
- MEDIUM `[enforce-step-tests-dependency]`: The Input section says the step's test files come from "the same post-call git-changed delta the test-authoring gate already computes", but `plan_tool/launcher.py` captures that gate's baseline only when the gate applies (`git_test_baseline = _git_changed_paths(repo_root) if enforce_step_tests else set()`, itself gated on `_step_requires_test_authoring`, which honors the per-step `enforce_test_authoring: false` opt-out). On a plan with `enforce_step_tests` unset there is no gate delta to reuse, and the plan never says whether the check runs there. The clean-tree precondition already settles the direction: with a clean tree at step start the post-call changed set *is* the step's delta, so the check can compute it without the gate.

Step 10 (`Document the check in the run flow and reconcile BACKLOG #203`) declares `depends_on: [9]`, so closing the plan and reconciling #203 waits on field data that may not exist for an arbitrary length of time.
- MEDIUM `[advisory-surface]`: Step 7 (`Run the check after the step's call and print the advisory without blocking advancement`) leaves the finding's destination undefined — whether it is console-only or also lands in the run log or a saved report sidecar. That decision drives two other commitments the plan does make: the criterion "The finding never flips an exit code" needs to hold against whatever consumer reads the persisted findings, and step 9's rate has nothing to count if the advisory is never stored.
- MEDIUM `[stop-condition-response]`: The Stop condition — "if most real characterization files cannot run pre-change for legitimate reasons, stop and report that rate rather than tuning" — defines no threshold for "most" and no consequence. Nothing says what a triggered stop changes: step 10 reconciles `BACKLOG.md` #203 the same way either way, and the plan does not say whether a high rate flips the check's default, holds the #203 removal, or files a design finding.
- MEDIUM `[sandbox-path-collision]`: The plan says the sandbox path comes from `plan_tool/worktree.py`'s `derive_worktree_path`, which returns a deterministic `base / slug` for the same inputs, but never says what slug the check uses or what happens when that path already exists. `classify_target` reports `NON_EMPTY` for a leftover directory from a crashed run, and `git worktree add` fails on a non-empty target, so two runs of the same plan — or one run after an interrupted one — collide on the same path.
- MEDIUM `[durable-opt-out]`: Step 8 (`Add the --no-characterization-check flag to plan-tool run…`) gives the check only a per-invocation CLI opt-out, while the Risks section's mitigation for worktree cost and the Architecture's recommendation both just say "an opt-out". The sibling test-authoring gate carries a persistent pair — plan-level `enforce_step_tests` and per-step `enforce_test_authoring: false` — so a plan or a single step that legitimately cannot run pre-change has no way to record that, and every operator invocation must remember the flag.
- MEDIUM `[prune-on-entry]`: The Risks entry on leaked worktrees mitigates with "cleanup in a `finally`, and a prune on entry", but a prune before the sandbox is created appears nowhere else — the Architecture mechanism lists prune only as the final step ("Remove the worktree and prune, always"), and the criterion says only "Worktrees are removed on every path, including failures." A prior run's leaked administrative entry is exactly what a prune on entry would clear, and no step or criterion owns it.
