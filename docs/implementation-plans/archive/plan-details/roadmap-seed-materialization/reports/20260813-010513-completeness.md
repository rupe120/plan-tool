- HIGH `[seed-classification-shape]`: Step 3 ("Add a module that reports whether every plan has a valid draft seed") states its output as a single valid/invalid answer, but step 5's depends_on_notes says step 3 is "used to select which plan ids are missing or stale," and step 6's depends_on_notes says it "supplies the per-plan validity classification apply now refuses on." Both need a named category per plan (missing, stale, malformed, path-escaping, duplicate, digest-mismatched — the acceptance criteria's own list), not a plain valid/invalid flag. The plan also never says whether these categories become new `status` values in `seed-state.json` (whose `status` field today only allows `current`/`invalidated`) or are computed fresh each time step 3's module runs, from the existing fields plus a live file check.
  - Fix: rewrite step 3's title and intent to promise a per-plan classification into the acceptance criteria's named states, say whether that classification is stored in `seed-state.json` or computed at read time, and note in steps 5, 6, and 8 which category of that classification each one consumes.
- MEDIUM `[refresh-vs-materialize-flag]`: The Input section leaves open whether the new capability rides on the existing `--refresh-seeds` flag or a separate one — "the plan decides whether refresh becomes the per-seed materializer's public surface or delegates to it" — but step 5's title, "Add a CLI flag to materialize missing or stale draft seeds," already assumes a new, separate flag next to `--refresh-seeds` (step 4). Today `--refresh-seeds` regenerates every plan's seed unconditionally (`refresh_roadmap_seeds` loops over every `artifact.plans` row, not just invalidated ones), while step 5's flag is supposed to skip drafts "that are already valid." Running both flags side by side, with different and overlapping targeting rules, is a real product decision the plan never states plainly, even though step 5 has already picked an answer the Input section still calls open.
  - Fix: state directly that `--refresh-seeds` (full, unconditional regenerate, one call per plan after step 4) and the new flag (selective, skips already-valid drafts) are two separate, coexisting entry points, and drop the Input section's framing of this as still undecided.
- MEDIUM `[duplicate-seed-definition]`: The word "duplicate" names one of six draft states in the acceptance criteria ("Missing, stale, malformed, path-escaping, duplicate, and digest-mismatched drafts are visible in views and block promotion") and in step 8's title ("Show stale, mismatched, malformed, and duplicate seed states in roadmap views"), but nothing in Architecture, Input, or any step intent says what makes a draft "duplicate." The codebase already has a check with this name: `check_draft_seed_bundle_alignment` in `roadmap_gates.py` flags two plan rows that share one `draft_seed_path` basename — a check that reads only the roadmap's plan rows and needs no materialized file on disk. But step 3's module is scoped to "whether every plan has a valid draft seed," listing this state alongside malformed/stale/digest-mismatched, which are all properties of a materialized file, not of a plan row. A reader building step 1's shared validator, step 3's module, or step 8's view could reasonably build either the existing plan-row basename check (a static, file-free comparison) or a new check comparing materialized draft content/digests across plans (a much more expensive, materialization-time comparison) — two different mechanisms with a different owner and a different cost.
  - Fix: state in Architecture or Input which mechanism "duplicate" means — the existing plan-row basename collision, or a content/digest collision across materialized drafts — and make step 1, step 3, and step 8 name that same mechanism.
- HIGH `[path-escaping-classification]`: The acceptance criteria and step 8 ("Show stale, mismatched, malformed, and duplicate seed states in roadmap views") name "path-escaping" as one of six co-equal draft states a view must surface, but nothing says which stored value that check runs against. A plan row's own `draft_seed_path` already gets checked for escaping inside `_parse_plan_rows` (`plan_tool/roadmap_artifacts.py`, via `_validate_draft_seed_path`) while `04-roadmap.md` is parsed — an escaping row raises `RoadmapArtifactError` before the artifact loads, so an accepted roadmap can never carry one, and "path-escaping" sourced from the plan row could never actually appear in a rendered view. The value that can genuinely drift unchecked is the `seed-state.json` sidecar's own `draft_seed_path` field: `validate_seed_state` (`plan_tool/roadmap_seed_state.py`) only requires it be a non-empty string, with no escape check, so a hand-edited or stale sidecar entry is the one place this state is reachable at runtime.
  - Fix: name the sidecar's `draft_seed_path` (not the plan row's) as the value step 3's classifier checks for escaping, and have step 1's shared validator gate sidecar entries the same way `_validate_draft_seed_path` gates plan rows, everywhere `seed-state.json`'s `draft_seed_path` is read as trusted.
- MEDIUM `[seed-summary-classification-mapping]`: Step 7 ("Route the roadmap view's seed summary through the new manifest module") is typed `refactor` and claims to give views "the same completeness authority" as apply, but doesn't say how the view's existing three-bucket output (`current`/`invalidated`/`untracked` in `summarize_seed_lifecycle`, `plan_tool/roadmap_view.py`) maps onto step 3's richer per-draft classification (missing/stale/malformed/path-escaping/duplicate/digest-mismatched). Today `summarize_seed_lifecycle` reads only the sidecar's `status` field directly; once it reads through step 3's stricter module instead, a draft the sidecar still marks "current" but whose file was hand-edited (digest mismatch) or deleted (missing) could newly fall out of the "current" bucket — a real behavior change riding inside a step labeled a pure routing refactor, ahead of step 8's new report lines.
  - Fix: state which of step 3's states step 7 folds into each existing bucket, or state that step 7 keeps the summary's output unchanged and defers every new state to step 8, so the refactor/feature boundary between the two steps is unambiguous.

  - Fix: add `DATA_CONTRACT.md` to the file list of the step that changes `draft_seed_count`'s behavior (step 9) or the step that touches `seed-state.json`'s fields (step 3), and require that step keep the sidecar and `draft_seed_count` documentation current.

The Deferred section is explicit that computing which plan ids actually go stale belongs to `roadmap-incremental-revision.md`, "not yet promoted to a plan." Until that sibling ships, every revision still invalidates every draft together, so there are no "unaffected valid drafts" left for steps 4/5 to skip — the benefit advertised for the plan's own motivating problem isn't deliverable by anything in this plan's scope.
  - Fix: state in the Problem statement/Architecture that selective post-revision refresh is conditioned on `roadmap-incremental-revision.md` landing first, and scope steps 4/5's near-term value to backend-call independence, resumability, and first-time missing-seed backfill rather than skipping revision-unaffected drafts.
