- MEDIUM `[open-row-decision-anchor]` [confidence: limited]: Step 2 (stack gates and decision anchors) leaves the outcome undefined when a decision is anchored to a stack row that is `open`. Architecture § "Open and pending" says "an `open` row has no choice to decide and is never `pending`", while step 2 makes "stack ids as decision anchors so a choice can be pending". The existing `check_decisions` anchor resolution in `plan_tool/roadmap_gates.py` only checks that an anchor id resolves, so it would accept a `pending` decision on an `open` row. Two implementers could then differ. One refuses it, so the "never pending" rule holds. The other accepts it, so the row is listed as both open and pending, or as neither. Step 5 and step 6 (the summary's two separate lists) and the testing bullet "first-run output and `INDEX.md` list open and pending concerns separately" cannot be verified without this choice.
  - Fix: State once what happens to a `pending` decision anchored to an `open` stack row (refuse it with a gate violation, or accept it and define how it is listed). Reconcile step 2, the summary module in step 5, and the callout in step 6 to that rule, and add a test case for it.
- MEDIUM `[stack-product-difference-note]` [confidence: limited]: Step 6 and the Architecture § "One source of truth" promise a note when "a stack choice differs from a set hosting or store `product`", but never define "differs". The pairing is not stated: the deployment-platform concern against a hosting `product`, and the store-engine concern against a store `product` (`03-components.md` may hold several store rows). Language/runtime has no `product` counterpart. The comparison between a stack choice and a `product` string is also unspecified: exact match, case-insensitive, or a vendor-name mapping. The plan also bans "a closed vendor or product vocabulary", so a mapping cannot be assumed. The acceptance criterion "a stack choice that differs from a set `product` is noted in review" has more than one passing reading, for example whether `PostgreSQL` against `postgres` is a difference.
  - Fix: Define which concern pairs with which `product` field, how multiple store rows are handled, and the comparison rule, for example a normalized string comparison with no vocabulary. Then pin that rule in the step 6 intent and in the candidate-review test.
- MEDIUM `[totality-binding-predicate]` [confidence: limited]: Steps 2 and 5 and Architecture § "Totality and version compatibility" tell a first stage run apart by the gate envelope carrying no `predecessor`. `ArtifactEnvelope.predecessor` is `Optional[StageArtifact]` and is `None` in any call that does not supply it. At HEAD the other `ArtifactEnvelope(...)` construction sites include `plan_tool/roadmap_candidate_narrative.py:127` and the revision and continuity gates in `plan_tool/roadmap_gates.py`, which treat a missing predecessor as "no revision context". Only the first-run path is named as binding, and the plan states the below-stage re-gating pass as a separate case. It does not say what happens for every other predecessor-free call, such as a candidate gated before its predecessor is loaded or a feedback-free batch. If any of those binds totality, a stack-less lineage is refused for the absence, which breaks the stated compatibility guarantee. If none binds it, a first run is the only binder, and the plan should say so as an explicit enumeration.
  - Fix: Add one sentence listing every gate-envelope construction path with no predecessor and whether it binds stack totality. Make the step 2 test cover each path, not only the first run, the re-gating pass, and a stack-less candidate.
- MEDIUM `[step2-components-gate-role]` [confidence: limited]: Step 2's title adds stack gates "to the constraints and components gate sets". Architecture § "Totality and version compatibility" places a gate only "next to `check_hosting_totality` in the constraints gate tuple". At HEAD, `CONSTRAINTS_GATES` holds `check_hosting_totality` and `check_constraint_anchors`. `COMPONENTS_GATES` holds neither, and it holds only the store checks (`check_store_definitions`, `check_store_value_membership`). The plan never names a stack gate that belongs in `COMPONENTS_GATES`. Read as written, the title requires a components-side change that no sentence in the plan describes.
  - Fix: Either name the components-gate behavior step 2 owns (for example a stack-aware check that touches store rows) and say why it exists, or drop "and components" from the step 2 title and intent so both match the Architecture.
