- MEDIUM `[stack-section-boundary]` [confidence: limited]: Step 2 (`Carry the seed's rendered stack section into the plan body`) says "The seed's rendered stack section is the only stack source `create` reads", and the Architecture says "A seed without that section carries nothing". No sentence says how `create`, or step 1's rematerialization, tells the tool-rendered section apart from model-authored draft text. The draft is written by `materialize_plan_seed` from a model reply, and `validate_draft_seed_content` only checks fences, provenance frontmatter and references. A draft that has no rendered section but quotes a stack-like heading would read as stack-bearing. A draft whose model prose names SQLite beside the rendered PostgreSQL row would hand `create` two stacks. The plan commits to a rendered section being the single source but does not say how it is marked, how a lookalike inside model text is rejected, or what wins when model text contradicts the rendered rows.
  - Fix: Make the plan state one structural marker that identifies the rendered stack section (a fixed heading the renderer owns, excluded from fenced spans). Give a precedence rule for lookalike or contradicting text in the model-authored remainder, and add a step 1 and step 2 test for it.
- MEDIUM `[stack-freshness-on-carry]` [confidence: limited]: Step 2 has `create` treat the seed's stack as settled, but the plan only promises that "A changed accepted store or hosting row changes the rendered stack on rematerialization". `roadmap_seed_manifest.py:classify_draft_seeds` marks a draft `current` when its digest matches the sidecar and `validate_draft_seed_content` passes. `invalidated` is set only through `roadmap_seed_state.invalidated_seed_state`, which is documented for plans-artifact changes (`roadmap.py` near "A roadmap write that changes the plans artifact may invalidate derived"). The plan does not say whether a hosting or store edit in `02-constraints.md` or `03-components.md` invalidates the draft. If it does not, `create` reads an out-of-date stack and presents it as settled. The Risks entry covers only seeds that predate the change.
  - Fix: State whether an accepted-version change to hosting or store rows invalidates enrolled drafts. If it does not, name that as an accepted limit in Risks and have `create` say which accepted version the carried stack came from.
- MEDIUM `[stack-row-selection]` [confidence: limited]: Step 1 (Render the accepted hosting and store stack into each draft seed) renders "every store row named by the plan row's components". The plan never says what a plan row with empty `component_ids` renders, or what a cross-cutting plan renders (`PlanDisposition.CROSS_CUTTING`, `cross_cutting: true` provenance in `roadmap_gates.py`). The Overview says the seed carries "every hosting row, plus every store row named by the plan row's components". Implementers could emit only hosting rows, all store rows, or no stack section. The last choice would make `create` read a cross-cutting seed as stack-less.
  - Fix: State the rendered result for a plan row with no components and for a cross-cutting row. Cover the hosting-only case and say whether the section is always emitted. Add that case to step 1's owned tests.
- MEDIUM `[carried-stack-fidelity]` [confidence: limited]: Step 2 says "A plan built from a stack-bearing seed keeps the roadmap's store and hosting choices", and step 3 has `detail` treat "the plan's settled stack as fixed". `create` writes the plan body through the model, and the plan names no route that guarantees the stack appears in the plan in a form `detail` can read. The tests only assert that the prompt carries the stack. If the model paraphrases or drops it, step 3 has no stack to carry, and nothing says what the `detail` prompt does then.
  - Fix: Name where the carried stack lives in the plan: for example, the seed's section copied verbatim under a fixed plan heading. Say what `detail` does when that heading is missing, using the same "plan states it had none" rule as step 2.

- MEDIUM `[carried-stack-fidelity]` [confidence: limited]: The Overview and step 2 say "`create` carries the stack into the plan as settled" and "A plan built from a stack-bearing seed keeps the roadmap's store and hosting choices". `create` writes the plan body through the model, and step 3's `detail` must then find "the plan's settled stack". No sentence says whether the stack enters the plan body verbatim by deterministic insertion or by the model restating it. It also gives no fixed section name in the plan that `detail` reads. The acceptance criteria assert only that the prompts "carry" the stack, which says nothing about the plan body.
  - Fix: State that the plan body carries the stack under a fixed named section, filled by the tool from the seed's rendered rows or by the model under a stated instruction. Have step 3 read that section by name, and add a criterion covering the stack-less statement.

A draft that is not rematerialized after the accepted version changes can still be read by `create` as current. The plan does not say whether `classify_draft_seeds` in `roadmap_seed_manifest.py` marks such a draft drifted because of the stack rows. Step 1's test requires that a rendered section does not read as drifted, but nothing covers a stale one. As a result, `create` can carry an outdated PostgreSQL-versus-other choice as "settled".
  - Fix: State whether a draft whose rendered stack no longer equals the accepted rows is classified as drifted. Add one step 1 test for a stale stack, or record explicitly that staleness is left to the existing digest check.
