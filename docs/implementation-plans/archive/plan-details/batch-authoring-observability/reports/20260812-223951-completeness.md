- MEDIUM `[interrupt-precedence-race]`: Architecture and Acceptance criteria both assert that when an operator interrupt and a monitor-thread kill (`silence_timeout` or `configured_timeout`) become true "near-simultaneously," the interrupt always wins, and that "the tracked value's own update order enforces this, not a separate check." At HEAD, the kill ladder runs on a background heartbeat thread (`launcher.py`'s `_heartbeat()`) that calls `proc.terminate()`/`proc.kill()` directly, while a `KeyboardInterrupt` is delivered to the main thread blocked in `proc.wait()` — two genuinely independent threads that can both decide "this call is ending" around the same moment. "Update order enforces it" only guarantees interrupt-wins if there's a single, real ordering guarantee between the two threads' writes to the tracked reason (e.g., a lock-guarded check-before-overwrite, or the monitor thread refusing to record a reason once an interrupt is pending) — plain last-write-wins across two racing threads does not by itself guarantee which one wins. The plan already requires a Testing bullet proving this exact scenario, so the gap is real: nothing states the actual mechanism that makes the guarantee hold.
  - Fix: name the concrete mechanism (e.g., a lock-guarded single-writer rule, or an explicit check-before-overwrite keyed on whether an interrupt was already recorded) that makes interrupt-always-wins hold under a genuine race between the heartbeat thread's kill and the main thread's `KeyboardInterrupt`, rather than asserting "update order" alone.
