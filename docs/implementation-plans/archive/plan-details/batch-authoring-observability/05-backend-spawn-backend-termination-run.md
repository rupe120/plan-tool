# Step 5 — Add the backend_spawn, backend_termination, run_interrupted, and backend_recovery_wait run-log events

## Summary

Adds four new run-log event types — `BackendSpawn`, `BackendTermination`, `RunInterrupted`, `BackendRecoveryWait` — to `plan_tool/run_log.py`, gives `RunLogWriter` matching emit methods plus internal tracking of the most recent termination reason so `run_end()` can report it without every one of its 23 existing call sites changing, and registers all four with `plan_tool/data_contract.py` and `DATA_CONTRACT.md`. `plan_tool/claude_errors.py` gains a pair of factories, modeled on the existing `make_wait_seam`, that wrap a caller's rate-limit `wait` seam and transient `sleep` seam to emit `backend_recovery_wait` before sleeping and `run_interrupted` on a `KeyboardInterrupt` raised out of either — closing the one quiet window in `plan_tool/rate_limit_loop.py:run_with_rate_limit_recovery` that today produces no run-log trace on either the batch (`plan_tool/shell.py:claude_invoke`) or streaming (`plan_tool/launcher.py:shell_invoker`) lane. `shell.py` also gains a new writer-carrying `ContextVar` (parallel to its existing `_active_sink`) so `claude_invoke` can reach a real `RunLogWriter`, wired through `RunLogWriter.bind_shell_sink` / `install_call_end_sink`, and uses it to bracket its own subprocess call with `backend_spawn` / `backend_termination`. The streaming lane's own `backend_spawn` / `backend_termination` (bracketing the shared Popen runner's child process, with `plan_tool/backend_runner.py`'s step-4 seven-value termination-reason vocabulary) is deferred — that file is outside this step's declared scope — leaving `backend_recovery_wait` / `run_interrupted` as the concrete new signal on the `run` lane this step ships. Green when all four events round-trip through `RunLogWriter`, `claude_invoke`'s recovery loop emits `backend_recovery_wait` on both the rate-limit and transient paths (with `shell_invoker` doing the same for `run`), a `KeyboardInterrupt` raised during either wait produces one `run_interrupted` row and still propagates, and the full suite stays green.

## Why

`plan_tool/rate_limit_loop.py:run_with_rate_limit_recovery` already drives every rate-limit wait and transient backoff for both `claude_invoke` and `shell_invoker`, and it already accepts injected `wait` / `sleep` seams so callers can observe or fake them in tests. Nothing today writes anything to the run log while one of those seams is blocking: a rate-limit wait can hold a process for up to `claude_errors.MAX_RATE_LIMIT_WAIT_SECONDS` (24h) and a transient backoff schedule stretches over several `2 ** n` delays, and for the whole window the JSONL is silent between the failed attempt's `claude_call_end` and the retried attempt's `claude_call_start`. An operator reading the log mid-run cannot tell "intentionally sleeping" from "hung" — the same ambiguity step 3/4 closed for the shared streaming runner's `proc.wait()`, but the loop's own sleep is a separate quiet window neither of those steps touched (there is no child process alive during a recovery wait to kill or reap, so the runner's kill-on-any-exception net in `plan_tool/backend_runner.py` cannot reach it). This is true on **both** lanes — `claude_invoke`'s batch callers (`roadmap`, `create`, `review`, …) and `run`/`apply_finding` via `shell_invoker` — which is why this step's Implementation section below builds one shared wrapper in `plan_tool/claude_errors.py` rather than two near-duplicate ones.

Separately, nothing in the run log today marks that a backend child process is about to run or records *why* it stopped (as opposed to `claude_call_end`'s bare `rc`). `plan_tool/run_log.py:RunEnd` has no way to say a run ended because an operator pressed Ctrl-C rather than because the backend returned an error — `run_end(outcome="error")` looks identical either way at every one of its current call sites. This step gives that fact a place to live (`RunLogWriter`'s internally tracked termination reason, read by `run_end()` when the caller doesn't pass one explicitly) and a producer for the batch lane (`shell.py:_run_once`'s spawn/termination bracket). The streaming lane's own Popen-level spawn/termination — inside `plan_tool/backend_runner.py:run_streaming_once`, extended with the closed seven-value vocabulary in step 4 (`completed`, `configured_timeout`, `silence_timeout`, `operator_interrupt`, `spawn_failure`, `backend_nonzero`, `unknown`) — is **not** wired here: `backend_runner.py` is not in this step's declared `files:`, and that module is the only place that actually knows which of the seven reasons applied. Wiring it without that source data would mean guessing, so it stays for the step that touches `backend_runner.py` directly (see Deferred).

## Input

- **`plan_tool/rate_limit_loop.py:run_with_rate_limit_recovery`'s existing seam contract.** `wait: Callable[[int], bool]` is called at most once per rate-limit retry, immediately before the loop increments its internal `current_attempt` and re-drives `run_once`; `sleep: Callable[[float], None]` is called at most once per transient retry, immediately before the same increment. Neither seam receives the attempt number as an argument — but `run_once: Callable[[int], Any]` does: the loop passes its real `current_attempt` into every `run_once(current_attempt)` call. That is the one place the loop's true attempt state is observable from outside, and it is what `next_attempt` must derive from: the caller's `run_once` closure records the attempt number it was last called with in a one-slot cell, and the wait/sleep wrappers compute `next_attempt` as that recorded value plus one. A parallel caller-side counter incremented only inside the `wait`/`sleep` seams is **not** equivalent and must not be built: the loop also bumps `current_attempt` on a successful backend SWITCH and on an ASK-switch — retry paths that `continue` without ever calling `wait` or `sleep` — so a seam-side counter undercounts by one per switch, and the `next_attempt` it emits disagrees with the `attempt` the very next `backend_spawn`/`claude_call_end` reports for the same retry. Deriving from `run_once`'s received attempt is correct across every retry path with nothing to observe on the switch arms. This module takes **no** first-party imports and this step must not add one — the wrapping lives in `claude_errors.py` and the two invoker modules, never in `rate_limit_loop.py` itself (the plan's stated rule: "the seam-wrapping caller emits, never the leaf").
- **`plan_tool/claude_errors.py:make_wait_seam(sleep, clock)`.** Builds the `wait(target)` closure both callers pass today by delegating to `wait_until_epoch`. This step adds sibling factories beside it rather than changing its signature — existing callers of `make_wait_seam` that don't want the new observability (there are none today, but the function is public) keep working unchanged.
- **`wait_until_epoch` already catches and swallows `KeyboardInterrupt` internally — it does not re-raise.** Its own docstring says so: a Ctrl-C during the countdown is one of three inputs (alongside `cancel_check`/`key_check`) that produce a normal `WaitUntilResult(STOP)` return, not an exception — the same "cancel this wait, fall through" meaning as pressing `q`. `wait_until_epoch` has exactly one caller today (`make_wait_seam`'s `wait_seam` closure, `claude_errors.py:188`), which has exactly two callers (`launcher.py:668`, `shell.py:547` — both being replaced by this step). Wrapping the *outer* `wait(target)` call in a `try/except KeyboardInterrupt` — the shape a first draft of this step might reach for — cannot work: the exception never reaches that outer frame, because `wait_until_epoch` already caught and converted it three stack frames down. `test_wait_interrupted_plain` (`tests/test_claude_errors.py`) pins the swallow-and-return-STOP behavior directly and must stay green unmodified — this step adds a new opt-in parameter, it does not change that default.
- **Step 4's termination-reason vocabulary** (`plan_tool/backend_runner.py`, not in this step's files) is closed and seven-valued for the streaming runner specifically. This step's `BackendTermination.reason` field does not import or re-declare that vocabulary — it follows the same open-string, producer-owned convention `AttemptFailed.failure_kind` already uses (see `plan_tool/run_log.py:AttemptFailed`'s docstring: "an open string; the vocabulary is the producer's ... above this leaf"). The batch lane wired in this step reuses three of the seven spellings (`completed`, `configured_timeout`, `backend_nonzero`) plus a defensive `unknown` fallback, because those are the only outcomes `_run_once`'s existing `(rc, stdout, stderr, ...)` return can distinguish; it cannot produce `silence_timeout` (no silence monitor on a blocking `subprocess.run` call), `spawn_failure` (the missing-binary check already returns before any spawn is attempted), or `operator_interrupt` (deliberately not wired for `_run_once` itself in this step — see Deferred).
- **`plan_tool/run_log.py:RunLogWriter.bind_shell_sink` / `install_call_end_sink`'s existing contract.** Both already install `shell.set_active_sink(...)` for their scope and restore the prior sink on exit — `bind_shell_sink` via a local closure variable inside its `@contextmanager` block, `install_call_end_sink` via the explicit `_prev_shell_sinks` stack (needed because it has no `with` block of its own to rely on for LIFO unwinding). This step's new writer-carrying `ContextVar` in `shell.py` must be set and restored by both methods using the same two patterns respectively, not a third mechanism.
- **`plan_tool/launcher.py:_run_logger_var`**, already set by `run_step` around every `invoker(prompt)` call (including when `run_logger` is `None`) and already read by `shell_invoker`. This step's `shell_invoker` changes read the same `ContextVar` — no new plumbing is needed there, unlike `shell.py`, which has no equivalent today.

## Implementation

### The four events and `RunLogWriter`'s termination-reason tracking

Add the four dataclasses to `plan_tool/run_log.py` following `AttemptFailed` / `GateViolations`'s exact shape (frozen, inherits `_BaseEvent`, string `event` discriminator last):

- **`BackendSpawn`** — `phase: str`, `attempt: int`, `backend: str` (the active backend's name, e.g. `"claude"`), plus the four operator-facing fields the plan's Architecture promises, all `Optional` defaulting to `None`: `transport: Optional[str]` (a safe descriptor only — which of argv/stdin carries the prompt — never the `PromptTransport` object), `child_pid: Optional[int]`, `effective_timeout_ms: Optional[int]` (the earlier of the configured timeout and the silence threshold, per Architecture's precedence rule), `prompt_bytes: Optional[int]`. This step's own batch-lane bracket (below) emits all four as `None` — `_run_once`'s buffered `subprocess.run` call exposes none of them, and that bracket is retired by step 7 anyway — while step 7's runner-native bracket, the one production emitter that survives this plan, populates them from the runner's own state, where every one is actually known. Marks that a child process is about to run.
- **`BackendTermination`** — `phase: str`, `attempt: int`, `backend: str`, `reason: str` (open, producer-owned — see Input), `duration_ms: int`, plus two `Optional[...] = None` fields only step 7's runner-native bracket can populate: `signal_or_timeout: Optional[str]` (which kill mechanism fired, when one did) and `silent_ms: Optional[int]` (how long the child had been silent at termination). Marks how that child ended.
- **`RunInterrupted`** — `phase: str`, `attempt: int`, `source: str` (open; this step produces `"recovery_wait"` only — see Deferred for the reserved `"proc_wait"` value a later step may add), `signal: str = "SIGINT"` (every interrupt this plan produces is Python's `KeyboardInterrupt`, the main-thread SIGINT translation; the field is a fixed label reserved for a future non-SIGINT source, not classification work). No `reason` field: every row of this event kind *is* an operator interrupt by construction, so a redundant field would only restate the discriminator.
- **`BackendRecoveryWait`** — `phase: str`, `attempt: int`, `reason: str` (`"rate_limit"` or `"transient"`), `delay_ms: int`, `next_attempt: int`, `backend: str`. `next_attempt` is the upcoming retry's ordinal, not a timestamp — matches the `attempt` field every other call event already carries; `delay_ms` carries the wait's duration.

Add all four to the `Event` union and give `RunLogWriter` matching methods (`backend_spawn`, `backend_termination`, `run_interrupted`, `backend_recovery_wait`), each accepting `**extra` and delegating to `self._emit(...)` exactly like `attempt_failed` does.

`RunLogWriter.backend_termination()` and `.run_interrupted()` each set a new instance attribute — e.g. `self._last_termination_reason: Optional[str]` — as their last action: `backend_termination` sets it to its `reason` argument, `run_interrupted` sets it unconditionally to `"operator_interrupt"`. Add the slot to `__slots__` and initialize it to `None` in `__init__`. Because `run_interrupted` always re-raises the interrupt it observed (see below) and nothing else in this plan runs after that, plain last-write-wins on this one attribute already gives the "interrupt wins" precedence — no extra bookkeeping needed to make an interrupt override a same-run backend-nonzero reason recorded earlier.

Extend `run_end`'s signature with `termination_reason: Optional[str] = None`. When the caller passes an explicit value it wins (no known caller needs to suppress a tracked value, but the override stays available); when absent (the default — true for all 23 existing call sites), fall back to `self._last_termination_reason`, which is itself `None` for any run that never reached a `backend_termination` or `run_interrupted` call (e.g. `jira`, `annotate`). Only include the field in the emitted payload when it resolves non-`None`, matching how `run_end` already handles its optional `error` kwarg (`self._emit(ev, error=error)` only when truthy) — do the same for `termination_reason` so a run with no backend-lane activity keeps emitting today's exact `run_end` shape.

`bind_shell_sink` and `install_call_end_sink` each already install `shell.set_active_sink(...)` for their scope; add a call to the new `shell.set_active_run_logger(self)` right beside each, and restore the previous writer on exit the same way each method already restores the previous sink — a local `prev_writer` variable inside `bind_shell_sink`'s `@contextmanager` body, and a second stack (`_prev_run_loggers`, parallel to the existing `_prev_shell_sinks`) inside `install_call_end_sink` / `uninstall_call_end_sink`.

### The shared recovery-wait wrapper (`claude_errors.py`)

`make_wait_seam(sleep, clock)` already exists as the one place both callers build their `wait` seam so they "can't drift" (its own docstring's stated reason for living in this module rather than being duplicated). Add two sibling factories here, following the same shape — a factory function that closes over caller-supplied accessors and returns a plain callable matching the loop's existing `wait` / `sleep` parameter types exactly, so `claude_invoke` and `shell_invoker` can drop the wrapped callables straight into their existing `run_with_rate_limit_recovery(...)` calls with no other changes to that call:

- **`wait_until_epoch` gains `on_interrupt: Optional[Callable[[], None]] = None`.** Inside the existing `except KeyboardInterrupt:` block, after the existing "wait interrupted." print and SIGINT-handler reinstall (both stay — they're useful regardless), call `on_interrupt()` when it is not `None`, then `raise` (re-raise the caught `KeyboardInterrupt`) **instead of** `return WaitUntilResult(action=WaitUntilAction.STOP)`. When `on_interrupt` is `None` (the default — every existing caller, since neither of `make_wait_seam`'s two call sites is changed to pass it), behavior is byte-identical to today: swallow, print, reinstall, return `STOP`. This is the actual fix for the swallow noted in Input — propagation has to happen inside `wait_until_epoch`, at the point the exception is still live, not in a caller three frames up that never sees it.
- The rate-limit factory does **not** wrap `make_wait_seam`'s output — it calls `wait_until_epoch` directly (bypassing the `wait_seam` closure, which has no way to pass the new parameter), supplying `sleep`/`clock` as `make_wait_seam` would and the new `on_interrupt` hook. Only when the caller's writer accessor returns non-`None`: before the call, emit `backend_recovery_wait(reason="rate_limit", delay_ms=<target minus current clock, in ms, floored at 0>, next_attempt=<incremented counter>, backend=<caller's backend-name accessor>)`; build `on_interrupt` as a closure over the same writer accessor that emits `run_interrupted(source="recovery_wait")` when called. Translate the returned `WaitUntilResult` back to the `bool` `wait(target)` contract `run_with_rate_limit_recovery` expects (`action is WaitUntilAction.RETRY`), matching `wait_seam`'s own translation — this factory is `wait_seam` plus the two new emissions, not a different contract. No outer `try/except` around this call: by the time control returns (normal case) or `on_interrupt` has already fired and the `KeyboardInterrupt` is already re-raised (interrupt case) — there is nothing left for an outer handler at this layer to do beyond letting the exception propagate, which is `claude_invoke`'s/`shell_invoker`'s existing unhandled-exception behavior already.
- One factory wraps a caller-supplied `sleep` callable the same way, using `reason="transient"` and `delay_ms` from the `sleep(delay)` argument directly (`int(delay * 1000)`).

Both factories take the writer as a zero-argument accessor (`Callable[[], Optional[RunLogWriter]]`), not a bound writer, so they read whichever writer is active *at wait time* rather than at seam-construction time — this matters because `claude_invoke`'s writer is read from a `ContextVar` that could in principle change between the seam's construction and the loop actually calling it (it won't in practice within one `claude_invoke` call, but the accessor shape costs nothing and avoids a stale-capture bug class). Each factory also takes a `next_attempt` accessor (a zero-argument callable returning the attempt number the caller's `run_once` closure most recently received, plus one — see Input for why it must derive from `run_once`'s argument rather than counting `wait`/`sleep` calls) and a `backend_name` accessor, plus the caller's `phase` string. `plan_tool/rate_limit_loop.py` itself is untouched; this is purely two new functions in `claude_errors.py` plus two call-site changes.

**Important:** do not reuse the *same* raw `_sleep` callable for both the transient-sleep wrapper and the countdown inside `wait_until_epoch`. `wait_until_epoch` calls `sleep(_COUNTDOWN_TICK_SECONDS)` once per second for the whole rate-limit wait — passing a wrapped callable as its `sleep=` argument would fire a `backend_recovery_wait` row on every tick, not once per actual wait. The rate-limit factory calls `wait_until_epoch(target, sleep=_sleep, clock=_clock, on_interrupt=...)` with the caller's raw, unwrapped `_sleep`/`_clock` exactly as `make_wait_seam` would have passed them — only `on_interrupt` is new — so the countdown ticks stay silent and only fire `backend_recovery_wait` once, before the call, and `run_interrupted` at most once, only on an actual interrupt. Build a *separate* wrapped callable for the loop's top-level `sleep=` parameter (fires once per transient retry, over `sleep(delay)` directly — no per-tick countdown to worry about there).

### `shell.py`: writer `ContextVar` + batch-lane spawn/termination

Add `_active_run_logger: contextvars.ContextVar[Optional["RunLogWriter"]]` next to the existing `_active_sink`, with `get_active_run_logger()` / `set_active_run_logger(writer)` accessors mirroring `get_active_sink` / `set_active_sink` exactly (same `ContextVar`-not-global reasoning — thread-scoped so `bench`'s background-worker timeout harness can't corrupt the main thread's binding).

Inside `claude_invoke`, replace the current `wait=make_wait_seam(_sleep, _clock)` / `sleep=_sleep` arguments to `run_with_rate_limit_recovery` with the two new wrapped seams, supplying `get_active_run_logger` as the writer accessor, `phase` as the caller's phase, `lambda: get_active_backend().name` as the backend-name accessor, and a `next_attempt` accessor backed by a one-slot cell that `claude_invoke`'s own `run_once` closure writes on every invocation with the attempt number the loop handed it (Input's derive-don't-count rule; seed the cell from `claude_invoke`'s own `attempt` parameter so a wait before any attempt would still resolve).

Inside `_run_once_seam` (the existing closure that calls `_run_once` and then `_emit_call_end`), bracket the `_run_once(prompt)` call: before it, if `get_active_run_logger()` is not `None`, emit `backend_spawn(phase=phase, attempt=attempt_number, backend=get_active_backend().name)`; after it returns, classify a reason from the returned `(rc, stdout, stderr, duration_ms, ...)` tuple with a small private helper (e.g. `_classify_batch_termination_reason(rc, stderr) -> str`, kept local to `shell.py` — do not add this to `claude_errors.py:classify()`, which step 4 explicitly kept unchanged) and emit `backend_termination(phase=phase, attempt=attempt_number, backend=..., reason=..., duration_ms=duration_ms)`, reusing the `duration_ms` `_run_once` already computed rather than timing the call again. The classifier only needs three branches plus a fallback: `rc == 0` → `"completed"`; `BACKEND_TIMEOUT_SENTINEL in stderr` (already imported in this module) → `"configured_timeout"`; nonzero `rc` otherwise → `"backend_nonzero"`; anything else → `"unknown"`.

## Acceptance criteria

- `plan_tool/run_log.py` exports `BackendSpawn`, `BackendTermination`, `RunInterrupted`, `BackendRecoveryWait`, each a frozen dataclass in the `Event` union with the fields listed in Implementation.
- `RunLogWriter` exposes `.backend_spawn(...)`, `.backend_termination(...)`, `.run_interrupted(...)`, `.backend_recovery_wait(...)`, each appending one JSONL line via the existing `_emit` path.
- `RunLogWriter.run_end(...)` accepts an optional `termination_reason` kwarg; when omitted, the emitted `run_end` row's `termination_reason` reflects the most recent `backend_termination`/`run_interrupted` call on that writer (or is absent/`None` when neither ever fired).
- `shell.get_active_run_logger()` / `shell.set_active_run_logger(...)` exist and are set/restored by `RunLogWriter.bind_shell_sink` and `install_call_end_sink`/`uninstall_call_end_sink` exactly as the existing sink accessors are.
- `plan_tool/claude_errors.py` exposes the two new wrapper factories and `wait_until_epoch`'s new `on_interrupt` parameter; `wait_until_epoch` called with no `on_interrupt` (every existing caller) is byte-identical to today, proven by `test_wait_until_epoch_interrupted_default_stays_swallowed`; `plan_tool/rate_limit_loop.py` is byte-for-byte unchanged by this step.
- A `KeyboardInterrupt` during the rate-limit wait's *countdown* (not just a fake `wait` seam raising directly) propagates out of `claude_invoke`/`shell_invoker` — proven against the real `wait_until_epoch` path, not a fixture that bypasses it.
- With a bound writer, `claude_invoke` emits `backend_recovery_wait` before every rate-limit wait and every transient sleep, and `backend_spawn`/`backend_termination` once per subprocess attempt; with no writer bound, behavior is unchanged from before this step (verified by the existing rate-limit/transient test suite staying green).
- With a bound `run_logger`, `shell_invoker` emits `backend_recovery_wait` before every rate-limit wait and every transient sleep it drives.
- A `KeyboardInterrupt` raised while either lane's recovery loop is waiting produces exactly one `run_interrupted(source="recovery_wait")` row (when a writer is bound) and still propagates out of `claude_invoke` / `shell_invoker` unchanged.
- All four new events are registered in `plan_tool/data_contract.py:persisted_dataclass_contracts()` and documented in `DATA_CONTRACT.md` under `## Run log events`, each with a field table and a `Producer:` line.
- `uv run pytest tests/ -q -n auto` is green.

- [signal — Set handlers for asynchronous events (Python)](https://docs.python.org/3/library/signal.html) — SIGINT → `KeyboardInterrupt` translation on the main thread, directly relevant to catching the interrupt around the recovery-wait seams.

## Applicable guardrails

- **Out of scope: wiring `run_interrupted`/`backend_spawn`/`backend_termination`/`backend_recovery_wait` into any `apply_finding` call site.** This step's `claude_errors.py` wrapper factories are only invoked from `claude_invoke` and `shell_invoker`; `apply_finding` calls `invoker(prompt)` through the same `shell_invoker`, so it inherits the wrapper's *code path*, but `apply_finding` never sets `_run_logger_var` (it only calls `run_logger.bind_shell_sink(...)`), so no event from this step is ever visible on that call. This step must not add any `_run_logger_var`-setting (or equivalent) to `apply_finding` to change that.
- **Out of scope: wiring `create`, `annotate`, `detail`, `jira`, `lessons`, and `review` with their own phase/attempt event labels.** This step gives every `claude_invoke` caller the underlying mechanism (via the new writer `ContextVar`), but assigning any of them roadmap-quality per-command phase labeling or operator rendering is explicitly deferred to follow-up work outside this plan; this step's `phase` values stay whatever the existing caller already passes (or the `"claude_invoke"` default).

## Deferred

- **Streaming-lane `backend_spawn` / `backend_termination`** (bracketing `plan_tool/backend_runner.py:run_streaming_once`'s Popen child with step 4's full seven-value termination-reason vocabulary) — `backend_runner.py` is not in this step's declared `files:`, and it is the only module that knows which of the seven reasons actually applied. A later step that touches that module wires it, reusing the same `RunLogWriter` methods this step ships.
- **`RunInterrupted.source == "proc_wait"`** (an interrupt caught inside the shared runner's `proc.wait()` net, as opposed to this step's `"recovery_wait"`) — reserved value, not produced by any code this step ships; lands with the streaming-lane spawn/termination work above.
- **`_run_once`'s own `KeyboardInterrupt` handling** (emitting `backend_termination(reason="operator_interrupt")` for a Ctrl-C that lands *during* the batch lane's `subprocess.run` call itself, rather than during the recovery wait between attempts) — `subprocess.run` already kills the child safely on any exception, so nothing is unsafe today; this step closes only the recovery-wait quiet window the plan's Why section names, not every conceivable interrupt point. Left for a follow-up step or BACKLOG entry if operator demand shows up.
- **`runs show` / `runs watch` rendering of any of these four events** — no CLI surface change lands in this plan; an operator reads the JSONL directly, per the plan's stated scope fence.
- **Assigning `backend`/`reason` semantics for backends other than the currently active one mid-run** — every emit in this step reads `get_active_backend().name` at call time, matching the existing rate-limit `SWITCH` handling's own scoping; no new cross-backend bookkeeping is added.
