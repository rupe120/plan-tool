# Step 3 — Route the three purity call sites through one cache helper that skips Claude on an unchanged step

## Summary

Add one shared cache helper in `plan_tool/detail.py` that wraps the expensive Claude-judged MIXED-STEP purity portion of `plan_tool/detail.py:collect_detail_quality_findings`, and route all three purity call sites through it: the two intra-authoring sites in `generate_detail`'s convergence loop (the initial scan and the loop re-scan) and `plan_tool/cli/completeness_phases.py:_collect_purity_split_findings`. The helper computes the combined key from step 1's `compute_purity_cache_key` and reads/writes step 2's `plan_tool/purity_cache.py` store. The **key design decision (plan decision 2) is that read-to-skip is audit-path-only**: only `_collect_purity_split_findings` reuses a cached verdict and skips the Claude call on a hit — it keeps only the purity subset anyway. `detail.py`'s two authoring-time sites run in **write-through** mode: they *always* call Claude and then record the fresh purity verdict for the audit path to reuse. The reason they can't skip is that the single Claude call also produces semantic grounding (apply-eligible `## Findings` recs) that Reads/Greps files *outside* the step's declared set — which the cache key can't cover — so skipping it at authoring time would silently drop grounding-against-current-code. The helper is a drop-in for `collect_detail_quality_findings` (same merged-findings return); its two modes differ only in whether a hit is allowed to skip. On green, a step whose detail body, declared-files content, and `change_type`/`depends_on` are unchanged makes no Claude call on the next `completeness-audit`, while the `detail` loop always re-checks (and refreshes the cache) and any real input change forces a re-check.

## Why

The per-step MIXED-STEP purity judgment is an expensive Claude call — BACKLOG #133 measured ~130–255s per step on ~130–150KB prompts — and today it runs from two independent places with nothing cached between them. `plan_tool/detail.py:generate_detail`'s post-authoring convergence loop calls `collect_detail_quality_findings` twice (an initial scan, then a re-scan each loop pass), and `plan_tool/cli/completeness_phases.py:_collect_purity_split_findings` calls the same producer whenever `completeness-audit` runs with purity on. A step whose detail content is unchanged from what `detail` already validated pays a full Claude call the next time a standalone `completeness-audit` runs on it — pure waste, possibly hours or days after `detail` last checked the identical content. Steps 1 and 2 built the sound cache key and the store; this step is the wiring that makes the two call sites share one verdict so whichever runs first pays the cost once.

## Input

This step consumes contracts from its two dependency steps and from the existing purity producer; its correctness depends on their shapes, not on recomputing them:

- **The combined cache key** — step 1 produces `compute_purity_cache_key(plan, plan_path, step, repo_root)` in `plan_tool/fingerprint.py`, returning one hex `str` that changes when the detail file, any of `step.all_files` (declared `files:` plus `creates:`), or the step's `change_type`/`depends_on` changes. This step treats the key as opaque — call it, compare for equality, store it. Do not recompute a key by hand.
- **The persistence store** — step 2's `plan_tool/purity_cache.py` reads/writes `.plan-tool/purity-cache/<slug>.json` keyed by step id. Each entry holds the combined key, the key's individual components (`detail_hash`, `all_files_fingerprint`, `change_type`, `depends_on`, `purity_verdict_logic_version` — which this step persists on write-back so step 4 can grade them one at a time), the cached purity verdict (a list of `plan_tool/review.py:Recommendation` findings, empty list = "checked, pure"), and the concatenated `## Implementation` + `## Tests` section text. Use its load/save functions; treat entry *presence* as "this step was **successfully** checked" and an empty finding list as a real verdict from a successful call, never as "never checked" — and never save on a failed call (decision 3a).
- **The purity producer's output shape** — `plan_tool/detail.py:collect_detail_quality_findings` returns a merged list combining Claude-derived recommendations, advisory altitude findings, deterministic grounding (`collect_step_grounding_findings`, `collect_change_type_test_order_findings`), and the MIXED-STEP purity findings from `parse_mixed_step_findings`. The purity subset is exactly the findings whose `source` is `plan_tool/granularity.py:GRANULARITY_SPLIT_SOURCE` — the same literal `_collect_purity_split_findings` already filters on. Note the Claude-derived `## Findings` semantic-grounding recs in that return Read/Grep files *beyond* `step.all_files`, so they are **not** covered by the cache key and must never be served from cache (why detail.py's sites stay write-through).
- **The detail-body section text** — extract the `## Implementation` + `## Tests` text step 2 stores by reusing `plan_tool/detail.py:parse_detail_file_sections`, which returns a `dict[str, str]` of the detail file's sections. Do not hand-roll a section splitter.

Limit on verifying this contract: step 1's key deliberately excludes lessons-file content (plan decision 5), so a lessons-only change can't be detected — an accepted staleness window, not something this step's wiring can close.

## Implementation

**What changes.** Add one helper in `plan_tool/detail.py` that owns the cache boundary around the Claude-judged purity portion, and point all three call sites at it — but with a mode flag that decides whether a hit may skip Claude. In the **audit path** (read-through): on a hit, return the purity verdict from the store and skip the Claude call; on a genuine miss, call the real producer, save the purity subset, and return. In the **detail-authoring path** (write-through): *always* call the real producer, then save the fresh purity subset for later audit reuse — never skip.

**The helper contract (recommended shape).** Make the helper a drop-in for `collect_detail_quality_findings` — same inputs (`plan_path`, `step`, `repo_root=`, `plan_name=`, `invoker=`, and the reporter/run-logger passthroughs) plus a `read_through: bool` mode flag, same `list[Recommendation]` return to the caller. That single shape lets all three sites swap their existing `collect_detail_quality_findings(...)` call for the helper with no caller-side restructuring.

**Expose a call-success signal — the write-gate cannot be inferred from the findings list.** This is the round-3 correctness fix: a *failed* call (`""` → `parse_mixed_step_findings` → `[]`), a *no-detail quiet-probe* (`collect_detail_quality_findings` short-circuits to `[]` before any Claude call), and a *genuinely-pure success* all return the **same** empty purity subset, so the helper cannot tell them apart from the return value. The success signal must therefore come from the **invoke layer**. Give the producer an opt-in that surfaces it — e.g. `collect_detail_quality_findings(..., return_status=True) -> tuple[list[Recommendation], bool]` — or drive the purity portion through a thin wrapper that returns `(findings, succeeded)`. **`succeeded` must be stronger than "non-empty", and must key on the right marker:** `parse_mixed_step_findings` returns `[]` for *any* text lacking a `## Structural findings` block without erroring, so a truncated/garbled reply would read as `succeeded=True` with an empty subset and cache a false-pure hit. But the marker must be the **mandatory final `## Findings` heading**, *not* `## Structural findings`: `prompts/detail-quality.md` requires `## Findings` in every well-formed response ("remains mandatory and must stay the final section") but tells the model to **omit `## Structural findings` for a type-pure step**. So define `succeeded=True` only when the raw response **contains the `## Findings` section** — this correctly caches a genuinely-pure reply (which reached `## Findings` but has no `## Structural findings`, the common case) while still rejecting a truncated reply cut off before `## Findings`. Keying on `## Structural findings` instead would grade every pure step `succeeded=False` and never cache it (defeating the feature for the majority case), and couldn't distinguish a pure reply from a truncated one. The helper consumes `succeeded` and returns only the findings list to its caller. Internally:

- **Compute the key** with step 1's `compute_purity_cache_key(plan, plan_path, step, repo_root)`. Parse the plan once (the callers already have a `plan_path`; the helper can `parse_plan` like `collect_detail_quality_findings` does, or accept the parsed plan — pick whichever keeps the call sites clean).
- **Load the step's entry** from step 2's store. A hit is: an entry exists for this step id *and* its stored key equals the freshly computed key. Anything else (no entry, or a key mismatch) is a miss.
- **On a hit, `read_through=True` (audit path only):** return the cached purity findings merged with *fresh* deterministic grounding — call `collect_step_grounding_findings` and `collect_change_type_test_order_findings` directly (both cheap, no Claude) and merge with the cached purity list via the same `_merge_findings` the producer uses. This matches plan decision 2: the audit path keeps only the purity subset anyway, so skipping the Claude call loses nothing there.
- **On a miss, or whenever `read_through=False` (detail-authoring path):** call the producer for real *with the success signal* (`return_status=True`), and **success-gate the write** (plan decision 3a) on that `succeeded` bool — **not** on whether the findings list is empty. Only when `succeeded` is true: filter the result to the `GRANULARITY_SPLIT_SOURCE` findings for the cached verdict, extract the `## Implementation` + `## Tests` section text via `parse_detail_file_sections`, and save the full entry — the combined key, **the key's components** (`detail_hash`, `all_files_fingerprint`, `change_type`, `depends_on`, `purity_verdict_logic_version`, from step 1's `PurityKeyComponents`), the step's **`detail_relpath`** (for step 4's renumber guard), the verdict, and the section text — to the store. When `succeeded` is false (a failed invoke, a quiet-probe that never called Claude, **or a truncated/garbled reply lacking the mandatory final `## Findings` heading**), **write nothing** and return the empty result uncached, so the step re-checks next audit instead of caching a false-pure verdict. Either way return the producer's full merged list unchanged. The write-through path always lands here regardless of a hit — it refreshes the cache (on success) but never trades away the fresh call.

**The design tension to respect — why detail.py's loop can't skip the call.** The single Claude call inside `collect_detail_quality_findings` produces more than the purity verdict: it also emits apply-eligible `## Findings` semantic-grounding recs that Read/Grep files *outside* the step's declared `files:` — files the cache key (step 1) does not and cannot cover. So a cache hit is only sound for a consumer that ignores those grounding recs:

- `_collect_purity_split_findings` (audit path) keeps only the medium `GRANULARITY_SPLIT_SOURCE` recs and discards grounding — so reusing a hit there loses nothing. This is the one site that reads through to skip (`read_through=True`).
- `generate_detail`'s convergence loop uses the *full* merged list, grounding included, to drive its apply loop against current code every pass. If it skipped the Claude call on a hit it would silently drop grounding-against-current-code that could newly fail (a producer/sibling file changed outside `step.all_files`, invisible to the key) — a regression versus today's always-re-ground behavior. So the two detail-loop sites run `read_through=False`: they always call Claude and merely *write through* the fresh purity verdict for the audit path to reuse later. Call this out in the helper's docstring so a future reader doesn't try to "optimize" the detail loop into skipping.

**Constraints that are not free to vary:**

- **Only the audit path reads through to skip.** `_collect_purity_split_findings` passes `read_through=True`; `generate_detail`'s two sites pass `read_through=False`. A detail-loop call always reaches the real Claude producer (write-through), never returns a cached verdict in place of the call. This is the plan-decision-2 grounding-safety invariant, not a tunable.
- **A hit requires a key match, not just a present entry.** Compare the stored key to the freshly computed one every time. An entry whose key differs is a miss — that is exactly what forces a re-check when a declared file changed, or `change_type`/`depends_on` flipped, under an unchanged detail body (the plan's soundness requirement).
- **An empty verdict from a *successful* call is a real "pure" verdict; an empty list from a *failed* or *quiet-probe* call is not a verdict at all — and the two are told apart by the invoke-layer signal, never by the empty list.** This is load-bearing and non-obvious: a failed call, a no-detail quiet-probe, and a genuinely-pure success all yield `[]`, so the emptiness of the findings list carries **zero** information about which happened. Gate the save on the producer's `succeeded` bool — where `succeeded` requires the raw response to contain the mandatory final `## Findings` heading (not `## Structural findings`, which a pure step omits), so a **truncated/garbled** non-empty reply counts as a failure while a genuinely-pure reply is correctly cached: cache `[]` only when `succeeded` is true, so a timeout / exec-not-found / quiet-probe / truncated reply never persists a false-pure hit that a later audit would serve. A persisted entry (matching key) is a valid hit precisely because it only exists for a successful check.
- **Keep step 3's audit miss path uniform — always call Claude on a genuine miss.** Do not add the completeness-only below-0.5% threshold short-circuit here; that is step 4's job (plan decision 6), layered on the completeness call site's miss path only. Step 3's helper stays: audit hit → reuse, audit miss → Claude, detail-loop always → Claude.
- **Preserve the existing monkeypatch seam.** `_collect_purity_split_findings` uses a body-local `from plan_tool import detail as detail_mod` and calls `detail_mod.collect_detail_quality_findings` so tests can patch it; the completeness and detail suites patch `plan_tool.detail.collect_detail_quality_findings`. Route the new helper's producer call through the same module-level name (call `collect_detail_quality_findings` as a module global, not a local rebind) so those existing patches still intercept the Claude call. **Test-migration caveat (not "unchanged"):** the helper calls the producer with `return_status=True`, expecting a `(findings, succeeded)` tuple, so existing tests that patch `collect_detail_quality_findings` with a mock returning a **bare `list[Recommendation]`** and then flow through the audit path (`_collect_purity_split_findings`) will hit a tuple-unpack and break — those mocks must be updated to return `(findings, True)`. Make the `return_status` opt-in *default off* so it stays a pure addition: a direct caller/test not passing `return_status=True` still gets a bare list unchanged; only the mocks exercised *through the new helper* need the tuple. Budget for that small mock migration rather than claiming the suite is untouched.
- **Write back on every *successful* real Claude call (miss in the audit path, or any detail-loop call).** Do not re-save on an audit hit — the entry is already current — and do not save at all on a failed/empty call (decision 3a): a failure leaves the cache untouched so the step re-checks next time.

**Rejected alternative.** Caching the *entire* `collect_detail_quality_findings` return (Claude recs + altitude + grounding) rather than just the purity subset. Rejected per plan decision 2: the deterministic grounding is cheap and must re-run fresh against current content every call, and the apply-eligible Claude recommendations are loop-internal state that shouldn't be replayed from a stale cache. Cache the purity verdict only; recompute the rest.

## Acceptance criteria

- In the audit path (`_collect_purity_split_findings`, `read_through=True`), a step whose detail body, every `step.all_files` entry's content, and `change_type`/`depends_on` are unchanged since its last purity check makes **no Claude call** — the cached verdict is reused.
- In the detail-authoring path (`generate_detail`'s two sites, `read_through=False`), the helper **always** calls Claude even on a matching entry — grounding-against-current-code is never served from cache — and writes the fresh verdict through.
- A step whose declared `files:` content, or its `change_type`/`depends_on`, changed under an unchanged detail body is **not** served a stale verdict in the audit path — the helper's key differs and it calls Claude.
- On a **successful** real Claude call (audit miss, or any detail-loop call — `succeeded=True`), the helper writes an entry to `.plan-tool/purity-cache/<slug>.json` with the current key, its components (`detail_hash`, `all_files_fingerprint`, `change_type`, `depends_on`, `purity_verdict_logic_version`), the purity verdict, and the Implementation+Tests section text, and returns the producer's full merged findings.
- On a **failed** call or quiet-probe (`succeeded=False`, even though the findings list is `[]`), the helper writes **no** entry and returns the empty result uncached, so the next audit re-checks rather than serving a false-pure hit (decision 3a — gated on the invoke signal, not list-emptiness).
- On an audit-path hit, the helper returns the cached purity findings merged with freshly computed `collect_step_grounding_findings` / `collect_change_type_test_order_findings` results — deterministic grounding always runs fresh.
- An empty cached finding list with a matching key is treated as a hit in the audit path (a confirmed-pure step is not re-checked there).
- All three call sites route through the one helper (audit with `read_through=True`, both detail-loop sites with `read_through=False`).
- Every existing purity/detail-quality and completeness-audit test still passes with an empty cache.
- The new tests listed above are green.
