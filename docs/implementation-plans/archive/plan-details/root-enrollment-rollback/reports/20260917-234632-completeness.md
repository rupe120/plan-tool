- HIGH `[rollback-receipt-idempotence]` [confidence: limited]: Step 1's content-addressed receipt cannot deliver the idempotent replay the plan describes. Architecture states:

```
Before clearing the selector, rollback publishes one durable, content-addressed
receipt through `roadmap_evidence_store.py`'s `publish_evidence` (a new
namespace alongside the existing `ESCALATIONS` and `IMPACT_ANALYSES`), naming
the rolled-back root's version id, the rollback timestamp, and the confirmed
operator intent. Idempotent replay reads that receipt back with
`read_evidence_final` rather than writing a second one: `publish_evidence`'s
own `EVIDENCE_EXISTING` outcome is what lets a repeated call recognize
"already rolled back" instead of writing again or erroring.
```

`publish_evidence`'s `final_name` is the content address (a 64-hex-char name the store validates), and finding a record again — by `read_evidence_final` or by a repeat `publish_evidence` call — requires recomputing that same name. If the address is derived from everything the paragraph says the receipt "names," including the rollback timestamp, a replay call computes a new timestamp and therefore a different address, so it can't find the original: it would see "missing" and either write a second receipt under a new address or fail, exactly what Risk 2 and the acceptance criteria warn against. The paragraph is also inconsistent about which function does the lookup — it says replay uses `read_evidence_final` "rather than writing a second one," then justifies that with `publish_evidence`'s own `EVIDENCE_EXISTING` outcome, which only ever comes from calling `publish_evidence` again. The Testing section repeats the same conflation:

```
Prove idempotence: roll back twice and assert the second call reports the
already-rolled-back state by reading the existing receipt back
(`EVIDENCE_EXISTING`), without a second receipt write or error.
```

`read_evidence_final` returns an `EvidenceExactReadResult` (`data`/`failure`) with no `EVIDENCE_EXISTING` state at all — that value belongs only to `publish_evidence`'s `PublishOutcome`. The codebase already solves this exact problem: `roadmap_escalation.py`'s `EscalationReceipt.final_name` is a `semantic_id` hashed only over semantic fields, with `created_at` deliberately excluded from that hash so the same event re-derives the same address regardless of when it's checked. The plan never makes that separation, so the described lookup and the acceptance/testing language built on it fail on the very case ("roll back twice") they exist to prove.
  - Fix: State that the receipt's content address is derived only from stable identifying facts — the roadmap slug, the rolled-back root's version id, and the confirmed-intent marker — excluding the rollback timestamp, mirroring `roadmap_escalation.py`'s split between hashed semantic fields and its unhashed `created_at`, and settle on one lookup mechanism for replay instead of naming `read_evidence_final` and `publish_evidence`'s `EVIDENCE_EXISTING` as if they were the same check.
- HIGH `[rollback-seed-state-eligibility]` [confidence: limited]: Step 1's "no seed state" eligibility condition doesn't say whether an already-invalidated seed entry counts as "tracked." Architecture states:

```
The eligibility check is a closed predicate over four independently-triggerable
conditions: the accepted head names exactly the root version, no candidate
admission exists, no pending generation is recorded, and no roadmap seed state
is tracked for the slug.
```

and step 1's own intent line repeats it as "no candidate, review, seal, pending generation, or seed state depends on it." `roadmap_seed_state.py`'s schema recognizes exactly two seed-entry statuses, `"current"` and `"invalidated"` (`validate_seed_state`), and the codebase already treats them as different facts: `has_invalidated_seed` exists to tell one from the other, and `roadmap.py` uses it to report invalidated-seed counts separately. Ordinary stage revision invalidates tracked seed entries in place rather than removing them (`_publication_members` in `roadmap_revision_publish.py` calls `invalidated_seed_state`, which only flips `status` to `"invalidated"` and keeps the entry). So a roadmap that generated a seed at any point before its final, clean revision — a routine sequence, not an edge case — carries a non-empty `state["seeds"]` made entirely of dead, invalidated entries by the time it is enrolled as a root. If the eligibility check reads "seed state is tracked" as "`state["seeds"]` is non-empty," it refuses rollback forever for that roadmap even though nothing live depends on the root, defeating the plan's stated Outcome for a common case rather than the narrow one (a genuinely live, `"current"` seed) the condition is meant to protect.
  - Fix: Specify that the "no roadmap seed state is tracked" condition counts only entries with `status: "current"`; an entry already marked `"invalidated"` by a prior ordinary revision does not block rollback. Apply this to the condition itself, its Testing mutation fixture, and the acceptance criterion that restates it.
