# Step 6 — Make seed promotion refuse missing, stale, malformed, path-escaping, duplicate, or digest-mismatched drafts

## Summary

Rewrites `_apply_roadmap_seeds`'s draft preflight in `plan_tool/roadmap.py` to use step 3's `classify_draft_seeds` as its single source of per-draft state: promotion refuses any draft classified anything but `current`, replacing today's two ad hoc checks (`source.is_file()` for missing, a bare `parse_draft_seed_provenance` for unparseable) that let a hand-edited, well-formed draft promote silently. The classification runs twice — once at preflight, and again after `_confirm_apply_seeds`'s prompt returns, immediately before the staged commit — so a draft that turns `stale` or `digest-mismatched` while the confirm prompt sits open refuses instead of promoting on a stale verdict. `RoadmapApplyResult` drops its `missing_drafts`/`unparseable_drafts` fields for a per-draft refused-classification field, `_render_apply_result` in `plan_tool/cli/roadmap_cmd.py` names each refused draft's actual state in the classifier's own vocabulary, and `RoadmapSeedApplyResult` in `plan_tool/run_log.py` (plus its `DATA_CONTRACT.md` table) counts all six non-`current` states instead of the original two. On green, `--apply` promotes only a set of drafts step 3 would call entirely `current`, and every refusal says which draft failed and why, in the same word every other consumer of the classification uses.

## Why

Today `_apply_roadmap_seeds` decides whether a draft is promotable with two checks of its own: `source.is_file()` (missing) and a `try: parse_draft_seed_provenance(...)` (unparseable). That preflight is blind to every other way a draft can be untrustworthy — a sidecar `status` of `invalidated` after applied feedback, a hand edit that changed the file so its recorded `digest` no longer matches, a sidecar `draft_seed_path` hand-edited into something path-escaping, or two plan rows whose basenames collide. A reviewer who hand-tunes a draft's prose, keeping it perfectly parseable, gets it promoted into `plan-seeds/` today with no signal that the content on disk is not what generation produced and validated. Step 3 builds `classify_draft_seeds` precisely so every consumer answers "is this draft safe right now" the same way; this step makes promotion — the one consumer that writes into `plan-seeds/` — the strictest of them, refusing on any classification but `current`. It is also a second preflight this promotion path has needed to keep honest across its confirm prompt: the existing `os.link` commit already refuses a *destination* that appeared while the operator was deciding, and it does so atomically — the link call itself is the check. This step adds a check for a *source* that went bad in the same window, but it is narrower than that guard, not a matching twin of it (see Implementation's "Post-confirm re-check" for why).

## Input

This step consumes three contracts it does not own:

- **Step 3's classifier**, `plan_tool.roadmap_seed_manifest.classify_draft_seeds(artifact, *, plans_dir, slug) -> dict[str, DraftSeedClassification]`, plus the seven `DRAFT_SEED_STATE_*` constants and the precedence order the plan's Architecture section fixes (`duplicate` → `path-escaping` → `missing` → `digest-mismatched` → `stale` → `malformed` → `current`). Each `DraftSeedClassification` carries `plan_id`, `state`, and a human-readable `detail` written to be surfaced directly — this step's refusal lines print it rather than re-deriving an explanation. The classifier is read-only and recomputes fresh on every call, which is what makes calling it twice in one apply meaningful. It lets `RoadmapSeedStateError` propagate on a corrupt sidecar; this step owns converting that to `RoadmapError` for the apply path (the same conversion `plan_tool/roadmap.py:_load_roadmap_seed_state` already does for its own reads), because `plan_tool/cli/roadmap_cmd.py:_cmd_roadmap_apply` catches only `RoadmapError`/`RoadmapArtifactError`. One consequence worth stating plainly: a draft with **no sidecar entry at all** classifies `digest-mismatched` (no recorded identity to trust), so a bare draft file that today's preflight waves through will refuse — that is the intended behavior change, not a side effect. **The `stale`-before-`malformed` half of this precedence is only fully accurate once step 9 lands** (see step 3's detail, "This ordering's correctness depends on..."): until then, an ordinary no-feedback revision leaves a changed plan's sidecar `status` at `current` rather than `invalidated`, so this step's refusal may name `malformed` where the true cause is an unacknowledged revision. This does not change what this step refuses — every non-`current` state still refuses promotion identically — only the reason line an operator sees during that window. **A related but separate hazard in the same pre-step-9 window is not a matter of the reason line at all: without the fix Implementation's "Post-confirm re-check" specifies, it would be a silent promotion.** Pre-step-9, an ordinary no-feedback revision does not invalidate anything (see this bullet's own first sentence) — so a revision that changes a plan's `component_ids` while the confirm prompt is open, with no open feedback and no hand edit to the draft itself, leaves the sidecar `status` at `current` and the digest matching. A re-check that judged this case against the *preflight's* plan-row snapshot (the one the operator's confirm was shown) would find no mismatch and promote a draft validated against `component_ids` the roadmap no longer has. This is exactly why the re-check reloads `04-roadmap.md` fresh rather than reusing the preflight's `artifact` for classification (see Implementation): the fresh reload sees the revision's current `component_ids`, so the same content-validation check that made the preflight pass can now correctly fail it, refusing instead of promoting. The `targets` list itself is not re-derived from the reload — only the classification lookup is — so this fix cannot silently substitute a different set of plans than the one the operator confirmed (see Implementation for why that distinction matters).
- **The apply path's existing shape** in `plan_tool/roadmap.py`: `apply_roadmap_seeds` (run-log scope, outcome→rc mapping in its `finally`), `_apply_roadmap_seeds` (bijection check → targets → preflight → `allow_apply` gate → `_confirm_apply_seeds` → stage-and-link commit with rollback), `ordered_plan_seed_targets` (ordering-sequenced `(plan_id, source, dest)` triples), and `_promoted_seed_body` (frontmatter strip on the write path). The bijection check, the `dest.exists()` collision check, the recommend-only outcome, the confirm mechanics, and the whole `os.link` two-phase commit are not this step's to change.
- **The run-log event contract**: `plan_tool/run_log.py:RoadmapSeedApplyResult` and its writer method `RunLogWriter.roadmap_seed_apply_result`, documented in `DATA_CONTRACT.md`'s `RoadmapSeedApplyResult` section and drift-guarded by `plan_tool/data_contract.py`'s registration (enforced via `tests/test_data_contract.py`) — the dataclass and the doc table must change together. No production reader consumes the two existing draft-count fields (`missing_draft_count`, `unparseable_draft_count`); `read_run_events` returns plain dicts, so already-written logs stay readable after the field change.

## Implementation

**Preflight: classification replaces the ad hoc checks.** In `_apply_roadmap_seeds`, after the unchanged `ordering_plans_bijection_error` check and `ordered_plan_seed_targets` call:

- Call `classify_draft_seeds(artifact, plans_dir=plans_dir, slug=slug)` inside a small wrapper (a private helper or inline `try`) that converts `RoadmapSeedStateError` to `RoadmapError`, mirroring `_load_roadmap_seed_state`. A corrupt sidecar is a roadmap-level failure the CLI already knows how to report; letting the raw error escape would crash `_cmd_roadmap_apply` instead.
- Collect the refused set by walking `targets` in order and keeping each plan id whose classification's state is not `DRAFT_SEED_STATE_CURRENT`. Walking `targets` (not the classifier's dict) keeps refusal output in `ordering` sequence, matching how promotions already report.
- Delete the `source.is_file()` and `parse_draft_seed_provenance` preflight checks entirely — classification's `missing` and `malformed` states own those judgments now. Keep the `dest.exists()` collision loop unchanged: a destination collision is a property of `plan-seeds/`, not a draft state, and step 3's classifier deliberately knows nothing about destinations.
- Refuse (outcome `APPLY_OUTCOME_REFUSED`, no writes) when the refused set or the collision list is non-empty, carrying both in the result.

The order of the surviving gates is a constraint: bijection error first (it means the target list itself is unbuildable), then classification + collisions together, then the `allow_apply` recommend-only gate, then the confirm. This keeps the recommend-only outcome meaning what it means today — "everything checked out, nothing was written" — rather than recommending a set that would refuse on `--apply`.

**Post-confirm re-check.** After `_confirm_apply_seeds` returns `True` and before the staging loop (before the `plan_seeds_dir.mkdir` is fine too), reload `04-roadmap.md` fresh via `load_plans_artifact(plans_path(plans_dir, slug))` — wrapped the same way the preflight's own load already is, converting `RoadmapArtifactError`/`RoadmapSeedStateError` to `RoadmapError` rather than crashing — and run `classify_draft_seeds` against that **freshly reloaded** artifact, not the pre-confirm one. Refuse the same way if anything is no longer `current`. The confirm prompt holds the check-to-use window open for as long as the operator takes to answer; a concurrent `--refresh-seeds`, `--materialize`, or hand edit inside that window changes the drafts or the sidecar, and the classifier reads both fresh — that half was already true when this re-check reused the stale artifact, since it only reads the sidecar, never the plan rows. Reloading fresh is what additionally makes a concurrent roadmap *revision* visible: the sidecar's `stale` state alone does not catch a no-feedback revision pre-step-9 (see the Input section's discussion of this exact gap), but a fresh artifact carries the revision's current `component_ids`, so `validate_draft_seed_content` runs against what the roadmap says *now*, not what it said when the operator was shown the confirm prompt.

**Do not re-derive `targets` from the reloaded artifact.** Walk the same `targets` list the preflight built, unchanged in membership and order — only the classification *lookup* uses the fresh artifact's map. Re-deriving `targets` itself (a fresh `ordered_plan_seed_targets` call) is deliberately out of scope here: it would let a revision silently add, drop, or reorder which plans this apply promotes, changing the set the operator already confirmed — the exact hazard reloading is being used to avoid, not invite. A target whose plan id no longer appears in the fresh artifact's classification map (the revision dropped that plan row entirely) refuses that target the same way any other non-`current` state does, naming the row as no longer present in the reason line rather than inventing a classifier state that doesn't exist for it.

**This re-check narrows the source-side race; it does not close it, and it is not the destination guard's structural twin.** The `os.link` commit's guard is atomic — the link call itself is the check, so no window exists between "destination looked clear" and "destination is now claimed." The post-confirm classification is a different shape: it is a read (inside `classify_draft_seeds`, to compute each draft's digest) that completes and returns before the staging loop begins; the staging loop then calls `source.read_text(...)` again, independently, inside `_promoted_seed_body`'s caller — a second, later, unrelated read of the same file, with nothing atomically tying it back to the re-check's verdict. What the re-check buys is real: it shrinks the vulnerable window from "preflight to commit" down to "re-check to staging," and it catches every `--refresh-seeds`/`--materialize`/hand-edit that lands before the re-check runs. What it does not buy is the destination side's atomicity — a hand edit landing in the narrow gap between the re-check's read and the staging loop's own read of the same source is an accepted, pre-existing risk this step does not eliminate. Describe the two guards accurately wherever this design is documented (comments, docs): state what each one actually closes, not that they are one design.

**`RoadmapApplyResult` rework.** Drop `missing_drafts: tuple[Path, ...]` and `unparseable_drafts: tuple[Path, ...]`; add one field carrying the refused drafts with their classifications. One way: `refused_drafts: tuple[DraftSeedClassification, ...]` reusing step 3's frozen type directly (the import direction is fine — `roadmap_seed_manifest` is a leaf below `roadmap.py` by step 3's design). The renderer can recover each refused draft's source path from `result.targets` by plan id, so the field does not need to duplicate paths — but if the implementer prefers a self-contained `(plan_id, source_path, state, detail)` tuple, that is equally acceptable; what is not free to vary is that the field carries the plan id, the exact classifier state string, and the classifier's `detail`, for every refused draft, in `ordering` sequence. `targets`, `promotions`, `collisions`, and `bijection_error` keep their shapes.

**Telemetry.** In `plan_tool/run_log.py`, replace `RoadmapSeedApplyResult`'s `missing_draft_count`/`unparseable_draft_count` pair with one count per non-`current` state: keep `missing_draft_count`, rename the unparseable one to `malformed_draft_count`, and add `stale_draft_count`, `path_escaping_draft_count`, `duplicate_draft_count`, `digest_mismatched_draft_count`. The rename is deliberate, not cosmetic: the plan's acceptance criteria pin one vocabulary across every surface ("never a different word — 'unparseable' vs. `malformed`"), and the event field is a surface. Update `RunLogWriter.roadmap_seed_apply_result`'s keyword parameters to match, and `apply_roadmap_seeds`'s emission to count states out of the result's refused field. `collision_count`, `target_count`, `promotion_count`, and the `outcome` field are unchanged, as is the rc mapping in the `finally` block. No `RUN_LOG_SCHEMA_VERSION` bump: no reader keys on the removed field (verified — the only consumers are the emitter and tests), and `read_run_events` returns dicts, so old logs remain readable.

**`DATA_CONTRACT.md`.** Update the `RoadmapSeedApplyResult` table to the new field set — one row per count, each described in the classifier's words. `plan_tool/data_contract.py` registers this class against that section, so the drift guard makes the doc edit mandatory, not optional.

**Rendering.** In `plan_tool/cli/roadmap_cmd.py:_render_apply_result`'s refused branch, replace the two `missing_drafts`/`unparseable_drafts` loops with one loop over the refused drafts printing, per draft: the plan id, the draft's path (via `result.targets`), the state string verbatim, and the classifier's `detail` when non-empty. Keep the bijection and collision lines as they are. Likely worth one trailing hint line pointing at `plan-tool roadmap <slug> --materialize` for the states step 5's flag can regenerate — the tool's `Next steps:` convention allows only `plan-tool` commands — but keep it one line; the per-state remedy catalog belongs to the step 8 view, not here.

**Vocabulary sweep (do this before calling the step done).** The defect class is "a promotion surface using its own word for a draft state." Sweep by identifier — `missing_drafts`, `unparseable_drafts`, `missing_draft_count`, `unparseable_draft_count` — and by vocabulary — `unparseable`, "missing draft", "provenance not parseable" — across `plan_tool/roadmap.py` (including `apply_roadmap_seeds`'s docstring, which currently enumerates the old refusal reasons), `plan_tool/run_log.py`, `plan_tool/cli/roadmap_cmd.py`, `DATA_CONTRACT.md`, and both test files. `_promoted_seed_body`'s `parse_draft_seed_provenance` call is deliberately **not** part of the class: on the write path it is the frontmatter-stripping mechanism at the strict-parser boundary, not a validation channel, and by the time it runs classification has already vetted every draft twice. Leave it.

The rejected alternative, for the record: keeping the old preflight checks beside the classification as a belt-and-braces double check. That is exactly the "second copy of the same judgment" this plan exists to remove — two checks drift the first time either rule changes, and the step's intent names the ad hoc preflight as the thing being replaced, not supplemented.

## Applicable guardrails

- **The plan's "## Out of scope", regeneration and replacement** — refusal is the whole action: this step never deletes a refused draft, never regenerates one, and never writes a replacement. The refusal output may point at the explicit regeneration commands; it must not invoke them.
- **The plan's "## Out of scope", correctness gates on seed content** — the refusal keys only on the binary observable (each plan id has exactly one valid draft with the recorded identity). No style, length, or quality judgment enters the preflight; `malformed` means step 1's shared content check failed, nothing softer.
- **The plan's "## Out of scope", second seed store** — the post-confirm re-check and the refused-classification field add no sidecar field and no new persisted state; classification stays computed-fresh, per step 3's read-only contract.
- **The plan's architecture, one shared classification for every consumer** — this step must not re-derive any draft-state judgment locally; every state word it stores, counts, or prints comes from step 3's constants, which is what keeps `--apply` and the later view steps resolving the same file to the same word.
- **The plan's "## Out of scope", routing discoveries** — anything this step's sweep surfaces beyond the promotion path (for example other run-log events with drift-prone vocabulary) goes to `BACKLOG.md`/`BUG_BACKLOG.md`, not into this diff.
