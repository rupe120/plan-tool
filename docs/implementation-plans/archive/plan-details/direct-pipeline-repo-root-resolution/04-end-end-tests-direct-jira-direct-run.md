# Step 4 — Add end-to-end tests for direct-jira and direct-run when create relocates the repo root

## Summary

This step adds real, unstubbed-handler end-to-end coverage to `tests/cli/test_direct_cmd.py` that drives `cmd_direct_jira`/`cmd_direct_run` through an actual seed-derived repo-root relocation, once steps 1–3 land the fix. The existing tests in this file (steps 2/3) stub every stage handler (`cmd_create`, `cmd_detail`, …) and hand-build a `CreateResult` pointing at a relocated `plan_path` — that proves the *threading* and the *dirty guard* work given a relocation, but never exercises the thing that actually triggers a relocation: `plan_tool/cli/authoring.py:cmd_create`'s seed-scan (`extract_file_path_candidates` → `find_umbrella_root`) and its `_confirm_repo_root` non-interactive path. This step closes that gap by building a real **sibling** (disjoint — `find_umbrella_root` case 1, one other `.git` that is neither nested nor an ancestor of cwd) git-repo fixture — the case the plan actually handles — a seed whose body references a file under it, and driving the real `cmd_direct_jira`/`cmd_direct_run` chains with every stage's Claude seam neutralized at its own call-site module. (Note: an *ancestor* "umbrella" — `find_umbrella_root` case 2 — is not the handled case; it is refused per decision 7, exercised by the nested/ancestor fixture below.) It also builds a **nested** fixture to prove the opposite: that a nested/ancestor relocation is **refused** (step 2's Architecture-decision-7 guard) with a clear error, not handled — since the plan deliberately scopes the nested/embedded-repo case out (deferred to BACKLOG #146). No production code changes ship with this step — it is a pure test-authoring step against the interface steps 1–3 establish. On green: both verbs complete end to end for the disjoint/sibling relocation, git commits are confirmed landing in the relocated repo (not the original cwd-derived one), a nested-relocation seed makes both verbs refuse cleanly, and a disjoint relocated root with pre-existing unrelated dirt aborts the chain before `cmd_detail` runs.

## Why

Step 2's Deferred section names this step directly: "End-to-end coverage driving real narrower/broader seed-derived relocations through the full chain (both verbs, both directions) — step 4's job; this step's tests are unit-level against stubbed stage handlers." Step 3's Deferred section says the same for its dirty-root guard: "this step's tests stub the stage handlers and exercise the guard at the unit level." Both steps prove their own mechanism works given a relocated `CreateResult` they construct by hand — neither one proves that a real `--from-existing` seed, run through the real `cmd_create`, actually produces that relocation in the first place. That trigger path — `plan_tool/cli/authoring.py:cmd_create`'s `explicit_root` check, the seed-derived `find_umbrella_root` override, and the non-interactive branch of `_confirm_repo_root` — is exactly what this whole plan exists to make downstream stages aware of (per the plan's Problem statement and Testing section, which asks for a seed resolving to a broader/sibling **disjoint** root driven through both verbs end-to-end — confirming the plan is found by every stage, commits land in the relocated repo, and a pre-existing dirty relocated repo aborts cleanly — plus a **nested** seed confirming both verbs refuse per decision 7). Without this step, the plan's whole fix ships with only its unit-level threading proven, not its actual trigger.

## Input

This step builds on steps 1–3's mechanisms without renegotiating any of them, plus one existing `cmd_create` contract that the plan does not modify:

- **`created_repo_root` derivation and threading** (step 2, `depends_on: 3` transitively covers it): once steps 1–3 land, every `_stage_namespace(...)` call in `cmd_direct_jira`/`cmd_direct_run` carries `repo_root=created_repo_root`, and every post-create `working_tree_dirty`/`commit_all` call targets it. This step drives that machinery for real rather than re-verifying it in isolation.
- **`unexpected_dirty_paths`/the relocated-root guard** (step 3): once landed, a (disjoint) relocated root with dirty content outside `create`'s own known writes — `{plan_path, manifest_path, concepts_path(plan_path), grounding_path(plan_path)}` plus, on a same-slug collision-replace, `{replaced_archives, replaced_manifest_entries, plan_details_renamed_to}` — aborts the chain before `cmd_detail` runs. This step's dirty-abort scenarios exercise that guard against a real `git status`, not a stubbed one. (Step 3's own detail file is the authority on the exact set; this restatement includes `grounding_path` and the collision-replace paths to stay consistent with it.)
- **Step 2's nested/ancestor refuse-guard** (Architecture decision 7): a relocation where `created_repo_root` is nested inside — or a strict ancestor of — the original `repo_root` is refused with a non-zero error before any stage runs. This step's nested-fixture scenario exercises that refusal end-to-end (a real nested-repo seed → the verb refuses), the counterpart to the disjoint scenarios proving the handled path.
- **`cmd_create`'s existing seed-derived relocation** (`plan_tool/cli/authoring.py:cmd_create`, unmodified by this plan): `explicit_root = getattr(args, "repo_root", None) is not None or resolve_repo_root(None) is not None` — when true, both the seed-derived `find_umbrella_root` override and the `_confirm_repo_root` prompt are skipped outright, and `repo_root` never changes from the pre-create value. This is the mechanism this step must actually trigger, and it constrains how the test's `args` namespace can be built (see [Implementation](#implementation)).
- **`CreateResult`'s existing invariants** (`plan_tool/create.py`, unchanged): `plan_path` is `None` only on the multi-plan split short-circuit; `manifest_path` is always populated. Neither changes here — this step just reaches them via the real `cmd_create` instead of constructing them.

Verifying this step is limited to driving the real CLI entry points end to end; there's no persisted schema or saved report to check beyond what `git log`/the plan/detail files on disk show after each chain run.

## Implementation

**The one constraint that isn't free to vary: the test's `args.repo_root` must stay unset for relocation to trigger at all.** `cmd_create`'s `explicit_root` check treats a non-`None` `args.repo_root` as "the operator owns the choice" and skips the seed-derived override entirely — and so does `_resolve_cmd_repo_root`, which every stage (including the step-0 precondition) calls. The existing `_input_args` helper in this file always sets `repo_root=tmp_path` explicitly; so does the repo-wide `tests/cli/conftest.py:CliRepo.argv()` convention, deliberately, "to keep `main()` off the ambient cwd-discovery path" for hermeticity. Both are exactly the setting that makes relocation impossible to exercise. For this step's tests: build `args` with `repo_root=None` (and no `--repo-root` equivalent set anywhere), `monkeypatch.delenv("PLAN_TOOL_REPO_ROOT", raising=False)`, and `monkeypatch.chdir()` into the original repo before invoking the verb, so `_resolve_cmd_repo_root`/`cmd_create`'s `explicit_root` check both fall through to the real `find_repo_root_from_cwd()` walk and the seed-derived umbrella override actually runs. This is the step's central design decision — everything else follows from it.

**Building the two relocation fixtures.** Both need a *real*, initialized git repo — not just a `.git` marker directory — because `working_tree_dirty`/`commit_all` (`plan_tool/cli/gitcommit.py`) shell out to `git status`/`git commit` for the assertions in this step, unlike `find_umbrella_root`'s `_controlling_git_repo` (`plan_tool/locator.py`), which only checks `.git`'s existence to pick the owning root:

- **Broader/sibling (disjoint — the handled case):** create a sibling directory *not* under the original root, `git init` it. The seed body references an absolute path resolving under that sibling. A single file reference resolving to one other owning `.git` is enough — `find_umbrella_root`'s case 1 (all files share one owning repo) already relocates there directly; you don't need a seed spanning two distinct owning repos to get the "broader (outside)" `relation` string `cmd_create` logs (that's case 2, a genuinely `.git`-less umbrella, and it's out of scope — see [Deferred](#deferred)). This is the disjoint relocation the plan handles end-to-end.
- **Nested (the refused case):** create a nested directory under the original root's tree, `git init` it there too, and a seed whose body references a file path resolving under that nested directory. `cmd_create` will relocate to the nested root; the point of this fixture is *not* to drive the chain through — it's to assert step 2's Architecture-decision-7 refuse-guard fires (`created_repo_root.is_relative_to(repo_root)`), so both verbs return non-zero with the nested-repo error and no stage runs. Do **not** build the chain-completes assertions on this fixture — the nested case is deliberately unsupported (deferred to BACKLOG #146); it exists only to lock in the refusal.
- Mirror `tests/cli/test_gitcommit.py:_init_git_repo` for the init helper (`git init -q` + `user.email`/`user.name` config) — a 4-line function, worth a local equivalent in this file rather than a cross-file import, since the two test files don't share fixtures today.
- Both repos must exist on disk *before* the chain runs (not lazily created by `create`), since the dirty-abort scenarios need to seed unrelated dirt into the relocated root ahead of time.

**Getting `cmd_create` to write a plan without a real claude call.** `--from-existing <path>` lifts steps deterministically when the seed matches the canonical layout, or asks claude when it doesn't (`plan_tool/create.py:read_existing_description`) — either way, stub the seams so no real call happens regardless of shape: `create.py`'s `shell_claude_invoker` / module-level `propose_steps_from_claude`/`propose_references_from_claude`, plus the post-write convergence loop's `create_module.apply_finding` (per `TESTING.md`'s table, rows for `create.py`). Put the umbrella-triggering file reference in the seed body's prose (a backtick-fenced or inline path with a directory component and an extension, matching `create.py`'s `_FILE_PATH_PATTERN`) — `extract_file_path_candidates` scans `seed_body`/`description` text, not the destination directory tree.

**Neutralizing every stage's Claude seam — the largest surface in this step, since every handler now runs for real instead of being stubbed.** Consult `TESTING.md`'s "Backend fallback seams" table for `create.py`/`detail.py`/`launcher.py`/`cli/completeness_apply_parallel.py`, and add the seams this step's audit found that table doesn't enumerate:

- `cmd_jira`'s real export path — `plan_tool/cli/jira_cmd.py`'s imported `export_jira` — stub it the way the existing (unedited-by-this-step) `tests/cli/test_jira_cmds.py` already does: `monkeypatch.setattr("plan_tool.cli.jira_cmd.export_jira", fake_export)`.
- `cmd_run`'s real step execution — `plan_tool/cli/run_cmd.py`'s imported `run_step` — stub it the way `tests/cli/test_run_cmd.py:TestRunResumeCommand.test_cmd_run_registers_resume_command_during_run_step` already does: `monkeypatch.setattr(run_cmd, "run_step", fake_run_step)`, modeled on that file's `_FakeRunResult`. **Unlike that test, do not also stub `run_cmd._working_tree_dirty`/`_commit_green_step`** — this step's commit-location assertions need `cmd_run --all --commit`'s own per-green-step commit to actually run against the relocated root.
- `cmd_reconcile_code`'s real step execution — `plan_tool/cli/reconcile.py` also imports `run_step` directly — needs the same call-site-module stub as `run_cmd.py`, at `reconcile.py`'s own binding.
- Each of these is a direct `from plan_tool.launcher import run_step`-style import into the caller's own module namespace, so — per `TESTING.md`'s "Mocking conventions" ("this is per-caller because `from plan_tool.launcher import apply_finding` binds the name in the caller's namespace") — patching the shared domain module (`plan_tool.launcher.run_step`) has no effect on these callers; patch each call-site module directly. `cli/completeness_apply_parallel.py` is the opposite case: it reads `launcher.apply_finding` via qualified attribute access, so patching the shared module *does* work there — both conventions coexist in the same test.
- `record_known_root`'s cache write (fired inside `cmd_create`'s relocation branch) resolves under `Path.home()` — already isolated globally by `tests/conftest.py:_isolate_known_roots_cache` (autouse); no extra setup needed here.

**Test organization.** Add the new section after the file's existing step-6 section, following the same banner-comment convention. Mark it `@pytest.mark.integration` — it drives real orchestrators across `create.py`/`detail.py`/`launcher.py`/`jira.py`/`review.py` in one process, matching `TESTING.md`'s "add an integration test when a unit test can't prove what you need" criterion (steps 2/3's fully-stubbed unit tests cannot prove the seed-scan-to-relocation trigger fires). Keep the two fixtures and the shared seam-neutralization setup as helpers reused across both verbs and both directions, mirroring how `gate_create_result_size`/`_stage_namespace` are already shared in `plan_tool/cli/direct_cmd.py` rather than copy-pasted per verb.

**Assertions, per scenario:**

- *"Plan is found by every stage"* — each stage's rc is 0, and the plan's `step.detail` pointer (once detail runs) resolves under the *relocated* root's `docs/implementation-plans/plan-details/...`, not the original.
- *"Commits land in the relocated repo"* — after the chain, `git log` (or a helper mirroring `tests/cli/test_gitcommit.py`'s `_git`) in the relocated root shows the `direct-jira(<slug>): author plan and detail` / `direct-run(<slug>): author plan and detail` commit subjects (the literal f-strings already in `plan_tool/cli/direct_cmd.py`); the original root's own history shows none of them.
- *"Pre-existing dirty relocated repo aborts cleanly"* — seed an unrelated untracked/modified file into the relocated root (not one of `create`'s own expected writes) before the chain runs; assert non-zero rc, the offending path named in stderr, and no detail bundle directory written under the relocated root's `plan-details/<slug>/`.

**Constraints:**

- No production code changes ship with this step. If writing these tests surfaces a real gap between steps 1–3's actual behavior and their own detail files' description, that's a reconcile-routed finding against those steps, not something to patch here.
- Don't duplicate the fixture-building or seam-neutralization setup between the `direct-jira` and `direct-run` scenario tests — share it, per the file's established pattern.

## Tests

- `test_seed_relocates_to_broader_sibling_root_via_real_create` — sanity check: driving the real `cmd_create` alone (not the full chain), with `args.repo_root=None` and cwd set to the original root, using the broader/sibling seed, relocates and registers the plan under the sibling root's manifest. Establishes the fixture is sound before layering the chain on top.
- `test_seed_relocates_to_nested_root_via_real_create` — companion sanity check: the nested seed drives real `cmd_create` to relocate under the nested root (proves the fixture *does* trigger a nested relocation, so the refusal tests below are exercising a real relocation, not a no-op).
- `test_direct_jira_broader_relocation_end_to_end` — real chain (`create → detail → completeness-apply → jira`) with the broader/sibling seed completes with rc 0; every stage's artifacts land under the sibling root.
- `test_direct_run_broader_relocation_end_to_end` — real chain (`create → detail → completeness-apply → run --all --commit → reconcile-code`) with the broader/sibling seed completes with rc 0; every stage's artifacts land under the sibling root.
- `test_direct_jira_nested_relocation_seed_refused` — the nested seed driven through the real `cmd_direct_jira`: the chain **refuses** with a non-zero rc, the error names the nested-repo situation, and no detail bundle / jira export is produced (step 2's decision-7 guard fired). Proves the scoped-out case fails cleanly rather than corrupting state.
- `test_direct_run_nested_relocation_seed_refused` — same for `cmd_direct_run`.
- `test_direct_jira_relocation_commits_land_in_relocated_repo_not_original` — for the broader/sibling direction (original and relocated roots are unrelated siblings), `git log` in the relocated root shows the chain's commit subjects; `git log` in the original root shows none of them (except the original root's own archived-seed commit from step 2, which *does* land there — assert that one specifically is present in the original and absent from the sibling).
- `test_direct_run_relocation_commits_land_in_relocated_repo_not_original` — same for `cmd_direct_run`.
- `test_direct_jira_relocated_root_preexisting_dirt_aborts_before_detail` — unrelated dirt seeded into the relocated (sibling) root before the chain runs; non-zero rc, offending path named in stderr, no detail bundle written.
- `test_direct_run_relocated_root_preexisting_dirt_aborts_before_detail` — same for `cmd_direct_run`.
- `test_direct_jira_no_relocation_real_chain_still_succeeds` — a seed with no umbrella-triggering file references, driven through the real chain with `repo_root=None`, completes end to end with a single root throughout (no relocation) — the plan's "no-relocation case is behaviorally unchanged" acceptance criterion, now proven against the real `cmd_create` path rather than a hand-built `CreateResult`. (`direct-run`'s no-relocation case stays covered at the unit level by steps 2/3; a duplicate real-chain run adds cost without new signal.)

### Test-creation order (feature step)

Add the two fixture-sanity tests first (broader-sibling relocates; nested relocates) — they prove the relocation trigger itself works, independent of the direct-* chain, and are the cheapest place to debug the `repo_root=None` + cwd + seed-body setup. Then the two broader/sibling full end-to-end "plan is found by every stage" tests (jira, run). Then the two nested-refusal tests. Then the two commit-location assertions, then the two dirty-abort tests, then the no-relocation regression guard. Every new test must be green before this step is considered finished.

## Acceptance criteria

- A seed whose file references resolve to a broader (sibling, disjoint) `.git` ancestor, driven through the real `cmd_direct_jira`, completes `create → detail → completeness-apply → jira` with rc 0, with every stage's artifacts under the sibling root; same for `cmd_direct_run` through `create → detail → completeness-apply → run --all --commit → reconcile-code`.
- A seed whose file references resolve to a **nested** (or ancestor) `.git` ancestor makes both `cmd_direct_jira` and `cmd_direct_run` **refuse** with a non-zero rc and a clear nested-repo error, producing no detail bundle / no downstream stage — proving the scoped-out case fails cleanly (deferred to BACKLOG #146).
- `git log` in the relocated (sibling) root shows the chain's `direct-jira(...)`/`direct-run(...)` commit subjects; the original cwd-derived root's history shows none of them except its own `archive superseded seed after relocation` commit (step 2), which lands in the original root by design.
- A disjoint relocated root with pre-existing dirt unrelated to `create`'s own writes makes the real chain abort with a non-zero rc before `cmd_detail` is reached, for both verbs.
- A seed with no umbrella-triggering file references still completes the real chain end to end with a single root throughout.
- All new and existing tests in `tests/cli/test_direct_cmd.py` pass, and no production file changes ship with this step.
