# Step 4 — Add a configured-timeout kill and a termination reason to the shared runner

## Summary

Extends `plan_tool/backend_runner.py:run_streaming_once` (relocated in step 2, given its kill-on-any-exception net in step 3) with two things: an elapsed-time kill the monitor thread enforces alongside its existing silence kill, gated by an explicit `enforce_configured_timeout` parameter that defaults to `False` so `run`'s call sites stay exempt without any edit to their unchanged call site; and a closed, seven-value termination-reason vocabulary (`completed`, `configured_timeout`, `silence_timeout`, `operator_interrupt`, `spawn_failure`, `backend_nonzero`, `unknown`) that every ending of the function can be sorted into. The monitor thread's two kill paths write the same `BACKEND_TIMEOUT_SENTINEL`-bearing stderr string `plan_tool/shell.py:_run_once` writes today, so `plan_tool/claude_errors.py:classify()` recognizes a runner-initiated kill exactly as it recognizes today's `subprocess.TimeoutExpired` path, with no change to `classify()` itself. `Popen()` itself also gets wrapped, so a spawn-time failure (missing binary removed between `shutil.which` and `Popen`, a permissions error) is classified `spawn_failure` instead of an uncaught traceback — the one path step 3's `proc.wait()` net can't reach. A per-caller silence-threshold override hook, mirroring `plan_tool/shell.py:scoped_claude_timeout`'s context-manager shape, ships alongside this work. Green when every one of the seven reasons is provable by a direct test against `run_streaming_once`, `run`'s existing behavior is unchanged (still defaults to no configured timeout and the existing 900-second silence kill), and `claude_errors.py`'s classification bridge is proven end to end with no code change to `classify()`.

## Why

Today only the buffered batch path enforces a configured timeout: `plan_tool/shell.py:_run_once` passes `timeout=` to `subprocess.run`, which raises `subprocess.TimeoutExpired`, and `_run_once`'s `except` handler turns that into a synthetic `(124, "", "__plan_tool_backend_timeout__: ...", ...)` outcome that `classify()` recognizes as terminal `ClaudeFailureKind.TIMEOUT`. The streaming runner (`run_streaming_once`, moved in step 2) has no equivalent — its monitor thread only watches for *silence* (`_STALL_THRESHOLD_S`/`_KILL_AFTER_SILENCE_S`), never total elapsed time. Once step 6 moves the batch path onto this same runner, that configured-timeout enforcement has to exist here or two real callers lose their bound: `completeness-audit`'s per-step purity check and any other `scoped_claude_timeout` caller (`plan_tool/shell.py:_effective_subprocess_timeout` reads the scope).

The exemption for `run`'s call sites can't be left to inference — the plan's Out of scope is explicit that the default (unbounded) total-duration timeout for every command stays unchanged, and `run`'s calls stay exempt from `PLAN_TOOL_CLAUDE_TIMEOUT`/`scoped_claude_timeout` exactly as today. Since both lanes will call the identical shared function once step 6 lands, that guarantee has to live in the function's own call contract — an explicit boolean parameter defaulting to the exempt behavior — not in an assumption about what any particular caller happens to pass.

Separately, once the monitor thread can end a call two different ways (silence vs. configured timeout) and the main thread can end it two more ways (a clean exit, an operator interrupt, or any other exception it now distinguishes per step 3's baseline net), there's no single place a caller — or this step's own tests — can read "why did this call end." Steps 5 and 9 need that answer to populate run-log events and `in-flight.json`, but neither of those files is in this step's scope; this step's job is only to make the answer determinable, in a shape those later steps can build on without re-deriving it.

## Implementation

**The configured-timeout parameter pair.** Add `enforce_configured_timeout: bool = False` and `configured_timeout_s: Optional[float] = None` as new keyword-only parameters on `run_streaming_once`. The boolean is the exemption contract the Why section describes — it's what's checked, not whether a value happens to be present, so `run`'s call sites stay exempt even if some future refactor accidentally threads a stray timeout value their way. `launcher.py`'s wrapper (`_run_streaming_once`, untouched by this step) forwards a fixed set of keyword arguments established in step 2 and doesn't know these two names exist, so it can't pass them — `run`'s calls get the defaults with zero edits to `launcher.py`, which is what keeps this step's `files:` list from needing to include it. No production caller passes `enforce_configured_timeout=True` yet; step 6 is where `claude_invoke`'s call site sets it `True` and resolves `configured_timeout_s` from `plan_tool/shell.py:_effective_subprocess_timeout()` (unchanged, not touched by this step) before calling in.

**The monitor-thread check.** The heartbeat closure already computes `silent = now - state["last_activity_monotonic"]` each tick and compares it to the silence threshold. Add a second comparison in the same tick — `elapsed = now - start_monotonic` against `configured_timeout_s` — but only when `enforce_configured_timeout` is `True` and `configured_timeout_s` is not `None`. Reuse the existing tick cadence (`_PROGRESS_INTERVAL_S`); a configured timeout doesn't need finer precision than the silence check already has; both are a same-tick termination, not a hard OS-level cutoff. Both checks should fire through one shared kill-ladder helper (`terminate()`, wait out the grace window, escalate to `kill()` if still alive) parameterized by which reason is firing, rather than duplicating the terminate/grace/kill block a second time inside the same closure. Guard whichever check fires first with the existing one-shot-fire flag (today's `killed_fired[0]`) so the two checks can't both fire for the same call.

**The termination-reason vocabulary.** Define the closed seven-value set at module scope in `backend_runner.py` — `completed`, `configured_timeout`, `silence_timeout`, `operator_interrupt`, `spawn_failure`, `backend_nonzero`, `unknown` — as a `str`-subclassed `Enum`, matching `claude_errors.ClaudeFailureKind`'s shape (strings, not auto-ints, so the value greps cleanly and survives a JSONL round-trip) without importing that module. Track which reason applies to the in-progress call as small internal state next to the existing `killed_fired`/`stall_fired` flags, and expose the finished call's reason through a **call-scoped** accessor, `get_last_termination_reason()`: a module-level `ContextVar` holds a small per-call mutable cell, set to a fresh cell on the calling thread at `run_streaming_once` entry; the classification writes into that cell right before the function returns (`completed`/`backend_nonzero`/`configured_timeout`/`silence_timeout`) or right before it re-raises (`operator_interrupt`/`unknown`/`spawn_failure`); the accessor reads the calling context's cell. The cell indirection is what makes this correct, not just tidy, on both axes at once: a plain module value is shared **across** concurrent calls — `completeness-apply --jobs N` already drives multiple worker threads through this same runner today, and step 6 adds `detail --jobs N`'s `claude_invoke` callers, so one thread's read could return a different, concurrently-finishing call's reason, corrupting the exact liveness data this plan exists to produce — while a plain `ContextVar.set()` fails in the *other* direction, because the monitor thread runs in a copied context (step 2's `contextvars.copy_context()` thread wiring) and its `set()` would never be visible to the caller. Setting the `ContextVar` to a cell on the calling thread and *mutating the cell's contents* from whichever thread classifies the ending threads the needle: the caller and its monitor thread share one cell object, and concurrent calls each own their own. This keeps the function's existing four-element return tuple unchanged — `launcher.py`'s destructuring call sites, none of them in this step's `files:` list, don't need to learn a fifth field — and keeps the same accessor name and call shape steps 6 and 7 already reference. Steps 5 and 9 (not this step) decide how a caller with a `RunLogWriter` turns this into a persisted event; this step's job is only to make the answer available, not to wire it anywhere.

**The precedence rule.** An operator interrupt always wins a race against a monitor-thread kill reason, per the plan's Architecture: writing `operator_interrupt` always overwrites whatever reason is currently tracked; a monitor-thread reason (`configured_timeout`/`silence_timeout`) is refused if the tracked value is already `operator_interrupt`. Guard the tracked-reason read-check-write with a lock (the existing `state_lock` or a dedicated one) so this holds regardless of which thread — the heartbeat racing to fire its kill ladder, or the main thread catching a `KeyboardInterrupt` out of `proc.wait()` — reaches the write first.

**The `BACKEND_TIMEOUT_SENTINEL` bridge.** Both new monitor-thread kill reasons (`configured_timeout`, `silence_timeout`) need the same synthetic stderr marker `_run_once`'s `TimeoutExpired` handler writes today, so `classify()` recognizes either one as terminal `TIMEOUT` with no code change on its side. Because `backend_runner.py` can't import `plan_tool.claude_errors` without breaking its own leaf constraint, mirror the literal string value as a local constant in `backend_runner.py` rather than importing `claude_errors.BACKEND_TIMEOUT_SENTINEL` — the same "mirror, don't import across a leaf boundary" shape this codebase already uses elsewhere (e.g. `plan_tool/reprocess.py`'s `_split_frontmatter_for_rewrite` mirrors `plan_tool/parser.py`'s frontmatter-fence scan rather than importing it, precisely because importing would cost the leaf its leaf status). Pin the two constants' equality with a dedicated test (see Tests) so a future edit to either value can't silently break the bridge. Append the mirrored marker to the kill's own stderr text before it reaches the returned `stderr_buffer` — whichever of the two new reasons fired, `classify()` only ever sees `TIMEOUT`; it has no way to distinguish `configured_timeout` from `silence_timeout`, and doesn't need to — that finer distinction is what the accessor from the previous bullet is for.

**The `spawn_failure` classification.** Wrap only the `subprocess.Popen(...)` call itself — not the `if proc.stdout is None or proc.stderr is None:` guard immediately after it, which is a separate, pre-existing, effectively-unreachable defensive check this step leaves as is. Catch `KeyboardInterrupt` first (classify `operator_interrupt`, matching every other place in this function a `KeyboardInterrupt` lands) and any other exception second (classify `spawn_failure`), then re-raise the original exception unchanged in both cases — the same two-arm shape as the refined `proc.wait()` except block, applied to the one call step 3's net can't reach because nothing has been spawned yet for it to kill. No stderr-sentinel bridge is needed for `spawn_failure` — once step 6 wires `claude_invoke` onto this function, that caller (not this step) is what will catch the re-raised exception and turn it into a `(rc, stdout, stderr)` outcome for `classify()`, using an ordinary nonzero `rc` with no `BACKEND_TIMEOUT_SENTINEL` marker — `classify()`'s existing fallback already buckets that as `UNKNOWN_NONZERO`, matching the plan's stated design (`spawn_failure` and `unknown` both terminal, no same-budget retry, surfaced once rather than silently retried as `TRANSIENT` would be). Building that catch-and-convert wiring in `shell.py` is step 6's work, not this step's — this step only has to make `spawn_failure` (and `unknown`) determinable at the point they're raised.

**`completed` vs. `backend_nonzero`.** After the (possibly refined) `try/except/finally` around `proc.wait()` completes without raising, and after the thread joins, classify the ending from `proc.returncode` and whether a kill fired: `completed` when the child exited zero and neither kill path fired; `backend_nonzero` when it exited nonzero with neither kill firing — a case that exists in the vocabulary today but has never previously needed a name at this altitude, since prior to this step every non-exception ending was implicitly "the child returned, look at `rc`."

**The silence-threshold override hook.** Add a `scoped_silence_timeout(seconds)` context manager and its backing `ContextVar`, structurally mirroring `plan_tool/shell.py:scoped_claude_timeout` (same sentinel-default-vs-explicit-`None`-scope shape, same reset-on-exit contract) — again mirrored rather than imported, for the same leaf-boundary reason as the sentinel constant. The heartbeat reads the effective silence threshold each tick through a small resolver (scope value if set, else the existing `_KILL_AFTER_SILENCE_S` module constant) in place of reading the module constant directly. This is code-level only — no CLI flag, no env var, no `run_streaming_once` parameter — matching the plan's Risks entry, which is explicit that this stays a developer-set override, not an operator-facing surface. No production call site sets it in this step; it exists so a future caller that needs a non-default threshold (surfaced by characterization, or by a caller added after this plan) has a documented, tested mechanism ready rather than another timeout mechanism getting invented ad hoc later.

## Acceptance criteria

- `run_streaming_once` accepts `enforce_configured_timeout: bool = False` and `configured_timeout_s: Optional[float] = None`; a call with `enforce_configured_timeout=True` and a short `configured_timeout_s` is killed once elapsed time (not silence) crosses that value, even while the child keeps producing fresh output.
- The same call made with `enforce_configured_timeout` left at its default is never killed by the elapsed-time check, regardless of `configured_timeout_s`.
- `launcher.py` needs no edit for `run`'s call sites to stay exempt — `git diff --stat` against this step's base commit shows no change to `plan_tool/launcher.py`.
- A configured-timeout kill and a silence kill both produce a returned `stderr` containing the value mirrored from `claude_errors.BACKEND_TIMEOUT_SENTINEL`, and `classify()` (unedited) classifies both as `ClaudeFailureKind.TIMEOUT`.
- The mirrored sentinel constant in `backend_runner.py` is asserted equal to `claude_errors.BACKEND_TIMEOUT_SENTINEL` by a dedicated test.
- Every one of the seven closed termination-reason values (`completed`, `configured_timeout`, `silence_timeout`, `operator_interrupt`, `spawn_failure`, `backend_nonzero`, `unknown`) is reachable and asserted by at least one direct test against `run_streaming_once`.
- `get_last_termination_reason()` is call-scoped: two concurrent `run_streaming_once` calls finishing near-simultaneously with different reasons each read back their own, proven by a test that reliably exercises the overlap rather than depending on timing luck.
- A `KeyboardInterrupt` is classified `operator_interrupt` regardless of whether it lands during `Popen()` or during `proc.wait()`; any other exception during either call is classified `spawn_failure` (at `Popen()`) or `unknown` (at `proc.wait()`) — in every case the original exception instance still propagates unchanged, matching step 3's existing guarantee.
- An operator interrupt racing a monitor-thread kill always resolves to `operator_interrupt`, proven by a test that reliably exercises the race rather than depending on timing luck.
- `scoped_silence_timeout(seconds)` overrides the global `_KILL_AFTER_SILENCE_S` threshold for calls made inside its scope only; a call outside the scope, concurrent or sequential, still reaps at the global default.
- `plan_tool/backend_runner.py` still imports no first-party module besides `plan_tool.backend` and `plan_tool.run_log` (step 2's `test_leaf_has_bounded_first_party_imports` stays green with no changes).

## Applicable guardrails

- **Plan's "## Out of scope" — the default unbounded total-duration timeout, and `run`'s exemption from `PLAN_TOOL_CLAUDE_TIMEOUT`/`scoped_claude_timeout`, stay unchanged.** This step must not give `run`'s call sites a configured timeout by default, and must not make the silence-threshold override an operator-facing flag or env var — the override hook stays code-level only, per the plan's Risks entry and Out of scope's "making per-command silence/stall thresholds configurable" exclusion.
- **Architecture's ordering-constraint bullet.** This step's new behavior (the configured-timeout kill, the termination-reason vocabulary, the `spawn_failure` classification) must land after step 3's baseline kill-on-any-exception net and before any run-log event wiring (steps 5, 7, 9) or batch-lane wiring (step 6) — this step defines the vocabulary those later steps consume; it does not itself wire any event or any new caller.
- **Architecture's "the shared runner extraction is global" / "allowed behavior changes" bullets.** This step's new kill and classification behavior applies to the one shared function every caller will eventually reach — it must not be built as a per-caller branch inside `run_streaming_once`; the exemption for `run` is the `enforce_configured_timeout` parameter's default, not a conditional on which caller is asking.
- **Plan's Architecture — `claude_errors.py` "survives unchanged."** This step's edit to that file is limited to documentation; any change to `classify()`'s logic, `BACKEND_TIMEOUT_SENTINEL`'s value, or the `ClaudeFailureKind` vocabulary itself is out of this step's scope.
