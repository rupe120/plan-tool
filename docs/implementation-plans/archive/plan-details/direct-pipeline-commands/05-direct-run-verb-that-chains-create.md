# Step 5 — Add the `direct-run` verb that chains create, detail, run `--commit`, and the reconcile-code loop

## Summary

This step adds the `cmd_direct_run` verb to `plan_tool/cli/direct_cmd.py` (the leaf step 3 creates). The verb runs the whole `create → detail → completeness-apply → run --all --commit → reconcile-code` chain in one process: it gates on a clean tree, calls `cmd_create`, catches the `CreateResult` through step 2's `_create_result_sink`, runs step 3's size-gate helper, calls `cmd_detail` (`--detail-only`), commits the authoring artifacts, calls `cmd_completeness_apply` (`--jobs N -y`) to apply the conceptual gaps from detail's saved audit and commits those, calls `cmd_run` with `--all --commit`, then calls `cmd_reconcile_code` once per **code** step (skipping non-code steps). Like `direct-jira` it reuses the existing handlers and threads one namespace into each; the main design points beyond `direct-jira` are the extra **run** and **reconcile** tail stages. The **clean-tree hand-off** serves both `completeness-apply`'s worktree isolation and the run stage's `--commit` gate: `cmd_create` and `cmd_detail` write the plan file, detail bundle, and manifest, which dirty the tree, but `cmd_run`'s `--commit` path refuses to run on a dirty tree — so the verb must commit those artifacts before the run stage. Like `direct-jira`, it reuses the existing stage handlers (`plan_tool/cli/authoring.py:cmd_create` / `cmd_detail`, `plan_tool/cli/run_cmd.py:cmd_run` / `cmd_reconcile_code`) and threads one args namespace into each, so cross-cutting flags ride through unchanged. On green, `plan-tool direct-run --from-existing <seed>` (once step 6 wires the parser) drives all four stages without a disk round-trip, a stage's non-zero exit stops the chain and is returned as-is, and the new verb + flag-propagation + failure tests in `tests/cli/test_direct_cmd.py` pass.

## Why

The `create → detail → run --commit → reconcile-code` pipeline exists today only as three or four separate CLI runs an operator strings together by hand: run `create`, then `detail`, then `run --commit`, then drive `reconcile-code` step by step. Each re-reads the plan from disk, each re-passes the same `--backend`/`--model`/`--on-rate-limit` flags, and a wrong path or forgotten flag breaks the chain. `BACKLOG.md #118` asks for a single verb that expresses the common "turn this idea into working, committed, plan-reconciled code" intent. Step 4 landed the sibling `direct-jira` verb and proved the pattern — sink hand-off, size gate, handler reuse, namespace copy — in `plan_tool/cli/direct_cmd.py`. This step adds the second verb, `direct-run`, into the same file. It reuses the same seams (step 2's `_create_result_sink`, step 3's size-gate helper) and adds the one thing `direct-jira` did not need: because the run stage commits each green step, its clean-tree gate forces the verb to commit the authoring artifacts first. Step 6 registers both verbs with the parser.

## Input

This verb reads four contracts it does not own:

- **`plan_tool/create.py:CreateResult`** — delivered in-process through step 2's `_create_result_sink` list attribute on the create args namespace. The verb depends on `plan_path: Optional[Path]` (the created plan to chain into `detail`/`run`/`reconcile-code`), `split_proposal`, and `iteration_stage_failure`. `plan_path` is `None` **only** on the multi-plan split short-circuit (`split_proposal` set, no plan written); every normal create sets it. `iteration_stage_failure` is set when `create`'s convergence loop aborted — `cmd_create` returns `0` on that path, so read this field (not the rc) to detect an unconverged plan. Branch on `plan_path is None` and on `iteration_stage_failure is not None` before chaining forward.
- **Step 3's size-gate helper and its `SizeGateResult`** — the frozen result (pass/stop flag + measured `step_count` + `threshold` + human `reason`, threshold `MAX_CHAINABLE_STEPS`) landed in `plan_tool/cli/direct_cmd.py`. The verb calls the helper on the `CreateResult` and acts on the verdict; it does not re-measure the plan. Step 3 owns how the gate treats the `plan_path is None` split case.
- **The downstream handlers' args contracts** — the fields each handler reads **directly** (raising `AttributeError` if absent), so the built namespaces must carry them:
  - `plan_tool/cli/authoring.py:cmd_detail` reads `name`, `step`, `force`, `dry_run` directly (`detail_only`, `all`, `commit`, `jobs` via `getattr`).
  - `cmd_completeness_apply` (`plan_tool/cli/completeness_cmd.py`) reads `name`, `jobs`, `yes`, `anchor`, `id`, `rewalk`, `include_info`, `apply_structural`, `commit`. The verb sets `jobs = N` (N>1) and `yes = True`; it reuses detail's saved audit (no re-audit).
  - `plan_tool/cli/run_cmd.py:cmd_run` reads `name`, `mode`, `step`, `dry_run`, `yes`, `allow_missing_parent`, `no_walk`, `no_save`, `max_steps` directly (`reconcile`, `archive`, `all`, `commit`, `iterate`, `switch_branch` via `getattr`).
  - `plan_tool/cli/run_cmd.py:cmd_reconcile_code` (through `plan_tool/cli/reconcile.py:_cmd_run_reconcile`) reads `name`, `step`, `dry_run`, `yes`, `allow_missing_parent` directly (`no_walk`, `no_save`, `reuse`, `reuse_id` via `getattr`).
- **`cmd_run`'s `--commit` clean-tree gate** — in `plan_tool/cli/run_cmd.py:cmd_run`, an execution run with `--commit` and a dirty tree calls `_working_tree_dirty(ctx.repo_root)` and returns `2` with "`--commit requires a clean working tree`". The verb must satisfy this **before** invoking the run stage, because create and detail leave the tree dirty. This is the one constraint step 4 (`direct-jira`, no `run`) never hit. The verb satisfies it with `plan_tool/cli/gitcommit.py:commit_all`, which returns a `tuple[int, str]` (rc, tail) — unpack the rc rather than truthiness-testing the tuple. **Crucially, `commit_all` runs `git add -A`**, so it would sweep in any *pre-existing, unrelated* working-tree change the operator had at chain start. To keep that mid-chain commit scoped to only the create/detail artifacts, the verb enforces a **clean-tree precondition at chain start** (before `create`) — mirroring what standalone `cmd_detail` and `cmd_run --commit` do by rejecting a dirty tree up front.

**Verification limit:** step 6 owns the actual `direct-run` subparser and its flag defaults, so at HEAD there is no parser feeding this verb an args namespace. Tests construct the namespace by hand (see [Tests](#tests)); field-completeness of the real parser namespace is verified end-to-end in step 6.

## Implementation

**What the verb does, in order.** `cmd_direct_run(args)` runs the stages in one process and returns an `int` exit code:

0. **Clean-tree precondition.** Before `create`, resolve the repo root and check `plan_tool/cli/gitcommit.py:working_tree_dirty(repo_root)`. If the tree is already dirty, stop with rc 2 and a **`direct-run`-specific** message — e.g. "`direct-run` requires a clean working tree (it commits the plan it authors before running; commit or stash your changes first)." Do **not** reuse the standalone "`--commit requires a clean working tree`" wording: the operator invoked `direct-run` and never passed `--commit`, so naming that flag would obscure why a plain `direct-run` refused to start. This mirrors the *intent* of standalone `cmd_detail` / `cmd_run --commit` (reject a dirty tree up front) and is what makes the mid-chain `commit_all` (step 4 below) safe: because the tree started clean, `git add -A` can only capture the create/detail artifacts the chain itself authored, never the operator's unrelated edits.
1. **Create.** Set a fresh `list` on the create args namespace under step 2's `_create_result_sink` attribute, call `plan_tool/cli/authoring.py:cmd_create`, then read the deposited `CreateResult` back out. If `cmd_create` returns non-zero, return that rc immediately.
2. **Guard the hand-off.** If the create surfaced a multi-plan split (`result.split_proposal is not None` / `result.plan_path is None`), stop the chain — there is no single plan to detail, run, or reconcile. `cmd_create` already printed the split proposal and returned 0, so this is not a hard failure. Next, if `result.iteration_stage_failure is not None` (an unconverged create — `cmd_create` returned 0 but its convergence loop aborted), surface it and stop **unconditionally** (no continue-prompt) rather than chaining an unconverged plan into detail/run/reconcile; read the field, not the rc. Then run step 3's size-gate helper; if it flags the plan over-large, print the gate's `reason` (pointing the operator at running the stages standalone) and stop. Reuse the same stop code and message shape step 4 chose so the two verbs stay consistent.
3. **Detail.** Build a detail args namespace (see below) with `name` set to the created plan, `step = None` (detail all steps), and `detail_only = True`, and call `cmd_detail`. This audits completeness and **saves the conceptual gap map** (it does not apply conceptual gaps — #85). Return its rc if non-zero.
4. **Commit authoring.** Resolve the repo root via `plan_tool/cli/context.py:_load_context(args)` (`ctx.repo_root`). If `plan_tool/cli/gitcommit.py:working_tree_dirty(repo_root)` is true, commit the authoring artifacts with `plan_tool/cli/gitcommit.py:commit_all(repo_root, subject)` (subject naming the plan slug, e.g. `plan(<slug>): author plan for direct-run`). This is what lets both `completeness-apply`'s worktree isolation and the run stage's `--commit` gate pass. `commit_all` returns a `tuple[int, str]` (rc, tail), so unpack it (`rc, _ = commit_all(...)`) — do not truthiness-test the tuple. A non-zero rc stops the chain.
5. **Completeness-apply.** Build a completeness-apply namespace with `jobs = N` (N>1), `yes = True` (**never** bare `-y`, which silently skips the walk on non-interactive stdin), plus the direct-read fields `id`/`anchor`/`rewalk`/`include_info`/`apply_structural` (`cmd_completeness_apply` reads these directly and they are not base-parser flags — omitting them crashes the handler mid-chain, uncatchable by the stubbed tests). This reuses detail's newest **saved** audit (no re-audit) and applies the conceptual gaps in a single replay pass in isolated worktrees off the clean HEAD from step 4. Return its rc if non-zero. Then commit the applied gaps — but **only if the tree is now dirty** (`working_tree_dirty`): a no-op apply (no conceptual gaps found) leaves nothing staged, and an unconditional `commit_all` would fail on the empty commit and wrongly halt the chain. The run stage's own clean-tree gate is satisfied either way (clean already, or clean after this commit).
6. **Run.** Build a run args namespace with `mode = "run"`, `all = True`, `commit = True`, `step = None`, `dry_run = False`, `reconcile = False`, and **reset `iterate = False`** (do not inherit create's `iterate = True`, or `cmd_run`'s non-reconcile path emits a spurious "`--iterate only applies to … --reconcile`" warning). Call `cmd_run`. This sweeps every runnable step, committing each green step. Return its rc if non-zero.
7. **Reconcile-code loop (code steps only).** Re-parse the plan with `plan_tool/parser.py:parse_plan(result.plan_path)`, then for each `step` in `plan.steps` **whose `change_type` is a code type** (skip non-code steps — docs/test steps like this plan's own steps 1 and 7 have no code to reconcile, and running a full Claude reconcile pass on them is wasted work and confusing output), build a reconcile args namespace with `step = step.id` and `dry_run = False` and call `cmd_reconcile_code`. Return the first non-zero rc, **naming the failed step id**, and stop; if all code steps complete, return 0. Match the change-type predicate to how the codebase classifies a code step (`schema.ChangeType` / the `non-code` value), not an ad-hoc string check.

**Reuse handlers, not orchestrators — same choice as step 4.** Call `cmd_create` / `cmd_detail` / `cmd_run` / `cmd_reconcile_code`, not `create_plan` / `generate_detail` / the run engine / `_cmd_run_reconcile` directly. The handlers own flag parsing, the run-log lifecycle, the gates, and the exit-code convention; calling them keeps every chained stage behaving exactly as its standalone verb. The rejected alternative — a shared orchestrator-level chain — is called out in the plan's `## Architecture` **Trade-offs.** paragraph and framed out-of-scope under `## Out of scope` ("New orchestrator logic").

**Build each stage's namespace by copying, then overriding.** Follow the idiom already in `plan_tool/cli/authoring.py` (the completeness tail does `argparse.Namespace(**vars(args))` then sets the stage-specific fields), the same idiom step 4's `cmd_direct_jira` uses:
- Start from `argparse.Namespace(**vars(args))` so every cross-cutting flag (`backend`, `model`, `on_rate_limit`, `fallback_backend`, and the rate-limit policy flags) copies through unchanged. This is what makes flag propagation free. **Exception — `yes`:** `direct-run` is an unattended one-shot pipeline, so it **forces `yes=True`** on the `completeness-apply`, `run`, and `reconcile-code` stage namespaces (overriding whatever the operator passed) — the internal stages must not block mid-chain on `cmd_run`'s missing-detail confirm or reconcile-code's per-finding walk. This matches the `-y` help string and the documented reconcile-auto-apply known limit; the operator's review point is the post-run `/code-review`, not a mid-chain prompt. Do **not** copy `yes` through for these stages.
- Set the plan name. `cmd_detail`, `cmd_run`, and `cmd_reconcile_code` all resolve their target through `resolve_plan_for_context(ctx, args.name)`, so set `name` to the created plan's handle derived from `CreateResult.plan_path` (e.g. its stem). `cmd_create` has already registered the plan in the manifest, so the by-name lookup resolves — no re-derivation from the seed.
- Set the stage-specific direct-read attributes listed in [Input](#input), or the handler raises `AttributeError` deep inside itself. This hand-built namespace is the plan's stated "namespace drifts from the standalone parser" risk — keep it field-complete against what each handler touches directly.

**The clean-tree commit is the new, most important piece.** `direct-jira` never runs `--commit`, so it never hit a clean-tree gate. `direct-run` does. Constraints to respect:
- **Require a clean tree at chain start.** Enforce the step-0 precondition above (`working_tree_dirty` → stop with rc 2) *before* `create` runs. This is load-bearing for the next bullet: `commit_all`'s `git add -A` is only safe because the tree started clean, so it can capture nothing but the create/detail artifacts. Skipping this precondition would fold the operator's unrelated pre-existing changes into the authoring commit — the exact behavior the standalone stages reject.
- **Commit after detail, before run.** create writes the plan file + manifest and detail writes the detail bundle + plan frontmatter, all uncommitted. `cmd_run` with `--commit` refuses a dirty tree (`_working_tree_dirty` → rc 2). Committing the authoring artifacts first is what makes `--commit` reach the steps.
- **Gate the commit on `working_tree_dirty`.** `commit_all` runs `git add -A` then `git commit`; a commit with nothing staged fails. Only commit when the tree is actually dirty (i.e. create/detail did write something).
- **`--all --commit` commits each green step.** This is the mandated multi-step-run behavior (keeps the tree clean between steps so the test-authoring gate's per-step delta stays correct). Let `cmd_run`'s `--all` sweep own the per-step commits; the verb does not commit steps itself.

**Reconcile-code is driven step by step — it has no `--all` and no `--iterate`.** `cmd_reconcile_code` reconciles one step (or the next runnable) per call and lands code edits inline; it exposes no sweep flag. So the verb loops over the plan's **code** steps and calls it once per step id (non-code steps are skipped — see step 6 of the chain above). Keep the loop simple:
- **One pass per code step.** Call `cmd_reconcile_code` once per **code** step in plan order (non-code steps are skipped, per the loop above). Do not attempt to re-run a step until its audit reports no remaining drift — `cmd_reconcile_code` returns `0` even when it finds and lands drift (findings never flip the exit code), so the return value carries no "drift remaining" signal the loop could read. Per-step convergence re-runs are deferred (see [Deferred](#deferred)).
- **Stop on failure-to-complete, naming the step.** A non-zero rc from any reconcile step means that step failed to complete; stop the loop and return it, printing which step id failed.
- **Reconcile edits stay uncommitted — partial-state end condition.** `cmd_reconcile_code` has no `--commit` flag; its inline edits land in the working tree for the operator to review, matching standalone behavior. The verb does not commit them. Consequence: a mid-loop failure at code step *k* leaves steps `1..k-1` reconciled (uncommitted) and `k..N` not, with no recorded completion marker. That is acceptable and matches standalone `reconcile-code --step N`: the operator resumes by re-running from the named failed step. A durable per-step reconcile-completion marker is out of scope (ties to BACKLOG #135); the plan's `## Risks` names this partial-reconcile end state explicitly.

**Invoke `detail` in `--detail-only` mode — set `detail_only = True` on the detail namespace.** Same as step 4's `cmd_direct_jira`: a passive copy of the create-flavored args would run `detail`'s costly per-step loop (create defaults `--iterate` ON). `--detail-only` (`cmd_detail`, `authoring.py:~1143`) pins the completeness tail's `--iterate` ON while keeping the per-step detail-quality loop off. That buys **deterministic well-formedness convergence + a saved conceptual gap map** — *not* conceptual application (the #85 split leaves `plan-correctness`/`plan-completeness` unapplied). Step 5's `completeness-apply` consumes that saved map. So set `detail_only = True`, don't also set `iterate`, and assert `detail_only is True` in the tests. Note the run stage does **not** simply inherit its default here — the verb resets `iterate = False` on the run namespace (chain step 6) to avoid a spurious warning; the reconcile pass is one sweep per code step regardless.

**Exit codes follow the standard convention.** Non-zero means a stage failed to complete; return the first non-zero stage rc and stop. A clean full chain returns 0. The size-gate stop and the split short-circuit are deliberate halts on a plan that *was* created and is usable on disk — return the same code step 4 chose for these (recommend 0 with a clear message; the plan is written and re-runnable by hand). Pin whichever code you use with a test so the two direct verbs agree.

**Keep the leaf thin and the writer single-sourced.** `cmd_direct_run` composes handlers and holds no create/detail/run/reconcile stage logic. Its only original code is the chain wiring, the clean-tree commit, and the per-step reconcile loop. `cmd_create` remains the only writer of new plan frontmatter.

**Foundational logic and where else it lives.** The core behavior is *compose the four run-side handlers in one process, satisfying the run stage's clean-tree precondition between authoring and execution*. The sibling of this logic is step 4's `cmd_direct_jira` in the same file — same sink hand-off, same size gate, same namespace-copy idiom — so factor any namespace-building or sink-reading helper the two verbs share rather than duplicating it (a small private helper in `plan_tool/cli/direct_cmd.py` is fine; a cross-module refactor is not). The clean-tree gate itself lives in `plan_tool/cli/run_cmd.py:cmd_run`, which checks the tree through its own private `_working_tree_dirty` (a behaviorally-identical duplicate of `plan_tool/cli/gitcommit.py:working_tree_dirty`); this verb consumes the public `plan_tool/cli/gitcommit.py:working_tree_dirty` / `commit_all` helpers to satisfy that gate, it does not reimplement the gate.

## Acceptance criteria

- `plan_tool/cli/direct_cmd.py` defines `cmd_direct_run(args)` returning `int`.
- With all stage handlers stubbed to return 0, `cmd_direct_run` calls `cmd_create`, `cmd_detail`, `cmd_completeness_apply`, `cmd_run`, then `cmd_reconcile_code` (once per code step) in that order and returns 0.
- The completeness-apply namespace has `jobs > 1` and `yes is True`; `commit_all` is called before it (clean HEAD) and again after it (before `cmd_run`).
- The run namespace passed to `cmd_run` has `iterate is False` (reset, not inherited from create), so no spurious `--iterate` warning is emitted.
- The verb sets a `list` on the create args' `_create_result_sink` before calling `cmd_create` and reads the `CreateResult` back from it after.
- The verb rejects a dirty working tree at chain start (rc 2) before calling `cmd_create` with a message naming `direct-run` (not `--commit`), so its mid-chain `commit_all` only ever captures create/detail artifacts.
- When the working tree is dirty after detail, the verb calls `commit_all` before `cmd_run`; when the tree is clean, it does not.
- The detail namespace passed to `cmd_detail` carries `detail_only is True` (completeness tail converges, per-step loop skipped), regardless of the input args' `iterate` value.
- `cmd_reconcile_code` is called only for the plan's **code** steps (non-code steps skipped by `change_type`), and a non-zero reconcile rc stops the loop and names the failed step id.
- A `CreateResult` with `iteration_stage_failure` set stops the chain before `detail` even though `cmd_create` returned 0.
- The run namespace passed to `cmd_run` has `mode == "run"`, `all is True`, and `commit is True`.
- `cmd_reconcile_code` is called once per **code** step (non-code steps skipped by `change_type`), each with its `step` set to that step's id, in plan order.
- A non-zero rc from any stage is returned unchanged and stops the chain before the next stage runs.
- A `CreateResult` with `plan_path is None` (split short-circuit) stops the chain without proceeding to detail.
- An over-large create result flagged by step 3's size-gate helper stops the chain before detail with the gate's reason printed.
