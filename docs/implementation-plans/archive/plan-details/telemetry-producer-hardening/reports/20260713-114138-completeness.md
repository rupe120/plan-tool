- HIGH `[invocation-failed]`: Step 3 (`Record unusable apply backend responses`) classifies a zero-exit response with `ClaudeRunStats.is_error` as `INVOCATION-FAILED → still-open` while requiring that `apply_finding` continue processing that same response unchanged. Because existing `apply_finding` can parse `APPLIED`, retain backend edits, and return success on this path, the telemetry can report still-open for work the host accepted as acted on; the body’s “unusable backend response” premise contradicts its preserved host behavior.
- MEDIUM `[canonical-parallel-telemetry]`: The Architecture and acceptance criteria promise that parallel apply “records every durable per-finding result exactly once,” while the Overview requires telemetry to remain best-effort and step 4 (`Record parallel apply results once from the canonical replay`) explicitly allows recorder failure without affecting the command. A failed append necessarily produces zero rows, and the design adds neither acknowledgement nor retry/deduplication, so it can guarantee only one recording attempt and at-most-once persistence.
- MEDIUM `[code-fingerprint-digest]`: Step 1 (`Replace oversized code fingerprint maps with a stable digest`) defines `""` for both an absent/unavailable code fingerprint and an empty map, although `plan_tool/fingerprint.py:compute_code_fingerprint` can legitimately return an empty computed code state when no watched files exist. This collapses “computed empty” and “not computed,” making equality joins ambiguous despite the step’s identity-preservation goal; `DATA_CONTRACT.md:Fingerprints` already recognizes this distinction for saved fingerprints through `code_fingerprint_present`.
- MEDIUM `[parallel-invocation-exception]`: Step 4 (`Record parallel apply results once from the canonical replay`) requires that “a raised invocation still needs the resolved step captured,” but step 3 requires `apply_finding` to re-raise the original exception, and `plan_tool/cli/completeness_apply_parallel.py:dispatch_parallel` currently converts arbitrary worker exceptions into metadata-free failures. The proposed deferred result seam never specifies how classification and resolved-step metadata survive that re-raise, so canonical replay cannot emit the promised failure event.
