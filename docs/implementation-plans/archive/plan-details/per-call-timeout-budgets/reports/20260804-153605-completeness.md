A rate-limit wait or transient backoff can therefore start a retry after the pass allowance, violating Step 3’s “never starts a backend call after its wall-clock allowance is exhausted” criterion.
  - Fix: Define a purity-scope deadline that clamps or stops retry attempts and recovery waits at expiration without changing recovery policy for other callers.
- HIGH `[purity-budget-cache-reuse]`: Step 3 (`Cap the full purity scan and report skipped steps`) conflicts with Architecture’s “Preserve completed or non-code step skipping, cache reuse” and “Only uncovered readable steps become blocking coverage findings”: its `Deferred` says “cache-only admission after a pass budget expires — keep the existing cache boundary unchanged here.” `plan_tool/detail.py:_cached_purity_findings` can return a valid exact-cache verdict without Claude, so the exhausted path would falsely report that covered step as a blocking skip or risk starting a backend call to discover the hit.
  - Fix: Allow valid cached purity verdicts to be reused after the ceiling and emit skipped coverage only for readable cache misses that still require a backend call.
- HIGH `[purity-budget-admission]`: Step 3 (`Cap the full purity scan and report skipped steps`) checks the deadline before calling `plan_tool/detail.py:_cached_purity_findings`, which can read and prepare cache data before `collect_detail_quality_findings` launches `shell_detail_invoker`. Time can expire during that work and still start a call under a stale timeout, breaking the criterion that no call starts after the allowance.
  - Fix: Define a backend-call admission boundary that refreshes remaining time immediately before launch and reports a refused call as skipped coverage.
- HIGH `[conceptual-timeout-iterate]`: `completeness-audit --iterate` calls `audit_plan_until_stable` from `plan_tool/cli/completeness_cmd.py:_run_iterate_convergence_loop`, but step 2 (`Give purity scans and conceptual audits separate timeout settings`) explicitly leaves that path outside its conceptual scope. Those conceptual backend calls therefore ignore `PLAN_TOOL_CONCEPTUAL_AUDIT_CLAUDE_TIMEOUT`.
  - Fix: Make the iterate-mode conceptual audit use the same conceptual timeout resolution and dynamic scope as `_sample_conceptual_audit`.
- MEDIUM `[purity-truncated-verdict]`: Step 3 (`Cap the full purity scan and report skipped steps`) Acceptance criteria says “A timeout, empty reply, or truncated reply from a call that started remains a `purity-scan-failed` finding,” but its Implementation says “A truncated reply that still lifted a medium split already has a verdict, so do not also claim coverage failed.” HEAD `plan_tool/cli/completeness_phases.py:_collect_purity_split_findings` follows the latter, so the acceptance criterion overstates the intended behavior.
  - Fix: Limit failed-scan coverage for truncated replies to replies that did not yield a usable MIXED-STEP verdict.
