# Step 1 — Add the code-grounded split detector to the reconcile lane

## Summary

Add a new deterministic producer to `plan_tool/review.py` that emits one advisory `granularity-split` recommendation for a single non-`DONE` step whose `heuristic_already_done` hits reveal it fuses a built part and an un-built part — the code-grounded **inverse** of the existing re-ground merge producer `_reground_already_built_recommendation`. The producer plugs into the reconcile-lane-only block in `extract_recommendations` (section 2a, behind the `reconcile_lane and step_filter is None` guard) and reads only the existing `HeuristicHit` list plus each step's declared `files`. It is advisory `info` only: it never mutates, never auto-dispatches to the split bridge, and never flips an exit code — it reuses the `granularity-split` literal, the `Recommendation` shape, and the split-branch `triage_reason` already in place. On green, `reconcile` (via `review_plan_full`) surfaces the finding in the markdown report, the returned recs, and the saved JSON sidecar while every non-reconcile surface stays silent. It does **not** appear in the default interactive walk: `plan_tool/review_walk.py:walk_recommendations`'s `skip_info` carve keeps only pairwise `granularity-merge` info recs visible, so this per-step `info` `granularity-split` finding is walked only under `--include-info` (the shipped info-visibility contract).

## Why

`reconcile` audits a plan against current code and already has a code-grounded **merge** producer — `plan_tool/review.py:_reground_already_built_recommendation` — that fires when ≥2 distinct steps look already-built and recommends re-baselining the set. Its inverse has no producer: a **single** step whose code reveals it spans two separable concerns (part built across multiple files, part not) should be split, but nothing detects that from code today. The only split producers are the static detectors in `plan_tool/granularity.py` (which read plan structure and titles, never code) and the completeness MIXED-STEP path into `escalate_to_split`. This step lands the code-grounded split producer that mirrors the re-ground sibling, so reconcile can finally say "this one step should split along the built/un-built seam."

## Input

The producer reads two existing contracts; it introduces no new persisted schema.

- **The `HeuristicHit` list** — produced by `plan_tool/review.py:heuristic_already_done` and passed into `extract_recommendations` as `heuristic_hits`. Each `HeuristicHit` (frozen dataclass at `plan_tool/review.py`, fields `step_id`, `file`, `symbol`, `pattern`) records one already-built match. **Key fact:** `heuristic_already_done` iterates `step.files` and stores the exact declared string in `HeuristicHit.file` (`file=f` in its scan loop), so a hit's `file` is string-equal to the entry in `Step.files` it came from. The trigger relies on that: matching hit files against declared files is a plain set comparison, no path normalization.
- **`Step.files`** (`plan_tool/schema.py`) — the declared set of existing files the heuristic actually scans. Use `step.files` (not `step.all_files`, which folds in `creates` the heuristic never scans) so the un-built check compares against exactly the set the heuristic reads. **Caveat — "no hit" is a proxy for un-built, not proof (three over-count classes):** `heuristic_already_done` emits **no** hit for a declared file that doesn't exist on disk (its `path.is_file()` guard) **or** whose extension isn't scannable (only `_CODE_EXTS`/`_PROSE_EXTS`/`_CONFIG_EXTS` are opened — e.g. `.yaml`, `.txt` are skipped), so "a declared file with no hit" conflates three cases: not-scanned (unscannable extension), not-yet-created, and — the **highest-frequency** — scanned-but-no-symbol-match (a declared `test_*.py` whose contents lack the derived title symbol). A qualifying step that merely declares one such file alongside ≥2 built files will trip the un-built trigger even if nothing is genuinely un-built. This is **accepted as precision-over-recall**: the finding is advisory `info` (recommend-only, never mutating), so that false-positive class is tolerated rather than narrowed — do **not** add existence/extension filtering to the un-built check here (that would be new code-scanning; see Deferred).
- **Symmetric recall blind spot — `step.creates` is invisible.** The mirror of the over-count above: because the un-built check reads only `step.files`, a step whose un-built work lives entirely in `step.creates` (new files not yet on disk) — with every existing `files` entry already hit — **never triggers**, even though "existing files done, new files pending" is the cleanest built/un-built seam the detector targets. This is an accepted recall limitation, not a bug to fix here: keying on `step.files` keeps the comparison a plain string set-diff against exactly what `heuristic_already_done` scans, and reaching into `creates` (never scanned) would be the new code-scanning this step excludes. Named so the accepted-limitation list covers both the over-count and under-count sides of the `files`-vs-`creates` choice.
- **Reconcile lane flag** — `review_plan_full` (`plan_tool/review.py`) calls `extract_recommendations(..., reconcile_lane=True)`; the shared completeness/run-gate fan-out `collect_deterministic_findings` calls it with `heuristic_hits=[]` and `reconcile_lane=False`. Both guards keep the producer off non-reconcile surfaces.

## Implementation

**Add one producer that reads the hit set per step and fires on the built/un-built co-occurrence.**

- **New function.** Add `_code_reveals_split_recommendations(heuristic_hits, plan, *, plan_name) -> list[Recommendation]` to `plan_tool/review.py`, near `_reground_already_built_recommendation`. Returning a list (one recommendation per qualifying step) keeps the emit block a single call. One way: group hits by `step_id` inside the function, iterate `plan.steps`, and append per qualifying step. An Optional-per-step builder called in a loop is a fine alternative — pick whichever reads cleaner; the emit block owns only the reconcile-lane gate.
- **Trigger (conservative, decidable, per step).** For each non-`DONE` step, fire one finding only when **all three** hold:
  - the step's hits cover **≥2 distinct `file` values** — count with a set comprehension mirroring the re-ground builder's distinct-step count (`{hit.file for hit in step_hits}`), and
  - **≥1 entry in `step.files` has no hit** — a proxy for "an un-built portion remains" (see the §Input caveat), and
  - **at least one un-hit `step.files` entry is a *non-test* file** — path not under a `tests/` directory and basename not matching `test_*`/`*_test` (a trivial string check on the already-in-hand path; no scan). This clause kills the dominant false positive: a step whose only un-hit file is its own test (impl landed, tests pending) is one half-done concern, not two separable ones, and the tool's type-purity model keeps tests riding with their feature — splitting there is wrong. If the un-hit set is *all* tests, do not fire.
  That narrowed co-occurrence is the signal the step fuses ≥2 concerns and should split along the built/un-built seam. Precision over recall: one finding per qualifying step, or none.
- **DONE steps are already excluded structurally.** `heuristic_already_done` emits no hits for a `DONE` step, so a done step always fails the "≥2 distinct hit files" condition and never yields a finding — the same structural guarantee the sibling `_reground_already_built_recommendation` relies on (it deliberately does **not** re-check status). An explicit `step.status`-vs-`StepStatus` done check is therefore redundant, not a load-bearing gate; leave it out and let the ≥2-hit condition absorb it (or add it only as belt-and-suspenders, never as the mechanism that excludes done steps).
- **Routing — reuse the `granularity-split` literal at `severity="info"`.** Emit `source="granularity-split"` as a **hard-coded string literal, not imported**: `plan_tool/review.py` must not import `plan_tool/granularity.py` (that would cycle — `granularity` imports `review`), exactly as the `STRUCTURAL_SOURCES` constant already duplicates the literal. Set `severity=_HEURISTIC_HIT_SEV` (the existing `"info"` constant re-ground also uses), `step_id=<the step's id>`, and remedy prose pointing at `plan-tool split`. Do **not** use the neutral `granularity-merge` literal — its directive grammar is merge/re-ground, the wrong family for a split.
- **Why `info` stays recommend-only.** `info` + `granularity-split` gives `is_structural(rec) == True`, so `triage_reason` routes it through the split branch (deferred, pointed at `plan-tool split`). But `plan_tool/review_walk.py:split_escalation_target` gates auto-dispatch on `rec.severity == "medium"` **and** the source being in `extra_apply_sources`, so an `info` finding is never dispatched to `escalate_to_split` — the same way today's deterministic `info` split hints stay advisory.
- **Rec id and prose.** Mint the id with `_make_rec_id(step.id, "granularity-split", fingerprint)`, using a **step-keyed** fingerprint `code-reveals-split:<step_id>` — **not** the hit-file set. The concept identity is the *step*, so keying on the volatile built-file set would re-hash the same "split step N" concept to a new id whenever a hit lands or another file gets built between passes, dropping a prior `skip` annotation (re-nag) and showing the convergence diagnostic churn instead of a stable recurrence. Mirror `_reground_already_built_recommendation`, which keys only on its step-id set. (Per-step id ⇒ stable across passes; two *different* qualifying steps still get distinct ids via their distinct `step_id`.) Carry the finding's own `title`/`body`/`suggested_action`: name the built files, the un-built remainder, and a **runnable** `plan-tool split {plan_name} --step {step.id}` scaffold. Render the plan-name + `--step <id>` prefix (both are in hand — `plan_name` is a kwarg, `step.id` is the qualifying step); the two `--into "…" --into "…"` half-titles genuinely can't be auto-derived, so append them as `--into "…" --into "…"` placeholders for the operator to fill. This matches the sibling code-grounded producers, which each emit a runnable invocation (`_reground_already_built_recommendation` carries `plan-tool create {plan_name} --from-existing <seed>`; the convergence `FORK_SCOPE_OUT` arm prints `plan-tool scope-out <name> --step N`) rather than a bare verb. The `triage_reason` structural branch names only the generic `plan-tool split` remedy (review.py:4386–4390), not the specific files or the `--step`, so the finding's own prose must carry those specifics. The body must also carry three caveats the coarse signal demands (mirroring re-ground's "confirm the steps really are built" hedge):
  - **Confirm two *separable* concerns, not one half-done concern** — the built/un-built seam is a proxy, not proof; tell the operator to verify the step genuinely fuses two concerns before splitting.
  - **Mark the built half `done` after splitting** — `plan-tool split` (`create.py:_apply_step_split`, invariant 6) leaves the first half at the target's status and later halves `PENDING`, so no half is marked `DONE`; since the detector's premise is that part is *already built*, the prose must tell the operator to mark the built half `done` after the split, or `run` re-implements built code. (Auto-marking is out of scope — the split verb can't; naming it in the prose is the in-scope fix for this detection↔remedy mismatch.)
  - **Apply highest-id-first when several steps qualify** — each rendered `--step <id>` is against the current numbering and `plan-tool split` renumbers to contiguous `1..N`, so splitting a lower-id step first invalidates later `--step <id>`s; note to apply highest-id-first (or re-run reconcile between splits).
- **Wiring — the reconcile-lane emit.** In `plan_tool/review.py:extract_recommendations`, inside the existing `if reconcile_lane and step_filter is None:` block (section 2a, where `_reground_already_built_recommendation` and the pairwise-merge loop already live), call the new producer and extend `recs` with its results. Placing the call in this block gives the finding the same double gate as re-ground: `collect_deterministic_findings` leaves `reconcile_lane=False` (block never runs) and passes `heuristic_hits=[]` (no signal), while `review_plan_full` passes `reconcile_lane=True`.
- **Make split and re-ground mutually exclusive — filter re-ground's input, not the builder.** Without this the two contradict: re-ground fires on ≥2 distinct step_ids-with-any-hit and its remedy is the **mutating** "mark the already-built steps `done`" (under `--reground`, `reground_bridge` marks them done). A split-qualifying step (≥2 hit files, ≥1 un-hit file) is only **partially** built, so it must never be offered for "mark done" — and a prose-only caveat can't reach the operator (re-ground is emitted first, is visible/mutating; the split advisory is `info`, hidden without `--include-info`). **Resolution:** in the emit block, compute the split-qualifying step-id set **first**, then call `_reground_already_built_recommendation` with the hit list **filtered to drop those steps' hits** — e.g. `reground = _reground_already_built_recommendation([h for h in heuristic_hits if h.step_id not in split_step_ids], plan_name=plan_name)`. A partially-built multi-file step is then a *split* candidate only, never a re-ground candidate; the two become clean inverses (fully/simply-built → re-ground; partially-built-across-≥2-files → split). This keeps `_reground_already_built_recommendation`'s **body untouched** (only its call-site input is filtered, so its own unit tests are unaffected) and honors "do not touch the re-ground builder." If the exclusion drops re-ground below 2 steps it correctly returns `None`. A gating test (below) pins that a co-qualifying step is in the split finding and **absent** from the re-ground set.
- **Apply the same exclusion to the static pairwise `granularity-merge` findings (section 2b).** The reconcile-lane block also appends static pairwise `granularity-merge` findings (`review.py:3419`), and "merge step A with its neighbor" (A too small) contradicts "split step A" (A too big) — worse, the pairwise merge is the *visible* one (kept past `skip_info`) while the split is hidden. Before appending a pairwise-merge finding, drop it if its flagged pair includes a split-qualifying step, so a split-qualifying step never also carries a merge advisory. This is a call-site filter in the same block; it touches neither the static advisor nor `granularity.py`. A test pins it.

**Constraints and gotchas that are not free to vary:**

- **Do not import `granularity`.** The `granularity-split` string must be a literal; a real import re-introduces the forbidden cycle. Match how `STRUCTURAL_SOURCES` and `_GRANULARITY_MERGE_SOURCE` already duplicate their literals with a pinning test.
- **Do not add the source to `APPLY_ELIGIBLE_SOURCES` or change `STRUCTURAL_SOURCES`.** `granularity-split` is already in `STRUCTURAL_SOURCES` and already disjoint from `APPLY_ELIGIBLE_SOURCES` (pinned by `test_structural_sources_disjoint_from_apply_eligible`). This step touches neither set.
- **Match `step.files`, not `step.all_files`.** The un-built check compares against exactly the set `heuristic_already_done` scans, so the comparison is a plain string set difference and a `creates` path (never scanned) doesn't force a false "un-built file remains."
- **Keep it reconcile-lane-only.** The finding must not appear on completeness, review, or run-gate surfaces — respect the `reconcile_lane and step_filter is None` guard and the empty-`heuristic_hits` path.

**Foundational logic and shared locations.** The core rule this step adds is: *distinct-file hit count ≥2 AND an un-hit declared file → advisory split finding, reconcile lane only.* The nearest sibling exercising the same "read the cross-step hit set, not one hit" pattern is `_reground_already_built_recommendation` (the inverse, ≥2 distinct **steps** → merge/re-ground). Mirror its distinct-count comprehension and its advisory/non-apply-eligible routing, but keep the two producers separate — they answer inverse questions (merge vs split) and correctly differ in source token and altitude (plan-wide vs per-step). The static split detectors in `plan_tool/granularity.py:assess_granularity` share the `granularity-split` source but read plan structure only; they stay untouched, and consolidating the two split producers would need a refactor step this detail cannot mint — left for reconcile if it ever surfaces (see Deferred).

## Acceptance criteria

- `reconcile` (via `plan_tool/review.py:review_plan_full`) surfaces an advisory `granularity-split` finding for a single non-`DONE` step whose `heuristic_already_done` hits cover ≥2 distinct files while ≥1 declared `step.files` entry has no hit — with `severity == "info"`, `step_id` set, and a runnable `plan-tool split <plan_name> --step <step_id>` scaffold in the suggested action (not a bare verb). "Surfaces" is the markdown report, the returned recs, and the saved JSON — **not** the default interactive walk, whose `skip_info` carve (`review_walk.py:walk_recommendations`) hides this per-step `info` finding unless `--include-info` is passed.
- Split and re-ground are **mutually exclusive**: a split-qualifying step is excluded from re-ground's input at the emit site, so it appears in the split finding and never in a re-ground set (a partially-built step is never offered for "mark done"). `_reground_already_built_recommendation`'s body is unchanged (only its call-site input is filtered), and its own unit tests stay green; if the exclusion drops re-ground below 2 steps, re-ground correctly emits nothing.
- The finding is absent from `collect_deterministic_findings`, from `extract_recommendations` when `reconcile_lane` is `False`, and when `step_filter` is not `None`.
- The finding has `is_structural(rec) == True` and routes through the split branch of `triage_reason`, but `split_escalation_target` returns `False` for it (info, not medium), so it is never auto-dispatched to `escalate_to_split`.
- `granularity-split` is still **not** in `APPLY_ELIGIBLE_SOURCES` (`test_structural_sources_disjoint_from_apply_eligible` stays green), and `plan_tool/review.py` still does not import `plan_tool/granularity.py`.
- The re-ground producer, the static granularity detectors, and every existing structural-routing test remain unchanged and green.
- All new tests listed above pass.
