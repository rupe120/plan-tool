Current seed semantics exclude `IMPLEMENTED` and include only `remaining_work` for `PARTIAL`, so low-grounding overclaims can still drop work from the backlog even if the report banner warns.
- MEDIUM `[batch-output-collisions]`: step 7 (`Add batch form`) adds shared `--seed-dir` and `--report-dir` outputs, but the plan does not cover two matched plans with the same stem from different directories writing the same derived report or seed filename. That creates the same false-success/overwrite class the archive-collision work is meant to remove.
- MEDIUM `[last-annotated-date]`: step 8 (`Add list --status rollup`) requires `last annotated date` from cached `*.annotated.md`, but annotate reports currently expose `grounded_files` only and the plan does not define whether the date comes from report metadata, filesystem mtime, or archive state. Without a stable source, the rollup cannot produce a reproducible date.
- MEDIUM `[batch-partial-failure-exit]`: step 7 (`Add batch form`) says the loop `"continues past per-file failures"` and prints a final summary, but the plan never defines the aggregate exit status when one or more files fail after the rest are processed. An unattended backlog drain needs a script-visible signal for partial failure instead of relying only on console text.
- MEDIUM `[step7-test-strategy]`: step 7 (`Add batch form`) is a new CLI behavior, but `Testing` says `"step 7 (refactor) — characterization tests pinned before the change; pass unchanged after"`. Batch `annotate <dir-or-glob> --seed-dir/--report-dir` needs new behavior tests for expansion, per-file failure continuation, summaries, and output paths.
- MEDIUM `[jira-lint-mode]`: step 9 (`Extend jira AC lint ... + add jira --lint flag`) and the acceptance criterion say `jira --lint` flags bad bullets, but the plan does not define what `--lint` reads or how it exits. The existing `lint_acceptance_criteria()` is a soft warning during export, so a dedicated lint mode needs a clear target such as generated stories for a plan or an existing `jira-stories.{md,json}` file.
- MEDIUM `[step5-bundle-collision]`: step 5 (`Make archive-target collisions loud or disambiguated`) handles `<stem>.replaced.N.md`, but `create.archive_existing_source` also archives `plan-details/<slug>/`, which can collide independently. The markdown file could move while the detail bundle fails, leaving a partial archive.
- MEDIUM `[step5-shared-archive-blast-radius]`: step 5 (`Make archive-target collisions loud or disambiguated`) changes `create.archive_existing_source`, which is shared by annotate and create archive paths, but the plan frames the behavior as annotate-only. That leaves `create --from-existing --archive` collision behavior unspecified.
- MEDIUM `[batch-archive-target]`: step 7 (`Add batch form`) defines `--seed-dir` and `--report-dir`, but not where originals go under `--archive` in batch mode. The P4 sweep layout promises `report+original→archive/`, yet batch archive destination remains unspecified.
- MEDIUM `[glob-empty-match]`: step 7 (`Add batch form`) covers sorting glob results but not the zero-match case for `annotate <dir-or-glob>`. A headless sweep could silently succeed without processing anything.
- MEDIUM `[list-status-column-collision]`: step 8 (`Add list --status rollup`) adds implementation-status counts to `list`, but `cli.inspect.cmd_list` already has a `STATUS` column for plan lifecycle status. Two status meanings in one table will be hard to scan.
