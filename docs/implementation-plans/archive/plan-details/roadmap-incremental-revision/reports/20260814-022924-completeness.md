Those choices give omitted fields different results, so the context, strict parser, and deterministic merger can all follow the plan yet disagree.
  - Fix: define the replacement payload, omitted-field behavior, and explicit empty-value validation once for context, parsing, merging, and tests
- HIGH `[writer-guard-baseline-order]`: Step 3, Architecture, the `Concurrency-blocking` risk, Testing, and the writer-guard acceptance criterion promise that a participating contender cannot read or write a mutable baseline, but Architecture only places the guard “Before backend work.” `roadmap.run_roadmap`, `accept_roadmap_seed`, `apply_roadmap_seeds`, `materialize_plan_seed`, and `refresh_roadmap_seeds` all establish reads before their writes; a writer that snapshots before acquiring the guard can overwrite a broad or seed update that lands in that gap.
  - Fix: require one per-roadmap cross-process guard before every participating owner’s first baseline read, retain it through success or failure, and pass its token through all nested writers with interleaving coverage
- HIGH `[writer-guard-participants]`: Step 3, Architecture’s “seed-mutating public commands,” the `Concurrency-blocking` risk, Testing, and the writer-guard acceptance criterion never name the complete participating-writer set. At HEAD, `roadmap.run_roadmap`, `apply_roadmap_seeds`, `accept_roadmap_seed`, `materialize_plan_seed`, and `refresh_roadmap_seeds` all mutate roadmap artifacts, seeds, or seed state; `refresh_roadmap_seeds` reaches `materialize_plan_seed` through `materialize_and_diff_one_plan`. One missed owner breaks the stated serialization guarantee.
  - Fix: name every participating public owner and its nested reuse path, and define which commands remain deliberately outside the guard
- MEDIUM `[revision-context-identities]`: Architecture’s backend-context sentence permits “immutable identifiers” to mean only target-row identifiers, while its response schema and the third acceptance criterion require a `respond-feedback` record carrying the selected feedback ID. Step 1 owns the record contract and step 4 owns context construction, but neither states that the backend receives both exact identities; without them the model must guess an identity that the merger rejects.
  - Fix: define the exact non-prose context fields, including the selected feedback ID, target-row ID, allowed field names and values, relation summary, and feedback state
