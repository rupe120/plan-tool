- HIGH `[region-focus-collision]`: ``: Step 6's id-primary split lets two distinct findings on the same step become two separate `RegionTrend` objects, but both still compute `focus`/`key` from `_normalized_focus(representative)` (`convergence_diagnosis.py`), which for any step-focused finding returns just `f"step{N}"` regardless of id or anchor — `finding.step_id`/`_step_token(anchor)` is all it reads. `_freeze_region` sets both `RegionTrend.focus` and `RegionTrend.key` this way, and `_spinning_trend_lines` prints `f"  • {region.focus}: recurs in {windowed} of {window} audits; severity {trend}"` as the *only* region-identifying text in the `spinning` render. So the exact scenario this plan's own Testing section requires ("two findings with different stable ids and dissimilar titles on the same step... → two regions, not one") prints as two bullets both labeled `step3` with no way for the operator to tell which recurring concern is which — the underlying data model stops conflating them, but the human-readable output the operator actually triages from still does. This directly undercuts the Problem statement's own complaint (regions "conflated" and unreadable) for the one surface a human reads. The same collision hits `RegionTrend.key`, currently unused by any production caller (only asserted in one test, `test_convergence_diagnosis.py:846`) but named as if unique per region, which will surprise whoever authors step 7's fixture assertions.
  - Fix: specify that step 6's region-building gives each region a distinguishing label component (its representative's anchor or id suffix) whenever more than one region in a series shares the same step focus, and that `_spinning_trend_lines`' printed bullet — plus `RegionTrend.key`/`focus`'s construction — carries that distinguishing text so two same-step regions never render identically; add this as an explicit testing/acceptance requirement, not just a region-count assertion.
- MEDIUM `[hand-resolution-read-failure]`: ``: Step 4 hooks the new prior-sidecar read into `cli/completeness_phases.py`'s `_persist_and_present_report`, whose sidecar-writing block is guarded only by `except OSError` (confirmed at HEAD — the whole fingerprint-capture/convergence-diagnosis/report-write block is one `try: ... except OSError as exc: warn(...)`). `review_persistence.load_review` raises `ReviewLoadError`, a plain `Exception` subclass, on a malformed sidecar — not caught by that guard — so an unparseable prior completeness sidecar would crash every subsequent `completeness-audit` invocation for the plan, not just skip the new telemetry. (The event-*write* half is separately safe: `telemetry.record_decision` already swallows every exception and never raises, per its own docstring and `except Exception: return False` — so only the prior-sidecar *read* is exposed, narrower than the general framing this gap has carried before.)
  - Fix: add an acceptance criterion that a `ReviewLoadError` (or any read failure) on the prior-sidecar load degrades hand-resolution inference to a no-op — skip recording, do not raise — so it can never break the completeness-audit save path that already tolerates a missing/unparseable sidecar elsewhere (`load_report_history` swallows the same exception the same way).
