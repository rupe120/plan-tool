Step 3's restore runner performs the identical peek-then-reconcile against the same checkpoint but explicitly excludes a dangling journal whose `kind == "revision-restore"`, stating the reason directly: "a dangling `"revision-restore"` journal from *this function's own* prior, interrupted attempt would otherwise also get folded in ... reconciling it would set every entry's `last_written_bytes` to `pre_run_bytes`". `PendingGeneration.kind` (`plan_tool/roadmap_source_identity.py:110-113`) is a plain string field, so the identical condition is checkable from `_run_roadmap`, but step 2 does not check it. If a `--restore-revision --confirm-restore-revision` call commits its generation and then crashes before its own `discard_checkpoint` runs, the checkpoint is left on disk with a dangling `"revision-restore"` journal. If the operator's next action is a fresh `run_roadmap` call instead of retrying restore, step 2's recovery-then-reconcile — lacking the `kind` exclusion — folds that journal's already-committed `pre_run_bytes` into `last_written_bytes` for every tracked entry, and `_run_roadmap` then continues treating the *old*, already-restored checkpoint as the baseline for this brand-new revision instead of discarding it and capturing a fresh one. A later restore of this new lineage, if it also fails, would then roll back much further than the new revision's own start.
  - Fix: Give step 2's checkpoint reconciliation the same `kind != "revision-restore"` exclusion step 3 already uses, so a continuing stage run never folds in its own already-completed restore attempt's journal and never adopts an old, already-restored checkpoint as if it belonged to a new revision.
