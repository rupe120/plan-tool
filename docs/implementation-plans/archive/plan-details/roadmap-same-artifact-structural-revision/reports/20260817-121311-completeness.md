- HIGH `[same-artifact-route-admission]`: Step 2 (`Add receipt-bound structural preflight and a bounded row and relation inventory`) admits a receipt using only selected-artifact facts, but a receipt carries only `handoff: requires-scope-review`; it does not prove a same-artifact route. `plan_tool.roadmap_impact_analysis:_classify_route` makes that decision from a current full relation closure, while Architecture, Input, and step 7 omit a current `same-artifact` impact-analysis check even though the Cross-artifact widening risk promises rejection. A cross-artifact request can therefore reach the backend and one-artifact publisher.
  - Fix: Require a named, current `same-artifact` impact analysis bound to the receipt, or an equivalent current closure check, before seed invalidation and reject every other route.
- HIGH `[marked-prose-boundary]`: Step 3’s `marked-prose replacement` and step 4’s whole-artifact-replacement ban leave no way to address prose: `plan_tool.roadmap_artifacts` models one opaque `body`, and `plan_tool.roadmap_gates:check_inventory_has_prose` requires every created row to be named there. Architecture, steps 3–4, Testing, and the criteria requiring new rules, entities, flows, and lifecycle maps never define marker syntax, marker availability in canonical artifacts, or how a new row gains its required prose without replacing the body.
  - Fix: Define canonical prose regions, their stable markers, their preflight rule, and the bounded replacement behavior that lets row creation update its required prose while preserving every other region.
- MEDIUM `[reorder-preservation]`: Step 3 permits reorder operations while Architecture and step 4 promise that unmentioned ordering remains unchanged, but neither states whether an operation supplies a full collection order, a named move with an anchor, or another rule. Moving one row changes other rows’ absolute positions, and Testing’s “incompatible ordering” case does not select a passing interpretation.
  - Fix: Define one reorder representation and the exact preservation rule for named and unmentioned rows, then make the operation and candidate criteria use it.
- HIGH `[unselected-feedback-target-removal]`: Step 4 (`Limit row and marked-prose replacements to named targets, record removals, and reject whole-artifact replacement`) can remove a row while Architecture, the unauthorized-mutation Risk, Testing, and acceptance criteria 7–9 require unselected feedback to remain unchanged. `plan_tool.roadmap_gates:check_feedback_integrity` intentionally resolves carried targets against predecessor rows and removal records, so an unselected row-targeted feedback record can survive while pointing at removed content.
  - Fix: Define and test a removal rule that rejects any candidate leaving unselected row-targeted feedback attached to a removed row
- HIGH `[selected-feedback-removal-authorization]`: Step 4 requires removal records but never binds their `feedback_ids` to the selected feedback, although Architecture and acceptance criterion 7 say the reply acts only on that selected row. `plan_tool.roadmap_gates:check_design_row_continuity` accepts any predecessor `open` feedback id as removal authority, so a candidate can remove a row for an unselected request without changing that feedback record.
  - Fix: Bind every new removal record to the selected feedback and reject unselected feedback ids as removal authority
- MEDIUM `[operation-conflict-precedence]`: Architecture rejects `duplicate operations`, but step 3’s schema and step 4’s merger do not define conflicts such as replacing then removing one row, moving one row twice, or creating then reordering it. Testing and acceptance criterion 8 name duplicate operations without defining whether these combinations reject, run in a fixed order, or let one win.
  - Fix: Define one operation-conflict and ordering rule for every operation pair, then align the schema, merger, tests, and acceptance language to it.
- MEDIUM `[relation-endpoint-boundary]`: Architecture promises relationship changes and explicit relation endpoints while limiting backend context to the selected artifact; Input reserves upstream artifacts for read-only gates, and step 2 calls its inventory a selected-artifact slice. `plan_tool.roadmap_relations:extract_declared_relations` includes valid selected rows that point upstream, including constraint anchors, component entity/constraint links, and plan component links, so step 3 leaves it unclear whether those immutable endpoints are allowed or refused.
  - Fix: Choose and state the endpoint policy for every cross-artifact relation kind without widening the one-artifact write set, then apply it to inventory, allowlists, gates, and tests.

## Conceptual completeness — reported, not auto-applied

Coverage gaps in the plan's own ideas are reported for visibility in this bare-plan audit. Apply actions for this axis are withheld until a complete detail bundle exists, so these findings are informational for now.

- HIGH `[unselected-feedback-target-removal]`: Step 4 can remove a row while keeping an unselected row-targeted feedback record unchanged. `plan_tool.roadmap_gates:check_feedback_integrity` accepts that carried feedback because it resolves targets against predecessor rows and removals, but `plan_tool.roadmap_escalation_selection:select_receipt_feedback` later requires a live target; the unselected request becomes unprocessable. Architecture’s selected-feedback-only rule, the preservation promise, the unauthorized-mutation risk, Testing, and the acceptance criteria cover changing another feedback row but not removing its target.
  - Fix: Define that a structural removal cannot remove a row targeted by any unselected carried feedback, and add a candidate acceptance criterion for that case.
- MEDIUM `[operation-json-integrity]`: Architecture requires a closed, versioned operation schema, but only receipt input explicitly rejects duplicate JSON members; step 3, Testing, and acceptance criterion 8 cover duplicate operations, not duplicate object members. `plan_tool.roadmap_revision:_decode_single_json_object` already rejects duplicate keys for local revision, while a default structural decoder could silently use the last value and accept an ambiguous operation.
  - Fix: Require structural operation decoding to reject duplicate JSON members and nonstandard JSON values before schema validation, with an acceptance test.
