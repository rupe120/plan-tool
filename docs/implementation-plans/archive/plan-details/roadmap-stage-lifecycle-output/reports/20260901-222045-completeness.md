A feedback-free stage therefore has no live start signal at all.
  - Fix: add a bounded feedback-free stage-start fact before re-gating and retain a separate result fact without opening a call handle, then align the one-line decision, tests, and criteria.
- MEDIUM `[nonretry-stage-failure]` [confidence: limited]: Testing says “Every non-retrying path reports a stage failure,” but the Architecture and acceptance lists stop at the two attempt loops. `roadmap.py:_run_roadmap` can instead produce `stage-invalid` after `publish_stage_artifact` raises `RoadmapSourceAdmissionError` or `RoadmapRevisionPublishError`, or after `admit_stage_artifact` rejects the just-written artifact; none is named in the lifecycle contract or test set.
  - Fix: define the bounded stage-failure behavior for every post-call `stage-invalid` route and cover it alongside the existing loop failures.
- HIGH `[interrupt-handle-cleanup]` [confidence: limited]: The “Every opened handle closes exactly once” guarantee spans Step 2’s reporter seam and step 3’s call wrapper, but `progress.py:_StderrStepHandle.__init__` starts its heartbeat before returning the handle and `complete`/`fail` release the notifier only after interruptible work. A `KeyboardInterrupt` can therefore escape before the wrapper owns or fully releases the handle, despite Architecture, Risks, and Testing requiring no escaped heartbeat.
  - Fix: define a reporter-owned interruption cleanup boundary that covers handle acquisition and finalization, and test interrupts at both points as well as during a live call.
- HIGH `[terminal-delivery-boundary]` [confidence: limited]: Architecture says an interrupt before terminal emission returns 130 while an interrupt after delivery preserves the normal result, but it never defines what happens when the interrupt lands inside terminal `emit`. `cmd_roadmap` catches interrupts for the whole dispatch, so reasonable implementations can either print a terminal line then return 130 or return normally without a terminal line.
  - Fix: define one interruption-safe terminal-delivery boundary that keeps the terminal line and exit result consistent, including an interrupt during emission.
- HIGH `[final-attempt-failure-kind]` [confidence: limited]: Architecture says “After each closed call” roadmap emits a retry line, while § Testing’s exhaustion case requires three attempts plus `stage-exhausted` and the acceptance criterion requires every retry-consuming failure kind be named at the attempt that produced it. `plan_tool.roadmap:_run_stage` and `_run_bounded_stage_feedback` retain the final `failure_kind`, but the plan never chooses whether the last failed attempt emits a non-retry failure fact or the terminal carries that kind; “retrying after gates” on the last attempt would be false.
  - Fix: define and test final-attempt reporting so retry wording appears only when another call will run and the exhausting failure kind remains live without adding vocabulary.
- MEDIUM `[call-heartbeat-boundary]` [confidence: limited]: Overview promises one call heartbeat per backend invocation and Acceptance requires one handle per actual backend invocation, but Architecture opens one handle around an `invoker` call. `roadmap.shell_roadmap_invoker` delegates to `shell.claude_invoke`, whose recovery loop can invoke `backend_runner.run_streaming_once` multiple times for transport retries or a backend switch, so the planned handle can span several actual backend calls.
  - Fix: Define whether a roadmap call heartbeat covers one content attempt or each shell recovery invocation, then align the lifecycle wording and tests to that boundary.
