### Correctness (run these first)

_Verified: file paths resolve, dependencies are coherent, and the plan's stated concepts are internally sound._

- MEDIUM `[branch-resolution-flag-off]`: Step 3 (`worktree-command-group`) and acceptance criterion #1 specify a bare `plan-tool worktree add <plan>` whose branch is "derived via branch-awareness," but CLAUDE.md states branch-awareness is **OFF by default**, and the Architecture says only "When branch-awareness is off … accept a `--branch` argument" — leaving the off-and-no-`--branch` case undefined. `derive_branch(slug, branch_prefixes(repo))` is in fact a pure helper that resolves to default prefixes regardless of the flag, so the bare invocation *can* always derive a name; the plan should commit to that rather than conditioning derivation on a flag that is normally off.
- MEDIUM `[worktree-add-current-branch]`: Step 3's "reuse existing rather than failing" idempotence claim collides with git's same-branch restriction in the most common case: when the plan's branch is already checked out in the **main** working tree (you are working on plan A and ask for A's worktree), `git worktree add` refuses, and that main tree is not a derived-path worktree the reuse logic can find — so the user gets a refuse, not a reuse. The plan covers "same-branch-twice between two worktrees" but not "branch held by the main tree."
- HIGH `[uncommitted-plan-registration]`: Step 3 (`worktree-command-group`) provisions the worktree by creating/checking out a branch from a committed ref (`default_branch` / the plan's branch), but a worktree's tracked `.plan-tool/plans.json` reflects only what is *committed on that branch*. A plan just created/registered on `main` with the manifest change uncommitted — or registered on a different branch — is absent from the new worktree's committed manifest, so `plan-tool <cmd> <plan>` inside it fails "plan not found" immediately after `worktree add <plan>` succeeded. The plan names this only as a documentation risk (`per-branch manifest visibility`), but Step 3's own happy path trips it.
- MEDIUM `[clone-branch-checkout]`: The `--clone` path in Step 3 (`worktree-command-group`) and acceptance criterion #7 ("`--clone` provisions a full clone") leave branch checkout unoperationalized: a fresh `git clone` checks out the origin's default branch, not plan P's branch, so the "checked out to the plan's branch" guarantee of acceptance #1 does not hold for clones without an explicit post-clone branch create/checkout step the plan never names.
- MEDIUM `[prune-archived-source]`: Step 4 (`worktree remove + prune`) says `worktree prune` "drops worktrees whose plan is archived/deregistered," but determining archived/deregistered status requires reading the manifest/plan state — and that state is per-branch and per-working-tree (`locator.py` scopes to the cwd's git tree). The plan never says *which* tree's manifest prune consults: a plan deregistered on `main` may still be registered on its own worktree branch, so "archived/deregistered" is ambiguous and prune could delete a still-live worktree or skip a dead one.
