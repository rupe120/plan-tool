### Correctness (run these first)

_Verified: file paths resolve, dependencies are coherent, and the plan's stated concepts are internally sound._

- MEDIUM `[narrowed-plan-current-pointer]`: The "Re-establish a run cursor" decision in **Architecture** promotes "the first PENDING after the last DONE" to CURRENT unconditionally, but the carved step is only *"typically CURRENT"* (the decision's own hedge) and `--step N` lets the operator carve any step. Two edge cases break the rule: (a) if the carved step was *not* the CURRENT one, a surviving CURRENT remains and promoting another yields two CURRENT steps; (b) if every survivor is DONE (no PENDING after the carve), there is nothing to promote and `run` has no cursor — but that is a complete plan, not an error. The promote must be conditional on *no surviving CURRENT* and *a PENDING survivor existing*.
- MEDIUM `[carved-step-upstream-deps]`: The **Architecture** "Dependency-graph integrity" decision says outbound prerequisites (the carved step `depends_on` surviving upstream steps) "must be captured in the seed as done-context," and AC1 repeats "done-context prose (incl. its upstream-dep context)." This conflates *upstream dependency* with *done work*: an upstream prerequisite that is still PENDING (possible since `--step N` carves any step, not only one whose deps are DONE) would be rendered as already-implemented — the same run-state overclaim the plan carefully forbids in its "carry = done-context PROSE, not a live-status round-trip" decision.
- MEDIUM `[narrow-renumber-reuse-feasibility]`: Step 2's narrow reuses `detail._migrate_downstream_details_after_merge` (per **Architecture** "The narrow is a NEW primitive…"), but that helper's boundary parameter has survivor-fold semantics a survivor-less drop must remap. It selects `downstream = steps with s.id > merged_new_id` and renames each to its already-renumbered `s.id`. In a merge the survivor *keeps* `merged_new_id`, so `>` correctly excludes it; in a drop there is no survivor, so the first surviving step's new id *equals* the carved id and would be wrongly excluded by `>`. The plan asserts "(fixes `narrow-renumber-reuse-feasibility`)" but never states the drop must pass the boundary one below the hole (`carved_id - 1`) so the first shifted survivor's file is migrated.
- MEDIUM `[convergence-flip-applies-gate]`: Step 5 (`flip the convergence scope-out fork-arm`) renders the runnable `plan-tool scope-out … --step N` keyed only on `classify_fork` resolving a single step, not on whether that carve would pass the safety gate (an inbound dependent makes it recommend-only). The suggested command will therefore sometimes refuse when run. This is tolerable because `scope_out` re-validates on entry, but the rendered prose should signal the command may recommend-only rather than imply it always actuates.
- MEDIUM `[safety-gate-precedes-seed]`: The "Seed-first atomicity contract" in **Architecture** frames the seed write as the first mutation, but the safety gate states "every other path (unattended, unsafe, non-TTY, declined, empty-plan) … mutates nothing." Step 3 (`seed-first sequencing + safety gate`) never states the gate (step-missing / empty-plan / inbound-dependent / downstream-orphan / TTY-confirm) is evaluated **before** the seed write; if it runs after, a refused carve leaves an orphan seed under `plan-seeds/`, contradicting "mutates nothing."
