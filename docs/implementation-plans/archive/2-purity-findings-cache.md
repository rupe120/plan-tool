# Purity Findings Cache

## Overview

Adds a per-step cache for the expensive MIXED-STEP purity/quality judgment so a step whose inputs are unchanged incurs no redundant Claude call on a subsequent `completeness-audit` run. The cache is a new persisted file under `.plan-tool/purity-cache/<slug>.json`, keyed by step id on a combined fingerprint — the detail-file content hash, a fingerprint of the step's declared `files:` at their current content, and the step's verdict-affecting frontmatter (`change_type`, `depends_on`). **The cache is a pure optimization: it only skips genuinely redundant work and never removes a capability.** The `completeness-audit` path (`_collect_purity_split_findings`) reads the cache and skips the Claude call on a hit; on a *genuine* miss — content actually changed above the #144 floor, or a cold/never-checked step — it still calls Claude and produces a real verdict, so `completeness-audit --purity` keeps delivering verdicts. `detail.py`'s two authoring-time call sites **write through** to the cache but always run their own Claude call: their convergence loop needs the full `collect_detail_quality_findings` result — including the semantic grounding review, which Reads/Greps files *outside* the step's declared set that the key cannot cover — so they must never skip it (decision 2). It also folds in BACKLOG #144's resolved magnitude threshold, applied in the audit path only: a below-0.5% Implementation/Tests section diff with no `files:`/`change_type:`/`depends_on:` change reuses the cached verdict without Claude, while an at/above-threshold (or cold) miss re-computes.

## Problem statement

The per-step MIXED-STEP purity judgment (`plan_tool/detail.py:collect_detail_quality_findings`, prompt at `plan_tool/prompts/detail-quality.md`) is expensive — BACKLOG #133 measured ~130-255s per step (~130-150KB prompts) — and is invoked from two independent call sites with no cache between them:

1. `plan_tool/detail.py`'s own post-authoring per-step convergence loop (the initial scan around `detail.py:3524` and the loop's re-scan around `detail.py:3982`) — the "detail's post-detail completeness sweep" BACKLOG #115 documents.
2. `plan_tool/cli/completeness_phases.py:_collect_purity_split_findings` (around line 498), called whenever `completeness-audit` runs with purity on (`run_purity=True`, gated by the shipped `--no-purity` flag) — a separate process, possibly run hours or days after `detail` last validated the same step.

A step whose detail content is byte-identical to what `detail` already validated still pays a full Claude call the next time a standalone `completeness-audit` runs on it — pure waste. Because `render_detail_quality_prompt` (`plan_tool/detail.py:932`) also folds in the current on-disk contents of the step's declared `files:` (`files_contents_block` via `_format_files_contents_block`), a naive cache keyed only on the detail file's hash is unsound: a step whose detail prose is byte-identical but whose declared files changed underneath it (a sibling step landed first, or a hand-edit) could legitimately purity-flag differently, and a detail-hash-only cache would silently serve a stale verdict.

## Architecture

**Combined cache key and its stored components (decision 1).** The key is the detail-file content hash, plus a fingerprint of the step's `all_files` (declared `files:` **and** `creates:`) at their current content, plus the step's verdict-affecting frontmatter — `change_type` and `depends_on` — plus a **verdict-logic version** (a `PURITY_VERDICT_LOGIC_VERSION` constant bumped whenever `plan_tool/prompts/detail-quality.md`'s MIXED-STEP criteria or `parse_mixed_step_findings` change). The verdict-logic version closes the prompt-invalidation gap: the key otherwise covers only the prompt's *inputs*, so editing the MIXED-STEP criteria would leave every input unchanged and serve verdicts computed under the old prompt indefinitely; folding a version the maintainer bumps on any verdict-logic change invalidates every entry at once. **The entry stores these components *separately*, not only as one opaque digest** (see decision 3): the combined digest is the hit test, but decision 6's below-floor grading must be able to tell *which* component moved (a source-file change vs. a trivial detail edit), which a single digest cannot. Grounding on `all_files` — not just `files:` — matters because `plan_tool/detail.py:_format_files_contents_block` shows the model `step.all_files`, so a changed `creates:` file under an unchanged detail body must also force a fresh check. `change_type` is load-bearing: the MIXED-STEP prompt directs the verdict by it (`render_detail_quality_prompt` folds in a `change_type` directive, and the prompt states "a `non-code` step is never mixed"), yet it lives in the plan frontmatter, not the detail file — so flipping a step `refactor`→`feature` (or to `non-code`) leaves the detail bytes and declared-files bytes unchanged and, without `change_type` in the key, would yield a stale cache **hit** on a now-wrong verdict. `depends_on` is included both because the prompt folds it in and because BACKLOG #144's frontmatter-change OR (decision 6) keys off it. Reuse `plan_tool/fingerprint.py`'s existing primitives rather than inventing new hashing: `compute_detail_bundle_fingerprint(plan, plan_path, repo_root)` already produces a `{step-detail-relpath: sha256}` map (the detail-file half); for the declared-files half, hash each of `step.all_files` the same way `compute_code_fingerprint` hashes `step.files`/`creates` (via `plan_tool/drift_detection.py:compute_content_hash`); fold the detail-file hash, the `all_files` fingerprint, the `change_type`/`depends_on` values, and the `PURITY_VERDICT_LOGIC_VERSION` into one combined key (a stable sorted-items digest is likely simplest) — while also returning/persisting those components individually so decision 6 can compare them one at a time. Lessons-file content, and the softer `title`/`complexity` context the prompt also folds in, are intentionally excluded from the key (decision 5) — an accepted low-impact staleness window, since including them would over-invalidate on cosmetic edits while their effect on the *purity* verdict (as opposed to `change_type`) is marginal.

**Cache scope — read-to-skip is audit-path-only (decision 2).** The cache stores only the Claude-derived structural/MIXED-STEP purity finding(s) (present or absent) per step — not the full `collect_detail_quality_findings` return. The critical asymmetry: the single Claude call inside `collect_detail_quality_findings` produces more than the purity verdict — it also emits apply-eligible `## Findings` semantic-grounding recs (`source="claude"`) and altitude advisories, and that grounding review Reads/Greps files *outside* the step's declared `files:`, which the key (decision 1) does not and cannot cover. Skipping the whole Claude call on a hit therefore skips grounding-against-current-code that could newly fail. So **only the `completeness-audit` path reads the cache to skip Claude**: `_collect_purity_split_findings` keeps only the `GRANULARITY_SPLIT_SOURCE` (MIXED-STEP) subset and *discards* the grounding findings anyway, so skipping them on a hit loses nothing there. `detail.py`'s two authoring-time call sites **write through** to the cache (recording the purity verdict they compute) but do **not** skip their Claude call — their convergence loop needs the full findings set, grounding included, re-run against current code every pass. The deterministic grounding findings (`collect_step_grounding_findings` — file-check, files-coherence, detail-coverage, detail-body) stay cheap and outside the cache on every path; the shared helper wraps only the *Claude call + parse* portion (rendering the prompt, invoking, lifting `## Structural findings`).

**Persistence (decision 3).** Persist the cache in a small dedicated file under `.plan-tool/` — not the audit-run sidecar. The audit JSON sidecars under `.plan-tool/runs/<slug>/` are timestamped report history, not a stable lookup target. Use `.plan-tool/purity-cache/<slug>.json`, following the existing `.plan-tool/` tool-state convention (alongside `runs/`, `checkpoints/`), keyed by step id, storing per entry: the combined fingerprint key (decision 1, the hit test); the cached purity finding(s) — or an explicit "no finding" marker, not just an absent key, so a confirmed-pure step isn't re-checked every time; the prior `## Implementation`/`## Tests` section text; and the key's **individual components** — the detail-file hash, the `all_files` content fingerprint, `change_type`, `depends_on`, and the `PURITY_VERDICT_LOGIC_VERSION` — plus the step's **detail-file relpath** (the renumber-safety identity token decision 6 checks). Storing the components (not just the opaque combined digest) is load-bearing for decision 6: on a miss the combined key has moved, but the below-floor grading must isolate *which* component moved — specifically, it must confirm the `all_files` fingerprint is **unchanged** before treating a miss as a trivial detail-only edit, or a source-file (`files:`/`creates:`) change would be mis-graded as below-floor and reused. Needs a `DATA_CONTRACT.md` entry.
- **The cache directory is gitignored.** `.gitignore` enumerates each `.plan-tool/` runtime-state subdir individually (`runs`, `checkpoints`, `reviews`, `telemetry`, …); a step must add `.plan-tool/purity-cache/` alongside them. The cache is per-machine, best-effort runtime state — leaving it tracked would (a) contradict the "gitignored" claim in the `DATA_CONTRACT.md` prose and (b), worse, let a `run --commit` sweep per-machine cache files into commits.
- **Concurrency posture.** The store is a single whole-file JSON map, written atomically via `os.replace`. Every command that writes it (`detail`, `completeness-audit`) already holds the repo mutation lock (`plan_tool/repo_lock.py`), which serializes all mutating plan-tool commands on a repo — so the "two concurrent writers do an unlocked read-modify-write and clobber each other's entries" race cannot occur (it is the same lock that makes a second `detail`/`audit` on the same repo refuse rather than run). A cache write is best-effort regardless: the failure mode of a lost or clobbered entry is a *re-check* (a fresh Claude call), never a stale verdict, since the combined key gates correctness. Do not add per-worker locking or per-step files for concurrency — the repo lock already covers it.
- **Only a *successful* call is cached (decision 3a — load-bearing correctness).** An entry means "this step was **successfully** purity-checked and the verdict was X" — *not* merely "a call was attempted." This distinction is critical because a **failed** purity call is indistinguishable at the finding level from a genuinely-pure one: `shell_detail_invoker` returns `""` on a timeout (the `scoped_claude_timeout(PURITY_CLAUDE_TIMEOUT_S)` retry-exhausted fall-through), on exec-not-found (rc 127), and on transient exhaustion, and `parse_mixed_step_findings("")` → `[]` — the same empty list a truly-pure step yields. Today that is harmless: a failed call just re-checks next audit. But caching an empty-from-failure verdict would turn it into a *sticky false-pure hit* that masks a real MIXED-STEP finding until the step's inputs change — breaking the "never removes a capability" invariant. So the write-back is gated on **call success** — and the success signal must come from the **invoke layer**, not be inferred from the findings list. This is the subtle part: `collect_detail_quality_findings` returns only a `list[Recommendation]`, and a failed call (`""`), a no-detail quiet-probe (short-circuits to `[]` before any Claude call), and a genuinely-pure success all yield the *same* empty purity subset — so the helper cannot distinguish them from the return value alone. The fix is to surface the raw call outcome: the purity call must expose whether the invoke actually ran and returned a **well-formed** response (e.g. `collect_detail_quality_findings` gains an opt-in that also returns a `call_succeeded` / raw-response signal, or the helper drives the purity portion through a thin wrapper that returns `(findings, succeeded)`). "Well-formed" must be stronger than "non-empty": `parse_mixed_step_findings` returns `[]` for *any* text lacking a `## Structural findings` block without erroring, so a truncated or garbled non-empty reply would otherwise read as a pure success and cache a false-pure hit. The correct success marker is the **mandatory final `## Findings` heading**: `prompts/detail-quality.md` requires `## Findings` in *every* well-formed response ("remains mandatory and must stay the final section"), while it tells the model to **omit `## Structural findings` entirely for a type-pure step**. So `succeeded` is true only when the raw response contains the `## Findings` section — **not** `## Structural findings`. Keying on `## Structural findings` would be doubly wrong: it would grade every genuinely-pure step (the common case the cache most wants to record) `succeeded=False` and never cache it — defeating the feature for the majority case — and it could not tell a pure reply from a truncated one (both lack it). Keying on the always-present, always-last `## Findings` gets both right: a truncated reply cut off before it grades `succeeded=False`, while a pure *or* mixed reply that reached it grades true (verdict extraction still reads `## Structural findings`, which is simply empty/absent for a pure step). The helper caches a verdict **only when `succeeded` is true**; on a failed/empty/timed-out/quiet-probe/**truncated** call (no `## Findings`) it writes **nothing** and returns the (empty) result uncached, preserving today's re-check-next-time behavior. "No finding" is cached only as the result of a *successful, well-formed* call whose outcome the invoke layer confirmed.
- **Lifecycle / pruning.** Entries are keyed by step id, and a later split/merge/scope-out can remove or renumber a step, orphaning its entry. Orphans are *safe* (a renumbered id yields a mismatched key → re-check, never a stale hit) but would accumulate unbounded, so prune on load: drop any entry whose step id is absent from the current plan. Cheap, deterministic, no Claude. (File-granularity orphans — a whole `<slug>.json` left behind when a plan is renamed or deleted — are **not** pruned; this matches the un-pruned `runs/`/`checkpoints/` siblings and is left as a conventional, low-impact accretion rather than implied-complete pruning.)

**Shared helper wiring (decision 4).** Build one small helper — e.g. `plan_tool/detail.py:_cached_purity_findings(plan_path, step, *, repo_root, plan_name, invoker, cache_path, read_through, ...) -> list[Recommendation]` — that computes the combined key and either reuses the cached verdict or calls `collect_detail_quality_findings`, always writing the computed result back. It exposes two modes matching decision 2's split: **read-through-skip** (used by `_collect_purity_split_findings` in the audit path — reuse on a hit, call Claude only on a genuine miss) and **write-through-only** (used by `detail.py`'s two call sites at `:3524`, `:3982` — always call Claude for the full findings set, then record the purity verdict for later audit reuse). All three sites route the Claude-judged portion through this one helper so the key/cache logic lives in one place; only the audit path lets a hit skip the call. The write-back is **success-gated** (decision 3a) using the **invoke-layer success signal** (not the findings list, which cannot distinguish a failure from a pure verdict): the helper caches only when the purity call's `succeeded` flag is true (a non-empty, parseable response); on a failure/empty/timeout/quiet-probe it writes nothing, so the step re-checks next time and an empty list from a *failed* call is never persisted as a false-pure verdict. On write it persists the key's individual components (decision 1/3) alongside the verdict, so decision 6 can grade component-by-component. Filter the cached/fresh findings on `plan_tool/granularity.py:GRANULARITY_SPLIT_SOURCE`, the same source literal `_collect_purity_split_findings` already keys on.

**Fold-in of BACKLOG #144 (decision 6).** In the `completeness-audit` path, a cache *miss* is graded before deciding what to do, so the audit reuses across a trivial edit but re-computes across a material one. The grading works **component-by-component** against the entry's stored components (decision 3), not against the opaque combined key — because on any miss the combined key has moved and cannot say *which* input changed. The below-floor (reuse) branch is taken only when **all** of these hold: the entry is **for the same step identity** (its stored detail-file relpath equals the current step's — see below), the entry's stored `all_files` fingerprint equals the current one (**no `files:`/`creates:` source change**), `change_type` and `depends_on` are unchanged, the `PURITY_VERDICT_LOGIC_VERSION` is unchanged, and the `## Implementation` + `## Tests` diff ratio (`difflib.SequenceMatcher`, scoped to those two sections) is below 0.5%. If the `all_files` fingerprint moved, the miss is a genuine source-file change → re-compute, never reuse (this is the guard the acceptance criterion "a `files:` **or** a `creates:` file changed… forces a fresh check" requires). **Step-identity guard (renumber safety):** because the below-floor branch reuses *despite* a combined-key mismatch, it cannot lean on the exact-key hit path's "a renumbered id yields a mismatched key → re-check" argument. A split/merge/scope-out drop-renumber can reassign entry id `2` to a now-different step; the entry stores that step's detail-file relpath (decision 3), and below-floor reuse requires it to equal the current step's detail relpath — a renumber changes the `NN-…` prefix, so the paths differ and the miss grades genuine, never leaking the old step's verdict onto the new one. Grading:
- **Below 0.5%, `all_files` fingerprint / frontmatter / logic-version all unchanged** → treat as a trivial edit: reuse the cached verdict, no Claude call, and emit an informational advisory (`purity reused for step N — changed M% of Implementation/Tests, below the re-check floor`). **A below-floor reuse writes nothing — the stored baseline is not advanced** (consistent with decision 3a: no call → no write). This is deliberate and load-bearing: leaving the baseline at the last *real* check means a run of individually-sub-0.5% edits is diffed cumulatively against that fixed baseline, so once their sum crosses the floor the next audit re-checks — a reuse that advanced the baseline would let cumulative sub-floor drift hide a real MIXED-STEP change forever.
- **At/above 0.5%, or any `files:`/`change_type:`/`depends_on:` change, or a cold/never-checked step** → a *genuine* miss: call Claude and produce a fresh verdict (per the audit-still-computes decision). This is the case that keeps `completeness-audit --purity` delivering real verdicts rather than only nudging.

This refines — does not contradict — #144's "keep the audit non-Claude": the audit stays non-Claude for the *trivial-change short-circuit* (the below-floor reuse), while a genuine change still earns a real re-check rather than silently vanishing (the [audit-purity-verdict-removal] gap). `detail.py`'s own authoring-time loop is unaffected by this grading — it always calls Claude for the full findings set on every pass (decision 2). Storing the prior `## Implementation`/`## Tests` section text (not just its hash) is required by this diff — a hash detects *that* something changed, not *how much* — and is part of decision 3's entry shape.

## Input

## Out of scope

- Redesigning `render_detail_quality_prompt`'s inputs — this plan caches around the existing prompt contract, it doesn't change what the prompt reads.
- Including lessons-file content, or the `title`/`complexity` frontmatter, in the cache key (decision 5) — an accepted, documented low-impact staleness window, not a gap to close here.
- Changing `detail.py`'s authoring-time behavior — it always runs the full `collect_detail_quality_findings` (grounding included) on every pass and only *writes through* to the cache; the read-to-skip optimization is scoped to the `completeness-audit` path (decision 2).
- Caching or skipping the Claude call's semantic-grounding output — the cache holds the purity verdict only; grounding-against-current-code is never served from cache (decision 2).
- Narrowing the audit's genuine-miss re-compute to a purity-only prompt — when decision D re-computes on a genuine miss it still invokes the full `collect_detail_quality_findings` grounding contract and keeps only the purity subset (the pre-existing request/discard shape). Trimming that to a slim purity-only prompt is **BACKLOG #151**, a deliberate post-#145 follow-up; this plan lands the cache first (which already removes the call entirely on a hit or below-floor miss), and #151 collapses to a short verification once #145 is in.
- BACKLOG #133 (speeding up the purity call itself) and #103/#115 (related purity-pass observability items) — this plan is about not re-paying the cost on unchanged content, not about making a genuine call faster.

## Risks

- Stale verdict if the cache key omits a verdict-affecting input the purity prompt reads. Mitigation: the combined key (decision 1) covers the detail-file hash, the `all_files` (`files:` **and** `creates:`) content fingerprint, **and** the `change_type`/`depends_on` frontmatter — the latter load-bearing because the MIXED-STEP verdict is directed by `change_type`, which lives in frontmatter and would otherwise let a `refactor`→`feature` flip hit a stale entry. The excluded inputs (`title`/`complexity`, lessons) do not steer the purity verdict (decision 5).
- False-pure verdict cached from a failed **or truncated** purity call. Mitigation (decision 3a): the write-back is success-gated on the **invoke-layer success signal** (not the findings list, which can't tell a failure from a pure verdict), and `succeeded` requires the raw response to contain the **mandatory final `## Findings` heading** (present in every well-formed reply; *not* `## Structural findings`, which the prompt omits for a pure step) — so a failed/empty/timed-out/quiet-probe call *and* a non-empty-but-truncated/garbled reply lacking `## Findings` all write nothing and re-check next audit, while a genuinely-pure reply (which reached `## Findings`) is correctly cached.
- Stale verdict after the MIXED-STEP prompt/parse logic itself changes (its *inputs* unchanged). Mitigation (decision 1): a `PURITY_VERDICT_LOGIC_VERSION` folded into the key is bumped whenever `prompts/detail-quality.md`'s criteria or `parse_mixed_step_findings` change, invalidating every entry at once. Because that bump relies on maintainer discipline, it is **enforced by a drift-guard test** (mirroring `tests/test_data_contract.py`'s contract-drift guard): a test hashes the prompt template + the parser's relevant logic and fails if they change without a version bump, so a forgotten bump can't silently serve old-logic verdicts.
- Renumber leak — below-floor reuse serving another step's verdict. Mitigation (decisions 3/6): the entry stores the step's detail-file relpath, and below-floor reuse (which reuses *despite* a combined-key mismatch) requires that relpath to match the current step's; a split/merge/scope-out renumber changes the `NN-…` prefix, so a reassigned id grades as a genuine miss and re-computes.
- Source-file change mis-graded as a trivial below-floor edit. Mitigation (decisions 1/3/6): the entry stores the `all_files` fingerprint as a *separate* component, and the below-floor reuse branch requires it to be unchanged — so a `files:`/`creates:` content change (which always scores ~0% on the Impl/Tests diff) is re-computed, never reused.
- Cumulative sub-floor drift hiding a real change. Mitigation (decision 6): a below-floor reuse writes nothing, so the stored baseline stays at the last *real* check; a run of individually-sub-0.5% edits is diffed cumulatively against that fixed baseline and re-checks once the sum crosses the floor.
- Below-floor reuse across a substantive edit confined to non-Implementation/Tests sections. The #144 magnitude signal diffs only `## Implementation` + `## Tests`, but the key hashes the whole detail file and the prompt reads the whole body — so a wholesale rewrite of `## Summary`/`## Why`/`## Files`/`## Acceptance criteria` crosses the key (→ miss) yet scores ~0% on the Impl/Tests diff (→ below-floor reuse). Mitigation/rationale: this is a deliberate scoped staleness window — the MIXED-STEP *purity* verdict tracks what the step implements/tests (its concern-mixing), not its prose sections, so an edit that leaves Implementation/Tests byte-identical does not change the purity judgment; documented like the decision-5 window rather than widened, since widening the diff to the whole body would re-inflate the very cost #144 cut.
- Grounding regression if a cache hit skipped the whole Claude call. Mitigation (decision 2): read-to-skip is scoped to the `completeness-audit` path, which discards grounding anyway; `detail.py`'s authoring loop always runs the full call, so grounding-against-current-code (which reads files outside the step's declared set the key cannot cover) is never served from cache.
- Lessons/`title`/`complexity` staleness (decision 5): these are folded into the prompt but excluded from the key, so a change confined to them leaves a cached verdict in place. Severity low — they change rarely and do not steer the *purity* judgment. Documented as an accepted staleness window; a future BACKLOG item can revisit if it proves to matter.
- #144's below-floor short-circuit could reuse a verdict across a small Implementation/Tests edit. Mitigation: the 0.5% diff is scoped to the Implementation+Tests sections and OR'd with the full `files:`/`change_type:`/`depends_on:` frontmatter-change trigger; it applies only in the audit path, only the below-floor case reuses (an at/above miss re-computes), and `detail.py`'s authoring loop validates every pass for real.
- Concurrent/lost cache writes. Mitigation (decision 3): all writers hold the repo mutation lock (serialized), the whole-file write is atomic (`os.replace`), and a lost/clobbered entry costs only a re-check, never a stale verdict.

## Testing

Follow the project's unit-first convention (`TESTING.md`): default to unit tests exercising one function/class in isolation with the invoker seam overridden so no real backend binary spawns; add `@pytest.mark.integration` only for cross-module wiring driving an orchestrator end-to-end. Required behaviors to cover:
- A step whose detail content is byte-identical to its last purity check makes no Claude call on a second check (cache hit).
- A step whose `all_files` content changed underneath an unchanged detail body still re-checks — covering **both** a `files:` edit and a `creates:` edit (proves the key grounds on `all_files`, not just `files:` or the detail file).
- A step whose `change_type` (or `depends_on`) flipped, detail and files unchanged, still re-checks (the `refactor`→`feature` stale-hit guard).
- A below-threshold miss in the `completeness-audit` path reuses the cached verdict with no Claude call (informational advisory only).
- A genuine miss (Impl/Tests diff ≥0.5%, any frontmatter change, or a cold step) in the audit path calls Claude and produces a verdict.
- A **failed** purity call (invoker returns `""`/timeout) — and a no-detail quiet-probe — writes **no** cache entry (gated on the invoke success signal, not the empty list), and a subsequent audit re-checks rather than serving a false-pure hit (guards decision 3a).
- In the audit path, a miss caused by an `all_files` (`files:`/`creates:`) content change is **re-computed even when the Impl/Tests diff is below 0.5%** (proves below-floor reuse is gated on the stored `all_files` fingerprint, not just the Impl/Tests diff — the round-3 HIGH guard).
- Bumping `PURITY_VERDICT_LOGIC_VERSION` turns every prior entry into a miss (proves prompt/parse-logic changes invalidate the cache).
- `detail.py`'s own loop always calls Claude for real (write-through) and never skips on a hit, regardless of magnitude.
Existing purity/detail-quality and completeness-audit suites must still pass. Mirror new modules to their `tests/test_X.py` per the project convention (e.g. cache-key and persistence helpers under their owning module's test file).

## Acceptance criteria

- In the `completeness-audit` path, a step whose detail content, declared-files content, and `change_type`/`depends_on` are all unchanged since its last purity check incurs **no Claude call** — the cached verdict (present or absent finding) is reused.
- A step whose `all_files` content (a `files:` **or** a `creates:` file) **or** its `change_type`/`depends_on` frontmatter changed, even with an unchanged detail body, is **not** served a stale cached verdict — the combined key (decision 1) forces a fresh check (this is the `refactor`→`feature` stale-hit guard, and it covers `creates:` files, not only `files:`).
- The audit path still delivers verdicts: on a **genuine** miss — Implementation+Tests diff at/above 0.5%, any `files:`/`change_type:`/`depends_on:` change, or a cold/never-checked step — `completeness-audit --purity` calls Claude and produces a real verdict, not merely a nudge.
- In the audit path, a miss reuses the cached verdict with **no Claude call** (informational advisory only) **only when all** hold: the entry's stored detail-file relpath equals the current step's (renumber guard), the Implementation+Tests section-diff is below 0.5%, the stored `all_files` fingerprint is unchanged (no `files:`/`creates:` source change), `change_type`/`depends_on` are unchanged, and the `PURITY_VERDICT_LOGIC_VERSION` is unchanged. A below-floor reuse writes nothing and does **not** advance the stored baseline (so cumulative sub-floor drift re-checks once its sum crosses the floor).
- A split/merge/scope-out **renumber** that reassigns a cache-entry step id to a different step does not leak the old verdict: below-floor reuse's detail-relpath match fails, so the new step re-computes.
- Editing the MIXED-STEP prompt/parse logic invalidates every cached verdict, and a **drift-guard test fails if the prompt/parser changes without bumping `PURITY_VERDICT_LOGIC_VERSION`** — so no step is served a verdict computed under the old logic, even if the bump is forgotten.
- A non-empty but **truncated/garbled** purity reply lacking the mandatory final `## Findings` heading is treated as a failed call (`succeeded=False`) and is **not** cached; conversely a genuinely-**pure** reply (which reached `## Findings` but has no `## Structural findings` block) **is** cached as an empty verdict — so pure steps stop re-checking every audit.
- `.plan-tool/purity-cache/` is added to `.gitignore` (the cache is per-machine runtime state; it is never tracked, and `run --commit` never sweeps it into a commit).
- `detail.py`'s two authoring-time call sites **always** run the full `collect_detail_quality_findings` (grounding included) and **write through** to the cache; they never skip the Claude call on a hit, so authoring-time grounding-against-current-code is never served from cache.
- A **failed** purity call (timeout / exec-not-found / transient exhaustion → empty response) **or** a no-detail quiet-probe (`[]` before any Claude call) is **never** cached as a verdict: the write-back is gated on the invoke-layer success signal (decision 3a), not on the empty findings list, so a failure re-checks on the next audit instead of persisting a false-pure hit.
- Two concurrent mutating commands cannot corrupt the cache (serialized by the repo mutation lock); a lost/clobbered entry costs only a re-check.
- The cache is a new persisted file under `.plan-tool/`, documented in `DATA_CONTRACT.md`, and prunes entries for step ids no longer in the plan.
- `BACKLOG.md`'s #144 and #145 entries are marked shipped/removed once the fix lands — #144 in full, since its full frontmatter-change OR (`files:`/`change_type:`/`depends_on:`) ships here.

## Deferred

- Revisiting lessons-file staleness (decision 5): the accepted staleness window is a permanent exclusion here (see `## Out of scope`), but the `## Risks` section notes a future `BACKLOG.md` item may revisit it if it proves to matter — that follow-up, not the exclusion, is what could come back.

**Known residual gaps (surfaced by the completeness audit; accepted as implementation-time items). — CLOSED in the post-run tail.** All four were addressed against the built code (see the per-item notes): the nondeterminism tradeoff is named in `plan_tool/purity_cache.py`'s module docstring; the drift-guard is scoped to the purity-verdict region of the prompt (`tests/test_fingerprint.py:_purity_prompt_verdict_text`, whole-file fallback); the declared-path *set* is folded into `all_files_fingerprint` (`plan_tool/fingerprint.py`, with a test for an absent-path re-check); and `plan.title`'s exclusion is noted. Retained here as the design record:

- **Verdict non-determinism (accepted tradeoff — the deepest one).** The MIXED-STEP purity verdict is a *non-deterministic* Claude call: identical inputs can yield a `## Structural findings` bullet on one call and omit it on another. Caching therefore freezes one sample — a step the model happened to judge "pure" stays pure until its inputs change, even if a re-roll would flag it mixed. This is **intrinsic to caching any noisy judgment**, not a fixable defect, and it is in fact the feature's *premise* ("unchanged content → don't re-check; skipping that re-check is the redundant work we're cutting"). Implementation must **name this tradeoff explicitly** (the "pure optimization / never removes a capability" wording should be qualified: it removes the *re-roll* on unchanged content, deliberately). If the re-roll turns out to matter, a future option is an occasional forced re-check (e.g. TTL / sampled re-validation) — a follow-up, not this plan.
- **Drift-guard invalidation scope (`[verdict-logic-version-scope]`).** The `PURITY_VERDICT_LOGIC_VERSION` drift-guard hashes the *whole* co-tenanted `prompts/detail-quality.md`, so an edit to its grounding/altitude/style regions (tuned far more often than the MIXED-STEP criteria) trips the guard, forces a bump, and cold-invalidates the entire cache — eroding the hit rate. Implementation should either scope the hashed surface to just the MIXED-STEP region (e.g. a marked block) or consciously accept the coarse invalidation and say so; decide against real prompt structure at code time.
- **Declared-path-*set* not in the key (`[declared-files-set-key]`).** The key covers `all_files` by *content* (absent paths omitted), but the prompt also renders the declared-files *list*; adding/swapping a `files:`/`creates:` path that does **not** resolve on disk leaves the `all_files_fingerprint` byte-identical → a stale hit, and step 4's frontmatter-OR (content-only) misses it too. Fix at implementation: fold the sorted declared-path *set* (not just existing-file content hashes) into the key/fingerprint, and cover it with a test (a `files:`-list edit to an absent path forces a re-check).
- **Under-enumerated key contract (advisory).** `render_detail_quality_prompt` also folds in `plan.title` (`plan_title`), which the `## Input` enumeration and decision-5 exclusion set both omit. It is *not* a stale-hit hazard (a plan-title change is cosmetic, not verdict-steering), but the "which inputs the key covers vs. excludes" contract should list it as an explicit exclusion when the code is written.
