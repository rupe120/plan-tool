The Architecture also forbids editing `_matches` (its other caller, `telemetry_analysis._sidecar_outcome`, needs the step-focus tier to stay authoritative for its synthetic `id="decision-focus"` resolution), so `recurring_regions` cannot deliver "split by id" for exactly the case that motivates it — two conceptual findings both anchored `step3-...` — by calling `_matches` unmodified as its join predicate. The same paragraph says to keep the anchor/fuzzy-title fallback "for the cases id-continuity cannot decide," but every `plan-correctness`/`plan-completeness` `Recommendation` always carries a non-empty `.id` (confirmed in `review.py`'s `_make_rec_id`/`Recommendation`), so it's unclear any same-step pair ever reaches that fallback.
  - Fix: specify `recurring_regions`'s join predicate as its own conceptual algorithm rather than a call to `_matches` unmodified — when both the candidate and an existing region's representative resolve the same step focus, use id equality as the deciding check (join on `.id` match, start a new region on an id mismatch) and reserve unmodified `_matches` for pairs where neither side resolves a step focus at all — and state this as the one algorithm the whole join loop uses, not an isolated example.
- HIGH `[hand-resolution-cleared-multiplicity]`: Step 5's clearance path says a hand-resolved finding id is recorded as cleared "on the hand-resolution event's presence alone" against `analyze_finding_drift`'s "per-plan finding-class origins" (Architecture, "Where hand-resolution evidence actually goes"). But `analyze_finding_drift` (`telemetry_analysis.py`) creates one origin observation per snapshot a finding id appears in: a finding present in three consecutive completeness sidecars before it is hand-resolved between the third and fourth today produces three separate `(finding_class, "unresolved")` entries, since each occurrence independently hits `if step is None or identity is None or selected is None: observations.append((finding_class, "unresolved"))`. Under step 5's design, one id lookup against a single hand-resolution event would flip all three occurrences to `"cleared"`, so one real resolution inflates the `cleared` count relative to `confirmed`/`unresolved`, which distorts `confirmed_rate` and the `LOW_IMPACT_DEMOTION_MAX_CONFIRMED_RATE` threshold `build_low_impact_demotion_lookup` reads — the exact calibration math this plan exists to fix. Step 7's acceptance criterion ("23 hand-resolution events... each must land as cleared evidence") would not catch this: it only requires each of the 23 to land as cleared, not that the cleared total stays at 23.
  - Fix: specify that step 5 clears exactly one origin per resolved finding id (e.g. only the origin occurrence in the sidecar immediately preceding the one where the id disappeared, or an explicit dedup pass before counting), and tighten step 7's testing language to assert the cleared count for these ids is not inflated by how many rounds the finding persisted before resolution.
