## Why

After steps 3 and 4 land, `cmd_completeness_apply` still owns the part of the verb that does the real work: walking the narrowed findings through `walk_recommendations`, deciding per-gap dispositions, handling the `--jobs N>1` non-interactive fan-out, and committing. None of that is CLI-layer work — it doesn't touch `argparse.Namespace` beyond a few already-parsed flags, and it prints progress/advisory text rather than mapping to exit codes on its own terms (the two hard exits inside it are gap-walk outcomes, not argument validation). This is the step that finally empties `cmd_completeness_apply` down to the "thin handler" shape the plan's Architecture section describes: argument validation, dispatch, and terminal-output/exit-code mapping, with every phase's real logic living in `completeness_phases.py`.

Two things confirmed against current HEAD while drafting this file, both undercounted by a naive reading of the step's own line-range description: `_completeness_apply_commit_subject` (used by both `cmd_completeness_apply`'s own `--commit` block and by `_apply_walk_recs_parallel`'s) sits physically between the two ranges named by the plan and belongs to this step, matching the plan's own step intent. And `_load_saved_data_contract_payloads` / `_data_contract_payload_target` / `_data_contract_completeness_redirect` are a shared dependency neither step 3 nor step 4 claimed — step 3 calls `_load_saved_data_contract_payloads` once at its own boundary, and this step's own `action_fn` closure calls `_data_contract_completeness_redirect` once — so this step is the one that resolves where all three finally live.

**Add one new function reproducing the dispatch-and-execute tail's control flow, unchanged, in order.** Something like `_run_apply_walk(walk_recs, conceptual_walk_recs, *, saved, saved_path, plan_path, ctx, args, parallel, plan_is_bare, data_contract_payloads, pre_apply_presentation)` in `completeness_phases.py`, following this file's `_run_`-prefixed naming already used for `_run_deterministic_checks` and (after step 2) `_run_iterate_convergence_loop`. **Two parameters beyond `walk_recs`/`parallel` are required, not optional**: `conceptual_walk_recs` — the parallel branch calls `_apply_walk_recs_parallel(conceptual_walk_recs, saved=saved, ...)` (`completeness_cmd.py:542-543`), passing `conceptual_walk_recs`, not `walk_recs`, as the positional arg; substituting `walk_recs` there would silently change which findings `--jobs N>1` applies, a real behavior change against this plan's zero-behavior-change contract — and `plan_is_bare` — read at `completeness_cmd.py:647` to compute `_allow_split`, the gate on structural-split apply passed into `_build_review_action_fn`. Both come from step 4's `_ApplyWalkTargets` result (see Input below). Unlike steps 3 and 4's phase functions, this one doesn't need a result dataclass — nothing runs in `cmd_completeness_apply` after this range today, so the function can simply `return` the same `int` exit codes the current code returns inline: `0` for the "nothing to walk" and success paths, `2` when `plan_path is None` or the walk is skipped on non-interactive stdin, `1` when the closing `git commit` fails, and (when `parallel` is set) whatever `_apply_walk_recs_parallel` itself returns. `cmd_completeness_apply`'s own tail becomes one line:

```python

```
