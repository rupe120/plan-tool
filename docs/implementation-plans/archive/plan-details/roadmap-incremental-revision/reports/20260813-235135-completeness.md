- HIGH `[row-write-allowlist]`: Architecture defines selected `artifact:id` roots and an affected *collection* order, but never defines the allowed row set in each dependent collection. Steps 4 (`Reject invalid artifact-qualified feedback selections...`), 5 (`Parse and render... patches`), 6 (`Merge allowlisted patches...`), and 9 (`Run one bounded patch request...`) can therefore accept a patch that changes an unselected row; `plan_tool/roadmap_gates.check_design_row_continuity` only requires a removal to cite local open feedback and never checks that its target is the removed row. This breaks the Architecture merger promise and the Acceptance criteria’s non-target-row fence.
  - Fix: define a deterministic row-level write allowlist for every collection, including the exact selected-feedback-to-removal authorization and rules for permitted new rows, then make every patch, context block, and merger check use it.
- HIGH `[baseline-conflict-detection]`: Architecture’s transaction lock serializes plan-tool commands but cannot stop a reviewer from editing a roadmap artifact or `seed-state.json` while the backend is running. The publication protocol records preimage digests but never requires a pre-replace comparison or a guarded restore; a later reviewer edit can therefore be overwritten by publication, or by recovery after a checkpoint failure, despite the Overview and Architecture promises to preserve reviewer-owned state. `plan_tool/roadmap._write_artifact` confirms that the current write path is unconditional replacement.
  - Fix: require the publisher and recovery path to detect baseline or candidate digest conflicts for every revision-owned path and refuse without overwriting newer external bytes.
- HIGH `[seed-state-vocabulary]`: Architecture’s stale-plan paragraph says impacted entries become `stale`, removed IDs become `removed`, and “the sidecar changes status only”; the Input, Deferred section, and stale-draft Acceptance criterion depend on that signal. This contradicts `plan_tool/roadmap_seed_state.validate_seed_state`, which accepts only `current` and `invalidated`; `roadmap_seed_manifest.classify_draft_seeds` derives `stale` from `invalidated`, and `find_orphan_seed_records` treats an entry for a removed plan as an orphan. Steps 2, 3, and 8 do not choose a compatible representation or migration.
  - Fix: retain the raw `current`/`invalidated` status contract for extant drafts, record removed IDs in the published session record, and reconcile the Architecture, Deferred section, acceptance criteria, and all seed consumers to that representation.
- HIGH `[seed-command-lock-lifetime]`: Architecture calls `materialize_plan_seed`, `refresh_roadmap_seeds`, `accept_roadmap_seed`, `_apply_roadmap_seeds`, `_cmd_roadmap_materialize`, and `_confirm_invalidated_roadmap_seed` “public readers” that take the lock only briefly, but the first five also write drafts, promoted copies, or `seed-state.json`. `plan_tool/roadmap.materialize_plan_seed`, `accept_roadmap_seed`, `refresh_roadmap_seeds`, and `_apply_roadmap_seeds` currently make those writes after reading their inputs, so a targeted publish can race them and lose a `stale` status or recreate a removed entry.
  - Fix: define one lock or snapshot-revalidation rule for each named seed-mutating command so its final write cannot commit against a targeted revision that changed its roadmap or sidecar baseline.
- HIGH `[recovery-preimage-completeness]`: Architecture makes a durable `prepared` marker the recovery authority, yet only says it carries “staged preimage paths”; it does not require every preimage—including a path that did not exist—to be durably staged before that marker is written. The Risks, Testing section, and pre-checkpoint recovery Acceptance criterion promise restoration after interruption, but a durable marker without durable restore inputs cannot meet that promise.
  - Fix: define the preimage staging order and absent-path representation so recovery never begins after `prepared` exists unless it can restore every revision-owned path exactly.
