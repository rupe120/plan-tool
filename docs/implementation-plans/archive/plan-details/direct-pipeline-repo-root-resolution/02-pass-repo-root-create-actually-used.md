# Step 2 — Pass the repo root create actually used into every later pipeline stage

## Summary

`cmd_direct_jira` and `cmd_direct_run` in `plan_tool/cli/direct_cmd.py` each resolve `repo_root` once via `_resolve_cmd_repo_root(args)` before `create` runs, then keep using that same pre-create value for every commit/dirty-check after `create`, and `_stage_namespace` never sets `.repo_root` on the namespaces it builds for `detail`/`completeness-apply`/`jira`/`run`/`reconcile-code` — so when `create` relocates its working root (a `--from-existing` seed whose files resolve under a different `.git` ancestor), every downstream stage silently falls back to its own cwd-walk and lands on the stale, pre-relocation root. This step adds a small helper that derives the root `create` actually used from the returned `CreateResult` (by walking up from `result.plan_path`'s parent, not by reading `manifest_path.parent.parent`, which can diverge under an explicit `--manifest` override), keeps that value in a distinct local so the original cwd-derived root stays available for step 3's cleanliness check, then — in this order — **(a)** refuses a non-disjoint (nested/ancestor) relocation with a clear error (the plan's Architecture decision 7 scope boundary), **(b)** commits any dirt `cmd_create` itself already left in the *original* root (the archived seed file, when relocation happened via `--from-existing`), so that repointing every later stage doesn't orphan it, and **(c)** threads the resolved root as an explicit `repo_root=` override into every `_stage_namespace(...)` call built after `create` returns, repointing every post-create `working_tree_dirty`/`commit_all` call at it. The refuse-guard in (a) is what makes (b)'s `git add -A` safe: because any nested/ancestor relocation is rejected before (b) runs, `repo_root` and `created_repo_root` are guaranteed disjoint trees, so the commit cannot stage one as an embedded gitlink inside the other. The step-0 precondition (before `create` runs) is untouched — there is no relocated root to check yet at that point. On green, a **disjoint** relocated chain's `detail`/`completeness-apply`/`jira`/`run`/`reconcile-code` stages all resolve the plan and commit against the root `create` actually wrote to, the original root's own residual dirt (if any) is committed rather than left stranded, a **nested/ancestor** relocation is refused cleanly (deferred to BACKLOG #146), and the common (non-relocated) case is behaviorally unchanged.

## Why

`cmd_direct_jira` and `cmd_direct_run` both open with `repo_root = _resolve_cmd_repo_root(args)`, computed from cwd/`--repo-root` before `create` has run — call it "the original root." Every later stage in both functions reuses that same local: the `working_tree_dirty(repo_root)` / `commit_all(repo_root, ...)` calls after `detail` and after `completeness-apply`, and the five `_stage_namespace(...)` calls that build `detail_args` / `apply_args` / `jira_args` / `run_args` / the per-step `reconcile_args`. None of those `_stage_namespace(...)` calls sets `.repo_root` as an override, so the copied namespace carries whatever `args.repo_root` was at parse time (typically `None`, since the operator didn't pass `--repo-root`) straight into `_load_context(args)` → `build_plan_tool_context(..., repo_root_override=args.repo_root)` — which then falls back to its own cwd-derived auto-discovery, exactly like the top-of-function resolution did. When `create` relocates (`plan_tool/cli/authoring.py:cmd_create`'s seed-derived `find_umbrella_root` override, or the `_confirm_repo_root` prompt under `--yes`), the plan, its detail bundle, and its manifest entry all land under the new root — but every downstream stage still asks for the plan under the stale one. Concretely, `cmd_detail`'s `resolve_plan_for_context(ctx, args.name)` can't find `plan_name` in the wrong manifest and the chain aborts "plan not found" even though `create` just succeeded and the plan is sitting on disk. The commits in step 4+ of both verbs are worse than a lookup failure — `working_tree_dirty(repo_root)` / `commit_all(repo_root, ...)` silently check and commit against the *wrong* git working tree, so a relocated run's authoring artifacts never get committed where they were written.

## Input

This step is a pure threading fix on top of contracts that already exist and aren't renegotiated here:

- **`CreateResult`** (`plan_tool/create.py`): after the split-proposal / `iteration_stage_failure` / size-gate guards earlier in both verbs, `result.plan_path` is guaranteed non-`None` (the guard block above `plan_name = result.plan_path.stem` already returns early on the one case where it can be `None`). `result.manifest_path` is always populated (never `Optional`), but per the plan's Architecture decision 2, don't derive the working root from `result.manifest_path.parent.parent` — it silently assumes the `<repo_root>/.plan-tool/plans.json` layout and breaks under an explicit `--manifest` override to a path outside that shape.
- **The existing `--repo-root` override plumbing**: every downstream stage handler (`cmd_detail`, `cmd_completeness_apply`, `cmd_jira`, `cmd_run`, `cmd_reconcile_code`) already resolves its working root via `_load_context(args)` → `build_plan_tool_context(..., repo_root_override=args.repo_root)` (`plan_tool/cli/context.py:_load_context`). Setting `.repo_root` explicitly on a stage namespace is enough to make that stage use the relocated root — no new resolution seam, no handler-side change.
- **Step 1's `create_plan` fix** (this step's `depends_on`): once `create_plan` passes `repo_root` into `default_manifest_path(repo_root)`, the manifest entry for a relocated plan is guaranteed to live under the *same* root as `result.plan_path`, which is what makes deriving "the root `create` used" from `plan_path` alone a reliable signal for the manifest lookups every downstream stage performs.
- **`cmd_create`'s seed-adjacent writes** (`plan_tool/cli/authoring.py`, `plan_tool/create.py`): on `--from-existing` (`source_path is not None`, never `--from`), `cmd_create` makes up to **three** writes relative to `source.parent` (the seed file's own directory): the consumed source-seed archive (`archive_existing_source`, ~line 702), a provenance-seed archive when the canonical carries provenance (~line 724), and a distilled-artifact write-then-archive (~line 755). `archive_existing_source`'s `repo_root` parameter is only a cosmetic `_display_path` string — the archive directory is always `source.parent`. **Which root these land in depends on where the seed file physically lives, not on the relocation direction:** a seed under the operator's own project (the original, pre-relocation root — the common case) puts them in `repo_root`; a *shared* seed that physically lives under the relocated sibling root (a plausible workflow) puts them in `created_repo_root`. The common (seed-in-original-root) case is what this step's original-root commit covers; the seed-in-relocated-root case is a documented best-effort limitation of step 3's guard (see step 3's Deferred and BACKLOG #150).

## Implementation

**Add one small, deterministic helper next to `gate_create_result_size`** (same file, same style — no `invoker=` seam, since there's no judgment to delegate) that turns a `CreateResult` into the repo root `create` actually used:

- Signature shape: takes the `CreateResult` (or just its non-`None` `plan_path`), returns a `Path`.
- Implementation: `find_repo_root_from_cwd(start=result.plan_path.parent)` (`plan_tool/locator.py`) — walk up from the plan file's own directory to the nearest `.git`/`.plan-tool/plans.json` ancestor. This is the same primitive `plan_tool/cli/authoring.py:cmd_create`'s own root-confirmation logic and `find_umbrella_root` are built on (`plan_tool/locator.py`'s `is_project_root`/`collect_project_root_ancestors`), and it's already exercised this way in `tests/test_locator.py` (`TestFindRepoRootFromCwd.test_finds_git_from_explicit_start`, `test_nearest_marker_wins_over_ancestor_git`) — a proven, precedented call shape, not a new one.
- Needs a new import: `from plan_tool.locator import find_repo_root_from_cwd`.
- Reject the `manifest_path.parent.parent` shortcut explicitly (per the plan's Architecture decision 2) — it's simpler to write but wrong the moment `--manifest` points somewhere that doesn't follow the `<root>/.plan-tool/plans.json` layout.

**Keep the resolved root in a distinct local — do not overwrite the original `repo_root`.** Step 3 (`depends_on: 2`, "Add a safety check that stops the chain if the relocated repo has unrelated uncommitted changes") needs to compare "the root `create` actually used" against "the root checked at step 0" to decide whether a *new* cleanliness check is even necessary — it only fires when the two differ. If this step reassigns the same `repo_root` name after `create` returns, that comparison is only recoverable by calling `_resolve_cmd_repo_root(args)` a second time in step 3, which is redundant and a step 3 problem to reintroduce needlessly. Pick a clearly distinct name for the post-create value (e.g. `created_repo_root`) and use *that* — not `repo_root` — for every git operation and stage namespace built after the guards. This is the one constraint in this step that isn't free to vary; everything else (helper name, exact call ordering) is a normal engineering choice.

**Refuse a non-disjoint (nested / ancestor) relocation up front.** Immediately after `created_repo_root` is computed, and before the original-root commit below, check disjointness against the original `repo_root` (both `.resolve()`d): if `created_repo_root.is_relative_to(repo_root)` **or** `repo_root.is_relative_to(created_repo_root)` — i.e. one tree is nested inside the other (this covers the narrower/nested case *and* `find_umbrella_root`'s strict-ancestor case) — call `error(...)` with a clear, actionable message (e.g. `f"{verb}: create relocated the plan to a repo nested within (or containing) the current one ({created_repo_root}); nested-repo relocation is unsupported — run plan-tool create/detail/run from that repo directly"`) and `return 2`, before any commit or stage-namespace threading. This is the plan's Architecture decision 7 scope boundary: git's embedded-repository semantics make the non-disjoint case hazardous (a nested `.git` reads as opaque `?? nested/` dirt; `git add -A` on the outer root stages the inner as a `mode 160000` gitlink), and full support is deferred to **BACKLOG #146**. `Path.is_relative_to` (3.9+) is the exact predicate; a `created_repo_root == repo_root` (no relocation) is *not* non-disjoint — `is_relative_to` self-returns True, so guard the whole check on `created_repo_root != repo_root` first (no relocation → no refuse, no commit, straight through). Place this refuse before the original-root commit so a refused chain never leaves a half-committed original root. **One residual on the ancestor sub-case (accepted, not corruption):** when `created_repo_root` is a strict *ancestor* of cwd, there is no embedded-`.git` tripwire, so `create` has already run and archived the `--from-existing` seed by the time this guard fires; refusing here returns *before* the original-root commit, leaving that archival dirt uncommitted (it trips the step-0 precondition on a later run — a benign spurious abort the operator clears by committing/removing the archive). Do **not** try to commit or roll back `create`'s already-written state on the refuse path — cleaning up a half-run of an unsupported relocation is deferred to **BACKLOG #146**; this guard's job is only to stop the chain cleanly before it corrupts anything, which it does. (The plan's Risks section documents this residual explicitly.)

**Before repointing anything downstream, commit the original root's own known dirt — if any.** Reached only when the relocation is disjoint (the refuse-guard above already returned on the nested/ancestor case). Once `created_repo_root` is computed, and only when it differs from `repo_root`: check `working_tree_dirty(repo_root)` (the *original* root, using the existing `plan_tool/cli/gitcommit.py` helper already imported by this module). If dirty, `commit_all(repo_root, f"{verb}({plan_name}): archive superseded seed after relocation")` before doing anything else — this sweeps (`git add -A`) whichever of `cmd_create`'s seed-adjacent writes landed in the original root: the source-seed archive, the provenance-seed archive, and the distilled-artifact write/archive (up to three writes, per [Input](#input) — not just one). Once every later `_stage_namespace`/git-op call in this step repoints at `created_repo_root`, nothing else will ever check or commit the original root again for the rest of this process. Because the roots are guaranteed disjoint here, this `git add -A` cannot stage `created_repo_root` as an embedded gitlink. Skipping this step would leave that archival permanently uncommitted after a relocated `--from-existing` run, silently, until a *later*, unrelated invocation from the original root trips the unchanged step-0 `working_tree_dirty(repo_root)` precondition and aborts "requires a clean working tree" — a regression this step would otherwise introduce in exactly the scenario it exists to support. This check is a no-op (no commit, no error) when `created_repo_root == repo_root` (no relocation) or when `--from` was used (no seed file, so `archive_existing_source` never ran and `repo_root` has nothing new to commit).

**Thread `created_repo_root` into every `_stage_namespace(...)` call built after the guards**, as one more `repo_root=created_repo_root` override alongside the existing ones:

- `cmd_direct_jira`: the `detail_args`, `apply_args`, and `jira_args` builds.
- `cmd_direct_run`: the `detail_args`, `apply_args`, and `run_args` builds, plus the `reconcile_args` build inside the per-step reconcile-code loop (it's rebuilt once per code step, so the override needs to be part of that loop body, not just the three top-level builds).

**Repoint every post-create `working_tree_dirty`/`commit_all` call at `created_repo_root`.** In both verbs this is the "4. Commit the authoring artifacts…" gate/commit pair (after `detail`, before `completeness-apply`) and the "Commit the applied gaps only if any landed" gate/commit pair (after `completeness-apply`). Leave the step-0 precondition (`if working_tree_dirty(repo_root): ...` before `cmd_create(args)` runs) targeting the original `repo_root` local exactly as today — there is no relocated root yet at that point, and the plan's Architecture section calls this out explicitly as staying unchanged.

**Constraints to respect:**

- `created_repo_root` must be computed *after* the split-proposal / `iteration_stage_failure` / size-gate guards — at the same point `plan_name = result.plan_path.stem` is already set, since it depends on the same non-`None` `result.plan_path` invariant those guards establish.
- Don't touch the step-0 `working_tree_dirty(repo_root)` precondition — it's pre-create and has no relocated root to know about yet.
- Don't add the cleanliness re-check on the relocated root here — that's step 3's job (see [Deferred](#deferred)); this step only threads the value, it doesn't gate on it.
- `_stage_namespace`'s contract (per its own docstring) is that a missing direct-read field raises `AttributeError` mid-chain — `repo_root` is always a defined attribute on the parser-built `args` (global `--repo-root` flag), so adding it as an override is safe and doesn't risk a missing-field crash the way a stage-specific field would.
- The original-root commit (if any) must happen *before* any `_stage_namespace(...)` call is built with `repo_root=created_repo_root` — ordering matters here, unlike the threading calls themselves, which can happen in any order relative to each other.
- The non-disjoint refuse-guard must run *before* the original-root commit (which must run before step 3's relocated-root guard). Full order: derive `created_repo_root` → refuse if non-disjoint → commit original root (if disjoint + dirty) → thread `created_repo_root` → (step 3's relocated-root cleanliness guard, then stages). A refuse must leave nothing half-committed.
- The disjointness check guards on `created_repo_root != repo_root` first — `Path.is_relative_to` self-returns True, so an un-guarded check would wrongly flag the no-relocation case as nested.

## Acceptance criteria

- A helper function exists in `plan_tool/cli/direct_cmd.py` that derives the repo root `create` actually used from a `CreateResult`, without reading `manifest_path.parent.parent`.
- Every `_stage_namespace(...)` call built after the split-proposal / iteration-failure / size-gate guards in both `cmd_direct_jira` and `cmd_direct_run` (`detail_args`, `apply_args`, `jira_args`/`run_args`, and the per-step `reconcile_args`) carries `repo_root` set to that derived value.
- Every `working_tree_dirty`/`commit_all` call after `create` returns in both verbs targets the derived value, not the pre-create `repo_root` local.
- The step-0 `working_tree_dirty(repo_root)` precondition (before `cmd_create(args)` runs) is unchanged and still targets the original cwd-derived root.
- When `created_repo_root` differs from `repo_root` and the original root is dirty from `create`'s own seed-archival write, that dirt is committed against the original root before any downstream stage namespace is built — not left uncommitted, and not folded into a commit against `created_repo_root`.
- When there is no relocation, or the original root has nothing dirty, no extra commit or dirty-check against the original root occurs beyond the step-0 precondition.
- When the derived `created_repo_root` is nested inside `repo_root` **or** a strict ancestor of it (non-disjoint), the verb refuses with a clear, non-zero error before any commit or stage runs — and a disjoint (sibling) relocation is *not* refused. The disjointness check is gated on `created_repo_root != repo_root` so the no-relocation case is never misread as nested.
- All new and existing tests in `tests/cli/test_direct_cmd.py` pass.
