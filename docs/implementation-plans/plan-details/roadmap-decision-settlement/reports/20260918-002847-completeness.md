- CRITICAL `[enrolled-settlement-write-boundary]` [confidence: limited]: Step 5 commits the enrolled write path to "advancing the accepted head through the existing guarded write" via, per the Architecture section, "the existing `promote_review_seal` boundary" — while step 5's own intent line requires this "without ever editing its accepted head in place and without inventing a model-authored review lineage." But `promote_review_seal` (`plan_tool/roadmap_version_promotion.py:43`) is not a generic accepted-head write: it loads a `CandidateReviewSeal` (`roadmap_candidate_review.py:413`) and validates it against a full model-authored chain — an admitted `CandidateProposalAdmission` produced only by `run_initial_candidate_proposal`, which invokes a Claude backend (`shell_candidate_proposal_invoker`, `roadmap_candidate_run.py:309`), plus a question inventory, a reviewer answer, an answer-incorporation record, and a replacement binding, all cross-checked by `_require_seal_bindings`/`_require_replacement_binding`/`_require_final_capsule_binding`. `promote_review_seal` is confirmed as the *sole* writer of `accepted_head_path` after root enrollment (`roadmap.py:929` writes it once, before enrollment, and the deterministic structural-rewrite path in `roadmap_structural_revision_run.py` never touches `accepted_head_path` or `promote_review_seal`), so there is no lighter existing boundary to fall back on. Reusing it as described therefore requires either constructing a full non-model synthetic candidate/review/seal chain (never mentioned — far more than "storing a deterministic candidate version") or a new write path the plan's own guardrail ("it always goes through the existing candidate/promotion boundary") forbids. This also leaves step 2's shared preflight unresolved on the read side: `roadmap_view.py:load_roadmap()`, the only reader already converted for enrolled content, reads an enrolled roadmap's canonical bytes from `accepted_version.artifact_bytes` and explicitly refuses to fall back to "live artifact paths," while the selector precedent the plan cites (`ReceiptSafeSelector`, `CanonicalArtifactSnapshot.source_digest`) is, per the plan's own References, "wired only for an un-enrolled roadmap today" — the plan never says which source the enrolled preflight reads.
  - Fix: Specify the enrolled write mechanism at the plan level: either scope a new, narrower guarded write for the accepted head that step 5 can build without a model-authored candidate lineage, or state plainly that settlement will construct a full non-model candidate/review/seal chain to reuse `promote_review_seal`, and resolve step 2's preflight source (on-disk bytes vs. accepted-version bytes) for the enrolled case to match.
- HIGH `[settlement-evidence-authorship]` [confidence: limited]: Step 2's preflight and the Architecture require the cited feedback row to carry "non-empty reviewer-authored response text," and Testing repeats this as "recorded response text," but `FeedbackRow` (`plan_tool/roadmap_artifacts.py:536`) has no field that is both reviewer-authored and a response. `proposed_response` is the field literally named "response," and its own docstring says it "is what the model offered back" — confirmed by `--revise-feedback`'s CLI help text (`cli/roadmap_cmd.py`), which states the flag "Makes exactly one backend request" to produce it, so it is Claude-authored, not operator-authored. `request` is the only field that is genuinely "the reviewer's own words" (same docstring), but it is documented as a "reviewer redirect" — an objection or change ask, not an approval — and the plan never names it as the evidence field. Whichever field an implementer picks fails half of the plan's own two-part requirement; picking `proposed_response` (the natural reading of "response text") would make the route's evidentiary check a check on model output, not reviewer judgment — the exact trap CLAUDE.md's own "Validating a semantic property you cannot observe" section warns against, and the opposite of what the Risks section believes it has avoided by checking only "checkable facts."
  - Fix: Name the exact feedback field the settlement evidence checks — either adopt `request` as the evidence field and drop "response" from its description, or add a genuinely reviewer-authored acknowledgment field the route can check instead of the model-authored `proposed_response`.
- CRITICAL `[settlement-baseline-desync]` [confidence: limited]: Step 4's un-enrolled write silently breaks every other narrow un-enrolled action on the same roadmap stage the first time it runs, and nothing in Testing would catch it. Step 4 commits to:

  ```
  Settle one decision on an un-enrolled roadmap and publish its receipt,
  keeping the existing journal recovery (roll back or drop an in-flight
  generation) unchanged and replacing only the selected artifact's bytes —
  no baseline, seed-state, or other artifact is rewritten
  ```

  while Architecture says the write reuses "the same guard every other narrow un-enrolled action already uses," and References points step 2/4 at `ReceiptSafeSelector`/`CanonicalArtifactSnapshot.source_digest` as "the structural precedent this route's selector, predecessor-digest staleness check, and named-reason refusal shape should follow." That precedent is `admit_versioned_artifact_source` → `admit_baseline_backed_source` (`plan_tool/roadmap_source_identity.py`), and both `--reopen-feedback` (`roadmap_feedback_reopen.py:_admitted_stage_source`) and `--escalate-feedback` (`roadmap_escalation_run.py`) call it before every write. `admit_baseline_backed_source` refuses with `RoadmapSourceIdentityError("roadmap source differs from its baseline")` whenever the live artifact disagrees with its stored `.roadmap-baselines/<stage>.json` record, and that record is built by `canonical_projection`, which excludes only `"feedback"` — a decision row's `status` field is not excluded. `--reopen-feedback`'s own write (`publish_feedback_reopen_candidate`) gets away with touching only the artifact file precisely because feedback is the one thing the baseline ignores. A decision's `status` is not in that carve-out, so the moment step 4 flips `pending` → `settled` in the artifact file without touching that stage's baseline record, the two permanently disagree. From then on, any `admit_baseline_backed_source` check on that same stage — another `--reopen-feedback`, an `--escalate-feedback`, or a second settlement built the same way — fails with "roadmap source differs from its baseline," locking the operator out of every other narrow action on that roadmap after the very first successful settlement, with no error at settlement time and no stated repair anywhere in Risks or Deferred. The Risks section's "Gate interaction" entry only asks for a "changed-baseline fixture" to cover a concurrent-edit race; it never names the settlement's own successful write as the thing that changes the baseline relationship. Sites: step 4's title and Architecture's "Un-enrolled roadmap" bullet; step 2 (whose preflight is meant to share this same admission precedent); `plan_tool/roadmap_source_identity.py:canonical_projection`/`admit_baseline_backed_source`; `plan_tool/roadmap_feedback_reopen.py:_admitted_stage_source`/`publish_feedback_reopen_candidate`; `plan_tool/roadmap_escalation_run.py`'s matching admission call.
  - Fix: Revise step 4 (and step 2's shared preflight, if it reuses baseline admission) so the settlement write also refreshes the affected stage's `.roadmap-baselines` record alongside the artifact bytes, following the same multi-member generation pattern `publish_stage_artifact` already uses — or, if leaving the baseline untouched is meant to be safe, state at plan level why a permanently stale decisions-baseline is tolerable, since "no baseline... is rewritten" as written breaks every later baseline-admission check on that stage.
