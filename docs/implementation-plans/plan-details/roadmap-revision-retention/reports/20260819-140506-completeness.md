A reviewer who hand-edits a mid-list row's `state` to `closed` — the plan's own described closing move — leaves that row in its original position on disk until a later revision happens to run and the model re-emits the collection sorted; if no later revision ever runs, the row stays out of order indefinitely. The acceptance criteria state the ordering as an unconditional property ("renders after every non-`closed` row in the `feedback` collection"), but the plan names no route that fixes position on a reviewer's own edit.
  - Fix: state whether the ordering guarantee is scoped to "after the next revision" or specify a mechanical, render-time sort independent of the model — matching step 1's mechanical-snapshot precedent — so a reviewer's direct edit can't leave the artifact violating its own acceptance criterion.
- HIGH `[removal-record-persistence]`: `check_design_row_continuity` (`roadmap_gates.py:1211`, the removals loop at 1345-1399) only validates removals records that are *present* in the artifact under check against `carried = set(predecessor.removals)` (`roadmap_gates.py:1346`) — it never loops over `predecessor.removals` the way `check_feedback_integrity` loops over `predecessor.feedback` to catch a dropped row (`for prior in predecessor.feedback: if prior.id in present: continue; violations.append(VIOLATION_DROPPED_FEEDBACK...)`, `roadmap_gates.py:1476-1491`). The gate's own docstring says "the model may never drop a carried removal" (`roadmap_gates.py:1225-1226`) and `prompts/roadmap-revision.md:181-183` tells the model the same thing, but neither claim is backed by a check — a model that simply omits a carried removals record from its response passes every existing gate and everything step 1 adds. Before this plan that meant losing three already-thin fields; once step 1 (content snapshot) and step 2 (decision reference) ship, the same silent omission loses exactly the content this plan exists to retain, and the acceptance criteria only test *alteration* of a carried removal, never *deletion* of one, so nothing in Testing would catch it either.
  - Fix: add the missing property to the plan — a carried removals record must survive a revision the same way a carried feedback row must — and extend both the architecture commitment (step 1) and the acceptance/testing sections to cover a dropped, not just an altered, carried removal.
- MEDIUM `[mode-review-namespace-collision]`: `--mode review` names two unrelated CLI flags in this codebase: `roadmap --view … --mode {current,review}` (what step 6 means to rename) and the completely separate per-step audit primitive `run <name> --mode <review>` / `verify-all <name> --mode <m>` (`plan_tool/cli/__init__.py:44-45`, `README.md:1764-1771`), whose "review" is a placeholder for one of check/optimize/document/test/security/lint and has nothing to do with the roadmap arc. A literal-string sweep for the exact phrase `--mode review` happens to stay safe today (the unrelated flag is spelled `--mode <review>` / `--mode <m>`), but the step's own vocabulary doesn't state that distinction, so a reader following "everywhere it appears" has to independently notice the boundary the plan never names.
  - Fix: add one sentence to step 6 naming the unrelated `run`/`verify-all` review-mode audit flag as explicitly out of scope for this rename, so the sweep of the shared catalog docstring and README.md doesn't need to be inferred site-by-site.
- MEDIUM `[run-summary-closed-count]`: Step 5 asks to "count closed rows in both roadmap summary renderers," treating `_feedback_summary_lines` (`cli/roadmap_cmd.py`) and `_summary_feedback_counts`/`render_roadmap_summary` (`roadmap_view.py`) as symmetric fixes, but they aren't. `_summary_feedback_counts` already builds `{state: 0 for state in FeedbackState}` generically, so adding `CLOSED` to the enum needs no code change there — only the hardcoded three-part render string needs a fourth clause. `_feedback_summary_lines`, by contrast, reports a single pre-computed scalar, `result.feedback_awaiting_review` — `RoadmapResult` (`roadmap.py`) carries no per-state breakdown and no closed-row count at all; that field is populated by an `awaiting_review` accumulator at two separate call sites in `run_roadmap` (~line 1854 and ~1960), and no equivalent accumulator or dataclass field exists for closed rows. Step 5 doesn't name adding this field, and no acceptance criterion mentions the run/revision post-run summary reporting closed counts, so an implementer has no route to deliver that half of the step as written.
  - Fix: either add a `feedback_closed`-style field to `RoadmapResult`, populated the same way `feedback_awaiting_review` is at both call sites, so `_feedback_summary_lines` has real data to report, or narrow step 5's `_feedback_summary_lines` half to the "close by setting `state: closed`" text change only and drop the "count closed rows" claim for that renderer.
