- HIGH `[risk-proposal-before-publication]`: Architecture’s “Proposal plumbing precedent” says “The tier proposal follows the same shape” as `CreateResult(split_proposal=...)`, while step 3 requires the decision be saved “before the plan write.” At HEAD, `plan_tool/create.py:create_plan` returns a normal `CreateResult` only after `_publish_create_plan`, and `plan_tool/cli/authoring.py:cmd_create` handles `result.split_proposal` only after that return, so this handoff would publish an unreviewed normal plan.
  - Fix: Define a pre-publication risk-proposal and decision handoff that feeds step 3’s confirmed declaration into publication, leaving the existing split result as its no-write exit.
- MEDIUM `[counter-signal-tier]`: Architecture’s “Classification signals” says counter-signals force `standard`/`high`, but step 2 says counter-signaled results are forced to `standard`; Risks says only “at least `standard`,” Testing requires a feature-shaped seed to be `standard`, and Acceptance criteria requires only “never proposed `low`.” Named consumers, migrations, auth surfaces, and load-bearing seeds can therefore produce materially different stored tiers while satisfying the plan.
  - Fix: Choose one exact counter-signal tier rule and align Classification signals, step 2, Risks, Testing, and Acceptance criteria to it.
- MEDIUM `[distill-classification-branches]`: Architecture says seeds below `_DISTILL_SKIP_BELOW_BYTES` “skip distillation entirely,” and Testing frames parity as above and below a size gate. At HEAD, `plan_tool/create.py:_prepare_create_plan` skips only when `_canonical_seed_covers_all(...)` is true *and* the seed is below the threshold; `--no-distill` is another bypass, while small non-canonical seeds still run distill. The stated branch tests can therefore miss real classifier paths.
  - Fix: Describe the actual distill predicates and require classification parity for each seed-supplied path that bypasses distillation.
- MEDIUM `[standard-tier-declaration]`: Overview and Architecture’s “Persistence” require the accepted tier and rationale to be persisted, but `standard` is both the legacy meaning of an absent field and the required outcome for ambiguity, failure, and decline. Step 1, step 3, Testing, and Acceptance criteria never state whether a newly classified `standard` plan must write both fields; at HEAD, `plan_tool/parser.py:render_plan_text` and `write_plan` use `exclude_defaults=True`, so a default-valued tier can be omitted. That loses the fallback rationale and makes a new operator decision indistinguishable from a legacy plan.
  - Fix: State that only legacy omission means implicit standard and every new create, including fallback and decline, writes `standard` with an outcome-specific rationale and round-trip coverage.
- HIGH `[risk-decision-resume]`: Step 3 promises an operator-owned, resumable decision, and step 5 promises risk checkpoints retire only after publication, but Risks only requires caching the classifier result and Testing covers no accepted override or decline across a pre-publication failure. `docs/CREATE_RESUME_FLOW.md` confirms failed creates retain checkpoints; without restoring the final decision and rationale, resume can re-prompt or replace an override despite a cached classifier proposal.
  - Fix: Define and test that a pre-publication resume restores the exact accepted, overridden, or declined declaration and rationale without another classifier call or prompt, then retires it only after publication.
- HIGH `[non-tty-override]`: Architecture says non-TTY `-y` should “accept the proposed tier when the classifier is confident,” but Out of scope forbids “any path with no operator override,” while Scope contract allows no new user-visible behavior beyond the prompt and field. Testing’s `-y < /dev/null` path and Acceptance criteria’s non-TTY mode leave no declared way to override or decline before automatic acceptance; at HEAD, `plan_tool/create.py:_silent_input_fn` resolves prompts to defaults.
  - Fix: Choose whether headless default acceptance is itself operator authorization or provide an allowed nonblocking override/decline route, then define its precedence and run-log result.
- MEDIUM `[accepted-tier-rationale]`: Overview and Architecture > Persistence make the rationale explain the accepted tier, but step 3 permits override and decline without saying whether the stored rationale is the classifier’s proposal or the operator’s final reason. Testing covers declined tiers but not rationale meaning, so an overridden `high` can retain a deletion-shaped `low` rationale or discard useful proposal evidence with either reading appearing compliant.
  - Fix: Define the meaning and ownership of persisted and logged rationales for accept, override, and decline so the saved explanation always matches the final tier.
- MEDIUM `[risk-profile-frontmatter-shape]`: Overview defines `risk_profile: low | standard | high`, but Architecture > Persistence permits either `risk_profile_rationale` or “a structured sub-object — pick one at plan time”; Scope contract and Acceptance criteria depend on the scalar tier form. These are different public frontmatter contracts for `plan_tool/schema.py`, `plan_tool/parser.py`, `PLAN_FORMAT.md`, and future consumers.
  - Fix: choose one stable frontmatter shape and state its tier and rationale fields before step 1 implements validation and documentation.
- MEDIUM `[completion-summary-scope]`: Step 4 (`Show the saved risk tier in create's completion summary`) adds a user-visible completion change, but Architecture > Scope contract says Allowed behavior changes are “the new proposal prompt at create time and the new frontmatter field; nothing else user-visible.” The step cannot both ship and honor that scope fence.
  - Fix: either include the completion summary in the allowed behavior changes or remove step 4 from this plan.
