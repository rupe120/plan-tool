- HIGH `[relation-closure-semantics]`: Step 2 (`Add deterministic relation closure for one roadmap target`) and Architecture give each graph edge a direction but never define whether closure follows outgoing edges, incoming edges, or both, or how an `artifact` target expands to rows. `plan_tool/roadmap_escalation.py:ReceiptTarget` and `plan_tool/roadmap_escalation_selection.py:select_receipt_feedback` allow both `row` and `artifact` targets, while the route table and Acceptance criteria consume the resulting artifact count; compliant implementations can therefore classify the same receipt as `same-artifact` or `cross-artifact`.
  - Fix: define one closure root and traversal rule for both receipt target kinds, and use it consistently in Architecture, steps 1–2, step 5, route precedence, and acceptance tests.
- HIGH `[scope-review-trigger]`: Step 5 (`Define immutable impact analyses and route precedence`) promises `requires-scope-review` when evidence cannot establish a complete declared closure, but Architecture says the graph contains every gate-validated relation and step 2 returns a finite closure. A current gate-valid roadmap therefore has no stated condition that makes its declared closure incomplete, so implementations must either never emit this class or invent an evidence rule; this leaves the “reason becomes inferred scope” risk unresolved.
  - Fix: define the evidence-boundary predicate that proves a closure complete or requires scope review, including the recorded evidence and no-route result for each target and relation case.
- HIGH `[snapshot-gate-validation]`: Step 4 (`Capture and recheck one coherent roadmap and brief snapshot`) requires a coherent snapshot but never says that all four captured artifacts re-run their current staged gates before routing. `plan_tool.roadmap_escalation_selection.py:canonical_artifact_snapshot` checks parse/render canonicality only, while `plan_tool.roadmap.py:_load_and_regate_below` is the existing path that checks live cross-artifact relations; a hand-edited, render-canonical but gate-invalid roadmap could otherwise produce a route despite the Acceptance criterion that invalid roadmap inputs never route.
  - Fix: make full staged gate validation part of snapshot admission and freshness, with any violation producing `invalid` and no route.
- HIGH `[analysis-identity]`: Analysis identity is not defined end to end: Architecture’s record fields omit the selected receipt identity and an exact final-name/equality rule, while step 9 (`Wire exclusive impact analysis and log-free views`) must select one receipt even though `plan_tool.roadmap_evidence_store.py:scan_evidence` can return many. `publish_evidence` returns raw existing bytes for a final name, and `plan_tool.roadmap_escalation_run.py:current_escalation_receipt` only validates a specifically named receipt, so the design cannot reliably select, bind, reuse, or reject a substituted analysis.
  - Fix: define receipt selection, analysis identity, canonical equality, and collision handling so the persisted analysis binds one receipt plus its snapshot and closure evidence at every create and view path.
- MEDIUM `[no-route-workflow-field]`: Architecture says every analysis records a “next workflow name,” but the `invalid` and `requires-scope-review` rows have no workflow and explicitly require no route. Steps 5, 7, 8, 9, and 10 therefore leave open whether those records carry a name, a null value, or a printed operator command, weakening the no-route boundary.
  - Fix: define the closed workflow-field value and view/telemetry behavior for both no-route classes and reconcile it with the valid-class mappings.
- HIGH `[impact-mode-exclusivity]`: Step 9 (`Wire exclusive impact analysis and log-free views while preserving canonical, seed, receipt, local-revision, and broad write paths`) calls the mode exclusive but never defines its creation and inspection forms or its precedence beside `--from-stage`, seed actions, `--revise-feedback`, `--escalate-feedback`, `--view`, `--mode`, `--id`, `--from-existing`, and `-y`. `plan_tool.cli.roadmap_cmd:cmd_roadmap` dispatches several such modes, and its receipt paths use explicit conflict checks, so an impact option can otherwise be ignored or enter broad dispatch.
  - Fix: Define the exclusive impact-analysis create and view modes, their receipt selector, every rejected companion option, and the log/write behavior of each rejection.
- HIGH `[analysis-redaction-boundary]`: Relation evidence has no shared redaction rule across step 1 (`Extract typed roadmap relations`), step 5, step 7 (`Add redacted impact-analysis telemetry`), and step 9 views. Architecture requires stored “relation evidence,” while Testing forbids reviewer prose and artifact contents; `plan_tool.roadmap_artifacts:_row_id` accepts any non-empty string, whereas only the selected receipt uses `plan_tool.roadmap_feedback:is_receipt_safe_id`. A valid related row identifier can therefore persist or print reviewer-controlled text.
  - Fix: Define one allowed field and identifier boundary for analysis records, telemetry, and views, with invalid or unsafe relation evidence producing a no-route result.
- MEDIUM `[analysis-telemetry-contract]`: Step 7 (`Add redacted impact-analysis telemetry while preserving run-log appends, active-snapshot replacement, and guarded cleanup`) promises observable admission, publication, reuse, and failure but defines no closed events, facts, outcomes, nullability, or publication order when logging fails or is interrupted. `plan_tool.run_log:RoadmapEscalationPreflight` and `RoadmapEscalationResult` show that the existing receipt lifecycle needs those facts to be explicit; otherwise a durable analysis can exist without its promised lifecycle record or a failed preflight can publish evidence.
  - Fix: Define a closed redacted analysis lifecycle, including event facts and terminal outcomes, and state telemetry-failure and interruption behavior before and after immutable publication.
- HIGH `[receipt-snapshot-binding]`: Architecture first revalidates a current receipt and separately says the runner captures a guarded snapshot; steps 4 (`Capture and recheck one coherent roadmap and brief snapshot`), 5, and 8, the mixed-evidence Risk, Testing, and acceptance criteria 1 and 3 never require the receipt’s selected source, digest, and selection predicate to use the exact captured snapshot that feeds closure. `roadmap_escalation_run:current_escalation_receipt` currently reads its source separately, so validating before capture can bind a receipt to one revision and analyze another.
  - Fix: make the captured selected-artifact bytes the sole input to receipt revalidation and closure, then recheck that same binding immediately before publication.
- MEDIUM `[invalid-analysis-lifecycle]`: Architecture says malformed inputs “produce an `invalid` analysis” but also that invalid input produces “no partial readable analysis”; the route table, steps 5, 6, 8, and 9, Testing, and acceptance criterion 3 never choose whether invalid admission writes a complete immutable record or returns only a transient result. `roadmap_escalation_run:run_roadmap_escalation_receipt` currently publishes evidence only after accepted selection, so no existing lifecycle settles this choice.
  - Fix: define which invalid verdicts are durable records versus transient command results, including their identity, permitted fields, view status, telemetry, and cleanup behavior.
- MEDIUM `[recorded-brief-byte-snapshot]`: Step 3 (`Extract recorded-brief readers and preserve source.json replacement`) promises the same recorded brief “path and bytes” as broad execution, but `roadmap.py:_read_brief` uses `Path.read_text` and `_artifact_digest` hashes re-encoded text rather than raw file bytes. Architecture’s brief digest, step 4’s brief-content snapshot, Testing’s changed-brief cases, and acceptance criteria 1 and 3 therefore leave raw-byte versus broad-reader freshness inconsistent, including for newline conversion.
  - Fix: define the snapshot as the same decoded text and digest broad execution uses, and name it consistently rather than claiming unsupported byte equivalence.
