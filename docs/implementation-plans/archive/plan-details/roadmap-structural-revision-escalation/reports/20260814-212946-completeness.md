- MEDIUM `[creation-preflight-precedence]`: Step 2 (`Define strict receipt selection, canonicality, and reason capture`) and step 5 (`Wire exclusive escalation creation and log-free receipt views`) require exactly one preflight/terminal pair, but Architecture gives no precedence when one command has several failures—for example, a malformed selector and invalid reason, or either alongside a mode conflict. - MEDIUM `[receipt-temp-layout]`: Step 4’s storage contract says the ``escalations`` directory “contains only regular receipt files whose names are valid semantic ids,” but its publication contract writes a “private sibling temporary file”; step 5’s ``--view escalations`` then examines that same storage. A temp beside the final receipt breaks the stated directory invariant and leaves views without a rule for concurrent or crash-left staging files; placing it elsewhere is not specified.
  - Fix: place temporary payloads in a separate confined staging location, define cleanup and durability for them, and make views enumerate only final semantic-id receipt files.
- HIGH `[receipt-source-binding]`: Architecture’s “valid receipt row,” receipt-schema, and view paragraphs establish target facts at creation but require reuse and display to validate only schema, semantic id, stored path, and selected feedback identity/state; steps 2–5, Testing’s target/freshness cases, and acceptance criteria 1 and 4 never require the stored `target_kind` and `target_id` to match the target re-derived from the selected source. A self-consistent receipt can therefore show a wrong target and still hand off despite `plan_tool.roadmap_artifacts:FeedbackTarget` defining that target separately as kind plus row id.
  - Fix: Require reuse and views to re-derive and compare the selected feedback’s target kind and stable target id before classifying a receipt as valid or handing it off.
