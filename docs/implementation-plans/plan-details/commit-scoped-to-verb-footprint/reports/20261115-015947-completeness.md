- MEDIUM `[footprint-entry-absent-or-unchanged]` [confidence: limited]: Step 1 (`commit_all` takes a required `paths` argument) does not say what happens to a footprint entry that does not exist on disk or has no change. Several footprints name such entries. These include `.plan-tool/lessons/` files in steps 2 and 3, a `plan-details/<slug>/` directory before any detail is written, and a run that changes none of the listed paths. The code at HEAD shows why this matters:
  - `git add -A -- <path>` and `git commit -- <path>` fail with "pathspec did not match any file(s) known to git" for a path that is neither on disk nor tracked.
  - `git commit -- <paths>` exits non-zero with "nothing to commit" when no listed path has a change.
  - The old `_commit_green_step` (`plan_tool/cli/run_cmd.py`) filtered `p.exists()` before staging.

  Step 1 only specifies the gitignored-path skip, so implementers could read the missing-path case differently: fail the commit, skip silently, or warn. A routine run could then fail its commit even though nothing is wrong. The same ambiguity applies to the callers in steps 2, 3, 4 and 5, and to the post-commit clean check.
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): The commit helper must have one defined result for a footprint entry that is absent or unchanged, so a normal run's commit neither fails nor hides a real under-staging.
  - Fix: Define in step 1 how an entry that is absent from disk and untracked, or unchanged, is treated by staging, committing and the post-commit check. Keep a deleted but tracked path (the step 4 `plan_path`) staged. Add a unit test for each case.
- MEDIUM `[run-footprint-vs-acceptance]` [confidence: limited]: The acceptance criteria overclaim for `run --commit`.
  - Acceptance criterion: "No `--commit` surface commits a path outside its verb's footprint; the unrelated-dirty-file test passes on every converted surface."
  - Step 5 defines the run footprint as "the paths changed since a baseline taken just before `run_step`". It admits that "a file another process writes during the backend call is still indistinguishable from the step's own work".

  The criterion therefore cannot hold for `run` against the dirt that motivated the plan, and a reader could mark the plan done or not done on it either way.

  A second gap sits in step 5. `changed_paths_or_none` returns only a set of paths, with no content. A file that was already dirty before the baseline and that the step then edits is excluded from the delta. The step's real edit stays uncommitted, and the post-commit check cannot see it because that path is not in the footprint. Step 5 says "dirt from before the baseline is excluded" but does not say how this overlap case is reported or tested.
  - Fix: Narrow the acceptance criterion to say that for `run` the unrelated-dirty-file guarantee covers dirt present before the step's baseline, with the concurrent-write residual named. In step 5, state the overlap case (pre-dirty file edited by the step) as an explicit outcome with a test. For example, warn that the path was excluded as pre-existing dirt.
