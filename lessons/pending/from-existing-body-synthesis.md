## General

- `[create-heuristic]` **Prompt-file-only steps are M-complexity contract artifacts, not S or 'unknown' — they encode design decisions (placeholder set, output shape, worked examples, retry vocabulary) that 4+ downstream steps cite. The detail must lock those decisions in the prompt body, not defer to the implementing step.** — Treating a 'just write a prompt' step as trivial under-budgets the detail and produces ad-hoc prompts that drift from sibling prompts. The prompt's contract (placeholders, JSON shape, repair shape) is consumed by Python helpers, parsers, and tests in later steps — getting it wrong cascades. _(when: when a step's only file is a new prompt/template/contract artifact (e.g. under prompts/, schemas/, fixtures/) consumed by Python or other code in later steps)_ _(e.g. Step 1 here produced one prompt file but the detail enumerated: 3 placeholder names, 8 JSON keys, 2 worked-example shapes, repair-block reuse from reformat.md, and explicit lessons-trailer absence. Create-time complexity rating should be M, not S/unknown.)_
- `[detail-authoring]` **For doc-only or prompt-only steps where no pytest runs, write acceptance criteria as `git grep` invariants on file contents: placeholder set present, literal contract strings present, forbidden tokens absent, key inclusion/exclusion counts. Avoid narrative criteria like 'the prompt is well-formed'.** — Narrative criteria are unverifiable and the reviewer has to re-read the file from scratch. Grep invariants give a binary signal and are cheap to run after edits to confirm the contract held during iteration. _(when: when a step produces only documentation, prompt, schema, or template files and the Tests section would otherwise have nothing to assert)_ _(e.g. Step 1's acceptance criteria included: `git grep -nE '\$\{' <file>` returns exactly the 3 declared placeholders; the file contains the literal `Respond with **ONLY** a single JSON object`; zero occurrences of `Steps":` or `References":` as JSON keys.)_
- `[detail-authoring]` **When a new artifact lives in a directory of similar artifacts (prompts, helper modules, schema files, fixtures), the detail must cite the closest sibling by file:line as the structural template — not re-derive shape from prose. Generalizes the sibling-plan-detail-folder rule to any artifact directory.** — Conventions in this kind of directory are implicit, not documented. Forcing the detail to name a sibling pins the convention and surfaces drift early. Without this, every new artifact picks its own shape and the directory accretes inconsistency. _(when: when the new file's parent directory already contains ≥1 file of the same kind (prompt, parser, fixture, schema) — never introduce a new shape when a sibling shape exists)_ _(e.g. Step 1 cited `prompts/reformat.md` as the template for placeholder shape, repair-block shape, and constraints-section shape, and named `_parse_references_json` as the parser template for the helper added in step 2.)_
- `[cross-step]` **When a new step adds code (helper, parser, renderer) parallel to an existing piece of code, the detail must name the existing piece by file:line as the implementation template — this is the create-side of the sibling-template rule. Detail should not just describe the new helper's behavior abstractly when a concrete sibling exists.** — Downstream steps implementing the helper need a concrete model to mirror, not an abstract spec. Citing the sibling by file:line removes ambiguity about naming, signature, error handling, and checkpoint plumbing. The cross-step handoff is tighter when both sides reference the same template. _(when: when create proposes a new function/helper whose role mirrors an existing function in the same module (same naming pattern, same role in the call graph))_ _(e.g. Step 1's Deferred section named `propose_references_from_claude` (step 2 owner) and `_parse_references_json` (parser template) so step 2's implementation has a concrete model rather than re-deriving shape from the plan body.)_
- `[domain-shape]` **For prompts that need to enumerate a data structure already defined in code, template the enumeration in via a `${...}` placeholder rather than duplicating the list inline in markdown. Two sources of truth — Python constant and prompt body — drift silently.** — Inlining the list in the prompt body locks the prompt against the data structure at write time and produces a synchronization burden every time the structure changes. A templated catalog lets the caller derive the enumeration deterministically and lets the lint rule 'every entry appears in the prompt' be a Python-only check. _(when: when designing a prompt that needs to list / enumerate items that already exist as a Python constant, enum, or dict in the consuming code)_ _(e.g. Step 1's prompt uses `${section_shapes_block}` to template the catalog of canonical sections rather than inlining `PLAN_BODY_SECTION_SHAPES` — step 2's caller builds the block from the Python constant, so the prompt stays in sync automatically.)_

- `[cross-step]` **When a wiring step pairs with an immediately-downstream layering refactor (same observable behavior, different code seams), the detail must declare an observable-equivalence contract — one sentence stating that step N+1's diff is a refactor, not a behavior change, and why the split exists.
