- HIGH `[checkpoint-last-written-sync]` [confidence: limited]: Step 2 says to "update the last-written bytes after each stage publish and each source.json write," but a stage publish's commit (`publish_stage_artifact` → `publish_roadmap_generation` in `plan_tool/roadmap_revision_publish.py`) and the checkpoint's own bookkeeping update are two separate writes with nothing tying them together, so an ordinary crash or operator interrupt landing between them leaves the checkpoint's last-tracked bytes stale while the file on disk already holds the new, fully-committed value. `recover_roadmap_publication` already recognizes and accepts exactly this case:

  ```
  states = [_member_state(root / member.relative_path) for member in generation.members]
  old = [member.old_bytes for member in generation.members]
  new = [member.new_bytes for member in generation.members]
  if states == new or states == old:
      journal_path.unlink(missing_ok=True)
      return
  ```

  (`roadmap_revision_publish.py:388-393`): when the publish fully committed before the crash, it just deletes the leftover journal and returns, touching nothing else. On a later failed run, restore's own case matrix (Architecture, "Restore case matrix") then sees a file that matches neither the stale last-tracked value nor the pre-run value, and falls into "Anything else: refuse — the roadmap changed since the failed run" — even though nothing outside the tool touched it; the run's own successful, committed progress is what changed it. This can defeat the plan's own acceptance criterion ("one explicit, confirmed command restores every inventory file... from before the first consecutive failed run") in exactly the ordinary crash/interrupt scenario the plan exists to handle — the Integration incident this plan cites was itself an interrupted retry, not an outside edit.
  - Fix: State that the checkpoint's last-written bytes must reflect each tracked file's true committed state after `recover_roadmap_publication` runs, not only after this run's own stage-loop publishes and source.json writes, so a dangling-but-already-fully-committed generation left by an earlier crash keeps the checkpoint in sync instead of going stale.
- MEDIUM `[restore-hint-on-incomplete-run]` [confidence: limited]: Step 5 promises the restore command is named "in the closing message of every stage run that did not complete (invalid, exhausted, interrupted, or stopped by an error after a write) whenever a checkpoint exists," but at HEAD these four situations surface through three different, disconnected code paths in `plan_tool/cli/roadmap_cmd.py:cmd_roadmap`, and two of them have no closing-message machinery to hook into today. "Invalid" and "exhausted" produce a `RoadmapResult` that flows through `_print_invalid`/`_print_exhausted`/`emit_roadmap_terminal_status` (lines 636-661). "Stopped by an error after a write" — for example the `OSError`→`RoadmapEnvironmentalError` raised out of `_write_brief_source` right after a stage publishes, or any `RoadmapWriterGuardError` — instead raises an exception caught at lines 628-633, which only does `error(str(exc)); return _RC_INCOMPLETE`: no result object, no detail lines. "Interrupted" is caught separately at lines 663-665 (`except KeyboardInterrupt: error("interrupted"); return 130`), which today prints nothing but that one word. The plan does not say which of these three surfaces gains the checkpoint-existence check and the restore-command line, so two of the four named categories risk shipping with no reminder at all, undercutting the seed's own "In scope" line that "the closing message of a run that did not complete names it."
  - Fix: Say which layer — the CLI's plain exception-handling branches, the `KeyboardInterrupt` handler, or a change to what `run_roadmap` returns/raises so every incomplete run reaches one shared closing-message path — is responsible for checking checkpoint existence and printing the restore command for the "stopped by an error after a write" and "interrupted" categories, not only for the `RoadmapResult`-based "invalid"/"exhausted" categories.
- HIGH `[checkpoint-precedes-recovery]` [confidence: limited]: Step 2 says `run_roadmap` takes the checkpoint "right before its first write (including a confirmed brief rebind of source.json)," but at HEAD a confirmed brief rebind (the `_write_brief_source` call gated by `confirm_brief_rebind` in `plan_tool/roadmap.py:_run_roadmap`) runs *before* `recover_roadmap_publication` is called later in the same function. If an earlier, unrelated crash left a stage-publication journal half-applied from a previous stage publish, that journal has not yet been rolled back to its old bytes at the point this ordering would capture the checkpoint, so the checkpoint's "pre-run bytes" would record whatever transient, partially-replaced state happens to be on disk at that moment instead of the roadmap's actual last-stable state. The plan's own Architecture section requires the opposite ordering for restore ("Restore holds the writer lock and runs recover_roadmap_publication first ... so any half-written stage publish resolves before restore reads anything") but never applies that same reasoning to when `run_roadmap` takes its own checkpoint snapshot. A later restore replayed against that checkpoint would publish back bytes that never stably existed, instead of the state the roadmap was actually at before the revision started.
  - Fix: Specify that `run_roadmap` resolves any pending publication recovery (`recover_roadmap_publication`) before it captures the checkpoint's pre-run bytes, so the checkpoint's baseline is always the last fully-committed state rather than a possibly half-written one — and only then perform this run's own first write, including a confirmed brief rebind.
- HIGH `[cross-run-hand-edit-absorption]` [confidence: limited]: The Risks section states that "Restoring after another change would silently discard that work. The change check (last-tracked bytes) and the "anything else" refusal exist to prevent it," but Architecture's own design for spanning a checkpoint across consecutive failed runs — "a run that starts while an earlier failed run's checkpoint exists keeps that checkpoint, and its pre-run bytes stay those of the first failed run. The new run continues tracking what it writes" — describes the exact mechanism that defeats that guarantee. A later run in the same checkpoint lineage overwrites the checkpoint's last-written value for whatever file it touches, with no check that the file's current on-disk bytes still equal what the checkpoint last recorded before that run started writing to it. Concretely: run 1 fails after publishing stage 1 only, leaving checkpoint state pre_run[X]=P, last_written[X]=P for an untouched file X. Between run 1 and run 2, X is hand-edited to H. Run 2 starts (keeping the same checkpoint per Architecture), and its own stage work happens to also revise X — reading the current disk value H as input and writing a new value H′ — then run 2 fails too. The checkpoint's last_written[X] is now H′, with no trace H ever existed. An operator invoking restore finds X on disk equal to last_written[X]=H′, matches the "Files equal the run's last-tracked bytes" row of the restore matrix, and restore reverts X to the original pre_run bytes P — silently discarding both the hand edit and run 2's own work. This is precisely the scenario the Risks entry says the change check exists to prevent, in a case the described mechanism does not actually catch. It is the unaddressed complement of the Risks section's third entry, which only considers the checkpoint's tracked bytes falling *behind* reality (causing false refusals), not a later run *absorbing* an intervening independent change into its own tracked state (causing a false, silent accept).
  - Fix: Specify that before a run within an existing checkpoint's lineage writes to any inventory file, it confirms the file's current on-disk bytes still equal the checkpoint's own last-tracked value for that file, and treat a mismatch as an intervening change to handle explicitly rather than silently folding it into that run's own last-written record — covering Architecture's cross-run tracking description, step 2's update rule, and the Risks entry on restoring after another change.
