  - Fix: state, for step 9, whether `check_draft_seed_bundle_alignment` is dropped from `PLANS_GATES` or replaced by a version that accepts a partial bundle, and whether `_mark_roadmap_seeds_current` and every other reader of the sidecar's raw `status` field (at least `has_invalidated_seed`) is changed to mark `"current"` only the plan rows that actually got a body this run — cover both the gate and the write-time bookkeeping together, not just one.
- HIGH `[refresh-partial-failure-continuation]`: Step 4 ("Make explicit seed refresh generate each plan's seed independently") says this "lets an explicit refresh retry or partially complete instead of failing every seed when only one plan's generation goes wrong," but never picks which of those outcomes actually happens. Today `refresh_roadmap_seeds` (`plan_tool/roadmap.py`) makes one backend call covering every plan and reports one of exactly two outcomes, `SEED_REFRESH_OUTCOME_APPLIED` or `SEED_REFRESH_OUTCOME_EXHAUSTED` — there is no partial state. Once refresh makes one call per plan, the plan needs to say what happens when plan B's call fails right after plan A's succeeded: stop the whole run and report exhausted (throwing away A's good result), skip B and keep going through the rest (leaving B `invalidated` for later), or retry B some bounded number of times before moving on — the choice decides both the reported outcome and whether "partially complete" is actually true.
  - Fix: add a plan-level decision (and a matching acceptance criterion) naming the per-plan-failure continuation policy for `--refresh-seeds` — continue past a failed plan and report which plans landed versus which stayed invalidated, rather than aborting the whole run on the first failure — and say what a partial run reports to the operator.
- MEDIUM `[step7-live-check-behavior-change]`: Step 7 ("Route the roadmap view's seed summary through the new manifest module") calls itself "a pure routing refactor — the summary's visible output is unchanged," and the plan's Testing section classifies it `refactor`. But today's `summarize_seed_lifecycle` (`plan_tool/roadmap_view.py`) sorts a plan into "current" or "invalidated" by trusting the sidecar's stored `status` field alone, with no check that the file on disk actually exists or matches — while step 3's classifier is explicitly built to add "a live file/row check" on top of that stored value (Architecture). Routing the summary through step 3 therefore does change what an operator sees: a draft that is missing, hand-edited, or otherwise drifted but whose sidecar still says `status: current` shows as "current" today and would show as "invalidated" once step 7 lands — exactly the class of problem this plan exists to catch, not a side effect step 7 can call unchanged.
  - Fix: drop the "output is unchanged" framing and the `refactor` label from step 7, and say plainly that switching the summary's data source to a live-checked classification is the moment previously-mistracked drift becomes visible, so it gets scoped and tested as the behavior change it is.
