The plan's own measured case — 23 findings hand-closed across completeness-audit rounds 2–4, before the plan was ever run — has no `run-reconcile` sidecars in between those rounds, so none of those findings can ever pair with an outcome under the current algorithm, no matter what hand-resolution events step 4 records.
  - Fix: state in step 5 that `analyze_finding_drift` needs a new path where a finding recorded as hand-resolved counts as "cleared" on its own, without waiting for a matching run-reconcile sidecar, and update the acceptance criterion and step 8's fixture goal to match — both currently assume the existing run-reconcile-only pairing already delivers this.
- MEDIUM `[recurring-regions-scope-widening]`: Step 6's "scope widening" tells the implementer to widen the check `recurring_regions` uses to admit findings, and only rules out touching one specific name: the `STRUCTURAL_SOURCES` constant in review.py. But the check actually used at that call site is the function `is_structural_source` in convergence_diagnosis.py, and that same function is called directly by `telemetry_analysis._sidecar_outcome` to resolve `escalate-split`/`code-reveals-split` decisions — the exact consumer the plan's own Testing section says must keep matching by step focus after this change. Widening `is_structural_source` itself, the plain reading of "widen the filter" once only the other name is called off-limits, would quietly widen `_sidecar_outcome` too.
  - Fix: name `is_structural_source` itself as off-limits in step 6, alongside `STRUCTURAL_SOURCES`, and specify that the wider admit-check is a new, separate condition inside `recurring_regions`, not a change to the shared function.
- HIGH `[region-closure-hand-resolution]`: Step 7's hand-resolution-based region closure can never change a convergence verdict: `RegionTrend.closed` (convergence_diagnosis.py) is read in exactly one place, `_region_spins`, and that check first requires `latest_run_index in trend.run_indices` via `_recurs_in_window` — the region must appear in the *current* audit run before `closed` is even consulted. A hand-resolved finding is by definition missing from the current run (that absence is exactly what step 3's diff detects), so its region already fails this presence check and is excluded from spinning whether or not `closed` is ever set — marking it closed is a no-op. The step also cites the wrong existing mechanism as precedent: it says closure works "the same way an `Annotation`-resolved finding already does in `_is_resolved_in_run`," but `_freeze_region` (where `closed` is actually computed) never calls `_is_resolved_in_run` — that function only feeds the separate `_latest_blocking_findings`/`_open_medium_plus` advisories; `_freeze_region` computes `closed` inline from `_is_decline_close` plus its own "every match in the region's last occupied run was applied" check. As written, the acceptance criterion "each is tracked, and closes, independently" can never be exercised by a test, since the presence-in-latest-run rule step 6 already relies on gives each split-off finding independent, hand-resolution-blind closure for free.
  - Fix: require step 7 to demonstrate a concrete before/after case where `_region_spins`'s verdict actually changes because of a hand-resolution event; since the gating above shows none exists, fold its acceptance criterion into step 6 (independent closure already falls out of the id-primary split) and drop step 7 as a separate step, adjusting the step count and the "closes independently" criterion accordingly.
- HIGH `[prior-sidecar-kind-filter]`: Step 4 (Record inferred hand-resolutions when a completeness audit saves its sidecar) finds "the immediately prior saved completeness sidecar" via `review_persistence.list_saved_reviews(...)`, newest-first, skip the one about to be written" — but `list_saved_reviews` returns every saved sidecar for the plan regardless of kind (`review`, `detail-reconcile`, `run-reconcile`, `completeness` all share one reports directory, per `plan_reports_dir`/DATA_CONTRACT.md's `kind` field), and the design applies no `kind == "completeness"` filter before taking the next entry. Whenever a `detail-reconcile`/`run-reconcile`/plain `review` sidecar lands between two completeness audits — normal sequencing in this repo's own detail→run→completeness-audit workflow — "skip one, take the next" hands step 3's diff a non-completeness sidecar whose `recommendations` carry no `plan-correctness`/`plan-completeness` findings at all, so every id that actually resolved across the true prior completeness audit is silently missed and never recorded as a `hand-resolution`. The plan does specify checkpoint exclusion (`is_pre_apply_checkpoint`) but stops short of the kind filter, even though `completeness_report.is_reusable_audit_sidecar` — cited elsewhere in this same plan for its checkpoint half — already implements the exact predicate needed (`saved.kind == "completeness" and saved.is_pre_apply_checkpoint is False`).
  - Fix: specify that step 4's prior-sidecar lookup filters `list_saved_reviews`'s results to `kind == "completeness"` in addition to the existing checkpoint exclusion — mirroring `is_reusable_audit_sidecar`'s full predicate, not just its checkpoint half — and add a test case with a non-completeness sidecar interleaved between two completeness saves.
