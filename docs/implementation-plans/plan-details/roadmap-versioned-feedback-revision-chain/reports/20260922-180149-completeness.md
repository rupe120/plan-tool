  ```
  “A batch item may move from `open` to `awaiting-review` only through the existing model-response integrity rule and under the same guarded operation that stores candidate evidence.”
  ```

  but also says

  ```
  “Failed, rejected, interrupted, or unpromoted candidates leave both the ledger and accepted head unchanged.”
  ```

  Steps 4 (`Build feedback-free successor artifacts and a response patch limited to the admitted batch`) and 5 (`Store the candidate and batch responses together...`) require a stored candidate to update its batch items before review or promotion, while Testing requires that response transition. Define what happens to batch items when review rejects or otherwise resolves an unpromoted candidate; otherwise an implementation must either violate the unchanged-ledger guarantee or leave a stored batch permanently unresolved.
  - Fix: Define one complete batch-item lifecycle that distinguishes pre-storage failures from successful admission, review rejection, explicit resolution, and promotion, and reconcile the Architecture, steps 4–5, and Testing to it.
- MEDIUM `[empty-batch-outcome]` [confidence: limited]: Step 3 (`Build one ordered accepted-head batch from every eligible open ledger item`) leaves the zero-eligible-item result unclear. The Acceptance criterion says:

  ```
  “No eligible item returns a deterministic non-writing no-work result without a backend call, candidate, admission, ledger mutation, or head change.”
  ```

  but no section clearly states whether this means “when no eligible items exist, return no-work” or instead describes behavior of an individual item. Those readings differ on whether an empty batch may invoke the backend or create candidate state.
  - Fix: State that a selector-free run with zero eligible items returns the exact deterministic non-writing no-work outcome, and make step 3 and its tests use that condition.
