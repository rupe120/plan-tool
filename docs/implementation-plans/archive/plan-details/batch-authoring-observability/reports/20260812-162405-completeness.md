- HIGH `[batch-interrupt-safety-regression]`: Step 5 ("Run batch claude calls through the shared runner instead of subprocess.run") switches batch calls onto `_run_streaming_once` before step 7 ("Record a Ctrl-C as an interrupt and reap the child for roadmap and run") gives that runner any interrupt handling. Today `claude_invoke` runs through `shell.py`'s `_run_once`, which calls `subprocess.run(...)` — and CPython's `subprocess.run` wraps the child in a bare `except:` that calls `process.kill()` on any exception, including `KeyboardInterrupt`, so a Ctrl-C during a `roadmap` stage call today does not orphan the `claude` child. `launcher.py`'s `_run_streaming_once`, the runner step 5 moves batch calls onto, has no equivalent: its `finally` block only calls `stop.set()` to stop the heartbeat thread, never `proc.terminate()`/`proc.kill()` (confirmed by reading `_run_streaming_once`, lines ~941-967). If step 5 lands and is committed on its own — this repo's own convention is a commit per green step, and each step is meant to be independently reviewable — before step 7's handling exists, an operator's Ctrl-C during a batch call newly orphans the `claude` child: a regression from today's behavior, in the exact plan whose purpose is removing orphan-child hazards.
  - Fix: state in the Architecture's ordering constraint that step 5 must not ship standalone ahead of step 7's interrupt-safety, or fold a baseline kill-on-any-exception into the shared runner during its step 2/3 extraction so batch callers never lose today's protection even transiently, and pin this with an acceptance criterion.
- CRITICAL `[transcript-redaction-gap]`: The Testing section requires "a known secret fixture never reaches JSONL, verbose terminal output, or an opt-in transcript," but no step gives the raw-transcript writer (step 10, "Save a raw NDJSON transcript only when a call fails or stalls") the redaction step 9 builds. In `launcher.py`'s `_run_streaming_once`, `raw_stdout_lines.append(line)` captures every stdout line verbatim, before the line is parsed or summarized; the sibling transcript file (added by step 10) is written straight from that list. Step 9 ("Redact tool-input summaries in all three backend parsers") only changes the derived `tool_input_summary` field the parsers build for the `ClaudeStreamEvent` payload — a separate, later stage of the same pump that the raw-line capture never passes through. Redacting the summary does nothing to a Bash command or file path carrying a secret that's sitting in the raw JSON line step 10 persists to disk, which directly conflicts with the plan's own Acceptance Criteria line "No change weakens existing prompt, credential, artifact, or run-log size/atomicity protections."
  - Fix: give step 10 its own explicit requirement to scrub the same sensitive content from each raw line before it's written to the transcript file (or otherwise state how the transcript stays consistent with the credential-protection acceptance criterion), rather than assuming step 9's parser-level redaction already covers it.
- HIGH `[step1-non-code-misclassification]`: Step 1 ("Pin today's batch-call logging and timeout behavior with tests") is classified `non-code` in the Testing section's per-step table ("step 1 (non-code) — verification appropriate to the artifacts rather than unit tests"), even though its entire deliverable is a characterization test suite. Per `PLAN_FORMAT.md` and `launcher.py`'s `_step_requires_test_authoring`, a `non-code` step never gets the run prompt's "add or update tests" directive and is never gated on a test file actually appearing in the commit — the gate only fires for `feature`/`refactor` steps. Classifying step 1 `non-code` means the tool won't prompt for or enforce the tests this step exists to write, undermining the Architecture's own ordering rule that this step "characterize[s] today's start/end-only behavior in tests before touching anything" — the regression net the rest of the plan leans on.
  - Fix: reclassify step 1 as `feature` (or `refactor`, whichever the authoring stage settles on) so the run-time test directive and the test-authoring gate actually apply, and correct the Testing table's step 1 row to match.
- HIGH `[in-flight-same-slug-clobber]`: `in_flight_path(repo_root, slug)` in `run_log.py` names exactly one snapshot file per plan slug, and its own docstring says: "One snapshot per slug — last writer wins... Callers re-running `plan-tool` against the same plan overwrite this file; that's acceptable." Step 8 ("Keep in-flight.json current for the whole life of a call") builds directly on this file, but the plan's Testing section requires proving "concurrent runs don't clobber each other's snapshot/log state." If an operator re-runs `roadmap` against the same slug while an earlier call is still alive — exactly the "is it alive or dead?" situation this whole feature exists to answer — the second call's snapshot silently overwrites the first's, and the still-running call vanishes from `runs show`. The plan never says whether step 8 keeps this shared-file, last-writer-wins design (in which case the testing claim should say "distinct slugs," not "concurrent runs") or gives concurrent same-slug calls separate visibility.
  - Fix: decide whether in-flight.json keeps its one-file-per-slug, last-writer-wins contract (and narrow the "concurrent runs" testing claim to distinct slugs) or gives each concurrent same-slug call its own snapshot identity, and update step 8's design and the Testing claim to match whichever is chosen.
- MEDIUM `[transcript-capture-flag-wording]`: Architecture says raw NDJSON transcript capture "fires automatically when a call fails or stalls — not gated behind an operator flag set before invocation," but the ordering-constraint list two paragraphs later says to "land redaction before any transcript-capture flag ships" — wording that implies a flag exists. A reader implementing step 10 could reasonably wonder whether an operator flag (e.g. `--capture-transcript`) is expected after all.
  - Fix: reword the ordering constraint to "before transcript capture ships" (drop "flag") so it doesn't collide with the explicit no-operator-flag decision stated just above it.
- CRITICAL `[batch-streamevent-redaction-ordering]`: Step 6 ("Widen the active shell sink so batch calls record spawn, progress, stall and termination") is what first lets a batch call's stream events reach the JSONL run log. `_summarize_tool_input` in `plan_tool/backend.py` builds `tool_input_summary` today with zero redaction — a `Bash` tool's raw `command` string, or a raw JSON dump of any other tool's input — and that same function feeds all three parsers this plan wires into the widened sink. Step 9 ("Redact tool-input summaries in all three backend parsers") lands after step 6, and the Architecture's own explicit ordering-constraint list names five sequencing rules, including "land redaction before any transcript-capture flag ships," but never requires redaction before stream events start reaching the run log. Testing's bar — "a known secret fixture never reaches JSONL" — is broken by design for the window between step 6 and step 9: unlike the already-flagged raw-transcript gap (step 10, opt-in and failure/stall-only), this exposes every batch caller's tool input, unredacted, in the always-on log.
  - Fix: add a sixth ordering constraint sequencing step 9 before step 6, or fold the minimal `tool_input_summary` redaction into step 6 itself, so no batch caller ever writes an unredacted summary to the run log.
- HIGH `[shell-sink-contract-widening]`: Step 6 needs `claude_invoke` to build a richer observer "from the ContextVar-based active sink... widened to carry more than the current `ClaudeCallEnd`-only contract" (Architecture, "Observer wiring"), but `shell._emit_call_end` calls the installed sink as a bare one-argument `sink(event)` today, and roughly two dozen production and test sites install a plain single-argument function directly against that exact shape — `run_log.py`'s `bind_shell_sink`/`install_call_end_sink`, plus `shell.set_active_sink(recorded.append)`-style calls across `tests/test_shell.py`, `tests/test_run_log.py`, `tests/test_create.py`, and `tests/test_launcher.py`. The plan doesn't say whether the sink's type itself changes shape (breaking every one of those call sites) or whether the new spawn/progress/stall/termination events ride a separate channel that leaves today's single-callable contract untouched.
  - Fix: state which of the two the widening means, and if the contract itself changes, name updating every direct `MetaSink` installer and test call site — not just `run_log.py`'s two helper methods — as part of step 6's scope.
- MEDIUM `[scoped-threshold-vs-configurable-fence]`: The universal-silence-kill Risk says a legitimate long-burst caller found during characterization should have its "scoped threshold" raised, but Out of scope and Deferred both name "per-command silence/stall thresholds configurable" as excluded. The plan never says whether "scoped threshold" means a code-level override a developer sets for one caller (the existing `scoped_claude_timeout` context-manager pattern in `shell.py` is the closest precedent) or an operator-facing setting — which is exactly what the fence forbids. Read one way, the Risk's own mitigation is out of scope; read the other way, the Risk is left with no real mitigation.
  - Fix: state explicitly that "scoped threshold" means a developer-set, code-level override (not an operator flag/env var), matching the `scoped_claude_timeout` precedent, so the Risk's mitigation and the scope fence agree.
