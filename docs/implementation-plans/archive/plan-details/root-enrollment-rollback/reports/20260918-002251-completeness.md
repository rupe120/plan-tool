If the process is interrupted (killed, crashes, host reboot, OOM) after `publish_evidence` durably writes the receipt but before the next line clears `accepted-head.json`, every later invocation with the same target version id finds the receipt, reports "already rolled back," and — by this stated design — performs no further check and no mutation. `accepted-head.json` is never cleared, the roadmap stays permanently enrolled, `require_unenrolled_roadmap_writer` keeps refusing the legacy writer, and the tool insists rollback already succeeded. Risk 5 names the bad end state ("a receipt written with the selector still pointing at the root") but only guards the case where `publish_evidence` itself reports failure; it does not cover a *successful* publish followed by an ordinary interruption before the selector write, which is exactly the case the stated idempotency design cannot recover from. This is the fourth distinct symptom found at this same site across audit rounds (missing receipt → unstable address → wrong check ordering → now receipt/selector divergence on crash) — per this repo's own recurring-finding guidance, a different symptom recurring at one site means the previous fix was the wrong shape, so the remedy should re-derive the full case matrix rather than patch this one more cell.
  - Fix: Extend the receipt pre-check to also read the current selector: when a matching receipt exists but `accepted-head.json` still names the target root version, complete the interrupted clear (instead of reporting success with no mutation) before returning the idempotent outcome, and add a Risk/Testing entry proving this exact crash-recovery case alongside the already-covered receipt-absent cases.

Read literally, "the operator confirmation" (`--confirm-root-rollback`) is the flag carrying the version id, leaving `--rollback-root` a bare trigger.
