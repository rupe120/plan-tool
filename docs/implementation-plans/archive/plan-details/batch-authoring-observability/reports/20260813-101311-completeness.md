Step 5, the step that actually creates the `BackendSpawn` dataclass, ships it with only `phase: str, attempt: int, backend: str` — none of `transport`, `child_pid`, `effective_timeout_ms`, or `prompt_bytes` ever appear, and step 7's `on_spawn(phase, attempt, backend)` observer callback explicitly reuses step 5's field set rather than adding them. The plan's own Testing section turns the missing field into an explicit, checkable claim ("`backend_spawn.effective_timeout_ms` reports the configured timeout when a `claude_invoke` caller has both thresholds active and it is shorter than the silence threshold, and the silence threshold alone for a `run` step call or any caller with no configured timeout") that no step builds a way to satisfy — there is no field to hold the value. The gap cascades into step 9, whose in-flight.json refresh for `backend_spawn()` hedges "the child pid is the one an operator can act on, if the landed event has it" — it doesn't, so the operator value Architecture describes (see a live child's pid, know what timeout governs it) never ships.
- HIGH `[recovery-wait-next-attempt-drift]`: Step 5's `backend_recovery_wait` wrapper computes `next_attempt` from a caller-side counter that only advances right before a `wait`/`sleep` call — but the real loop (`rate_limit_loop.run_with_rate_limit_recovery`) also bumps its own `current_attempt` on a successful backend SWITCH or ASK-switch, a path that never calls `wait` or `sleep` at all (it just `continue`s). Step 5's Input section claims the caller-side counter "mirrors the loop's own `current_attempt` exactly," but that's false whenever a switch happens earlier in the same bracket: the next wait/sleep-triggered retry emits a `next_attempt` that undercounts by the number of switch-driven jumps, disagreeing with the `attempt` field the very next `backend_spawn`/`claude_call_end` reports for that same retry (those read the loop's real state directly). This breaks Testing's own bar — "gate-failure/retry logs still pair the right phase/attempt with each terminal call event" — and no test in step 5's roster (`test_claude_invoke_emits_backend_recovery_wait_on_rate_limit_retry` etc.) drives a switch before a wait/sleep retry, so nothing catches it.
- MEDIUM `[in-flight-concurrent-slug-teardown]`: `in_flight_path`'s own docstring and the plan's Out of scope both describe concurrent same-slug calls as "last-writer-wins... overwrites the first call's snapshot" — but `RunLogWriter.run_end()` doesn't overwrite the shared file, it unconditionally unlinks it (`plan_tool/run_log.py:RunLogWriter.run_end`). Step 9's own detail confirms this stays untouched: "`run_end()` unlinks the snapshot. This step relies on that cleanup and does not change it." So when two same-slug calls overlap and one finishes, its `run_end()` deletes `in-flight.json` out from under the other, still-running call — not a stale overwrite but a total loss of signal, reading as "nothing is running" until the survivor's next refresh. Step 9 sharpens the stakes: before it, the file barely changed after start, so a mid-run deletion was low-cost; after it, the snapshot is the operator's live answer for the whole call, so this false-negative window is exactly the thing step 9 exists to prevent.
