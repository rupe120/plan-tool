  - Fix: Refuse a dropped source record that names a current plan step and align story, handoff, tests, and criteria around complete current-step coverage.
- MEDIUM `[handoff-state-preservation]`: Step 3 promises to preserve each record’s handoff state, and Architecture says “a created record stays created,” but its one-to-one matching rule applies only to records with a nonempty `jira_issue_key`. `plan_tool.jira:_resolve_export_state` accepts `created` without a key, so Architecture, Testing, and acceptance criterion 5 leave an existing keyless `created` record without a defined current-story match or refusal outcome.
  - Fix: Define the matching or refusal rule for a non-dropped `created` record without a Jira key and cover it in the state-preservation criteria and tests.
- HIGH `[created-ticket-divergence]`: Architecture requires “Story prose and grouping still render from the current captured plan inputs,” which can change a `created` record’s source story while retaining its Jira key. Steps 3 and 6 (`Add an opt-in Jira companion CLI mode with explicit output behavior`), Testing, and acceptance criteria 4–5 do not require notice to the operator, despite `JIRA_FORMAT.md` requiring a created-ticket change to be “called out” and `plan_tool.jira:_export_jira_append` already reporting such divergence.
  - Fix: Require companion mode to report every changed created Jira record so the operator can update the live Jira ticket.
- MEDIUM `[dropped-record-lifecycle]`: Architecture says “a `dropped` record stays a historical dropped record,” but later says “It does not preserve old stories, append to a prior export, or maintain state about an earlier output.” Steps 3 and 5, Testing, and acceptance criteria 4–5 require both current-source replacement and historical dropped handling without stating where, if anywhere, that history appears; `plan_tool.jira:reconcile_existing_statuses` currently re-emits dropped records.
  - Fix: Choose and state the generated artifacts’ treatment of dropped records, including any visible historical representation, and align publication, tests, and criteria to it.
- HIGH `[cross-format-pair-identity]`: Architecture says `jira-stories.md` and `jira-stories.json` both yield the normalized stem `jira-stories`, so both formats use the same default companion path, while it also says an absent story destination has no prior Jira handoff metadata. A format switch therefore sees the other story file as absent but replaces the shared companion; `plan_tool.jira:derive_jira_output_path`, `scan_existing_story_numbers`, and `export_jira` keep those story files separate and can reuse their ids, losing their keys from the new source. Steps 3 (`Regenerate companion-mode stories with provable Jira-key ownership and state`), 5 (`Publish synchronized story and handoff source files without overwriting human guidance`), and 6 (`Add an opt-in Jira companion CLI mode with explicit output behavior`), Testing’s JSON/default-path fixtures, and Acceptance criteria 1, 4, and 5 do not choose the format-switch behavior.
  - Fix: Define a format-change policy that keeps each handoff bound to one story source or safely refuses or migrates a switch before either output is replaced.
