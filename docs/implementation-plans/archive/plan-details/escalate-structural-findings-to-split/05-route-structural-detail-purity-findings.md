# Step 5 — Always route structural (`detail-purity`) findings to `escalate_to_split` in the create/detail convergence loops — recommend always, auto-apply only under the `allow_split` opt-in

## Summary

- **Wires both convergence loops to the step-3 bridge.** Step 4 already re-points `plan_tool/detail.py:generate_detail` Phase B at `plan_tool/launcher.py:escalate_to_split` (the engine→bridge swap); step 5's `detail.py` deltas are the Phase-B interactive-guard drop (so unattended runs recommend), the all-six-outcome handling that drop exposes (the now-reachable `recommended` outcome — and the recommend-only `unsafe`/`split-failed` outcomes — fold the returned `Recommendation` into `emit_detail_findings_summary` instead of step 4's silent decline-no-op), and the `BLOCKED-STRUCTURAL` convergence-loop branch. `plan_tool/create.py:create_plan`'s post-write convergence loop routes any `review.is_structural` finding it would otherwise defer to the same bridge.
- **Catches the mid-apply trigger too (trigger 2).** Both loops already call `apply_finding`; when it returns `verdict == "BLOCKED-STRUCTURAL"` (Claude determined mid-apply the only fix is a split — step 2's new bucket) the loop routes that finding's target step through `escalate_to_split`, the same bridge, instead of silently dropping it as a non-`APPLIED` no-op. This wires trigger 2 (discovered mid-apply) alongside trigger 1 (pre-classified `is_structural` by source), mirroring step 6's review-walk verdict branch — so a `BLOCKED-STRUCTURAL` returned during a convergence apply finishes its life as a split (interactive + opt-in) or a recommendation (unattended) rather than dead-ending.
- **Single design decision:** the split engine is now reached through exactly one seam (`escalate_to_split`), so both loops inherit its safety gate, its TTY + `allow_split` interactive guard, and its unattended-recommendation behavior — neither loop re-implements `propose → safe → confirm → apply → migrate`.
- **`create_plan` gains one parameter** `allow_split: bool = False`; `generate_detail` already has `allow_split` and needs no signature change.
- **Honest scope note:** `collect_deterministic_findings` (create's only finding source) emits no `detail-purity` today, so create's routing is forward-safe wiring exercised by an injected structural finding in tests — inert in production until a structural source reaches create. Detail's Phase B already handles real `detail-purity` findings.
- **On green:** an interactive `detail --split` run still splits a mixed step in one pass (now via the bridge); an unattended detail/create run emits a split *recommendation* instead of silently skipping; rc stays 0 unless `--fail-on-findings`.

## Why

A finding whose only correct fix is "split this step into two" is recognized but dead-ended in the convergence loops. In `plan_tool/detail.py` the purity self-check tags mixed steps `detail-purity` (`_parse_purity_findings`), the convergence loop defers them (the source is absent from `APPLY_ELIGIBLE_SOURCES`), and the only split path is the inline Phase-B block — reachable nowhere else and re-implementing the engine sequence by hand. In `plan_tool/create.py` the post-write loop reports any non-apply-eligible finding via `emit_triage_summary` and then short-circuits ("all remaining findings are triaged-deferred"), with no escalation hook at all. Step 3 lifted the exact Phase-B sequence into `launcher.escalate_to_split`; this step makes both loops *call* that bridge so a structural finding finishes its life as a split (interactive + opt-in) or a recorded recommendation (unattended), instead of being skipped or hand-inlined.

## Implementation

### Foundational logic

- **The rule this step adds:** "a structural finding routes to `escalate_to_split` — never deferred-and-skipped, never hand-inlined — and a real split happens only when `escalate_to_split` itself permits it (TTY + `allow_split` + confirm)." A finding is structural via **either** trigger: it is `is_structural` by source (pre-classified, routed *before* apply) **or** an `apply_finding` call inside the loop returns `verdict == "BLOCKED-STRUCTURAL"` (discovered *during* apply). Both triggers funnel to the same bridge.
- **Shared call sites that exercise it (both in scope):** `plan_tool/detail.py:generate_detail` Phase B and `plan_tool/create.py:create_plan`'s convergence loop. The engine itself is already single-sourced in `plan_tool/launcher.py:escalate_to_split` (step 3) — no further consolidation needed; this step only redirects the two callers to it.

### `plan_tool/detail.py`

- **Step 4 owns the engine→bridge swap.** Step 4 (`re-point-detail-py-phase-split-sequence`, refactor) already replaces the inline `parse_plan` → `_split_is_safe` → `_propose_step_split` → `_confirm_split` → `_apply_step_split` → `_migrate_downstream_details_after_split` → `write_plan` block in the Phase-B loop with per-target `escalate_to_split` calls, including the high→low ordering, the full six-outcome (`applied`/`unsafe`/`recommended`/`split-failed`/`proposal-unusable`/`step-missing`) branch table, and the detail-less-half re-authoring loop. **Step 5 does not repeat that swap** — it builds on the bridged Phase B step 4 lands and adds only the two deltas below.

- **Drop the Phase-B interactive guard.** After step 4, the Phase-B loop is still gated by `if allow_split and mixed_steps and sys.stdin.isatty():`. To gain the unattended-recommendation behavior the plan asks for, iterate `mixed_steps` whenever it is non-empty and pass `allow_split=allow_split` down — let the bridge decide apply-vs-recommend on TTY + opt-in (`outcome == "recommended"` on a non-TTY / `allow_split`-off run is surfaced via the new in-loop emit call below). Guard only the post-loop half re-authoring on "did anything actually apply" (`split_target_ids`), since an all-recommended run creates no new halves.

- **Add a new Phase-B emission call (the only place a Phase-B recommendation can be surfaced).** The existing `emit_detail_findings_summary` calls (`detail.py:2253`, `2551`) run inside the Phase-A `for step in target_steps` loop, which completes *before* Phase B executes — so a `structural-split` `Recommendation` produced in the Phase-B loop can never reach them. Step 5 must add a **new `emit_detail_findings_summary` (or equivalent) call inside the Phase-B loop** that surfaces each non-`applied` outcome's `Recommendation` (`recommended`/`unsafe`/`split-failed`, plus `proposal-unusable`/`step-missing` when they carry one) as that target is processed. Without this call the unattended-detail headline behavior — "emit a split recommendation instead of silently skipping" — has no emission point and the recommendation is dropped.

- **Render `suggested_action` in `emit_detail_findings_summary`.** When folding a `structural-split` `Recommendation` into `emit_detail_findings_summary`, render both `rec.body` (proposed titles + rationale) **and** `rec.suggested_action` (the `plan-tool split --into …` command) beneath the finding's line — mirroring the create-side `emit_triage_summary` treatment step 1 adds. Without this the detail path surfaces the proposed titles but not the actionable split command, defeating part of the "surface the more-correct plan" intent. Non-`structural-split` recs keep the existing one-line `rec.body` rendering.

- **Branch on the `apply_finding` verdict (trigger 2).** `generate_detail`'s convergence apply loop calls `apply_finding` and currently inspects the result's verdict only for `== "APPLIED"`. Add a branch for `verdict == "BLOCKED-STRUCTURAL"`: **first revert `apply_finding`'s partial edits by restoring `result.pre_snapshot` (via `_revert_snapshot`) before calling `escalate_to_split`, matching step 6** — `apply_finding` runs Claude in `acceptEdits` mode and can leave prose edits on disk before concluding the fix must be a split, so reverting first ensures the bridge re-parses clean state and its structural write does not land on top of un-reverted partial edits. Guard `rec.step_id is None` first (mirror step 6): a plan-wide rec names no single step to split, so skip escalation, surface a "structural finding names no step to split" note, and leave it for manual review rather than calling the bridge. Otherwise route that finding's target step through `escalate_to_split(plan_path, step_id=rec.step_id, repo_root=repo_root, invoker=invoker, allow_split=allow_split, prompt_fn=prompt_fn)` and reuse the same six-outcome handling step 4 wires into the Phase-B loop for `"unsafe"`/`"recommended"`/`"split-failed"`/`"proposal-unusable"`/`"step-missing"` (each surfaces its existing feedback and makes no further attempt; `"split-failed"` carries a re-plan `Recommendation` and is handled identically to `"unsafe"`). The `"applied"` outcome here differs from step 4's post-loop Phase-B handling: this branch runs **inside** the convergence apply loop, which is itself nested in `for step in target_steps` (`detail.py:1662`), so an applied split renumbers ids 1..N on disk and every still-pending `rec.step_id` in the inner `for rec in open_apply` loop and every remaining `step.id` in the enclosing `for step in target_steps` loop becomes stale. On `outcome == "applied"`, therefore: record the target for half re-authoring, then **break out of the inner `for rec in open_apply` loop, re-parse the plan from disk, re-collect `target_steps` from the renumbered plan, and `break` out of the enclosing `for step in target_steps` loop** before proceeding — so no remaining `rec` is dispatched to `apply_finding(step_id=rec.step_id)` and no remaining `step` (a stale pre-split `Step`) is processed against renumbered ids (nor the `mixed_steps` ids captured at `detail.py:2107`). This mirrors the plan body's Touch-points requirement and the `if drift_halted: break` double-break already in the loop. Without this branch a `BLOCKED-STRUCTURAL` discovered mid-apply is dropped as a non-`APPLIED` no-op and the finding dead-ends; without the double-break-and-re-collect an applied split corrupts which step subsequent edits target. This mirrors step 6's review-walk verdict branch.

### `plan_tool/create.py`

- **Add the parameter.** `create_plan(..., allow_split: bool = False, ...)`. Default `False` keeps every existing caller (and the wizard's non-iterate path) unchanged. No `prompt_fn` parameter is needed — reuse the wizard's resolved `input_fn` as `escalate_to_split`'s `prompt_fn`, and `claude_invoker` (`ClaudeInvoker = Callable[[str], str]`, already the proposer shape) as its `invoker`.

- **Route in the convergence loop.** In the `while True:` body, after `open_apply, open_deferred = partition_findings_for_triage(...)` and before the `emit_triage_summary(open_deferred, ...)` call (which itself runs ahead of the `if not open_apply:` short-circuit), so a surfaced `Recommendation` can be folded into that summary:
  - Compute `structural = [r for r in open_deferred if is_structural(r)]`.
  - **Guard a missing step target first (mirror step 6).** Before calling the bridge, skip any rec whose `step_id is None` — a plan-wide structural rec names no single step to split, and `escalate_to_split` needs a concrete `step_id`. Leave such a rec in `open_deferred` so `emit_triage_summary` reports it for manual review, and do not call `escalate_to_split` for it. This is step 6's skip-and-report guard applied in the loop.
  - **Route whenever the remaining `structural` recs are non-empty — do not gate the route on `allow_split`.** For each rec with a concrete `step_id` call `escalate_to_split(plan_path, step_id=rec.step_id, repo_root=repo_root, invoker=claude_invoker, allow_split=effective_allow_split, prompt_fn=input_fn)`. **Compute `effective_allow_split = allow_split and not yes` once and pass *that* down — mirroring step 6's `effective_allow_split = allow_split and not state.yes_to_all`** so an unattended `--yes` run forces the bridge's recommend-only branch rather than leaning on `_confirm_split`'s default-NO + the silent `input_fn` returning `""`. Under `--yes` (`yes=True`) `effective_allow_split` is `False`, so the bridge never reaches its apply branch and always recommends, satisfying the never-mutate-unattended invariant without relying on the confirm default. Passing the effective value *down* lets the bridge decide apply-vs-recommend (TTY + opt-in + confirm → apply; otherwise → `outcome="recommended"` folded into `emit_triage_summary`). The opt-in gates only whether the split auto-applies; it never gates whether create detects the structural finding and surfaces the more-correct-plan recommendation. This matches the detail-side Phase B, which already iterates `mixed_steps` unconditionally and passes `allow_split` down, and the main plan's invariant (1): always validate the more-correct plan, never silently defer a structural finding.
  - On any `outcome == "applied"`, the plan changed on disk — `continue` the outer `while` after re-collecting (`current_findings = collect_deterministic_findings(...)`, refresh `state.current_finding_ids`, `record_iteration`) so the next pass sees the renumbered plan, mirroring the post-apply re-collect the loop already does after `apply_finding`.
  - On every non-`applied` outcome — `"recommended"`, `"unsafe"`, `"split-failed"`, `"proposal-unusable"`, and `"step-missing"` — leave the finding in `open_deferred`, let `emit_triage_summary` report it (fold the bridge's `Recommendation` if surfaced), and fall through to the existing short-circuit; none of these re-collect. The create loop treats `"split-failed"`, `"proposal-unusable"`, and `"step-missing"` identically to `"recommended"`/`"unsafe"` (deferred, no re-collect), mirroring the detail-side six-outcome contract — only `"applied"` re-collects.

- **Branch on the `apply_finding` verdict (trigger 2).** Where the loop calls `apply_finding` and currently inspects `apply_result.verdict` only for `== "APPLIED"`, add a branch for `apply_result.verdict == "BLOCKED-STRUCTURAL"`: **first revert `apply_finding`'s partial edits by restoring `apply_result.pre_snapshot` (via `_revert_snapshot`) before calling `escalate_to_split`, matching step 6** — `apply_finding` runs Claude in `acceptEdits` mode and can leave prose edits on disk before concluding the fix must be a split, so reverting first ensures the bridge re-parses clean state and its structural write does not land on top of un-reverted partial edits. Guard `rec.step_id is None` first (mirror step 6): a plan-wide rec names no single step to split, so skip escalation, surface a "structural finding names no step to split" note, and leave it deferred for manual review rather than calling the bridge. Otherwise route that finding's target step through `escalate_to_split(plan_path, step_id=rec.step_id, repo_root=repo_root, invoker=claude_invoker, allow_split=effective_allow_split, prompt_fn=input_fn)` — passing the same `effective_allow_split = allow_split and not yes` as the source-based block (so a `--yes` run forces recommend-only here too) — the same bridge and the same `"applied"`-re-collects handling as the source-based block above. On `outcome == "applied"` the trigger-2 branch must **`break` out of the inner `for rec in open_apply` apply loop before re-collecting (`current_findings = collect_deterministic_findings(...)`) and `continue`ing the outer `while`** — mirroring the existing `if drift_halted: break` double-break — so no remaining queued `open_apply` rec is dispatched to `apply_finding(step_id=rec.step_id)` against the now-renumbered ids the split produced. **The non-`applied` surfacing differs from the source-based block.** The trigger-2 branch runs *inside* the `for rec in open_apply` apply loop, which executes *after* this iteration's sole pre-loop `emit_triage_summary(open_deferred, ...)` has already fired — so the source-based block's fold-into-`emit_triage_summary` path is unreachable here and must **not** be reused. Instead, on every non-`applied` outcome (`"recommended"`, `"unsafe"`, `"split-failed"`, `"proposal-unusable"`, `"step-missing"`): when `escalate_to_split` returns a `Recommendation`, append it to `open_deferred`; when it returns `recommendation=None` (`proposal-unusable`/`step-missing`), append the **original `BLOCKED-STRUCTURAL` finding** to `open_deferred` instead (it originated from `open_apply`, never `open_deferred`, so the pre-loop emit never saw it) — mirroring the plan body's invariant (1)(a) "stays deferred-and-reported by its caller." Then surface these appended recs/findings via a **second, post-apply-loop `emit_triage_summary` (or explicit print) over only the trigger-2-appended recs and `recommendation=None` originals**, run after the `for rec in open_apply` loop closes and *distinct from* the already-fired pre-loop `emit_triage_summary` — do **not** rely on the pre-loop emit, which has no way to see a finding appended after it ran. Without this post-apply-loop emit a create-side trigger-2 recommendation (and, on `recommendation=None`, the unresolved finding) is silently dropped, violating invariant (1). Without the branch at all a `BLOCKED-STRUCTURAL` returned mid-apply is dropped as a non-`APPLIED` no-op and the finding dead-ends. This mirrors step 6's review-walk verdict branch.

- **Why this is forward-safe, not dead.** `collect_deterministic_findings` emits no `detail-purity` finding today, so `structural` is empty on every production create run and the block is a no-op — the route's inertness comes from the *empty finding set*, not from `allow_split` (which no longer gates the route; it only gates apply-vs-recommend once a finding is present). The wiring is symmetric with detail and ready for the moment a structural source reaches create (e.g. the granularity advisor feeding the loop). State this inertness in the test that injects a synthetic structural finding to prove the route.

- **Drift/lock interplay.** The escalation block sits inside the same `iteration_session` context as `apply_finding`; a split mutates `plan_path` and detail files, which are already excluded from the drift-watched set (only `step.files` are watched), so a split does not trip the pre-apply drift halt.

### Import discipline

- **Both modules already import `apply_finding` from `launcher` at module top**, so `create.py` and `detail.py` extend that same top-level line with `escalate_to_split` **and `_restore_text_files as _revert_snapshot`** (also defined in `launcher.py`; aliased as step 6 does) — the trigger-2 branches call `_revert_snapshot(result.pre_snapshot)` to revert `apply_finding`'s partial edits before escalating, so both modules must import it. No new cycle (launcher→create/detail is body-local inside `escalate_to_split`; create/detail→launcher at top is the existing direction).
- **`is_structural` is cycle-free into create** — add it to create's existing top-level `from plan_tool.review import (...)` block (review imports create only lazily). Detail needs no `is_structural` import: its `mixed_steps` are already the `detail-purity` findings, so the structural test is implicit.

## Acceptance criteria

- `create_plan` accepts `allow_split: bool = False`; omitting it preserves current behavior.
- With `allow_split=True`, a TTY, and a flagged mixed step, `generate_detail` Phase B reaches the split engine **only** through `escalate_to_split` — the inline `_apply_step_split`/`_propose_step_split` calls are gone from `generate_detail`.
- An interactive `detail --split` run still splits a mixed step and re-authors both halves in one pass.
- In unattended mode (non-TTY / `allow_split` off), neither loop mutates plan structure; a structural finding produces a recorded split recommendation, not a silent skip.
- `generate_detail` adds a new `emit_detail_findings_summary` (or equivalent) call inside the Phase-B loop that surfaces each non-`applied` outcome's `Recommendation`, since the Phase-A emits (`detail.py:2253`, `2551`) complete before Phase B and cannot reach it — without it an unattended detail run drops the Phase-B recommendation.
- `emit_detail_findings_summary` renders a `structural-split` rec's `suggested_action` (the `plan-tool split --into …` command) as well as its `body`, mirroring the create-side `emit_triage_summary`, so the detail path surfaces the actionable split command.
- The create convergence loop calls `escalate_to_split` for an injected `is_structural` finding regardless of `allow_split` (validation/routing is unconditional); with `allow_split=False` the bridge returns `outcome="recommended"` and the recommendation is folded into `emit_triage_summary` with no mutation, and with `allow_split=True` an interactive confirmed run applies the split.
- Create passes `effective_allow_split = allow_split and not yes` (not raw `allow_split`) to `escalate_to_split`, so a `--yes` (`yes=True`) run with `allow_split=True` forwards `allow_split=False` and recommends rather than splits — forcing the recommend-only branch the way step 6 does, not relying on `_confirm_split`'s default-NO.
- Both convergence loops route an `apply_finding` result with `verdict == "BLOCKED-STRUCTURAL"` through `escalate_to_split` for that finding's target step, rather than dropping it as a non-`APPLIED` no-op.
- In `detail`, a trigger-2 `BLOCKED-STRUCTURAL` apply that returns `outcome == "applied"` breaks out of the inner `for rec in open_apply` loop, re-parses the plan from disk, re-collects `target_steps` from the renumbered plan, and breaks out of the enclosing `for step in target_steps` loop before proceeding — so no remaining `rec`/`step` (nor the `mixed_steps` ids captured at `detail.py:2107`) is processed against the split's renumbered ids.
- In `create`, a trigger-2 `BLOCKED-STRUCTURAL` apply that returns `outcome == "applied"` breaks out of the inner `for rec in open_apply` loop before re-collecting (`collect_deterministic_findings`) and `continue`ing the outer `while` — mirroring the existing `if drift_halted: break` — so no remaining queued `open_apply` rec is dispatched to `apply_finding(step_id=…)` against the split's renumbered ids.
