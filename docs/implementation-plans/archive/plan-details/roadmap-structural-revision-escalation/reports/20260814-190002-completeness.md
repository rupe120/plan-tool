Editing or deleting the brief leaves the report current while `--from-stage` uses different or unreadable grounding, contrary to the Problem statement’s source-revision goal; the Architecture, Risks, Testing, and stale acceptance criterion name only source-record changes.
  - Fix: bind routing and freshness to a readable recorded brief and its content digest, and return no route when that input changes or disappears
- HIGH `[relation-edge-ownership]`: Step 2 (`Extract stable roadmap relation edges without changing existing views`) says the graph is “over typed design-row nodes” and orders edges by “stage, collection, row-id, and field order,” but lists `FieldRow.entity_id`, `OrderingEntry.depends_on`, and `OrderingEntry.assumption_targets`; `plan_tool/roadmap_artifacts.py:FieldRow` and `OrderingEntry` have no design-row id. Architecture, Input, Testing, and the relation acceptance criterion never choose the parent node, direction, projection, or sort key for those edges, so valid reports can produce different closures and digests.
  - Fix: define how nested field and ordering references attach to their containing design rows, including direction, projection, and deterministic ordering, then use that rule throughout the inventory and tests
- HIGH `[cross-artifact-route-safety]`: Step 3 routes every row-target closure from its minimum owner stage even for the `cross-artifact-impact` reason, while Architecture says classification does not select a route. A valid `PlanDisposition.CROSS_CUTTING` `PlanRow` can have no `component_ids` at HEAD, so its closure stays at stage 4 and the prescribed `--from-stage 4` cannot rewrite an upstream artifact that the feedback says must change; the Architecture routing rule, heuristic-routing risk, and broad-route acceptance criterion all still call it a recommendation.
  - Fix: make cross-artifact requests whose current closure cannot establish the needed scope return an explicit scope decision or clearly label the stage as only a lower bound, not a safe broad-command recommendation
- HIGH `[snapshot-publication-write-set]`: Step 5 (`Atomically publish immutable escalation reports without broadening the write set`) promises both concurrent snapshot safety and only report/telemetry writes, but it never chooses the coordination mechanism. The current shared writer guard, `plan_tool/roadmap_revision_publish.py:roadmap_writer_guard`, creates a persistent `.roadmap-<slug>.writer.lock` in the plans directory; without shared coordination, inputs can change after verification and simultaneous creators can overwrite the same report path. Architecture’s write-set promise, partial-or-mixed-evidence risk, Testing byte checks, and the no-write acceptance criterion cannot all hold as written.
  - Fix: define publication serialization with roadmap writers and either permit its durable lock in the declared write set or require a coordinating mechanism that leaves no persistent extra path
- MEDIUM `[escalation-telemetry-lifecycle]`: Step 4 (`Add redacted escalation run-log results while preserving ordinary view silence`) promises a closed preflight verdict plus one result outcome for creation, but Architecture lists only post-selection result outcomes and never defines the preflight vocabulary or whether selector and `mode-rejected` paths emit a result event. The exclusive-mode paragraph, Testing telemetry requirement, and telemetry acceptance criterion therefore permit incompatible event streams for the same rejected command.
  - Fix: define the closed preflight values, field nullability, and one event-emission matrix for every creation terminal path, including selector and mode rejection
- HIGH `[escalation-option-pairing]`: Step 6 (`Wire exclusive escalation creation and log-free escalation views`) requires both creation flags together, but Architecture and Testing never require rejection of a bare `--escalation-reason` or a selector missing its reason before normal dispatch. `plan_tool/cli/roadmap_cmd.py:cmd_roadmap` otherwise falls through to `run_roadmap` when no mode claims the invocation, so a partial escalation command could start the broad writer and violate the no-execution boundary; this affects Architecture’s creation/exclusivity paragraphs, Testing’s CLI cases, and acceptance criteria 10 and 13.
  - Fix: Treat either partial creation-flag combination, and either creation flag beside an escalation view, as a typed preflight rejection before any broad or view dispatch
- MEDIUM `[selected-feedback-projection]`: Step 3 names a selected-feedback projection but never defines its fields, while Architecture’s context estimate, Input, Risks’ context-boundary mitigation, Testing’s “exact selected-feedback” assertions, and acceptance criteria 1 and 5 make that projection control report bytes, semantic identity, and durable disclosure. Implementers can reasonably include the reviewer request or only identifiers and target state.
  - Fix: Define the selected-feedback projection field set and redaction boundary, then use it consistently in report identity, context accounting, fixtures, and documentation
- MEDIUM `[artifact-target-routing-outcome]`: Architecture says an artifact-targeted report “withholds a broad-route recommendation pending an ownership decision,” but only assigns `requires-schema-ownership-decision` to an unknown ownership mapping; an artifact target already has a known artifact stage. Step 3, Testing’s route/refusal cases, and acceptance criterion 9 therefore leave the report’s route result and operator action for every valid artifact target unspecified.
  - Fix: Define one closed no-route outcome and operator action for artifact targets, and carry it through the report, telemetry, CLI output, and tests
- HIGH `[snapshot-input-validity]`: Step 3 (`Define deterministic, snapshot-consistent escalation reports with bounded context and safe owner-stage routing`) promises a graph of validated relations and says unreadable changes yield `snapshot-interfered`, but it does not define the initial no-write result for a missing or unparseable artifact, a relation-invalid artifact, or malformed `source.json`. `plan_tool/roadmap_view:load_roadmap` deliberately permits those partial states, while Testing and acceptance criteria cover only interleaved changes.
  - Fix: define one closed preflight outcome for every initially invalid snapshot input and require no report, route, or backend call for each case
- MEDIUM `[stored-report-integrity]`: Step 5 creates immutable versioned JSON and step 6 (`Wire exclusive escalation creation and log-free escalation views`) reads it, but Architecture’s identity and view rules, Testing identity/live-freshness cases, and acceptance criteria 6–8 do not say how a view handles malformed JSON, an unsupported schema, or a payload whose semantic digest does not match its path.
  - Fix: define report-read validation and a no-route outcome for every untrusted stored-report shape before live freshness is evaluated
- MEDIUM `[attribute-disposition-relation]`: Architecture calls its listed identifier edges the complete relation inventory, while Input promises every validated inter-row relation field. `ConstraintRow.attribute` is validated against the unique `AttributeDispositionRow` by `plan_tool.roadmap_gates:check_attribute_totality`, but Steps 2–3, Testing, and acceptance criterion 4 omit that relation, so a closure can miss the disposition that gives a constraint its meaning.
  - Fix: Include the constraint-to-attribute-disposition relation in the closed graph contract and its closure tests.
- MEDIUM `[route-refusal-precedence]`: Step 3 can encounter both an unknown ownership mapping and a missing recorded brief, but Architecture says each condition separately “yields” a different route result. Its routing paragraph, Testing, and acceptance criterion 9 do not define whether the report emits both blockers or which one controls the operator action, so adding a brief can look like a sufficient next action when ownership is still unknown.
  - Fix: Define a deterministic multi-blocker or precedence rule that withholds every route until all route prerequisites are satisfied.
