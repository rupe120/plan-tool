  - Fix: define one ordered tier policy in which high signals, standard floors, model output, and parse/ambiguity fallback have explicit precedence, with overlap tests.

  - Fix: add the CLI summary owner to the declared scope and step 4 change set, with output coverage for the saved declaration.
- MEDIUM `[standard-fallback-compatibility]`: `Overview` calls a standard fallback “byte-for-byte today’s behavior,” but `Persistence` deliberately requires every newly created plan to write both new fields, and `plan_tool/parser.py:render_plan_text` serializes present non-default model fields. New standard plans will therefore differ in frontmatter from today’s output.
  - Fix: describe standard fallback as behaviorally compatible while stating that new plans intentionally gain an explicit frontmatter declaration.
- MEDIUM `[non-tty-decision-mode]`: `Architecture → Pre-publication declaration` defines only a non-TTY `-y` result, while `Acceptance criteria` requires “non-interactive standard” generally and `Out of scope` forbids non-TTY model-proposal acceptance. At HEAD, `plan_tool/create.py:_eof_default` lets a canonical create with closed stdin but without `-y` take prompt defaults, and `Testing → Decision` covers only `-y < /dev/null`; this leaves a real non-TTY mode without a risk-decision rule.
  - Fix: Define the declaration behavior for every non-TTY create mode, including EOF without `-y`, and test it independently of the `-y` path.
- MEDIUM `[risk-decision-run-log-scope]`: Step 3 requires the declaration to be “visible in the run log,” and `Acceptance criteria` requires the log to record the proposal, final declaration, and decision mode, but `Architecture → Scope contract` allows only the prompt, completion summary, and frontmatter fields as user-visible changes. The scope fence therefore forbids one of step 3’s promised outputs.
  - Fix: Add the risk-decision run-log record to the allowed behavior changes and keep the scope contract aligned with step 3 and Acceptance criteria.
- MEDIUM `[risk-decision-checkpoint-lifecycle]`: Step 3 (`Resolve and checkpoint the operator declaration before plan publication`), `Architecture → Pre-publication declaration`, `Risks → A failure loses an operator decision`, `Testing → Resume`, and the final acceptance criterion require a hash-gated replay of the exact choice, but do not define which changed inputs invalidate it or what happens if the checkpoint cannot be written. At HEAD, `plan_tool/checkpoint.py:save_checkpoint` can fail, so a changed seed can reuse a stale choice or a failed save can let publication lose an operator decision.
  - Fix: Define the checkpoint’s matching inputs and fail-closed save behavior, with resume coverage for changed inputs and checkpoint-write failure.
- MEDIUM `[tty-yes-risk-decision]`: Step 3 (`Resolve and checkpoint the operator declaration before plan publication`) says “On a TTY, the operator accepts” a proposal and defines only non-TTY `-y`, while `Testing → Decision` covers TTY choices and `-y < /dev/null` but not TTY `-y`. At HEAD, `plan_tool/create.py:_prepare_create_plan` replaces input with `_silent_input_fn` for any `--yes` run, so a TTY `create -y` has no declared policy and can silently persist a model proposal.
  - Fix: Define the TTY `--yes` decision mode and its logged result, then cover it alongside interactive and non-TTY creation.
