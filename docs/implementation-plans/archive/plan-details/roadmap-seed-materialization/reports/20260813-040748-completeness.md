The model prompt that actually decides what prefix a plan row's `draft_seed_path` gets, `plan_tool/prompts/roadmap-plans.md`, still hardcodes "must begin with `seeds/`" until step 9 rewrites it. Step 9 depends on steps 2 through 8 landing first, so for that whole span, every ordinary stage-4 run (a fresh roadmap or a revision) has the model emit `seeds/<name>.md` paths while the still-live writer drops the generated file under `<slug>/plan-seed-drafts/<name>.md` instead — a path no plan row declares. `resolve_draft_seed_path` then can't find the file at its declared path, so `--apply`, `--view walk`, and `create --from-existing` all see it as missing or stale, while the in-run gates pass because they only check the bundle dict in memory, never the file that actually lands on disk.
  - Fix: keep the still-live inline writer and the prompt's hardcoded prefix pinned to the old name until step 9 retires the writer and rewrites the prompt together — either hold the physical write-directory string separate from the renamed constant until step 9, or pull the prompt's prefix change forward into step 1 alongside the constant rename — so no committed step between 1 and 9 leaves the declared path and the actual write location disagreeing.
- HIGH `[digest-mismatched-accept-validation]`: Step 10 lets an operator "accept" a `digest-mismatched` draft as `current` without running it through step 1's shared content/provenance validator — it "records the file's live digest as current... calling neither step 2's generation primitive nor step 4's refresh." Its own stated reason for refusing every classification but `digest-mismatched` is that "accepting a missing or malformed draft as current would promote a broken or absent file," but Architecture's precedence order checks `digest-mismatched` before `malformed`, and `malformed` only fires when the digest still matches the recorded one. Any hand edit — the exact case step 10 exists for — changes the digest, so a broken hand edit (bad YAML, a missing required field) can never land in `malformed`; it always lands in `digest-mismatched`, the one bucket accept lets through with no check. Accept can therefore promote genuinely invalid content to `current`, and step 6's promotion refusal then lets it into `plan-seeds/` because it trusts the classification accept itself just wrote. This contradicts the plan's own binary observable for promotion — "whether each manifest plan ID has exactly one valid draft."
  - Fix: have step 10's accept action run the draft through step 1's shared validator before writing `current`, and refuse (reporting the validation failure) when it doesn't pass, instead of trusting the digest-mismatched classification alone as proof of a reviewed edit.
- HIGH `[digest-mismatch-invalidation-laundering]`: Step 9's stage-4 invalidation and the existing earlier-stage feedback path both call `_invalidate_roadmap_seeds` on every sidecar entry, and that function (unmodified per the plan's own text) recomputes each entry's recorded digest from the live file before flipping status to `invalidated` — confirmed in `roadmap.py:_invalidate_roadmap_seeds` (`digest = digest_text(source.read_text(...))` whenever the file exists). When a draft is `digest-mismatched` because an operator hand-edited it but hasn't yet run step 10's accept action, this recompute overwrites the recorded digest with the hand-edited content's own hash. The classifier's live-digest check then matches, so the draft silently reclassifies as plain `stale` instead of `digest-mismatched` — triggered by any feedback-driven revision to any of the four stages, not just a stage-4 rewrite. The edit isn't destroyed outright (refresh/materialize still show a diff before overwriting a `stale` draft), but the draft silently loses eligibility for step 10's accept action — which fires only on `digest-mismatched` — and loses the signal that a human touched it, until the file is edited again.
  - Fix: state whether invalidation must preserve a digest-mismatched entry's recorded digest (so it keeps classifying digest-mismatched and stays accept-eligible) instead of refreshing it to the live file, for every invalidation trigger this plan relies on — both the stage-4 replace path step 9 adds and the existing earlier-stage feedback path it reuses unmodified.
- HIGH `[digest-mismatched-materialize-guidance]`: Step 7 routes `_summary_attention` so `missing`/`stale`/`malformed`/`path-escaping`/`digest-mismatched` all recommend `--materialize`. But `digest-mismatched` is, by Architecture's own description, "the state step 10's accept action exists to resolve" — and `--materialize`/`--refresh-seeds` overwrite the draft directly with no archival of the pre-overwrite bytes, leaving only a diff in the single, next-run-overwritten `seed-refresh-report.md`. Recommending the same destructive tool for the one state whose entire purpose is preserving "a reviewed hand edit" (step 10's words) steers an operator toward destroying exactly what step 10 exists to save.
  - Fix: give `digest-mismatched` its own guidance line in step 7 — review the diff, then choose `--accept` (keep the edit) or `--materialize` (discard it) — instead of folding it into the same one-line recommendation as the other four states.
- MEDIUM `[seed-refresh-materialize-partial-outcome]`: Step 4 turns `refresh_roadmap_seeds` from one all-or-nothing call into a per-plan loop that "continues past one plan's failed generation call," and step 5's batch `--materialize` shares "step 4's per-plan failure-isolation policy." Today `RoadmapSeedRefreshResult.outcome` only ever holds `SEED_REFRESH_OUTCOME_APPLIED` (full success) or `SEED_REFRESH_OUTCOME_EXHAUSTED` (full failure), and `roadmap_cmd.py` maps that binary straight to the CLI exit code. Neither step names what a batch where 3 of 5 plans succeed and 2 fail should return, so an automated caller reading the exit code has no defined answer for a mixed result.
  - Fix: name the outcome/exit-code contract for a partial batch under both `--refresh-seeds` and `--materialize` — a new outcome value or a defined choice between the two existing ones — so it isn't left to an implementer's guess.
- MEDIUM `[apply-classification-recheck-timing]`: Step 6 replaces `_apply_roadmap_seeds`'s ad hoc preflight with step 3's classification at the same call site — before `_confirm_apply_seeds`, an interactive `input()` prompt that blocks for as long as an operator takes to answer (unless `--yes`). After confirm returns, the two-phase commit re-reads `source.read_text()` fresh and writes whatever it finds, with no second classification check. A draft classified `current` at preflight that a concurrent `--refresh-seeds`, `--materialize`, or hand edit turns `stale`/`digest-mismatched` while the prompt sits open still promotes on confirm — reopening the exact gap step 6 says it closes ("a promoted seed could be invalidated-but-unrefreshed... without `--apply` ever noticing") at the one point in the flow with the longest wait for a human.
  - Fix: state that promotion re-runs step 3's classification immediately before the atomic commit, after confirm returns, and refuses anything no longer `current` at that point.
