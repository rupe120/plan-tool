Unsound or contradictory concepts in the plan's design — the highest-priority gaps, addressed before the completeness gaps below. The audit reports these but does not apply them (read-only-audit split, #85): the paired apply verb walks them first, before the completeness gaps. Address them with:

- HIGH `[stateless-component-store]`: The Overview, Architecture’s “Stores are definitions,” Testing, and Acceptance criteria require every component to name a store; step 2 (`Add store definitions and component store references`) preserves an empty `store_ids`, then step 4 (`Require resolved, concrete store references`) rejects it. `STORE_CATEGORIES` never says that `in-process` represents no persisted data, so a stateless component must either invent a store or fail the gate—the harm this plan aims to prevent.
  - Fix: Define the representation and gate result for a component with no persisted roadmap data, then align the schema, prompts, gates, examples, and tests to that policy.
- MEDIUM `[hosting-row-error-precedence]`: Architecture’s “Parsing preserves recoverable defects” says out-of-vocabulary input reaches gates; step 1’s implementation says to reject `product` unless `facet == "compute"` while its Tests say an unknown facet parses; step 3 (`Require complete, concrete hosting answers`) expects `check_hosting_totality` to report an unknown facet. A row with both an unknown facet and `product` has no defined result, so either parsing hides the facet violation or the product rule waits for a later edit.
  - Fix: Define which result wins when an unknown hosting facet carries a product, and cover that policy in the parser and hosting-gate tests.
- MEDIUM `[global-id-gate-boundary]`: Architecture and step 3 require hosting and store ids to share the `check_duplicate_row_ids` identity view, but step 4 (`Require resolved, concrete store references`) says its gates “do not inspect hosting” and its acceptance criteria says “no gate reads `envelope.constraints.hosting`.” The planned global duplicate check must read hosting during the components stage to reject a hosting/store collision, so both statements cannot hold.
  - Fix: state that store-specific validation stays independent of hosting while the shared global-id gate remains the explicit cross-artifact exception, and align step 4’s acceptance and tests to that boundary.
- HIGH `[hosting-model-topology]`: `hosting.model: bridge` means one operator combines dedicated and shared application deployments (Architecture, step 3 Implementation), but only `compute: mixed` requires `topology: multi-unit` (Architecture; step 3 `check_hosting_compute_topology`, Tests, and Acceptance criteria). `model: bridge` with `topology: single-unit` can therefore pass while contradicting the recorded deployment shape.
  - Fix: define and gate the topology required by a bridge hosting model, then align the prompt, format example, and tests
