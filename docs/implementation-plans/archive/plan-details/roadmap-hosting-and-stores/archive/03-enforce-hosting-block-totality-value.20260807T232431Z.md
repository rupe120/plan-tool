# Step 3 — Enforce the hosting block: totality and value gates, the constraints prompt's behavioral directive, and its worked-example update

## Summary

`plan_tool/roadmap_gates.py` gains two gates — `check_hosting_totality` (exactly one hosting row per `HOSTING_FACETS` member, and a facet name outside that tuple is rejected) and `check_hosting_value_membership` (a hosting row's `value` must be one of the allowed values for its own facet) — plus a new gate-owned vocabulary, `HOSTING_FACET_VALUES`, mapping each of `compute`/`model`/`topology` to its own closed set of vendor-neutral values. Both gates join `CONSTRAINTS_GATES`. A one-line extension to `_constraints_rows` lists every hosting row as `("hosting", row.id)`, which is the single shared point that makes hosting rows resolvable decision anchors and subjects them to `check_duplicate_row_ids`, `check_inventory_has_prose`, and `check_design_row_continuity` for free — the same mechanism step 1 and step 2 already describe for dispositions and stores. `plan_tool/prompts/roadmap-constraints.md` gains two new numbered rules, a vocabulary listing so the model knows what values will pass, an instruction to commit to a value and record a `pending` decision when inferring, and a `hosting:` block in its `## Shape` worked example. `ROADMAP_FORMAT.md` gains the `hosting` schema block, four new vocabulary tables (the facet names plus the three per-facet value sets), two new gate-table rows, and a `hosting:` block in its own, separately-maintained `02-constraints.md` worked example. The largest risk in this step is not the two gates themselves — it is that landing them turns every "clean constraints artifact" test fixture across three files into a failing one unless each fixture's hosting rows are updated to match; `## Implementation` names the exact, small set of fixture builders that funnel this risk to a few single points.

## Why

Step 1 gives `02-constraints.md` a `hosting` collection and a `HOSTING_FACETS` constant, but deliberately leaves it inert: no gate reads `artifact.hosting`, the prompt never asks the stage to fill it in, and a hosting row is neither a resolvable decision anchor nor subject to the prose or continuity gates every other design row already gets. That gap is exactly the plan's `## Problem statement` measurements 2 and 3 restated in miniature — a tenancy ambiguity nothing resolves, and a hosting assumption smuggled into an unrelated quality-attribute tradeoff — except now there is a place in the schema to answer them and still nothing that requires an answer. This step is what turns "there is a field" into "the field must hold a real, checkable value or the stage's response is rejected." It also unblocks step 5's pair rule, which reads a specific `compute` value out of `02-constraints.md`; until this step names and gates that vocabulary, nothing forces a stage to write a `compute` value step 5 could ever check against.

## Implementation

**The two gates, in `plan_tool/roadmap_gates.py`.** `check_hosting_totality(envelope)` returns early (`[]`) when `envelope.constraints is None`, matching `check_attribute_totality`'s guard, then reports three kinds of defect over `envelope.constraints.hosting`: a `HOSTING_FACETS` member with no row at all (no row id to name — message names the missing facet, mirroring `VIOLATION_UNDISPOSED_ATTRIBUTE`'s `row_id=None` shape), a facet named by more than one row (mirroring `VIOLATION_REDUNDANT_DISPOSITION`), and a row whose `facet` is not a `HOSTING_FACETS` member at all (mirroring `VIOLATION_UNKNOWN_DISPOSED_ATTRIBUTE`). It does **not** need `check_attribute_totality`'s other two defect kinds (`unknown-constraint-attribute`, `constraint-on-not-load-bearing`) — those exist only because a *separate* row kind (`ConstraintRow`) independently references attribute names; nothing else in the schema references a hosting facet name by bare string, so there is no second row kind to validate against the vocabulary.

`check_hosting_value_membership(envelope)` is a second, separate function — not folded into `check_hosting_totality` — because it judges a different axis (a row's `value`, not its `facet`'s presence) and the plan's own `## Architecture` names it as distinct ("a hosting value-membership gate... distinct from `check_hosting_totality`, which enforces only facet presence, not value membership"). For each hosting row whose `facet` **is** a recognized `HOSTING_FACETS` member, check `row.value` against `HOSTING_FACET_VALUES[row.facet]`; skip rows with an unrecognized facet entirely — `check_hosting_totality` already reports those, and there is no vocabulary to check a value against for a facet that is not real. Do check every row independently of `check_hosting_totality`'s findings otherwise (a facet declared twice still gets both of its rows' values checked) — this mirrors how `check_attribute_totality`'s five defects can co-fire on one artifact without one gate suppressing another.

Neither gate's message needs a `--from-stage` pointer: both operate on the same stage the retried prompt is regenerating, so the model can fix either defect on its very next attempt. That escape hatch belongs to step 5's pair rule, which crosses from the components stage back into an already-accepted constraints artifact it cannot itself rewrite — do not copy that pattern here.

**`HOSTING_FACET_VALUES` — a new vocabulary owned in `plan_tool/roadmap_gates.py`, not in `plan_tool/roadmap_artifacts.py`.** This is a real, deliberate departure from where `QUALITY_ATTRIBUTES` and `HOSTING_FACETS` live, forced by this step's own `files:` list, which excludes `plan_tool/roadmap_artifacts.py`. It is also the *correct* home on the module's own terms: nothing in the parser needs to know a facet's allowed values — only this gate does — matching the module's stated principle that "membership belongs to a gate," just at gate-module scope instead of artifact-module scope this one time. A `Mapping[str, tuple[str, ...]]` keyed by facet name is a natural shape (`typing.Mapping` is already imported in this module); a test should assert `set(HOSTING_FACET_VALUES) == set(HOSTING_FACETS)` so the two constants cannot silently drift apart.

Recommended member sets, vendor-neutral per the plan's `## Architecture` and its own References list:

- `compute`: three members distinguishing per-request execution, managed containers, and long-lived instances — the plan's own prose uses "per-request execution" and "per-request functions" repeatedly for the first category, and this exact spelling is worth settling here rather than leaving to guesswork, because step 5's pair rule depends on recognizing it by name. `"per-request"` is a reasonable, literal choice for that member.
- `model` (tenancy): three members matching the Silo/Pool/Bridge taxonomy the plan's own References cite.
- `topology`: exactly two members, per `## Architecture`'s explicit narrowing — distinguishing a single deployable unit from more than one, nothing finer.

These are recommendations, not a mandate on exact spelling except for `compute`'s per-request member — settle whatever you choose once, use it consistently across the gate, the prompt's vocabulary listing, and both worked examples, and expect step 5 to cite the `compute` member you choose by name.

**Wiring hosting into `_constraints_rows` — the one shared extension point.** Add `*(("hosting", row.id) for row in artifact.hosting)` to the tuple `_constraints_rows` returns, positioned first — matching `CONSTRAINTS_ROW_KEYS`'s render order (`hosting` is its first entry per step 1) and the same ordering `_domain_rows` already uses relative to `DOMAIN_ROW_KEYS`. This one edit is what makes a hosting row's id resolvable as a `pending` decision's `anchor` (via `check_decision_records`'s `resolvable` set, built from `_envelope_rows`/`_rows_of`), subjects hosting rows to `check_duplicate_row_ids`'s cross-artifact uniqueness scope, requires each hosting row's id to appear in the prose body (`check_inventory_has_prose`), and protects a settled hosting row across a revision (`check_design_row_continuity`). No other code change is needed for any of those four gates to pick up hosting rows — this is the same "for free" mechanism step 2 describes for `components_design_rows` and store rows.

Optional, low-cost, and worth doing: `check_decision_records`'s `anchor_hint` text currently says "a quality attribute is reachable only through its disposition row's id, never by its bare name" whenever `envelope.constraints is not None`. A model anchoring a `pending` decision to the bare word `"compute"` instead of a hosting row's id is the identical mistake this hint already guards against for quality attributes — extending the hint to name hosting facets too is a small text change with no gating-logic change, and is not required for correctness (the underlying resolution already works either way).

**`CONSTRAINTS_GATES` and the four new violation-kind constants.** Add both gate functions to the `CONSTRAINTS_GATES` tuple — inserting them near `check_duplicate_row_ids`, ahead of `check_attribute_totality`, keeps the declared order matching hosting's "read before the per-attribute dispositions" precedence from step 1's `CONSTRAINTS_ROW_KEYS` change, but exact position is a style choice: the constraints-side order-sensitive tests key on set membership, not an exact sequence, unlike the domain-side `test_violation_order_is_stable`. Name the four new `VIOLATION_*` constants following the module's one-token-per-defect convention (e.g. a missing facet, a facet declared twice, an unrecognized facet name, and an out-of-vocabulary value) and add each to `ROADMAP_FORMAT.md`'s "One token per defect" comment block's spirit — the doc names every gate's kinds in its relation table (see below).

## Acceptance criteria

- `HOSTING_FACET_VALUES`'s keys equal `set(HOSTING_FACETS)` exactly; none of its three value sets contains an `undecided`, `unknown`, `tbd`, or `n/a` member.
- `check_hosting_totality` requires exactly one hosting row per `HOSTING_FACETS` member and rejects a facet outside that tuple the same way `check_attribute_totality` rejects an unknown `QUALITY_ATTRIBUTES` member; both new violation kinds name the missing facet or the offending row id.
- `check_hosting_value_membership` rejects a hosting row's `value` outside its own facet's allowed set, naming the offending value and the allowed set, and produces no violation for a row whose `facet` is itself unrecognized.
- A `pending` decision anchored to a specific hosting row's id passes `check_decision_records`; the same decision anchored to a bare facet name (e.g. `"compute"`) does not.
- A hosting row id colliding with any other row id in the envelope fails `check_duplicate_row_ids`; an undescribed hosting row fails `check_inventory_has_prose`; a hosting row a revision drops after being settled fails `check_design_row_continuity`.
- `CONSTRAINTS_GATES` holds both new gates; `run_constraints_gates` over a valid, hosting-carrying constraints artifact (upstream of a valid domain) returns `[]`.
- `plan_tool/prompts/roadmap-constraints.md` states a rule for both new gates in vocabulary `_CONSTRAINTS_GATE_PROMPT_SUBJECTS` pins, instructs the stage to commit to a hosting value and record a `pending` decision when inferring, and its own `## Shape` example carries a valid `hosting:` block that clears the real constraints gate set.
- `ROADMAP_FORMAT.md` documents the `hosting` schema block, `HOSTING_FACETS`, and all three per-facet value vocabularies; both new gates appear in the "### Relations — return violations" table with their violation kinds; its own `02-constraints.md` worked example carries a valid `hosting:` block that clears the real constraints gate set. (Verifiable by a reviewer grepping `check_hosting_totality` / `check_hosting_value_membership` against the doc, in addition to the automated parse/gate tests above.)
- Every existing test in `tests/test_roadmap_gates.py`, `tests/test_roadmap.py`, and `tests/test_roadmap_format.py` that built a "clean" constraints artifact and expected zero real-gate violations before this step still does after it — including the CLI-level `@pytest.mark.integration` tests in `tests/cli/test_roadmap_cmd.py`, checked though not formally in this step's file list.

## Applicable guardrails

- **`## Architecture`, "the gated vocabularies stay at category altitude"** — `HOSTING_FACET_VALUES`'s three sets must fit a traditional long-running server and a serverless deployment equally well, with no AWS-specific or vendor-specific member, gate, or branch. Vendor concretion belongs only in the ungated `product` field.
- **`## Scope guardrails`, "any compatibility rule beyond the single per-request/in-process pair"** — neither new gate may compare a hosting value against a store's `category` or `sharing`, or against any constraint, disposition, or latency claim. That check is step 5's, in `COMPONENTS_GATES`, not here.
- **`## Scope guardrails`, "any AWS-specific or vendor-specific vocabulary member, gate, or branch"** — bounds the recommended `HOSTING_FACET_VALUES` member names in `## Implementation`; do not name a vendor product as a gated value.
- **`## Scope guardrails`, "any quality judgment on a `pending` value"** — neither gate may read `DecisionStatus`, count pending decisions, or treat a `pending` hosting decision as a defect; `check_hosting_totality`/`check_hosting_value_membership` judge only `HostingRow.facet`/`.value`, never a decision's `status`.
- **`## Scope guardrails`, "any new exit-code flip"** — both gates return ordinary `Violation` lists; a stage that fails them retries with the violations quoted back, exactly like every other gate. This step touches no CLI or exit-code logic.
- **`## Out of scope`, "a new arc position or fifth artifact"** — this step adds no new stage, file, or CLI surface; it gates fields already living on `02-constraints.md`.
- **`## Architecture`, "### Parse-tolerant, gate-checked"** — neither new gate may raise; every defect surfaces as a `Violation` so `_load_and_regate_below`'s pre-flight re-gate can still report it as ordinary retry text rather than aborting on a parse error.
