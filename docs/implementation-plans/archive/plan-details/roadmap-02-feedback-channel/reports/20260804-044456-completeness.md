A reviewer typo in a hand-written `row_id` deadlocks the same way, and step 5 deliberately never gates the predecessor, so nothing catches it before the calls are spent.
- HIGH `[gate-rule-prompt-coverage]`: Step 2's acceptance criteria claim a green suite that step 4 says step 2 breaks, and the code at HEAD sides with step 4. Step 2 asserts "`uv run pytest tests/test_roadmap_gates.py tests/test_roadmap.py … -q` is green, with the last three files unmodified"; step 4 (`Add the shared revision prompt and its LLM reflection contract`) says "step 2's landing leaves those two cases red, and this step owns the repair". `tests/test_roadmap.py:test_domain_prompt_states_every_domain_gate_rule` is parametrized over `DOMAIN_GATES` and opens with `assert subjects, …`, so appending three gates with no entry in `_GATE_PROMPT_SUBJECTS` reddens three cases; the constraints sibling reddens three more. Step 4 is the more-detailed decision and is right about the mechanism, so the body to fix is step 2's: it cannot be marked done under a criterion that is false the moment it lands.
- MEDIUM `[cross-artifact-locality]`: Steps 4 and 5 both state a locality guarantee that cannot hold, because feedback rows live inside the artifact text those steps hand forward. Step 4's guardrails say "An upstream artifact's feedback text never reaches a later stage's prompt, even though its artifact text does" and step 5's repeat "An upstream artifact's feedback rows must not reach a later stage's envelope or prompt, even though its artifact text does" — but step 1 renders `feedback` into the artifact's frontmatter, and `_render_stage_prompt` sets `variables[f"{loaded.stage.artifact_key}_artifact"] = loaded.text`, the whole file. The plan body is already correct and narrower ("does not hand stage 1's active feedback text to stage 2"), so the detail guardrails are the side to fix; an implementer trying to satisfy them as written would have to strip feedback out of the upstream text, breaking the "disk is the interface between stages" property.
- MEDIUM `[deferred-feedback-citation]`: Step 2's removal-citation rule lets a `deferred` feedback row authorize dropping a design row, contradicting the plan's own statement that a deferred row is inactive. The gate says only "A **new** removal's `feedback_ids` each name a predecessor feedback row", with no constraint on that row's state, while the Architecture says "A deferred row is retained but not sent" and "Only open rows are active feedback". A model can therefore drop an entity and cite a request the reviewer explicitly parked, and the gate passes — the same hole `VIOLATION_INVENTED_FEEDBACK` exists to close, reached through a real id instead of a fabricated one.
- MEDIUM `[removal-record-lifetime]`: Step 2 contradicts itself on whether a removal record survives later revisions, and nothing in the design pins it either way. One paragraph calls it permanent — "a removal is a permanent record while feedback is deliberately transient" — and the next declines to choose: "the rule works whether removals accumulate across revisions or the reviewer prunes them — this step does not decide which". Continuity walks `_rows_of(predecessor)`, which names design rows only, so a removal record is unpinned and a model may silently drop it on the next revision, erasing the stated reason a row disappeared. The plan's Architecture leans on that record ("A model therefore cannot silently delete a row or declare arbitrary cleanup without a reviewer-originated reason"), so the undecided lifetime is load-bearing rather than cosmetic.
- HIGH `[gate-message-text-leak]`: Step 2's three new gates emit messages that `plan_tool/roadmap.py:_run_stage` passes straight into `run_logger.gate_violations(messages=violation_messages)`, so any message that quotes a reviewer's `request` or the model's `proposed_response` writes that text into `.plan-tool/runs/` — defeating the plan's own criterion "The run log proves delivery with ids, counts, and predecessor digest **while omitting feedback and response text**". Step 3 closes only two channels (the event's fields, and `**extra` via step 6) and step 2 says only that a message "anchors on ids only", which is a rule about retry-text standalone-ness, not a ban on quoting prose; an implementer writing `VIOLATION_ALTERED_FEEDBACK_SOURCE` would naturally quote the expected request so the model can fix it.
- HIGH `[verbatim-request-retype]`: Step 2's `VIOLATION_ALTERED_FEEDBACK_SOURCE` compares the predecessor's `request` to a string the model has to retype into YAML, and a multi-line request can differ in value while reading identically. A reviewer's `request: |` block carries a trailing newline; the renderer re-emits it as `request: 'line one\n\n  line two\n\n  '` (verified with `yaml.safe_dump` at HEAD), and a model that re-emits the same visible words on one quoted line or without the closing blank line produces `line one line two` or a value missing its trailing `\n` — a violation on a request nobody changed, on the plan's headline flow. Step 1 analyses this styling only for parse/render (`test_a_multi_line_request_round_trips_by_value`), never for the model's re-emission, and the resolving constraint is that the retry message cannot simply quote the expected text without the run-log leak above.
- HIGH `[invented-feedback-without-predecessor]`: Step 2 makes `VIOLATION_INVENTED_FEEDBACK` a predecessor-derived rule and leaves only feedback-id uniqueness running "always", so a stage with **no** predecessor can write model-authored `feedback` rows and cited `removals` with nothing to reject them. That is reachable, not theoretical: step 5 documents deleting an artifact as the way to ask for a fresh authoring pass, and a constraints stage authoring fresh receives the revised `01-domain.md` — feedback rows, reviewer prose and all — as its upstream text. The invented rows are indistinguishable from the reviewer's on the next run, where they can authorize a cited removal and be counted by step 7's "awaiting your review" block, breaking the Architecture's claim that a model "cannot silently delete a row or declare arbitrary cleanup without a reviewer-originated reason". The constraint that shapes the fix: a blanket "no feedback without a predecessor" gate would break `plan_tool/roadmap.py:_load_and_regate_below`, which re-gates below-stage artifacts with `predecessor is None` and where the reviewer's rows are legitimate — the envelope cannot today tell a first-run write from a below-stage re-gate.
- MEDIUM `[orchestrator-state-transition]`: The Architecture's "Touched surfaces and boundaries" says `roadmap.py` "performs the allowed feedback state transition", and step 6 (`Write lifecycle-preserving revisions without automatic feedback removal`) says the opposite as its headline decision: "**the orchestrator never edits a feedback row** — it does not flip a state, does not clear an answered row... writing the artifact that cleared step 2's gates is how the `open` → `awaiting-review` transition lands on disk." Step 6 is the more-detailed and deliberate decision — the whole step exists to forbid orchestrator-side lifecycle edits — so the body is what is wrong, and left as written it invites exactly the repair step 6 spends three paragraphs banning.
- MEDIUM `[cascade-removal-deadlock]`: A domain redirect that drops a design row leaves the constraints stage with no legal move, and no Risk or doc warns the reviewer before they pay for it. On `--from-stage 1`, if stage 1 drops an entity through a cited removal, `02-constraints.md` must drop the constraint anchored to it — but step 2's always-on `VIOLATION_UNCITED_REMOVAL` needs a feedback id **in the constraints artifact**, while keeping the row trips the shipped `check_constraint_anchors`. Step 2 names the cascade and ships the plan's answer ("the reviewer places feedback in each artifact"), yet that answer needs the reviewer to predict which rows the model will remove *before* the run; in practice stage 2 spends its whole budget and the run exits 1. The plan's Risks names only the general "deliberate duplication" cost, and step 8's RUNBOOK section says a low re-entry "sends every stage its own feedback" without naming this outcome.
- MEDIUM `[overwrite-advice-owner]`: No step corrects the printed advice that step 8 identifies as wrong, because step 10 assigns it to step 7 and step 7 declines it. Step 8's Why says `_overwrite_summary_lines`' "copy it aside first if you edited it by hand" is "now wrong as blanket advice, because a revision preserves ids, feedback rows, and settled decisions"; step 10's Deferred routes both that line and `_print_completed`'s in-code comment (`# Never "re-enter at that stage": --from-stage N rewrites artifact N itself, so that advice destroys the edit it just asked for`) to step 7 as code; step 7 instead says "Do not repeat the copy-aside caution here — the overwrite block owns it" and "Leave the existing line alone." The result is a summary that warns against the loop this position ships, in the one file (`plan_tool/cli/roadmap_cmd.py`) step 7 already owns.
- MEDIUM `[deferred-row-not-sent]`: Deferring a feedback row does not stop the model from seeing it, but the plan body twice promises it does. The Architecture says "A deferred row is retained but **not sent**" and the acceptance criteria say the reviewer can "defer it **without resending it**"; step 4 (`Add the shared revision prompt and its LLM reflection contract`) says the opposite — "`awaiting-review` and `deferred` rows **are visible to the model inside the predecessor artifact text**" — and step 6 (`Write lifecycle-preserving revisions without automatic feedback removal`) counts them as delivered: "The delivered set is the predecessor's **whole feedback inventory**, not just its `open` rows. The model saw every row." Steps 4 and 6 are the forced side (a revision must carry the whole prior artifact, and `counts_by_state` is meaningless without the non-active rows), so the body is what is wrong, and a reviewer who defers a row to keep it out of the prompt is misled about a promise the design cannot keep.
- MEDIUM `[restore-removed-row]`: Asking for a removed design row back is a violation with no move the model or reviewer is told to make. Step 2 (`Add predecessor continuity, feedback-integrity, and settled-choice gates`) runs "A removal does not name a row the same artifact still declares → `VIOLATION_REMOVAL_NAMES_A_PRESENT_ROW`" **always**, with no predecessor needed, and step 2 also keeps carried removals out of re-judgement by treating `carried = set(predecessor.removals)` as untouchable history — "a removal is a permanent record". So once `entity-3` is dropped by a cited removal, any later revision that re-declares `entity-3` trips the gate, and the only escape (dropping the carried removal record) is stated nowhere: step 4's revision contract describes the removal path only for *adding* one, and step 8's preserved-versus-not table never names the case. The same trap catches a reviewer who hand-restores the row, because `_load_and_regate_below` turns that violation into a hard pre-flight `RoadmapError` on a `--from-stage 2` run. This survives whichever way `[removal-record-lifetime]` is resolved: pinning removals as permanent makes the restore impossible, and pinning them as prunable still leaves the model with no stated permission to prune.
- MEDIUM `[step5-predecessor-dependency]`: Step 5 (`Load a stage's predecessor and build the temporal revision envelope`) declares `depends_on: [2]`, but its own Input section consumes step 4's contract — "Step 4 produces the revision prompt path. `_render_stage_prompt` gains a keyword-only `predecessor`" — and its test roster reuses the `feedback_row(...)` / `removal(...)` / `_predecessor(...)` helpers it says "step 4 adds to this same file". Step 5's code cannot compile against a tree where step 4 has not landed, so the declared graph permits an ordering the step forbids. Step 8 (`Document feedback lifecycle, targets, and the roadmap review loop`) has the same gap in the other direction: `depends_on: [1, 2, 4, 6, 7]` omits 5, while its Input reads "Step 5 owns when a predecessor exists".
- MEDIUM `[summary-both-outcomes]`: The Architecture scopes the feedback advisory to a completed run while step 7 deliberately prints it on an exhausted one too. The body says the CLI "after a **successful** re-entry, reports the number of feedback rows awaiting human review"; step 7 (`Surface feedback awaiting review in the roadmap completion summary`) makes the opposite its key design decision — "**the block is emitted for both outcomes, like the overwrite advice** — a stage that answered feedback and wrote it before a later stage ran out of attempts still produced a response the reviewer needs to read" — and pins it with `test_an_exhausted_run_that_wrote_a_revision_still_reports_the_count`. Step 7 is the more-detailed decision and carries the reason, so the body is the side that lags.

### Conceptual completeness

_Coverage gaps in the plan's own ideas that the detail bundle and code at HEAD don't already resolve: orphaned concepts, uncovered risks, dangling acceptance criteria, missing edge cases._

- HIGH `[clarification-answer-path]`: The plan promises a clarification exchange but never says how the reviewer answers one. The Architecture has the model "asking a focused question when the request is ambiguous", the Testing section requires "one genuinely ambiguous request", and step 9 (`Exercise real redirect and clarification feedback and record human outcomes`) calls answering it "the strongest available evidence that the loop closes rather than just delivers" — yet no step defines the human's half. Step 7's block names only three actions (close, reopen, defer), step 8's lifecycle walkthrough shows a reopened row as "state back to `open`, response cleared or kept", and the Architecture states flatly that a row's "id, target, and request are immutable", which reads as forbidding the one edit that would answer the question. Reopening an unchanged request just re-asks the model the same ambiguous thing. Mechanically the edit works — the predecessor is snapshotted after the reviewer's edits, so an amended request is the source the gate compares against — but that is nowhere said, so the loop's clarification arm has no documented close.
- MEDIUM `[fresh-authoring-escape]`: A re-entry carrying no feedback is now a locked revision, and no step documents the way out. Step 4 fixes that "Revision mode is selected by **predecessor presence, not feedback presence**", so a reviewer who rewrites the brief and re-runs `--from-stage 1` gets step 2's continuity gate pinning every predecessor design row id, with removals only legal when they cite feedback that does not exist — the model can add rows but can never drop one. - MEDIUM `[below-stage-open-feedback]`: Open feedback written into an artifact below the re-entry point is silently never delivered, and no step names the case. Step 8's caveat that "a re-entry high says nothing about a lower artifact's rows" is written about the awaiting-review count, not about undelivered open requests.
