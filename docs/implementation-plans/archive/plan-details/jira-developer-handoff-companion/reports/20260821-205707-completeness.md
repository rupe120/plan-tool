Architecture, Risks, Testing, and Acceptance criteria cover valid-input failures before writing, not a failure between the two final publications, so one fresh artifact can remain paired with an old or absent companion.
  - Fix: Define the paired-publication failure and recovery contract so readers cannot treat a mismatched pair as fresh, and test a failure between final publications.
- HIGH `[selected-input-validation-scope]`: Architecture says “If an input is absent or malformed, the export will fail before either final output is written,” while Acceptance criteria says “The normal story-only export and the independent Jira-grade authoring lane retain their current behavior.” Step 1 applies its snapshot to every Jira export, but at HEAD `plan_tool.jira:export_jira` and `_render_step_detail` allow run-grade steps with no detail file; the plan does not say whether the new hard gate is companion-only or changes that preserved behavior.
  - Fix: State the validation scope for companion and story-only modes, including which missing selected-input states remain valid for each grade.
- HIGH `[companion-provenance-lifecycle]`: Architecture says provenance “will make source changes visibly stale” and permits replacement only for a generated companion for the “same contract”; step 3 (`Define the generated developer-handoff format with provenance, staleness, and target ownership checks`), step 4, Testing, and Acceptance criteria do not define when freshness is compared or what stable identity makes two companions the same contract. A stored fingerprint cannot change when its sources change, and implementers can reasonably either reject stale regeneration by matching the fingerprint or overwrite an unrelated generated companion by not matching it.
  - Fix: Define when and how freshness is checked and reported, and distinguish stable replacement identity from the changing source-snapshot fingerprint.
- MEDIUM `[companion-cli-mode]`: Step 5 (`Add the opt-in Jira companion CLI mode...`) does not define how companion mode combines with existing `--format`, `--output`, `--dry-run`, `--no-write`, and `--stdout` behavior in `plan_tool.cli.jira_cmd:cmd_jira`. Those choices decide whether either artifact is written or printed and which target receives ownership checks, so operators can produce materially different handoffs while following the plan.
  - Fix: Specify companion-mode behavior for the existing output, format, dry-run, no-write, and stdout flags, including the paired artifact locations and reporting.
- HIGH `[source-conflict-visibility]`: Architecture, Testing’s “unresolved source-conflict fixture,” and the acceptance criterion require an unresolved source conflict to remain visible, but steps 1 (`Capture Jira inputs once...`), 3 (`Define the generated developer-handoff format...`), and 4 (`Publish the paired handoff atomically...`) do not name a source conflict signal or its owner. At HEAD, `plan_tool.schema:Plan` and `plan_tool.jira:export_jira` carry no source-conflict state, so the required fixture has no grounded input and could only invent a private resolution path.
  - Fix: Define what input condition records an unresolved source conflict, how the captured snapshot carries it, and how the companion presents it without resolving it.
- HIGH `[paired-snapshot-append-mode]`: Architecture requires both artifacts to identify the same selected paths, fingerprint, and generation mode, while steps 1, 2, and 4 preserve append behavior and Testing plus the first acceptance criterion require one captured snapshot. In `plan_tool.jira:read_existing_export` and `_export_jira_append`, `_FrozenTicket` keeps prior raw story content and a no-op append does not rewrite the story target; a companion built from current inputs can therefore claim a newer snapshot than its paired frozen stories.
  - Fix: Define paired-mode append and replacement behavior so the companion and retained story artifact either share one declared snapshot or the export refuses the misleading pairing.
