- HIGH `[stack-totality-binding]` [confidence: limited]: Step 2 (stack gates) makes totality bind "a first run and any lineage that already carries the collection" but not a candidate in a lineage without it. Constraints gates run on the artifact envelope alone (`plan_tool/roadmap_gates.py:CONSTRAINTS_GATES`, `check_hosting_totality(envelope)`), and a first run with no `stack` collection looks the same as an unrelated candidate with no `stack` collection. The plan cites two sentences as the property. Architecture: `Totality binds a first stage run and any version that already carries the collection.` Architecture: `A candidate in a lineage without the collection is not refused for that absence`. No step says how a first run is told apart from a candidate that predates the collection. Without that, either the first run silently skips totality, or every existing roadmap's unrelated candidates are refused, which is the first Risk. Step 4's prompt change also depends on this: a first run that omits the collection must be refused.
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): The plan promises that a first run must carry a complete stack and that an unrelated candidate in a stack-less lineage is not refused. It names no route that tells the two cases apart.
  - Fix: State the route by which the first-run case is distinguished from the stack-less-lineage candidate case when the totality gate runs, and give each case an acceptance example (first run missing the collection is refused; stack-less candidate is accepted). Leave the mechanism to `detail`.
- MEDIUM `[stack-single-source-of-truth]` [confidence: limited]: The plan says both "Each stack fact has exactly one source of truth across the roadmap" and, in step 2, that the gate checks "agreement between stack choices and any hosting or store `product`". An agreement check means two places hold the fact, so the single-source claim is false as written. Architecture also leaves the relationship "decided in `create`". Step 2's intent says stack rows are "the one source of truth that hosting and store `product` fields cannot contradict". Unchosen behavior: it is not stated what counts as a contradiction when the stack concern is `open` and a hosting or store `product` is set, or when a stack choice is `pending`. It also does not say which side a candidate must change to resolve one, or what happens to existing versions that already carry a store `product`, such as Integration's PostgreSQL, when a candidate adds the stack. Two implementers could build a refusal, a warning, or a silent override.
  - Fix: Pick one contract and state it once: which field is authoritative, which combinations of `open`, `pending`, and a `product` value are contradictions, and whether a contradiction refuses the artifact. Then reconcile Overview, Architecture, step 2, and the Risks entry to that wording.
- MEDIUM `[stack-open-vs-pending]` [confidence: limited]: The plan uses `open` (a concern the brief leaves undecided) and `pending` (a choice that is a decision anchor, step 2) as separate states. Step 5, step 6, and the first Testing bullet require them to be "listed separately". No section defines either term, says which one a concern may be in (a row, a decision record, or both), or says how a row moves between them. The "listed separately" criterion therefore has two materially different passing readings.
  - Fix: Define `open` and `pending` once in Architecture, with the state each row can hold. Make Testing and the Verification criterion cite those definitions.
- MEDIUM `[integration-replay-verifiability]` [confidence: limited]: The Verification criterion says "a Integration-brief replay records the deployment platform as open". Step 4 and Testing run the replay "under the invoker seam, never a real backend". A stubbed invoker returns canned output, so the test shows only that canned `open` is parsed and gated. It cannot show that the changed prompt makes a model record `open` or avoid inventing a vendor, which is the Integration symptom the Problem section describes.
  - Fix: Restate the replay's deterministic claim as what it can observe: canned output with `open` passes the gates and renders, and the prompt carries the open-versus-invented-vendor instruction. Record model behavior on the real Integration brief as a separate, non-gating observation.
