Under this rule a newer build that adds one optional key keeps writing `format_version: 1`; the older build's gate passes it as supported, `Plan.model_validate` then fails with the unknown-field error, and the operator is back at the exact harm the plan exists to remove. The Architecture states the rule for both classes at once:

  ```
  An additive field or section with a default does not bump a version. A break
  does. Readers support current and current-minus-one; writers emit current
  only; version N retires by a dated, user-approved record before N+2 ships.
  ```

  while the Problem statement already establishes why it cannot hold for the plan class:

  ```
  `Plan` sets `extra="forbid"` (`schema.py:208`), and `PLAN_FORMAT.md`
  validation rule 8 rejects any unknown frontmatter key. A plan written by a
  newer `plan-tool` is therefore a hard parse rejection by an older one,
  surfaced as an unknown-field typo, with nothing in the artifact saying the
  format moved.
  ```

  The rule is sound for the run-grade detail class, whose body parser (`detail.py:parse_detail_file_sections`, `review.py:check_detail_body_completeness`) ignores extra H2s — the asymmetry is between the two classes, and the single shared sentence hides it. Sites: Architecture § "Version evolution extends the documented policy, and reading never upgrades"; Problem statement; step 5 (`Register the two authored-artifact version constants…`), which writes this rule into `DATA_CONTRACT.md`.
  - Fix: Split the additive-vs-break rule by class in the Architecture paragraph and in the `DATA_CONTRACT.md` policy step 5 authors — any new plan frontmatter or step key is a break that bumps the plan format version because `Plan`/`Step` forbid extras, while the detail class keeps the additive-is-compatible rule — and add an acceptance criterion pinning that asymmetry.
- MEDIUM `[refused-detail-recovery-route]` [confidence: limited]: Step 3 (`Add the fixed run-grade detail body marker and shared parser…`) lists `detail` among the commands that stop on an unsupported marker — "audit, reconcile, annotation, detail, and scope-out stop before using the unsupported body" — while step 4 (`Make detail.py the sole authority for the current run-grade detail marker…`) promises "keeping the archive-then-overwrite of a prior detail file unchanged". `detail` is the only writer that can replace a refused body, and it reads prior bodies on several paths (`detail.py:_read_step_detail_body`, the merge path's `prior_bodies`, the quality read at `detail.py` that opens `step.detail`). Two implementers can read the plan as (a) `detail` refuses outright, leaving a refused file unfixable by the tool, or (b) the plain regenerate path never reads the prior body, so it archives and overwrites normally and only merge/quality/reconcile refuse. No criterion decides it, and the two produce materially different operator outcomes.
  - Fix: Decide in the plan whether `detail` regenerating a step whose existing run-grade body is refused proceeds through archive-then-overwrite or stops, state the operator's route to replace a refused detail file, and add an acceptance criterion that reconciles step 3's fail-closed reader list with step 4's unchanged-overwrite promise.
