- HIGH `[staging-reclamation]`: Architecture says step 1 removes its own staging file and later cleans crash-left entries after ownership checks; Risks, Testing, and the final-enumeration acceptance criterion repeat that cleanup must touch only owned staging files. A no-follow type/path check cannot tell a crashed file from another live creator’s staging file, so reclamation can delete active work or avoid all old files and leave crash debris forever, despite the required two-creator behavior.
  - Fix: define per-call staging identity and a recovery policy that preserves live creators while reclaiming only definitely orphaned staging entries, then cover it in the interleaving and cleanup tests
- MEDIUM `[unsafe-entry-scan-outcome]`: Architecture says “links, special entries, unexpected final filenames … produce `unsafe-storage`,” then says “Final enumeration returns safe final records plus entry status … for unsafe entries.” Testing and acceptance require both unsafe-shape rejection and final-only enumeration, but do not choose whether one bad sibling stops a scan or is returned as metadata beside safe results.
  - Fix: define the namespace-level versus entry-level unsafe outcome and reconcile Architecture, Testing, and acceptance criteria to that single scan rule
- MEDIUM `[final-scan-record-contract]`: Step 2 promises deterministic final-only scanning, but Architecture’s “safe final records plus entry status and escaped relative location metadata” does not say whether safe records carry opaque bytes, which statuses exist, how locations are escaped, or what ordering is deterministic. Testing and the final-enumeration criterion therefore permit incompatible scan APIs and cannot prove the promised result shape.
  - Fix: define one scan-entry contract covering safe payload availability, the closed status set, escaped-location format, and deterministic ordering across Architecture, Testing, and acceptance criteria
- HIGH `[link-safety-boundary]`: Architecture says “links … produce `unsafe-storage`” but also “links the staged file exclusively into the final directory”; Testing and the second acceptance criterion require links to be rejected, while steps 1 and 2 must publish and scan the resulting regular files. `O_NOFOLLOW` handles symbolic links, not hard-link aliases, so the plan neither defines the allowed publication link nor says how scanning treats other hard-linked regular files.
  - Fix: Define the symbolic-link and hard-link safety policy, including the expected private staging-to-final link and the checks that make a final record safe to reuse or enumerate.
- MEDIUM `[storage-failure-classification]`: Architecture reserves `unsafe-storage` for unsafe shapes and names `write-failed` without defining it, while the existing-record path can fail during open, read, file fsync, directory fsync, or staging cleanup after publication. Testing covers write failure but not the returned result for those paths, so callers can receive exceptions or different result codes for the same storage failure.
  - Fix: Define one result mapping for publication, existing-record reads, fsyncs, cleanup, and interruption, including failures after a final link exists.
