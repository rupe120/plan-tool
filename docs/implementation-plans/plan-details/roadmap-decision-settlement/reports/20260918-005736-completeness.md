- HIGH `[unenrolled-settlement-seed-invalidation]` [confidence: limited]: Step 4 and the Architecture section both claim the un-enrolled write touches only the target artifact and its own stage baseline, but the named mechanism does not deliver that by default. Step 4's title states:

```
Settle one decision on an un-enrolled roadmap and publish its receipt through publish_stage_artifact's multi-member generation, keeping the existing journal recovery (roll back or drop an in-flight generation) unchanged and updating the selected artifact's bytes and its stage baseline record together — no seed-state or other artifact/stage is rewritten
```

  and the Architecture "Un-enrolled roadmap" bullet restates it: "No other artifact, seed-state, or unrelated stage's baseline is touched." At HEAD, `publish_stage_artifact` (`plan_tool/roadmap_revision_publish.py:517`) defaults `invalidate_seeds=None`, which resolves `include_seed_state = True`, which always loads and rewrites the roadmap's single shared `seed_state.json` via `invalidated_seed_state(...)` — a function whose own docstring is "Return an independent state where every derived seed is stale" (`roadmap_seed_state.py:111`) and which unconditionally sets every existing seed entry's `status` to `"invalidated"` (`roadmap_seed_state.py:122`), a status consumed downstream to classify drafts as needing rework (`roadmap_seed_manifest.py:121,137`). The only existing call site of `publish_stage_artifact` (`plan_tool/roadmap.py:2932`, the ordinary stage-run path) never passes `invalidate_seeds`, so there is no precedent in the codebase for calling it with seed-state left alone — `invalidate_seeds=False` is currently unused anywhere. So the exact mechanism the plan names, used as the plan describes it, would silently mark every already-authored derived plan seed "invalidated" the moment an operator settles one Domain/Constraints/Components/Plans decision, on any stage, whenever the roadmap has already reached the point of deriving plan seeds — directly contradicting the plan's own stated guarantee that the write is narrow and touches nothing beyond the one artifact and its own baseline.
  - Fix: State explicitly, in the Architecture and step 4, that the un-enrolled settlement write must call the publication primitive with seed invalidation suppressed (e.g. `invalidate_seeds=False`), and add a test/acceptance criterion asserting the roadmap's seed state is byte-identical before and after a settlement.
- HIGH `[enrolled-settlement-version-provenance]` [confidence: limited]: Step 5 and its supporting Architecture text and Risk both assert the enrolled path can reuse `roadmap_versions.py`'s storage primitives independently of "the seal precondition chain," but at HEAD that storage layer's own schema — not just `promote_review_seal`'s preconditions — is where the review-provenance binding actually lives, so the claimed decoupling doesn't hold as stated. The Architecture "Enrolled roadmap" bullet says:

```
Settlement instead adds one new, narrow, non-model promotion boundary: store the settled artifact bytes as a new immutable version (reusing the existing storage primitives in roadmap_versions.py), prove it gate-valid with the existing check_complete_roadmap_gates evaluator ... then advance accepted_head_path under the existing writer-token lease and PendingGeneration journal — the same selector-swap mechanics promote_review_seal uses, without its seal/review preconditions.
```

  and the Risks section states: "an enrolled settlement must never fabricate a fake `CandidateProposalAdmission`/`CandidateReviewSeal` chain ... that would misrepresent a deterministic change as model-proposed and reviewer-sealed." At HEAD, `StoredRoadmapVersion.version_kind` is a closed `Literal["root", "candidate"]` (`roadmap_versions.py:115`); `"root"` can only ever be written once, at initial enrollment (`build_root_enrollment_generation` refuses when a selector already exists, `roadmap_versions.py:434`), so a post-enrollment settlement can only use `"candidate"`. The model validator on `StoredRoadmapVersion` requires a non-null `review_lineage_identity` for every `"candidate"` record (`roadmap_versions.py:184-187`), and that field is not a free-form identity: it is either the sentinel `INITIAL_EMPTY_REVIEW_LINEAGE_ID` (meaning "not yet reviewed," used only for a freshly-proposed, not-yet-promoted candidate at `roadmap_candidate_run.py:977,981`) or a hash of a genuine reviewer question-inventory id and answer id (`_review_lineage_identity`, `roadmap_candidate_review.py:1752`, produced only after a real review answer at `roadmap_candidate_review.py:1661`). Every `"candidate"`-kind stored version is additionally expected, by existing readers, to carry a matching on-disk evidence record that is checked field-for-field against it (`load_stored_candidate_proposal`, `roadmap_candidate_run.py:405-414`; `load_stored_candidate_review_replacement`, `roadmap_candidate_review.py:1281-1290`). So storing a settlement version as `"candidate"` forces a choice the plan never makes and that the current schema has no third option for: either give it `INITIAL_EMPTY_REVIEW_LINEAGE_ID` — misrepresenting an already-promoted, never-reviewed version as an ordinary unreviewed pending candidate, a case that has never previously reached the accepted head — or compute a lineage hash without a real inventory/answer pair, which is exactly the synthetic-provenance fabrication the plan's own Risk section forbids. Reusing "the existing storage primitives" is therefore not decoupled from the review-provenance meaning the plan wants to avoid; resolving this cleanly needs either a new `version_kind` (an unstated, unscoped closed-vocabulary change touching this model's own validator and its existing consumers) or an explicit, argued exception to what `review_lineage_identity` is allowed to mean, and the plan currently asserts a reuse path that neither the code nor its own stated constraint actually supports as described.
  - Fix: Decide explicitly, in the Architecture, how a settlement-authored stored version fits the closed `root`/`candidate` vocabulary and what its `review_lineage_identity` legitimately means without claiming a review that never happened — either define and scope a new version kind (naming every site in `roadmap_versions.py` and `roadmap_candidate_review.py` that must recognize it) or state the specific non-review-claiming value settlement will use and confirm no existing consumer treats it as an ordinary reviewed or pending candidate.
- MEDIUM `[settlement-write-path-authority]` [confidence: limited]: The plan's Problem statement and References section both point at extending `TEXT_FIELDS_BY_ROW_TYPE`/`preflight_feedback_revision` (`plan_tool/roadmap_revision.py`) as part of what fixes the missing settlement authority, but step 1 and the rest of Architecture commit to a wholly separate, dedicated helper that never touches that allowlist, explicitly keeping `replace_design_row` refusing enum fields exactly as today (confirmed at HEAD: `replace_design_row` in `plan_tool/roadmap_artifacts.py` rejects any field whose current value is an `enum.Enum`, which `status` is). `TEXT_FIELDS_BY_ROW_TYPE`/`preflight_feedback_revision` back the generic, unconfirmed `--revise-feedback` local-revision path (`replace-row-presentation`), which has no evidence selector, no confirm flag, and no receipt — the opposite of what the rest of this plan builds. An implementer following the References pointer literally, rather than step 1's title, could add `"status"` to the `decisions` tuple in `TEXT_FIELDS_BY_ROW_TYPE`, silently opening an unconfirmed, non-evidence-bound path to flip a decision's status that bypasses every guardrail this plan exists to add.

  ```
  preflight_feedback_revision) — the field-authority allowlist to extend,

  Step 1 title: "...replace_design_row keeps refusing enum fields and no

  ```
