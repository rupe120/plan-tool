- HIGH `[escalation-selector-eligibility]`: Step 1 (`Separate feedback selection from local revision eligibility while preserving seed invalidation and one-artifact replacement`) leaves escalation eligibility undefined. Architecture names “unknown, duplicate, closed, or stale selector,” while Testing and Acceptance criteria add “removed” and “cross-artifact-invalid”; `plan_tool.roadmap_artifacts:FeedbackState` has only `open`, `awaiting-review`, and `deferred`, and `FeedbackTarget` has no target-artifact field. `plan_tool.roadmap_revision:parse_feedback_selector` and `preflight_feedback_revision` cannot supply those meanings, so deferred, artifact-targeted, removed-target, and stale-report rows can be handled differently.
  - Fix: Define one escalation eligibility and rejection vocabulary for feedback state, target resolution, artifact qualification, and report freshness while preserving intended local-ineligible cases.
- MEDIUM `[escalation-reason-vocabulary]`: Step 3 (`Define deterministic escalation reports with safe paths, bounded context, digest checks, and owner-stage routing`) promises a classification and an operator-selected reason, but Architecture only says reasons “cover prose, row or collection structure, relationship or decision semantics, and cross-artifact impact.” Step 6, Testing, and the deterministic-classification acceptance criterion therefore have no single set of values or reason-to-classification/routing rule to implement.
  - Fix: Specify the closed escalation-reason vocabulary and its deterministic mapping to report classification and routing outcome.
- HIGH `[relation-closure-owner-stage]`: Architecture and Input use “directly declared relation neighbors” and “declared relation closure”; Risks, Testing, and steps 2 (`Extract stable roadmap relation edges without changing existing views`), 3, and 6 depend on that boundary. `plan_tool.roadmap_view:build_citation_map` deliberately omits `FieldRow.entity_id`, `OrderingEntry.depends_on`, and `OrderingEntry.assumption_targets`, while `plan_tool.roadmap:STAGES` maps artifact keys to stages but supplies no closure-to-route rule. Reports can therefore disagree about included artifacts, context accounting, and the safe `--from-stage` recommendation.
  - Fix: Define one ordered relation-edge and closure contract, including direction, depth, cycle handling, refusal cases, and the rule that maps a resolved artifact set to one safe route or a schema/ownership-decision result.
- HIGH `[escalation-report-identity-freshness]`: Architecture says a report records “creation time, and a stale/current result” and is “immutable by convention,” while step 5 (`Write only new immutable escalation reports`) requires repeated writes and step 6 (`Wire --escalate-feedback and --view escalations to report-only writes and log-free reads`) must inspect them. Testing and Acceptance criteria require unchanged runs to be semantically identical and stale reports to be rejected, but define no report identity, path, collision policy, repeat-run behavior, view selection, or derived freshness rule; an immutable stored “current” result becomes false after source changes.
  - Fix: Define report identity and creation policy, report listing/selection, and a live freshness check from recorded input digests that withholds routing for every stale report.
- HIGH `[snapshot-consistency]`: Architecture’s report and digest paragraphs, Input, the stale-evidence Risk, Testing, and Acceptance criteria require revision-bound evidence across named artifacts; steps 3, 5, and 6 construct, persist, and display it. They do not define what happens when `plan_tool.roadmap:run_roadmap` changes an artifact while the report reads its closure; `plan_tool.roadmap_revision_publish:roadmap_writer_guard` coordinates canonical writers but the plan gives report readers no equivalent rule. The report can mix artifacts from different revisions and still appear current.
  - Fix: Define a coherent report-snapshot rule that detects or excludes concurrent canonical changes and emits stale/no-route evidence on interference.
- HIGH `[escalation-mode-exclusivity]`: Step 6 adds `--escalate-feedback` and `--view escalations`, but Architecture only says escalation never invokes `--from-stage`; it does not define conflicts with `--from-stage`, `--apply`, `--refresh-seeds`, `--accept-seed`, `--materialize`, `--from-existing`, `-y`, `--view`, `--mode`, or `--id`. `plan_tool.cli.roadmap_cmd:register` already gives `--revise-feedback` a special conflict path, so escalation can otherwise silently ignore a flag or reach a non-report branch.
  - Fix: Define escalation as an exclusive command mode and give every conflicting option one observable preflight-rejection result that preserves report-only writes.
- MEDIUM `[escalation-run-log-contract]`: Step 4 (`Add escalation run-log results while preserving atomic snapshot replacement and guarded cleanup`) forbids reviewer prose, while Architecture requires start, result, and failure records with selector, report digest, and stale/current outcome; step 5 consumes those results. Unlike the closed contracts in `plan_tool.run_log:RoadmapLocalRevisionPreflight` and `RoadmapLocalRevisionAttempt`, the plan defines no event fields, outcomes, nullability before a report exists, or redaction proof.
  - Fix: Define a redacted escalation event matrix for selector rejection, report creation, freshness read, write failure, and interruption, with tests for required fields and absent reviewer prose.
- HIGH `[relation-membership-staleness]`: The digest contract in Architecture, Input, Risks, Testing, and Acceptance criterion “Editing any named canonical artifact…” only checks artifacts already named by a report. Steps 2 and 3 can derive an incoming relation from an artifact absent from the old closure; `plan_tool.roadmap_view:build_citation_map` reads citations from all four roadmap artifacts. A new relevant relation can therefore leave an old route marked current.
  - Fix: Bind freshness to both relation-closure membership and the artifacts that determine that membership, so a new relevant relation invalidates prior routing evidence.
- MEDIUM `[broad-route-source-prerequisite]`: Architecture and Acceptance criterion 9 treat an unambiguous owner stage as enough to recommend `--from-stage`, but `plan_tool.roadmap:_resolve_brief_path` rejects that command without a recorded `source.json` unless the operator supplies `--from-existing PATH`. Input, steps 3 and 6, and Testing omit source availability, so the recommended next action can fail before stage routing.
  - Fix: Include recorded-brief availability in route recommendations and state the safe `--from-existing` alternative when it is absent.
- HIGH `[context-slice-boundary]`: Architecture says the context estimate includes “its owning artifact and target” and reports “included context slices,” while Input repeats that scope and the over-broad-context Risk excludes unrelated artifact prose. Steps 3, 5, and 6, Testing, and acceptance criteria 1 and 5 never say whether an included artifact contributes its full `body`, all rows, or only the target and relation fields; `plan_tool.roadmap_artifacts` stores free-text `body` alongside those rows.
  - Fix: define the exact context slice for each target kind and relation member, including body inclusion, ordering, and byte/count accounting.
