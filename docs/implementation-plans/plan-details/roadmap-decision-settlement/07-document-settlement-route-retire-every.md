# Step 7 — Document the settlement route; retire every live hand-edit instruction; correct the accepted-head-authority and drift-protection claims it invalidates

<!-- plan-tool:detail-format-version: 1 -->

## Summary

This step ships no code. It replaces the hand-edit instruction for settling a `pending` roadmap decision — currently repeated across eight docs — with the confirmed action steps 1–6 built (`plan-tool roadmap <slug> --settle-decision <artifact>:<decision-id> --settlement-evidence <artifact>:<feedback-id> --confirm-decision-settlement`), and gives an operator who already hand-edited a way back. It then corrects three claims those same steps falsified: `ROADMAP_FORMAT.md`'s "Immutable candidate-version authority" block and `CAPABILITIES.md`'s accepted-head paragraph both say only `promote_review_seal()` can move the accepted head, when step 5's `run_enrolled_decision_settlement()` is a second guarded writer; and `ROADMAP_FORMAT.md`'s Decision status paragraph and `check_settled_decisions`'s gate-table row both read as if settled-decision drift protection holds everywhere, when `BUG_BACKLOG.md` already records that the enrolled lineage's gate evaluator passes `predecessor=None` and never runs it. `tests/test_roadmap_format.py::test_candidate_policy_reference_keeps_review_inert_until_exact_promotion` pins the exact string this step edits and must change with it. The rest of the step is bookkeeping the new capability earns: a settlement bullet in `CAPABILITIES.md`'s roadmap entry, a third `EvidenceNamespace` and a new module paragraph in `docs/ARCHITECTURE.md`, a leaf-import bullet in `CLAUDE.md`, one `BUG_BACKLOG.md` entry extended to name the new journal shape and one removed because the capability it asked for now ships. On green, no doc tells an operator to hand-edit `status: settled`, every accepted-head claim names both writers, every drift-protection claim is confined to the lineage that actually has it, and `plan-tool validate` and the full suite stay clean.

## Why

Eight live docs currently tell an operator to settle a `pending` decision by hand-editing `status: pending` to `status: settled`: `README.md:524`, `docs/how-to/common-workflows.md:79` (the same paragraph, duplicated), `docs/how-to/roadmap-demo.md`'s "### `pending` decisions — settle by editing" (around line 205), `RUNBOOK.md:468` ("Settling a `pending` decision remains an editor action"), `docs/how-to/use-cases.md:317`'s parenthetical, `integrations/shared/DIRECTIVES.md:216`, `ROADMAP_FORMAT.md`'s Decision status paragraph (around line 1619: "editing its status to `settled` by hand"), and `docs/how-to/roadmap.md`'s § 4 heading and body (around lines 229–235: "That edit is the resolution; there is no separate settle command"). Step 4's own Why section confirms the instruction is not just stale but actively wrong: `status` is part of `canonical_projection`, so a hand-flipped row no longer matches its `.roadmap-baselines` record and re-entry refuses it (`tests/test_roadmap.py::TestBoundedReentryRoutes::test_semantic_reentry_drift_returns_invalid_without_invocation`). Every one of these docs is telling an operator to do something that fails, with no route back once they've done it.

Three more claims go stale the moment steps 4–6 land, independent of the docs above:

- `ROADMAP_FORMAT.md`'s "Immutable candidate-version authority" block (`<!-- immutable-candidate-version-authority:start -->`) states "Only `plan_tool/roadmap_version_promotion.py:promote_review_seal()` changes the accepted head." `CAPABILITIES.md`'s roadmap entry makes the same claim ("only that seal can move the accepted head"). Step 5 adds `plan_tool/roadmap_decision_settlement_enrolled.py:run_enrolled_decision_settlement()`, a second writer that moves the same selector through its own guarded journal (the `"decision-settlement"` `PendingGeneration.kind`). `tests/test_roadmap_format.py::test_candidate_policy_reference_keeps_review_inert_until_exact_promotion` pins the exact "Only …" sentence, so it goes red the moment the doc is corrected and stays red until the test is corrected with it.
- `ROADMAP_FORMAT.md`'s Decision status paragraph reads "On a revision, `check_settled_decisions` protects every predecessor decision marked `settled` with the same fence" — true on the lineage it was written for, and silently false on the other one. `BUG_BACKLOG.md`'s "An enrolled roadmap's candidate promotion never re-checks a settled decision against its predecessor" entry (already filed, untouched by this plan) records that `roadmap_impact_snapshot.py:_evaluate_full_roadmap_gates` — the evaluator every enrolled candidate promotion runs through — always builds `predecessor=None`, so `check_settled_decisions` is a permanent no-op there. The gate-table row for `check_settled_decisions` says "Predecessor only," which is true but doesn't say a predecessor is never supplied on the enrolled lineage. Once this plan ships an enrolled settlement action, a reader has every reason to assume settling a decision protects it the same way on both lineages; it does not, and step 6's own guardrails explicitly forbid writing a test or a docstring implying otherwise.
- `plan_tool/roadmap_evidence_store.py`'s two-member `EvidenceNamespace` (`ESCALATIONS`, `IMPACT_ANALYSES`) becomes a three-member enum once step 3 lands `DECISION_SETTLEMENTS`. `docs/ARCHITECTURE.md`'s "Immutable roadmap evidence" paragraph names the two existing namespaces and their fixed paths explicitly; left alone, it undercounts the store the moment step 3 ships. The same section's sibling paragraphs — "Structural escalation receipts," "Impact-routing analyses" — are the established shape for describing a namespace's consuming module family, and step 3's own Deferred section names this as step 7's job.
- `CLAUDE.md`'s "Cycle-free import constraints" list documents every leaf's import discipline in this package; step 2's own Deferred section names `plan_tool/roadmap_decision_settlement.py`'s leaf status ("first-party imports are exactly `roadmap_artifacts`, `roadmap_escalation_selection`, `roadmap_feedback`, `roadmap_source_identity`, and `roadmap_versions`; never `roadmap` or `roadmap_revision_publish`/`roadmap_feedback_reopen`") as belonging here, and it is absent today.
- `BUG_BACKLOG.md` carries "Approved roadmap decisions cannot transition from `pending` to `settled`" (filed against the exact gap steps 1–6 close) and "Incomplete immutable lifecycle journals can permanently block a resumed proposal, review, or promotion" (a class of bug step 5's new `"decision-settlement"` generation shape is now also an instance of, per step 5's own Deferred: "Repairing a settlement journal interrupted before the swap … tracked by the `BUG_BACKLOG.md` 'Incomplete immutable lifecycle journals' entry"). The first is fulfilled and must go; the second must name its new instance or a reader has no way to know the settlement journal shares the same recovery gap.

## Input

Steps 1–6 have detail files but none has landed at HEAD (this plan is still `status: planning`); read every name off the landed module once steps 1–6 ship, since the landed names win over any file, including this one. This step depends on step 6 for exactly these public facts:

- **The confirmed CLI shape** (step 6): `plan-tool roadmap <slug> --settle-decision <artifact-key>:<decision-id> --settlement-evidence <artifact-key>:<feedback-id> --confirm-decision-settlement`. One call, one decision, no batch form. The CLI tries the un-enrolled runner first and falls back to the enrolled runner only on `enrolled-roadmap-rejected`; both lineages produce the identical settled row for the same input (step 6's `TestDecisionSettlementProducesTheSameRowOnBothLineages`).
- **The shared result shape** (step 4, reused by step 5 and rendered by step 6): `DecisionSettlementRunResult` with outcomes `settled` (status `0`), `preflight-rejected` (status `2`), `receipt-rejected` (status `1`), `write-failed` (status `1`), `interrupted` (status `130`). The result is redacted — no `request`, `proposed_response`, or `rationale` text.
- **The receipt** (step 3): one immutable, redacted record committed to `HEAD` in the third `EvidenceNamespace` member, before any canonical write. `decision_settlement_receipt_proves_completion` proves an enrolled receipt for as long as the settled version stays in the accepted head's predecessor chain, and proves an un-enrolled receipt only while the stage's exact bytes still equal the settled bytes — an exact comparison that a later edit to the same artifact ends, **including deleting the cited feedback row**, which baseline admission alone cannot see (step 3, `test_deleting_the_cited_feedback_row_ends_the_unenrolled_proof_though_the_baseline_still_admits`).
- **The three enrolled-lineage limits, each stated as a permanent property of this design, not a bug this plan owes a fix for:**
  1. Citable feedback must predate enrollment — an enrolled roadmap's citable feedback set is exactly what the accepted version already carries; there is no route to add feedback after enrollment (`BACKLOG.md` #394).
  2. An admitted candidate lineage the operator never finishes blocks settlement, with no way to abandon it — step 5 refuses as `unpromoted-candidate-lineage` whenever a stored admission's `predecessor_version_id` equals the current accepted head, regardless of the admission's age or state, and there is no discard route (`BACKLOG.md` #395).
  3. Non-canonical accepted bytes block settlement with no repair path — step 2's render-canonical check (`source-not-canonical`) applies on both lineages, but a stored version's bytes are immutable by design, so there is nothing to normalize or rewrite on the enrolled lineage (step 2, `test_enrolled_noncanonical_accepted_bytes_are_refused`).
- **The hand-edit recovery fact** (step 4): a hand-flipped decision status fails source admission as `source-not-admitted`; restoring the pre-edit bytes (so the stage file matches its `.roadmap-baselines` record again) is what makes the same `--settle-decision` call succeed afterward (`test_documented_hand_edit_is_refused_until_the_pre_edit_bytes_are_restored`).
- **What `--revise-feedback` still cannot do**: `plan_tool/roadmap_revision.py:TEXT_FIELDS_BY_ROW_TYPE["decisions"]` is `("rationale",)` at HEAD, unchanged by this plan. `--revise-feedback` can replace a decision row's `rationale`; it has never been able to touch `status`, and this plan does not extend it to.

## Implementation

### 1. Retire the hand-edit instruction, with recovery guidance

Replace every instruction to hand-edit `status` to `settled` with the confirmed command. Put the fullest version of "what to do if you already hand-edited" in **`RUNBOOK.md`**, since it is this repo's dedicated recovery-recipes doc, and in **`docs/how-to/roadmap.md`** § 4, since step 4's and step 6's own References name it as the operator-facing procedure this plan's route replaces. The other six sites need only the corrected command and, where natural, a one-line pointer to those two — repeating the full recovery procedure in six places is exactly the restatement drift `CLAUDE.md`'s doc-ownership lessons warn about.

- **`README.md`** (the "`pending` decisions" bullet around line 524) and **`docs/how-to/common-workflows.md`** (the identical bullet around line 79, under "#### Two review channels") — both currently read "Settle one by editing its `status` to `settled` in place; that edit *is* the resolution." Replace with the confirmed command and its one-line contract (settles one decision on whichever lineage the roadmap is on; publishes a committed receipt; refuses an inherited row, a non-`pending` decision, unreviewed evidence, or a stale source). Consider also adding a synopsis line to README's `plan-tool roadmap <slug> ...` command catalog (the block at README.md:312–324, one line per action) matching that block's existing style, e.g. one way: `plan-tool roadmap <slug> --settle-decision <artifact>:<decision-id> --settlement-evidence <artifact>:<feedback-id> --confirm-decision-settlement # transition one Roadmap-derived decision pending → settled on whichever lineage the roadmap is on; publishes a committed receipt` — the hand-edit bullet sits directly below that catalog today, and leaving the catalog silent on the new action while the prose beside it explains it is the kind of split a reader has to reconcile by hand.
- **`docs/how-to/roadmap-demo.md`** — retitle and rewrite "### `pending` decisions — settle by editing" (around line 205–214). This doc is a live runbook for reproducing the demo, not a historical transcript, so its instruction has to keep working for a future demo run: it should tell the demo operator to run the confirmed command instead of hand-editing, and can drop "Settling a decision is an editor action" entirely. Leave § 5a ("The refused feedback row") untouched — that section is about the *reverse* direction (un-settling a decision to let a revision drop the row it anchors), which stays a hand-edit per the still-open "Reverting a settled decision to `pending` by hand fails source admission" `BUG_BACKLOG.md` entry, and this plan does not touch it.
- **`RUNBOOK.md`** — replace "Settling a `pending` decision remains an editor action. A subsequent feedback-free re-gate validates it but does not turn it into authoring work." (around line 468) with the confirmed command, and add the recovery recipe: an operator who already hand-edited a stage file's `status` field sees `source-not-admitted` on the next re-entry; the fix is reverting the edit so the stage file's bytes match its `.roadmap-baselines` record again, then running `--settle-decision`/`--settlement-evidence`/`--confirm-decision-settlement` instead. Leave the rest of this section alone — lines 479–490 and 576–581 both describe the *reverse* direction (a reviewer rejecting a revision's newly-settled decision, or un-settling one to permit a removal), which this plan does not build a route for and which stays editor work.
- **`docs/how-to/use-cases.md`** — the parenthetical at line 317 ("accepting a decision means changing its `status` to `settled`") becomes something like "accepting a decision means settling it: `plan-tool roadmap <slug> --settle-decision … --confirm-decision-settlement`."
- **`integrations/shared/DIRECTIVES.md`** — the sentence "Settle a `pending` decision by editing its `status` in place and re-entering **above** it so the edit is carried downstream" (around line 216) is not just stale but was already inaccurate before this plan (the hand edit fails source admission regardless of where you re-enter). Replace it with the confirmed command; this file is meant to be terse, so a single sentence naming the command and its one-line contract is enough — the fuller procedure belongs to `docs/how-to/roadmap.md`, which this file already points readers toward for the rest of the verb.
- **`ROADMAP_FORMAT.md`** — the Decision status paragraph's sentence "That still makes accepting a `pending` decision — editing its status to `settled` by hand — a queue an operator works down to zero" and the following "Editing the status is the *only* thing that edit does" (around lines 1618–1622) both describe the hand edit as the resolution mechanism. Correct them to describe the confirmed action instead, while keeping this paragraph's genuinely durable claim — that accepting a pending decision is a queue an operator works down to zero, never a tally that only rises — since that property is still true of the new action.
- **`docs/how-to/roadmap.md`** — restructure § 4 (heading stays numbered `## 4.`; nothing in the corpus links its anchor, so retitling is safe, but keep the section number since `BUG_BACKLOG.md:275` cites this doc as "§4" by number and needs it to keep resolving — `CLAUDE.md`'s own reference-docs bullet for this file cites only § 5, a different section, unaffected either way). Its first paragraph today ("Settle a load-bearing `pending` decision by changing its `status` to `settled` in the artifact. That edit is the resolution; there is no separate settle command.") is the exact claim this plan makes false. Replace it with the confirmed command's full contract: the two-lineage fallback behavior, the receipt, the three enrolled limits from Input (with their backlog pointers), and the fact that closing (deleting) the cited feedback row ends an un-enrolled receipt's proof. State plainly that `--revise-feedback` still cannot change `status` — it can only ever touch a decision row's `rationale` — so a reader doesn't wonder whether the new action folds into the existing revision route. Keep the section's second half (the feedback-free `--from-stage N` re-gate paragraph and example) exactly as it is; re-gating without settling is still the right tool for validating a direct semantic edit that isn't a decision status change.

## Applicable guardrails

- The plan's "## Scope guardrails" bar this plan from building an un-settle (`settled` → `pending`) route or claiming one exists. This step's docs must keep describing that direction as an editor action, exactly as `RUNBOOK.md` and `docs/how-to/roadmap-demo.md` § 5a already do, and must not extend the new command's documented behavior to cover it.
- Step 6's own guardrail — "don't claim anything about the enrolled lineage's drift protection" — binds this step directly: every place this step's docs describe `check_settled_decisions`, they must state the enrolled-lineage gap, never word it to imply parity between lineages.
- The plan's "## Out of scope" excludes any judgment of whether cited feedback constitutes real approval and any batch/bulk settlement form; this step's docs describe the command's actual refusal set (an unreviewed or non-`ROW`-targeted feedback row, more than one decision per call) without implying either capability exists.
- `CLAUDE.md`'s own "Documentation is forward-looking" rule governs every doc this step edits: the retired hand-edit instructions are deleted, not archived in place with a "used to" caveat, except where `RUNBOOK.md`'s recovery guidance genuinely needs to describe the prior (now-broken) state to tell an operator how to get out of it.
