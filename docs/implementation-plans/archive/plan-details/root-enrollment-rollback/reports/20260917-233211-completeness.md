- MEDIUM `[rollback-eligibility-independence]` [confidence: limited]: Step 1's eligibility gate treats "no accepted descendant" and "no review/seal record" as independent checks from "root-only accepted head" and "no candidate admission" — this five-condition list is repeated verbatim in Architecture, Risks ("Every one of the five eligibility conditions needs its own mutation test (violate one condition at a time, prove refusal, prove no write)"), Testing ("for each of the five conditions, construct a fixture that violates only that one condition and assert refusal"), and the Acceptance criteria bullet ("Any accepted descendant, candidate admission, review/seal record, pending generation, or tracked seed state blocks rollback..."). Neither of these two can be made false on its own under the code today: `accepted-head.json` names exactly one version at a time (`roadmap_versions.py:AcceptedRoadmapHead`/`accepted_head_path`) and `roadmap_version_promotion.py:promote_review_seal` only ever moves that selector forward from the currently accepted version to a new candidate, never back to a root — so an accepted head naming the root already rules out any accepted descendant. Likewise, every review/seal artifact (`roadmap_candidate_review.py:question_inventory_path`, `reviewer_answer_path`, `review_seal_path`) lives keyed off a materialized candidate's own version id, and a candidate can't materialize without a `CandidateProposalAdmission` first (`roadmap_candidate_run.py`, admission is written before `candidate_version_id` is ever set) — and no writer anywhere unlinks `candidate_admission_path`, so a review/seal record can't exist without a candidate-admission record also existing. A developer cannot build the "violates only that one condition" fixture the plan's own Testing section calls for on these two.
  - Fix: Clarify what "accepted descendant" and "review/seal record" independently mean beyond what "root-only accepted head" and "no candidate admission" already establish, or state plainly that these two conditions are subsumed by their siblings under the current writers and adjust the "violate one condition at a time" testing requirement to the conditions that can actually be independently triggered.
- HIGH `[rollback-receipt-coverage]` [confidence: limited]: The Testing section assumes a rollback receipt already exists and is checked on replay:

  ```
  Prove idempotence: roll back twice and assert the second call reports the
  already-rolled-back state without a second receipt write or error.
  ```

  but no such requirement appears in Architecture, Risks, or Acceptance criteria — nothing obliges rollback to write a durable record at all, so "reports the already-rolled-back state" has no defined signal to tell that state apart from "never enrolled." Step 1's own frontmatter lists `plan_tool/roadmap_evidence_store.py` as a file to modify, hinting at where a record might land, but the plan body never says so. Meanwhile the References section points the implementer at the wrong reuse candidate: `plan_tool/roadmap_escalation.py`'s `build_receipt`/`EscalationReceipt` models "one selected, still-open feedback row" — its `_ReceiptSemanticFields` requires a `ReceiptSelector` (`artifact_key` + `feedback_id`), a `ReceiptTarget`, a `ReceiptReason` from `roadmap_escalation_selection.py`, and enforces `feedback_state: Literal["open"]` — none of which describes un-enrolling a root, and its companion `receipt_worktree_for_plans_dir` (`roadmap_escalation_run.py`) ties it to a git-committed worktree flow built for escalation/impact-run, not a lightweight lifecycle fact. `roadmap_evidence_store.py`'s `EvidenceNamespace` enum has only `ESCALATIONS` and `IMPACT_ANALYSES` today, so even the file step 1 does list has no matching namespace yet.
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): The plan's idempotency requirement depends on a durable, checkable record of a completed rollback, but no Architecture commitment or acceptance criterion requires that record to exist, so nothing guarantees "already rolled back" is distinguishable from "never enrolled."
  - Fix: Add an Architecture commitment and an acceptance criterion for a durable, checkable rollback record (what it names, when it was written, and how idempotent replay reads it), and replace the References pointer with a mechanism that actually fits a root un-selection fact instead of the escalation-specific receipt shape.
- MEDIUM `[pending-generation-check-source]` [confidence: limited]: Architecture and References name two different functions for the same "pending generation" check. Architecture says:

  ```
  reuse `recover_roadmap_publication`'s pending-generation check rather than
  adding a second one, so a route never fires while a lifecycle journal is
  mid-write.
  ```

  but References separately lists `plan_tool/roadmap_source_identity.py:load_pending_generation` as one of "the three other eligibility checks." `recover_roadmap_publication` (`roadmap_revision_publish.py`) is not a pure check — it can unlink the pending-generation journal file or raise `RoadmapPublicationRecoveryError` as a side effect of running it. Read literally, Architecture tells the implementer to call that mutating recovery function inside rollback's eligibility gate, which would make checking rollback eligibility trigger or complete unrelated in-flight publication recovery — exactly the "separate incomplete-journal recovery bug" the plan's Out of scope section says to keep separate ("Keep the two mechanisms and their tests separate"). Calling `load_pending_generation` directly avoids this, but nothing in the plan states which reading is the intended one.
  - Fix: State explicitly that rollback's pending-generation check calls the plain read (`load_pending_generation`) and must never invoke `recover_roadmap_publication`'s recovery/mutation path.

- HIGH `[rollback-receipt-coverage]` [confidence: limited]: Step 1's own frontmatter commits to a durable rollback receipt that the plan body never specifies as a requirement. Step 1's `files:` list includes `plan_tool/roadmap_evidence_store.py` — the shared immutable evidence store whose only two existing namespaces are `ESCALATIONS` and `IMPACT_ANALYSES`, so the only reason step 1 would touch this file is to add a namespace for rollback receipts — and step 2's and step 3's `depends_on_notes` both describe step 1 as delivering it ("delivers the eligibility predicate, receipt, and atomic selector-clear"; "names the shipped module and its receipt mechanism"). Yet no step's title or intent says to build a receipt, no Risk names a missing or wrong receipt as a hazard, no Acceptance criterion requires one to exist or be readable, and the Testing section mentions it exactly once, negatively, in the idempotence bullet ("assert the second call reports the already-rolled-back state without a second receipt write or error") — nothing asserts the *first* successful rollback actually writes one, or that it records the right facts (which root, when, under what confirmed operator intent). The plan's own References section ("`plan_tool/roadmap_escalation.py` — existing durable-receipt mechanism to evaluate for reuse before adding a second one") and the BUG_BACKLOG fix text it cites ("preserve the immutable root and write a durable rollback receipt; then atomically clear only the active accepted-head selection") both treat the receipt as required, so this reads as dropped partway through authoring rather than a deliberate scope cut.
  - Fix: Add the receipt to step 1's stated intent, add an Acceptance criterion requiring a durable, readable record of which root was un-selected, when, and under what confirmed operator intent, and add a Testing bullet asserting the first successful rollback writes that record and it can be read back correctly.
