- HIGH `[proposal-currentness]` [confidence: limited]: The proposal lifecycle contradicts its supersession rule across Architecture, step 5 (`Store batch responses with one root-and-active-candidate pointer while retaining superseded candidate history`), step 8 (`Bind candidate questions, answers, rejection, and discard resolution to the exact active-candidate batch`), Testing, and the acceptance criteria. Architecture says:

  ```
  A proposal remains current while its candidate is the active candidate for the current root; it becomes stale when its bound predecessor is no longer the root or active candidate, or when its candidate is resolved without promotion.
  ```

  Yet it also says a successor leaves the former candidate and its proposals as `superseded` history. For a first candidate whose predecessor is the accepted root, that predecessor remains the root after a successor becomes active, so the stated stale conditions leave its proposal current even though its candidate is no longer active. Define supersession as a proposal-staling event and align every lifecycle and acceptance statement so only the active candidate can have current proposals.
  - Fix: Define one complete proposal-currentness rule that makes candidate supersession, rejection, discard, settlement staleness, and promotion consistently retire prior proposals while preserving their immutable evidence.
- MEDIUM `[accepted-head-writers]` [confidence: limited]: The accepted-head writer set is internally contradictory between Architecture, Scope guardrails, the Acceptance criteria, and step 2 (`Make root enrollment store feedback-free versions while blocking legacy feedback processing until explicit ledger migration`). They say review-seal promotion and enrolled decision settlement are the “two accepted-head writers” and “the only accepted-head writers,” while step 2 requires new enrollment to create a ledger-native accepted root. At HEAD, `plan_tool/roadmap_versions.py:build_root_enrollment_generation` creates the initial `accepted-head.json` member, so implementation and tests cannot follow the claimed closed writer set without treating enrollment as an unstated exception.
  - Fix: State that guarded root enrollment is the one initial accepted-head creation path, and reserve subsequent accepted-head changes for review-seal promotion and enrolled decision settlement.
- HIGH `[legacy-version-feedback-retirement]` [confidence: limited]: Legacy migration has no coherent way to satisfy feedback-free immutable versions without rewriting an immutable legacy root or adding an undeclared accepted-head transition. Architecture requires embedded-feedback enrollment, then says the artifact feedback field is retired from immutable version content; Step 2 forbids rewriting legacy working artifacts, while Acceptance criteria require:

  ```
  “Immutable roadmap artifact versions contain no mutable feedback channel.”
  ```

  The plan does not say whether historical enrolled versions may retain a read-only legacy field, or how migration creates a feedback-free canonical version while preserving the accepted-head writer rule.
  - Fix: Specify the post-migration status of embedded feedback in historical immutable versions and the permitted canonical-head transition, if any, so migration can meet the feedback-free guarantee without violating immutability or writer ownership.
