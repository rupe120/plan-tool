# Step 3 — Add the revision restore runner: under the writer lock, run recover_roadmap_publication first, then refuse or publish the pre-run bytes

<!-- plan-tool:detail-format-version: 1 -->

## Summary

This step adds `plan_tool/roadmap_revision_rollback.py`, a new standalone module holding one function, `restore_roadmap_revision(slug, *, plans_dir)`, that turns step 1's checkpoint and step 2's wiring into an actual restore. Modeled on the closest existing sibling — `plan_tool/roadmap_feedback_reopen.py:run_confirmed_feedback_reopen`, a standalone module that also holds the roadmap writer lock, calls `recover_roadmap_publication`, and returns a closed result type rather than raising for its own expected refusals — the new function acquires the writer lock, runs `recover_roadmap_publication` first, and then evaluates the plan's five-row restore matrix (no checkpoint, enrolled, matches the run's last-tracked bytes, already matches the pre-run bytes, or anything else) entirely from bytes already on disk and in the checkpoint. A restore publishes the checkpoint's `pre_run_bytes` for every tracked entry as one `PendingGeneration` through the unchanged `publish_roadmap_generation`, then discards the checkpoint; an already-restored state just discards it; every refusal changes nothing. On green, this module has no caller — steps 4 and 5 wire it into `plan-tool roadmap`'s CLI surface and its non-completion messages.

## Why

Step 2 makes `_run_roadmap` leave a checkpoint behind exactly when a revision did not complete, but nothing yet reads that checkpoint back. An operator whose run stopped partway — an invalid stage, an exhausted attempt budget, an interrupt, a crash — has a record of what the roadmap looked like before the revision, and no way to use it except by hand. This step is that use: one function that turns the checkpoint's `pre_run_bytes` back into the live roadmap, refusing whenever doing so would discard something the checkpoint cannot vouch for — a later hand edit, another writer's change, or enrollment. Steps 4 and 5 give it a command; this step gives it a correct, directly testable implementation.

## Input

- **Step 1's checkpoint contract** (`plan_tool/roadmap_revision_checkpoint.py`, landed in step 1; this step does not edit it) — `load_checkpoint(plans_dir, slug) -> RevisionCheckpoint | None`, `discard_checkpoint(plans_dir, slug) -> None` (no-op-safe when absent), and `RoadmapRevisionCheckpointError`. `RevisionCheckpoint.entries` is a tuple of `CheckpointEntry(relative_path, pre_run_bytes, last_written_bytes)`, one per tracked file, with `relative_path` root-relative and forward-slash — the same convention `GenerationMember.relative_path` uses, confirmed in step 1's own Input section. This step reads `checkpoint.entries` directly; it does not need `tracked_paths`, `capture_checkpoint`, `with_last_written`, or the render/parse/write functions, all of which are step 1's or step 2's to call.
- **Step 2's write-time bookkeeping** (`plan_tool/roadmap.py:_run_roadmap`) — the fact this step depends on, not the mechanism: a checkpoint that still exists on disk means the run that made it did not complete, and its `last_written_bytes` reflect whatever that run itself actually committed, updated after every stage publish and every `source.json` write. This step trusts that invariant; it does not re-derive it. It is not universal: a dangling journal from another roadmap writer that silently completes during *this* function's own `recover_roadmap_publication` call is an accepted residual (see the plan's Risks and this step's Deferred) — restore refuses rather than reconciling against it.
- **`roadmap_writer_guard`, `recover_roadmap_publication`, `publish_roadmap_generation`, `require_unenrolled_roadmap_writer`, and their error types** (`plan_tool/roadmap_revision_publish.py`) — called exactly as `plan_tool/roadmap_feedback_reopen.py:run_confirmed_feedback_reopen` already calls them, with one deliberate ordering difference: that function checks enrollment (`require_unenrolled_roadmap_writer`) *before* calling `recover_roadmap_publication`; this step's Architecture section requires the opposite order (recovery always runs first, unconditionally, "like every other roadmap writer"), because `recover_roadmap_publication` itself is what resolves a dangling journal left by an enrolled root's own generation kinds (`root-enrollment`, `review-seal-promotion`) — checking enrollment before recovery would refuse before that journal is ever resolved.
- **`GenerationMember(relative_path, old_bytes, new_bytes)` / `PendingGeneration(kind, members)`** (`plan_tool/roadmap_source_identity.py`) — unchanged; this step builds one `PendingGeneration` covering every tracked entry and publishes it through `publish_roadmap_generation`, the same primitive `publish_stage_artifact` and `publish_feedback_reopen_candidate` already build their own generations on top of.
- **`roadmap_dir(plans_dir, slug)`** (`plan_tool/roadmap_artifacts.py`) — used to turn each checkpoint entry's `relative_path` back into an absolute path for reading current bytes and for `_replace_generation_members`'s own resolution inside `publish_roadmap_generation`.
- **What this step does not need** — `plan_tool.roadmap` itself. Unlike `plan_tool/roadmap_feedback_reopen.py` (which imports `STAGES`/`RoadmapStage` from it to resolve a stage selector) and `plan_tool/roadmap_candidate_run.py`, this step never resolves a stage, never renders a prompt, and never reads `repo_root`; it only compares and republishes the ten tracked files' bytes. Not importing `plan_tool.roadmap` keeps this module's dependency footprint the same shape as `plan_tool/roadmap_revision_publish.py` itself, which also avoids importing `plan_tool/roadmap.py` at module level.

## Implementation

**Public shape.** One function, e.g. `restore_roadmap_revision(slug: str, *, plans_dir: Path) -> RevisionRestoreResult`, plus a small closed result type. Recommended shape, mirroring `ImmutableRootEnrollmentResult` and `RoadmapSeedAcceptResult` (`plan_tool/roadmap.py`) and `FeedbackReopenRunResult` (`plan_tool/roadmap_feedback_reopen.py`) — all three already pair a top-level outcome with an optional reason/refusal field rather than a flat string:

```python
RESTORE_OUTCOME_RESTORED = "restored"
RESTORE_OUTCOME_ALREADY_RESTORED = "already-restored"
RESTORE_OUTCOME_REFUSED = "refused"

@dataclass(frozen=True)
class RevisionRestoreResult:
    outcome: Literal["restored", "already-restored", "refused"]
    reason: Literal["no-checkpoint", "enrolled", "changed-since-failed-run"] | None = None
```

with a `__post_init__` requiring `reason` exactly when `outcome == "refused"` — the same self-validating pattern `ImmutableRootEnrollmentResult` already uses for its `version_id`/`outcome` pair. Step 4 reads `outcome` (and `reason` when refused) to choose an exit code and a message; this step does not decide exit codes itself (that is step 4's stated job).

**The five-row matrix is the function's only business vocabulary.** Everything the plan's Architecture section lists as a matrix outcome — no checkpoint, enrolled, matches last-tracked, matches pre-run, anything else — is returned as a `RevisionRestoreResult`, never raised. Everything *outside* that closed matrix — a writer-guard problem, a `recover_roadmap_publication` failure on a genuinely unrecoverable journal, a `publish_roadmap_generation` failure, a corrupted on-disk checkpoint file — is left to propagate as whatever exception `roadmap_revision_publish.py` or `roadmap_revision_checkpoint.py` already raises for it. This mirrors `enroll_roadmap_root`'s split (two named business refusals returned as a result; everything else raised as `RoadmapError`) rather than `run_confirmed_feedback_reopen`'s style of folding every exception into one generic outcome — the restore matrix is closed and exhaustive over exactly five rows, so nothing here should quietly become a sixth, undocumented outcome. Step 4 is free to add its own broad `except` clause around the call to this function for exit-code purposes; that does not require this function to swallow anything itself.

**Sequence, under `roadmap_writer_guard(plans_dir, slug)`:**

1. **Recover first, unconditionally.** Call `recover_roadmap_publication(plans_dir=plans_dir, slug=slug, writer_token=writer_token)` before reading anything else — before `load_checkpoint`, before the enrollment check, before any byte comparison. This is the step title's own ordering and the plan's stated invariant ("restore holds the writer lock and runs `recover_roadmap_publication` first, like every other roadmap writer, so any half-written stage publish resolves before restore reads anything"). Let any failure here propagate; it is not one of the five matrix rows. This function performs no reconciliation against whatever a dangling journal settles — a journal from another roadmap writer that silently completes here is an accepted residual (see Input and the plan's Risks section).
2. **No checkpoint → refuse.** `load_checkpoint(plans_dir, slug)` returning `None` is the first row: return `RevisionRestoreResult(outcome="refused", reason="no-checkpoint")` and touch nothing else.
3. **Enrolled → refuse.** Call `require_unenrolled_roadmap_writer(writer_token, plans_dir=plans_dir, slug=slug)` and catch only `EnrolledRoadmapWriteError` — it already covers both a genuinely enrolled roadmap and an invalid/unreadable accepted-head state (that function's own `except RoadmapVersionError` branch re-raises both as the same error), so this step does not need to call `is_roadmap_enrolled` separately or special-case a corrupt accepted-head file. On that catch, return `RevisionRestoreResult(outcome="refused", reason="enrolled")` and touch nothing else. Do not catch the broader `RoadmapWriterGuardError` here — a bad writer token is an infra problem, not an enrollment refusal, and must keep propagating. Nothing before this point writes anything, so this refusal changes no file by construction, not merely by the outcome not calling `publish_roadmap_generation`.
4. **Compare, as one vector, not per file.** For every entry in `checkpoint.entries`, read the current bytes at `roadmap_dir(plans_dir, slug) / entry.relative_path` (`None` on `FileNotFoundError`, mirroring the same convention step 1's `capture_checkpoint` and `roadmap_revision_publish.py:_member_state` both use). Then ask two whole-checkpoint questions, not ten independent ones: do *all* entries' current bytes equal their `last_written_bytes`? Do *all* entries' current bytes equal their `pre_run_bytes`? A per-entry check ("does this one file differ from both its own two values") is not enough — it misses the case where file A already matches its `last_written_bytes` and file B already matches its `pre_run_bytes`, which is a genuine "anything else" case even though neither file individually fails a from-both-my-own-values test. Only a uniform match across every entry counts as row 3 or row 4. **This is also what makes restore's own prior, interrupted attempt resolve correctly with no special-casing:** a dangling `"revision-restore"` journal that silently completes here lands every tracked file's current bytes at `pre_run_bytes` (that journal's own `new_bytes`, by construction — see step 5 below), so this comparison sees a uniform `pre_run_bytes` match and falls into the "already-restored" row, without this function needing to know or check the journal's `kind` at all.
5. **Matches last-tracked (uniformly) → restore.** Build one `GenerationMember(entry.relative_path, old_bytes=<the current bytes just read>, new_bytes=entry.pre_run_bytes)` per checkpoint entry — including entries where `pre_run_bytes is None`, which `_replace_generation_members` already deletes on replace, giving "deleting ones that did not exist before the run" for free — and publish them as one `PendingGeneration` (a new `kind`, e.g. `"revision-restore"`, distinct from every kind `roadmap_revision_publish.py` already defines) through the unmodified `publish_roadmap_generation`. On success, call `discard_checkpoint(plans_dir, slug)` and return `RevisionRestoreResult(outcome="restored")`. No `before_replace` recheck is needed here, unlike `enroll_roadmap_root`'s `final_recheck` — that recheck exists because capturing an impact snapshot reads repo state the roadmap writer lock does not protect; this step's whole check-then-publish sequence reads and writes only files under `roadmap_dir(plans_dir, slug)`, which the held writer lock already serializes against every other roadmap writer for the full duration of the call.
6. **Matches pre-run (uniformly) already → report, don't write.** No file needs changing. Skip `publish_roadmap_generation` entirely, call `discard_checkpoint(plans_dir, slug)`, and return `RevisionRestoreResult(outcome="already-restored")`. This is the "interrupted restore that already landed" row: a prior restore's own `publish_roadmap_generation` call committed, but the process died before `discard_checkpoint` ran, leaving the checkpoint on disk pointing at a roadmap that is already correct.
7. **Anything else → refuse, changed.** Return `RevisionRestoreResult(outcome="refused", reason="changed-since-failed-run")`. Do not discard the checkpoint here — the plan's own restore matrix pairs this refusal with "changes nothing", and discarding the checkpoint on a refusal would make a second restore attempt (after the operator sorts out the unexpected state by hand) impossible. This is also the row a dangling journal from *another* roadmap writer (a crashed enrollment, review-seal promotion, or any other writer sharing this journal path) falls into if it silently completes during this call's own recovery and happens to touch a tracked file: the checkpoint's `last_written_bytes` for that file stays whatever the original failed run left it at, matching neither value, so restore refuses rather than guessing. The accepted residual named in Input is this row, not a raise.

**A checkpoint whose entries were never written to** (`pre_run_bytes == last_written_bytes` for every entry — a run that captured a checkpoint but stopped before its first publish) satisfies sequence step 5 and step 6 simultaneously by construction. Step 5 is checked first, so it takes this path: it publishes a no-op generation (every member's `old_bytes` and `new_bytes` are equal) and discards the checkpoint. This is deliberate, not an oversight — restoring is a correct no-op here, and special-casing it to skip straight to step 6 would save one redundant write at the cost of a second branch with the same observable result.

**The corrupted-checkpoint case is deliberately not handled here.** `load_checkpoint` can raise `RoadmapRevisionCheckpointError` for a malformed on-disk checkpoint file. Step 2's own Deferred section leaves that same error "propagate uncaught, the same as other genuinely-corrupted-tool-state errors do today" when it escapes inside `_run_roadmap`; this step keeps that precedent rather than inventing a new recovery path for damaged tool state that neither step 1 nor step 2 handles either.

**`KeyboardInterrupt` is left alone.** Unlike `run_confirmed_feedback_reopen`, which catches it because nothing above it does, this function does not need to: the plan's step 5 already names `cmd_roadmap`'s existing `except KeyboardInterrupt` branch as one of the four places it will print the restore-command hint, confirming that branch is a shared handler above every roadmap subcommand dispatch, not something specific to a stage run. `roadmap_writer_guard`'s own `try`/`finally` already releases the lock correctly if a `KeyboardInterrupt` unwinds through this function, so nothing here needs to intercept it.

**What does not change.** `recover_roadmap_publication`, `publish_roadmap_generation`, `require_unenrolled_roadmap_writer`, `load_checkpoint`, and `discard_checkpoint` keep their existing signatures and bodies — this step calls them, it does not modify them.

## Acceptance criteria

- `restore_roadmap_revision` holds the roadmap writer lock for its entire duration and calls `recover_roadmap_publication` before reading the checkpoint, checking enrollment, or comparing any tracked file's bytes.
- With no checkpoint present, it returns a refusal naming that reason and changes no file.
- With the roadmap enrolled (including an invalid/unreadable accepted-head state), it returns a refusal naming that reason and changes no file.
- When every tracked file's current bytes equal the checkpoint's `last_written_bytes`, it publishes the checkpoint's `pre_run_bytes` for every tracked entry as one generation through the unmodified `publish_roadmap_generation` — deleting any file whose `pre_run_bytes` is `None` — and then discards the checkpoint.
- When every tracked file's current bytes already equal the checkpoint's `pre_run_bytes`, it discards the checkpoint and reports that state without calling `publish_roadmap_generation`.
- In every other case — including a mix where different files independently match different checkpoint values — it refuses, names that as the reason, changes no file, and leaves the checkpoint in place.
- A dangling publication journal present when restore starts (from an earlier interrupted restore or an earlier interrupted stage run) is resolved by `recover_roadmap_publication` before restore's own comparison runs.
- A dangling journal that is restore's own prior, interrupted attempt resolves to `"already-restored"` (not `"restored"`) with no dedicated mechanism — an emergent property of the whole-vector comparison against `pre_run_bytes`.
- A dangling journal from any *other* roadmap writer that silently completes during this function's own recovery call is an accepted residual: it is never reconciled into the checkpoint, and if it touches a tracked file, restore refuses as `"changed since the failed run"` rather than raising or silently absorbing the change.
- A corrupted on-disk checkpoint file, or a dangling journal `recover_roadmap_publication` cannot itself recover, propagates as an exception rather than becoming one of the five result outcomes.
- `recover_roadmap_publication`, `publish_roadmap_generation`, `require_unenrolled_roadmap_writer`, `load_checkpoint`, and `discard_checkpoint` are unchanged (same signatures, same bodies).
- `uv run pytest tests/test_roadmap_revision_rollback.py -q` passes, and the full suite (`uv run pytest tests/ -q -n auto`) passes.

## Applicable guardrails

The plan's `## Scope guardrails` bind this step on several points:

- "No automatic restore, and no restore offered on anything but an explicit command" — this step ships a function callable from a test or from step 4's CLI wiring; it is not called from `run_roadmap`, `_run_roadmap`, or anywhere else in the ordinary run path.
- "No change to enrollment, candidates, review seals, promotion, or the `.roadmap-versions/` namespace" — restore only *checks* enrollment through `require_unenrolled_roadmap_writer`; it never enrolls, promotes, or writes under `.roadmap-versions/`.
- "No new persisted state except the checkpoint" — the only write this step performs is republishing the ten already-tracked files and discarding the checkpoint step 1 defined; it introduces no new sidecar file or format.
- "Eligibility never reads run logs" — every row of the restore matrix is decided from on-disk file bytes and the checkpoint's own recorded values; nothing here reads `.plan-tool/runs/`.
- "No change to `--revise-feedback`, `--materialize`, `--enroll-baselines`, or `--enroll-version`" — this step's only file is the new `plan_tool/roadmap_revision_rollback.py`; it does not touch those existing entry points.
