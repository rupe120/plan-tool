plan-tool · value walkthrough

When the Plan
Caught Itself

A completeness-audit finding stopped us from shipping an over-engineered feature — and the feature in question was the exact thing built to catch it.

A real session · the feature-health plan

plan-tool turns an idea into a plan, audits it for gaps before any code, then runs or exports it. This is a true story from one authoring session.
the trigger

Mid-audit, the tool spoke up

We were authoring feature-health — a feature meant to group correctness findings across runs and flag a capability that keeps churning. The completeness audit emitted:

[MEDIUM] · plan-completeness

The plan claims features: "changes no existing run/detail/jira behavior," but its validation runs on every parse_plan — which run, jira, and detail all call. So a drifted features: block becomes a hard ValidationError that blocks all three — a new failure mode the "inert/declarative" framing denies.

Not a typo. An architectural contradiction between what the plan claimed and what its design would do.

the value moment

The author didn't hit apply

"Does it actually make sense to make this a hard stop? What exactly does the features block drive that would cause the application to fail if the feature list was changed?"

The finding's own fix was "document the tradeoff." The author asked whether there should be one.

The tool didn't fix anything here. It started the right conversation.

This is the thesis of the whole deck. An advisory, human-gated finding provoked a design conversation instead of silently mutating the plan.
the diagnosis

A category had been built as a functional unit

One grep settled what features: actually drives — because the frontmatter is machine-readable:

$ grep -rn "\.features" plan_tool/launcher.py plan_tool/jira.py plan_tool/detail.py
# (nothing) — run / jira / detail never read it

The hard failure was manufactured by where the check lived, not by the data. Root cause: the feature owned a validated list of step numbers —

features:
  - id: type-impurity
    steps: [2, 4, 5]   # ← parse-fatal validation + a renumber dangles it
Correct to fail-fast for the step graph, which run/jira consume. Wrong for features, which nothing consumes. Same mechanism, but the reason that makes it fatal doesn't carry over.
the fix

Reverse the ownership

before — feature owns steps

features:
  - id: type-impurity
    steps: [2, 4, 5]
    # renumber-fragile
    # parse-fatal

after — step owns features

steps:
  - id: 2
    features: [type-impurity]
    # tag rides with the step
    # validation advisory

Tags reference stable slugs, not step numbers — a renumber can't dangle them. Semantic checks move out of the parse-time validator, so run/jira/detail stay inert. The contradiction is gone — not footnoted.

the kicker

The feature caught itself

This conversation is the signature feature-health was built to detect: a sub-concept spawning escalating findings and pulling in cross-cutting machinery — one level up.

The plan that introduces brittleness-detection had itself churned:
3 completeness audits   +   6 detail-reconcile rounds

The right response to that signal was never another gate. It was this conversation.

why this is the demo

What plan-tool actually bought us

  • A design reviewer, not a linter — it caught validation living on the wrong seam.
  • Advisory, human-gated findings — the apply prompt triggered a conversation, not a silent edit.
  • Machine-readable frontmatter — "what does features drive?" was a 2-second grep.
  • Seed / plan separation — the fix was a seed rewrite + regenerate, not plan surgery.

The best plan-tool moment isn't when it writes the plan —
it's when it makes you ask if the plan is right.
