# Step 2 — Move the --iterate convergence loop itself into completeness_phases.py

## Summary

`_run_iterate_convergence_loop` (~1096 lines, `plan_tool/cli/completeness_cmd.py:_run_iterate_convergence_loop`) is the last major orchestration block left in the completeness-audit CLI handler after step 1 clears its 18 local helper dependencies out of the way. This step moves the function's full body, unedited, into `plan_tool/cli/completeness_phases.py`, and changes `cmd_completeness`'s one call site to a qualified reference (`completeness_phases._run_iterate_convergence_loop(...)`) instead of a bare name, matching the convention `completeness_phases.py`'s own docstring already states for `apply_finding` and `shell_review_invoker`. The move also removes two body-local imports that become same-module self-imports once the function lives beside what they name, and prunes a handful of re-imports in `completeness_cmd.py` that existed only for this function's sake. The bulk of the work is mechanical relocation; the real risk is the test file, where roughly a dozen call sites, six `inspect.getsource` checks, one direct monkeypatch, and three checkpoint-interception monkeypatches all resolve names through `plan_tool.cli.completeness_cmd` today and go silent or fail once the def moves. Observable result on green: identical CLI behavior, and the same three test outcomes step 1 aimed for — the primary test suite covering `_run_iterate_convergence_loop` needs only import/monkeypatch retargets, not assertion rewrites.

## Why

After step 1 relocates its 18 local helpers, `_run_iterate_convergence_loop` is the single largest piece of non-CLI orchestration still sitting in `completeness_cmd.py`, and it is why `completeness_phases.py`'s own module docstring currently carries a stale claim: it says the loop stays in `completeness_cmd.py` because moving it "would force a back-import (cycle)" through the loop's use of the pinned, re-exported `_fmt_finding_counts`/`_finding_progress_label` helpers. Step 1 relocates those helpers, so that reason is already false the moment step 1 lands; this step is what makes the paired claim ("so the loop stays here") false too, and updates the docstring to say so. Moving the loop is also what lets `cmd_completeness` shrink down to argument validation, dispatch, and terminal-output/exit-code mapping — the CLI-layering contract this whole plan restores — with `completeness_phases.py` holding every phase of the command's real work.

## Implementation

**The move itself.** Cut `_run_iterate_convergence_loop`'s definition — signature, docstring, and full body — out of `completeness_cmd.py` and paste it into `completeness_phases.py`, next to `_run_deterministic_checks` and `_sample_conceptual_audit`, the phases it already sits beside conceptually. Its signature and return type (`_IterateOutcome`, already defined in `completeness_phases.py`) don't change. Every body-local domain import stays exactly as written — `plan_tool.launcher.apply_finding`/`revert_apply_if_parse_broken`, the `plan_tool.review.*` names (`audit_plan_until_stable`, `collect_deterministic_findings`, `collect_self_consistency_findings`, `shell_review_invoker`, ...), the `plan_tool.scope_guard.*` names, `plan_tool.drift_detection.iteration_session`, and `plan_tool.progress`'s reporters. These are body-local specifically so a monkeypatch on the *domain* module (`plan_tool.review`, `plan_tool.launcher`) keeps intercepting regardless of which CLI module hosts the call — that property doesn't depend on which file the function lives in, so none of it needs touching.

**Two body-local imports become dead, not just relocatable.** The function currently has two `from plan_tool.cli.completeness_phases import (...)` statements inside its own body — one importing `emit_bare_plan_banner`/`emit_coverage_unconfirmed` near the top of the `if budget.enabled:` block, one importing `_audit_recs_for_report` partway through the loop. Both names are already `def`-owned by `completeness_phases.py` and have no caller in `completeness_cmd.py` outside this function. Once the function moves into that same module, these become same-module self-imports — legal Python, but dead weight a reader has to puzzle over. Delete both import statements as part of the move; the three names resolve as ordinary module globals afterward.

**The call site becomes qualified.** `cmd_completeness`'s one call — `outcome = _run_iterate_convergence_loop(plan, path, ctx, args, budget, bundle_status=..., ...)` — becomes `outcome = completeness_phases._run_iterate_convergence_loop(...)`, with the same keyword arguments. This needs a module-level qualified import of `plan_tool.cli.completeness_phases` added to `completeness_cmd.py`, alongside (not replacing) its existing bare-name `from plan_tool.cli.completeness_phases import (...)` block — that block stays, since `_IterateOutcome`, `_run_deterministic_checks`, `write_pre_apply_audit_checkpoint`'s other caller (see below), and the rest are still called by bare name elsewhere in `cmd_completeness`/`finalize_completeness_run`. This file already has a precedent for the qualified-module style: `plan_tool/cli/app.py` does `from plan_tool.cli import completeness_cmd as _completeness_commands` for exactly this kind of call-through-the-module reference. Following that naming pattern (or the plain `from plan_tool.cli import completeness_phases`, unaliased) is a reasonable default — the qualified name itself, not the alias spelling, is what the test retargets below depend on.

**Trim what becomes unused in `completeness_cmd.py`.** This mirrors step 1's own "trim what becomes unused" move for `CARRIED_RESOLUTION_APPLIED`/`_BLOCKED`/`_OPEN`, applied to this step's relocation instead:

- `write_pre_apply_audit_checkpoint` has exactly one call site left in `completeness_cmd.py` today, and it's inside the loop being moved. Once the loop leaves, this bare-name import has no remaining caller in the file — drop it from the top import block. (Its `completeness_phases.py` copy, where the function is actually defined, is unaffected.)
- Of the 18 helper names step 1 re-imports into `completeness_cmd.py`, six — `_sc_manual_fix_note`, `_remap_iterate_stop_for_conceptual_bar`, `_conceptual_bar_remedy_lines`, `_print_conceptual_bar_stop_remedies`, `_print_all_auto_apply_deferred_halt_message`, `_conceptual_completeness_manual_fix_note` — are called only from inside the loop today, either directly or transitively through one another (`_print_conceptual_bar_stop_remedies` calls `_conceptual_bar_remedy_lines`; `_print_all_auto_apply_deferred_halt_message` calls both `_conceptual_bar_remedy_lines` and `_conceptual_completeness_manual_fix_note`). None of `cmd_completeness`, `finalize_completeness_run`, `cmd_completeness_apply`, `_resolve_audit_reuse`, or `_completeness_has_blocking_findings` call any of these six. Once the loop moves, these six re-imports have no remaining caller in `completeness_cmd.py` — drop them. The other 12 of the 18 stay: each has a direct caller among those five functions independent of the loop (e.g. `_sampled_bundle_status` and `_conceptual_bar_from_audit_recs` are called both by the loop and directly by `cmd_completeness`/`finalize_completeness_run`).
- There's no lint gate to catch a missed one of these — this repo's `ruff` config deliberately disables `F401` (unused-import), specifically because other modules import names purely to re-export them, and a blanket unused-import fix would break those. Confirm each removal by hand (grep the name across `completeness_cmd.py` after the move) rather than trusting a tool; getting one wrong is silent (an unused import doesn't break anything), so this is a hygiene step to do carefully once, not something a re-run will catch later.

**What not to touch.** `completeness_cmd.py`'s own module docstring still names `_run_iterate_convergence_loop` as one of `cmd_completeness`'s "named phase helpers" — that claim goes false the moment this step lands, but step 5's own intent explicitly claims ownership of clearing it ("this step is the last of the two to land, so it owns clearing both stale claims"), alongside its apply-side monkeypatch-target claim. Leave that paragraph as written; only `completeness_phases.py`'s docstring is this step's to fix. `plan_tool/cli/app.py` needs no change — it re-exports `_finding_progress_label`/`_fmt_finding_counts`/`_completeness_has_blocking_findings`/`cmd_completeness`/`cmd_completeness_apply` from `completeness_cmd`, never `_run_iterate_convergence_loop`, so nothing there references the name being moved.
