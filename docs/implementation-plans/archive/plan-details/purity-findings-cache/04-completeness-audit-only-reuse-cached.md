# Step 4 — In completeness-audit only, grade a purity cache miss: reuse below the #144 floor, re-compute above it

## Summary

In the `completeness-audit` path only, grade a purity cache *miss* with a cheap no-Claude signal before deciding what to do, so the audit reuses across a trivial edit but re-computes across a material one — the cache stays a **pure optimization** that never removes `completeness-audit --purity`'s ability to deliver a verdict. On a miss: if the `## Implementation` + `## Tests` section text changed by less than 0.5% **and** none of the step's `files:`/`change_type:`/`depends_on:` frontmatter changed, reuse the cached verdict and emit one informational advisory (no Claude); otherwise — a genuine change (≥0.5%, or any frontmatter change), or a cold/never-checked step — call Claude and produce a fresh verdict (through step 3's write-through helper). The primary files are `plan_tool/cli/completeness_phases.py` (the `_collect_purity_split_findings` grading policy) and `plan_tool/detail.py` (a below-floor reuse hook on step 3's shared cache helper plus a shared Implementation/Tests concatenation helper). The key design decision: only a cache hit or a below-floor trivial miss skips Claude; a genuine miss still earns a real verdict. `detail.py`'s own authoring-time loop is unaffected — it always calls Claude (step 3, decision 2). On green, a standalone `completeness-audit --purity` reuses cached verdicts on unchanged/trivially-changed steps and re-computes on materially-changed or never-checked ones — so it still validates purity, it just stops re-paying for unchanged content.

## Why

After step 3, the audit path already skips Claude on a cache *hit*. The gap this step closes is the *miss*: without grading, an audit would re-pay the ~130–255s per-step purity call whenever a step's detail content changed at all since its last check, even a typo fix — the exact waste BACKLOG #144 was raised to cut. #144's calibration found that a magnitude signal is a reliable *low-side floor*: every trivial edit (typo, reworded sentence, a link, a symbol rename) scored below 0.5% on the Implementation/Tests section diff, while every substantive edit scored well above it. So this step grades a miss: below the 0.5% floor with no frontmatter change, the change is trivial — reuse the cached verdict and emit an informational advisory, no Claude. Above it, or on any `files:`/`change_type:`/`depends_on:` change, or on a step never checked through the cache, the change is genuine — call Claude and earn a fresh verdict, so `completeness-audit --purity` keeps delivering real verdicts rather than only nudging (the [audit-purity-verdict-removal] gap the round-1 audit flagged). `detail.py`'s authoring loop is untouched — it always calls Claude (step 3, decision 2), which is where every fresh purity judgment is earned.

## Input

This step consumes contracts from its dependency steps and from the resolved #144 decision; its correctness depends on their shapes, not on recomputing them:

- **Step 1's combined cache key** — `plan_tool/fingerprint.py:compute_purity_cache_key(plan, plan_path, step, repo_root)` returns one hex `str` that changes when the detail file or any of `step.all_files` (declared `files:` plus `creates:`) content changes. This step reads it only through step 3's helper; it does not recompute a key by hand. A `files:` list or file-content change already forces a miss through this key.
- **Step 2's cache entry** — `plan_tool/purity_cache.py:PurityCacheEntry` stores, per step id, the combined `cache_key`, the key's components (`detail_hash`, `all_files_fingerprint`, `change_type`, `depends_on`, `purity_verdict_logic_version`), the `detail_relpath` (renumber-guard identity token), the cached `findings` (the purity verdict; `[]` = checked and pure), and `impl_tests_text` (the concatenated `## Implementation` + `## Tests` detail-body text at check time). This step reads `impl_tests_text` as the "before" side of its diff; the stored `all_files_fingerprint`/`change_type`/`depends_on`/`purity_verdict_logic_version`/`detail_relpath` as the "before" side of the component checks; and `findings` as the verdict it reuses. It does not add fields to this entry — `purity_cache.py` is not in this step's files (step 2 already carries those fields).
- **Step 3's shared helper** — `plan_tool/detail.py:_cached_purity_findings` owns the cache load, key compute, hit/miss decision, and (on a miss, or in write-through mode) the Claude call plus write-back. This step adds a below-floor reuse hook so the audit caller can short-circuit a *trivial* miss without Claude; a genuine miss falls through to the helper's normal Claude call (`read_through=True`, miss → produce a real verdict), and the hit path is unchanged.
- **The resolved BACKLOG #144 decision** — a section-scoped diff on the concatenated `## Implementation` + `## Tests` text, treating a change below **0.005 (0.5%)** as trivial, calibrated against real local audit history (trivial edits scored 0.000–0.004, every substantive edit ≥ 0.018), OR'd with a change to any of `files:`/`change_type:`/`depends_on:`. Scoping the diff to `## Implementation` + `## Tests` is a *deliberate* choice — those are the richest MIXED-STEP evidence per `plan_tool/prompts/detail-quality.md`'s guidance — **not** because the prompt reads only them: `render_detail_quality_prompt` substitutes the whole `detail_body` plus the `change_type`/`title` fields. `change_type`'s influence on the verdict is handled by step 1's key (which folds it in), so the section diff doesn't need to; the diff's job is purely to grade *how much* the purity-relevant prose moved.
- **Known scoped staleness window — non-Implementation/Tests body edits.** Because step 1's key hashes the whole detail file, an edit confined to `## Summary`/`## Why`/`## Files`/`## Acceptance criteria` crosses the key (→ a miss) yet scores ~0% on the Implementation+Tests diff (→ below-floor reuse), even for a wholesale rewrite of those sections. This is a *deliberate* window, not an oversight: the MIXED-STEP purity verdict tracks what the step implements/tests (its concern-mixing), which lives in `## Implementation`/`## Tests` — an edit that leaves those two sections byte-identical does not change the purity judgment. Widening the below-floor diff to the whole body would re-inflate the very cost #144 cut, so it is documented (like the decision-5 lessons/`title`/`complexity` window) rather than closed. `detail.py`'s authoring loop is unaffected — it always re-checks for real regardless.

The full #144 frontmatter OR ships here, graded against step 2's stored key *components* (not the opaque combined key, which moves on any miss and can't say which input changed): a `files:`/`creates:` change is caught by comparing the stored `all_files_fingerprint` to the current one; `change_type:`/`depends_on:` changes by comparing their stored values — any of them unequal grades the miss genuine and re-computes, regardless of the Impl/Tests diff. A below-floor reuse is taken only when all components match and the diff is under 0.5%.

## Implementation

**What behavior changes.** In the audit path (`plan_tool/cli/completeness_phases.py:_collect_purity_split_findings`), a cache *miss* is graded before Claude is (or isn't) called. Only a trivial miss skips Claude; a genuine miss still computes:

- **Cache hit** (step 1's combined key matches the stored `cache_key`): reuse the cached verdict — unchanged from step 3. Keep only the medium `plan_tool/granularity.py:GRANULARITY_SPLIT_SOURCE` recs, as the existing filter already does. No Claude.
- **Below-floor (trivial) miss — reuse:** taken **only when the entry is for the same step identity, every one of its stored components except the detail hash is unchanged, and the detail change is trivial.** Concretely, all of: the entry's stored `detail_relpath` equals the current step's detail relpath (**renumber guard** — see below); the current `all_files_fingerprint` equals the entry's stored one (**no `files:`/`creates:` source change**); `change_type` and `depends_on` equal the stored values; the `purity_verdict_logic_version` equals the stored value; **and** the `## Implementation` + `## Tests` changed fraction is below 0.5%. Then reuse the cached verdict, no Claude, and emit one informational advisory. This is why step 2 stores the *components* (and the `detail_relpath`) and not just the opaque key: on a miss the combined key has moved, so it cannot tell whether the mover was a trivial detail edit, a source file, or a step renumber — only the stored components can.
- **Genuine miss — compute:** any of the above unequal (the stored `detail_relpath` differs → a renumber reassigned this id to a different step; the `all_files_fingerprint` moved → a `files:`/`creates:` change; `change_type`/`depends_on` changed; the logic version bumped) **or** the Impl/Tests changed fraction ≥ 0.5% → call Claude and produce a fresh verdict (fall through to step 3's helper's normal miss path, which invokes and writes back). The `all_files_fingerprint` guard is load-bearing: a `creates:`/`files:` content change leaves the detail body byte-identical, so its Impl/Tests diff is ~0% and *would* fall into the below-floor branch — checking the stored fingerprint is what forces the re-check the acceptance criterion "a `files:` **or** a `creates:` file changed… forces a fresh check" requires (the round-3 HIGH guard).
- **Renumber guard (round-4 finding).** The below-floor branch reuses *despite* a combined-key mismatch, so — unlike the exact-key hit path — it cannot lean on "a renumbered id yields a mismatched key → re-check." A split/merge/scope-out drop-renumber can reassign cache-entry id `2` to a now-different step whose `all_files`/`change_type`/`depends_on`/logic-version happen to coincide and whose Impl/Tests diff is <0.5% against the old text; without a guard, that leaks the old step's verdict onto the new step. The stored `detail_relpath` closes it: a renumber changes the `NN-…` filename prefix, so the stored and current relpaths differ and the miss grades genuine.
- **Miss with no cached entry at all** (the step was never purity-checked through the cache): call Claude and produce a fresh verdict, then write it through. There is nothing to reuse and nothing to diff, so this is a genuine miss — the audit computes rather than silently skipping (the [audit-purity-verdict-removal] fix). It is *not* a "nudge the operator" case.

**The diff signal — be precise about direction.** Use `difflib.SequenceMatcher` on the concatenated `## Implementation` + `## Tests` text: the cached `impl_tests_text` (before) vs the current detail body's same two sections (after). `SequenceMatcher.ratio()` returns *similarity* (1.0 = identical), so the changed fraction is `1 - ratio()`. The change is *trivial* only when `1 - ratio() < 0.005`. This inversion is the one easy-to-get-wrong spot — comparing `ratio()` directly against 0.005 would treat everything as genuine.

- **Concatenate the current sections exactly the way step 3 stored them.** Parse the current body with `plan_tool/detail.py:parse_detail_file_sections` (it returns `{"implementation": …, "tests": …}`), then join in the same order with the same separator step 3 used to build `impl_tests_text`. A different order or joiner makes the diff meaningless. The clean way: one shared helper both sides call — factor `_impl_tests_section_text(detail_body)` in `plan_tool/detail.py` and route both step 3's write-back and this diff through it.

**The component checks — grade against stored components, never the opaque key.** In addition to the diff, compare each of the entry's stored components against the step's current values (all available from step 1's `PurityKeyComponents` recomputed on the current tree, and from the stored entry): the `detail_relpath` (renumber guard), `all_files_fingerprint`, `change_type`, `depends_on`, and `purity_verdict_logic_version`. If **any** differs, the miss is genuine regardless of the diff ratio. This is the round-3 correction: it is *not* sound to reason "a `files:` change already moved the combined key, so I needn't check it" — the combined key moves on *any* miss (including a trivial detail edit) and cannot say *which* input changed, so a `creates:`/`files:` change (whose Impl/Tests diff is ~0%) would be mis-graded as below-floor and reused. Checking the stored `all_files_fingerprint` component directly is what closes that. This lands the full #144 OR precisely because step 2 persists the individual components, not just the digest.

**Below-floor reuse writes nothing — the baseline does not advance.** A below-floor reuse makes no Claude call, so (per decision 3a) it writes no cache entry: the stored `impl_tests_text` baseline stays at the last *real* check. This is deliberate and load-bearing. If a reuse advanced the baseline to the current text, a run of individually-sub-0.5% edits would each stay below the floor while their **sum** crossed it, letting a real MIXED-STEP change escape re-check forever. Leaving the baseline fixed means each subsequent diff is measured cumulatively against the last genuine verdict, so once the accumulated drift crosses 0.5% the next audit re-computes. Do not "refresh" the entry on a reuse.

**The reuse advisory (below-floor branch only).** When the below-floor branch reuses a cached verdict, mint one informational `plan_tool/review.py:Recommendation` recording it:
- `severity="info"` — it must stay advisory. Info-severity recs fold into the audit's `smell_recs` bucket (`_collect_purity_split_findings`'s return is added straight to `smell_recs` in `_run_deterministic_checks`), which the blocking gate never reads, so this never flips an exit code. Do not use `medium` here — that is the severity the split findings use.
- A new, descriptive `source` literal — e.g. `"purity-reuse-advisory"` — kept distinct from `GRANULARITY_SPLIT_SOURCE` so it is not confused with a real split finding and is not caught by the medium-`granularity-split` filter.
- `id` via `plan_tool/review.py:_make_rec_id(step.id, source, fingerprint)` with a **stable `fingerprint`** — pass a fixed per-step token such as `f"purity-reuse-step-{step.id}"`, **not** the `M%`-bearing body. This is the round-4 [purity-reuse-advisory] fix: `_make_rec_id` hashes its `fingerprint` arg into the id, so folding the volatile `M%` in would churn the id every audit, making the advisory read as a *new* finding each pass (and inflating `convergence_diagnosis.py`'s recurrence keys + the #125 low-yield counter — part of why the audit never reads clean). A stable id means the same reused step yields the same advisory id across passes.
- `step_id=step.id`, and a `title`/`body` like `purity reused for step N — changed M% of Implementation/Tests, below the re-check floor` (M = `round((1 - ratio()) * 100)`) — the M% may vary in the *body* prose, but must **not** feed the `id`. No follow-up command (the reuse is the resolution — nothing for the operator to do). The genuine-miss branches emit no advisory: they simply re-compute and return the fresh verdict, exactly as a normal purity pass would.

**The recommended wiring — a below-floor reuse hook on the shared helper.** Step 3 routed `_collect_purity_split_findings` through `plan_tool/detail.py:_cached_purity_findings` (with `read_through=True`), and the "one shared helper" outcome should hold. Add an optional `below_floor_reuse` callback the helper consults *only on a read-through miss, before calling Claude*: the helper hands it the loaded (stale) entry and the current detail body; if the callback returns a verdict (the change graded trivial), the helper returns that reuse and skips Claude; if it returns `None` (genuine change, or no entry), the helper proceeds to its normal Claude call + write-back. The audit caller supplies a callback that implements the diff-and-frontmatter grading above and mints the reuse advisory, living in `completeness_phases.py` so the completeness-specific logic stays out of `detail.py`. The two `detail.py` authoring sites pass no callback (and `read_through=False`), so they always call Claude — byte-for-byte the step 3 behavior.

- **Alternative, if the hook feels heavy:** have `_collect_purity_split_findings` compute step 1's key and load step 2's entry directly, deciding hit / below-floor-reuse / genuine-miss itself and calling `collect_detail_quality_findings` only on a genuine miss. This duplicates some of `_cached_purity_findings`'s load/key logic, so prefer the hook unless it complicates the helper's contract.

**Constraints that are not free to vary:**
- **A genuine miss in the audit path still calls Claude.** Only a cache hit or a below-floor-and-no-frontmatter-change miss skips it. The cache is an optimization on redundant work, not a removal of the purity capability — a cold/never-checked step re-computes, it does not silently vanish.
- **The audit path writes the cache on a genuine miss.** Because a genuine miss re-computes through step 3's write-through, the fresh verdict is persisted for next time. The below-floor reuse branch and the hit branch write nothing (the entry is already current or being reused).
- **`detail.py`'s authoring loop is untouched by the threshold.** It always calls Claude (step 3, `read_through=False`), regardless of the section-diff magnitude. #144's grading is audit-path-only.
- **An empty cached finding list is a real "pure" verdict.** On a below-floor reuse, reuse `[]` as the verdict — do not treat it as "not checked."
- **Preserve the monkeypatch seam.** `_collect_purity_split_findings` keeps calling through the body-local `from plan_tool import detail as detail_mod` name so the suites' patch of `plan_tool.detail.collect_detail_quality_findings` still intercepts on the genuine-miss paths that reach the producer.

**Foundational logic and where else it lives.** The core rule this step adds is "decide reuse-vs-advise from a section-scoped diff ratio, no Claude." That rule has no duplicate elsewhere — the only other `SequenceMatcher` users compute unrelated similarities (`plan_tool/convergence_diagnosis.py` title similarity, `plan_tool/review.py` near-miss token matching, `plan_tool/style.py` intra-line diffs). The section-parse it depends on, `parse_detail_file_sections`, is the single detail-section splitter and is reused, not re-implemented.

## Acceptance criteria

- A standalone `completeness-audit --purity` run makes **no Claude call** on steps whose inputs are unchanged (hit) or trivially changed (below-floor, no frontmatter change), and **does** call Claude on genuinely-changed or never-checked steps — so it still delivers real verdicts.
- On an audit miss with a cached entry whose concatenated `## Implementation` + `## Tests` changed fraction is **below 0.5%** AND whose stored `detail_relpath`, `all_files_fingerprint`, `change_type`, `depends_on`, and `purity_verdict_logic_version` are all unchanged, `_collect_purity_split_findings` returns the cached verdict plus one `info` reuse advisory, with **no backend spawn**, and **writes nothing** (the baseline is not advanced).
- On an audit miss **at or above 0.5%**, or on any change to the stored `detail_relpath` (a renumber), `all_files_fingerprint` (a `files:`/`creates:` edit — even under a ~0% Impl/Tests diff), `change_type`, `depends_on`, or `purity_verdict_logic_version`, or with **no cached entry**, it calls Claude, returns the fresh verdict, and writes it back.
- A renumber that reassigns a cache-entry id to a different step does not leak the old verdict: the stored `detail_relpath` differs from the new step's, so the below-floor branch is not taken and the step re-computes.
- The reuse advisory rec is `severity="info"`, has an `id` that is **stable across audit passes** (keyed on a per-step token, not the volatile `M%`), and does not make `_completeness_has_blocking_findings` return true.
- `detail.py`'s authoring-time convergence loop always calls Claude — the threshold does not touch it.
- `uv run pytest tests/cli/test_completeness_cmd.py -q` passes, and the pre-existing completeness-audit and purity suites still pass.
