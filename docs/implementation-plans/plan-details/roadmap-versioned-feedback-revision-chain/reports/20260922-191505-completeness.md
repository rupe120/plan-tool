- HIGH `[accepted-head-writer]` [confidence: limited]: Step 7 (`Gate enrolled decision settlement behind an atomic active-candidate confirmation`) makes decision settlement an accepted-root change, but Overview and Scope guardrails reserve every accepted-head advance for review-seal promotion. Overview says:

  ```
  Exact review-seal promotion remains the only operation that advances the accepted artifact head and never rewrites the ledger.
  ```

  Scope guardrails says:

  ```
  Only exact review-seal promotion advances it.
  ```

  Architecture instead says:

  ```
  When enrolled decision settlement would move the accepted root while an active candidate exists...
  ```

  The two paths cannot both be the sole accepted-head writer, leaving settlement’s publication authority and promotion’s exclusivity contradictory.
  - Fix: Define the explicit accepted-head authority exception for enrolled decision settlement, or redesign settlement so it does not advance the accepted head, and align Overview, Scope guardrails, Architecture, step 7, Testing, and acceptance criteria.
- HIGH `[active-candidate-publication]` [confidence: limited]: Step 5 (`Store batch responses with one root-and-active-candidate pointer while retaining superseded candidate history`) never defines the initial successful-storage transition that makes the stored candidate the active candidate. Architecture says:

  ```
  Processing reads only this pair: the accepted root and the active candidate, when present.
  ```

  It specifies replacing the pointer only for a successor, after a successor is stored, while candidate storage is otherwise only said to create evidence and awaiting-review proposals. Without an initial pointer publication, the first stored candidate is outside the processing pair and cannot reliably be reviewed, superseded, or promoted.
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): A successfully stored first candidate must become the active candidate for its accepted root before later lifecycle actions can use it.
  - Fix: Define successful initial candidate storage as atomically publishing the active-candidate pointer with its evidence and admitted-item proposals, while preserving the stated successor and failure behavior.
- MEDIUM `[ledger-item-closure-lifecycle]` [confidence: limited]: Step 6 (`Add explicit idempotent legacy migration and guarded mutable reviewer edits in predecessor-grouped ledger sections`) promises close and reopen operations, but the Architecture defines no closed lifecycle state, retained record rule, or allowed operations after closure. Deleting an item and retaining a terminal item would both appear to implement “close,” yet differ on stable identity, provenance, and reopening.

```text
Step 6 intent: “Let reviewers submit, retarget, defer, close, or confirm reopening items without changing artifact versions”

Architecture: “Closing, reopening, retargeting, and editing are ordinary mutable ledger operations on the same item”
```
  - Fix: Define closure as a retained ledger-item lifecycle state, including its preserved provenance and permitted later reopen or retarget operations, and add an acceptance criterion for it.
- HIGH `[migration-boundary-enrollment]` [confidence: limited]: The migration rule blocks every ledger route until a migration-completion record exists, while step 2 limits blocking to legacy feedback processing and requires feedback-free root enrollment. The plan never says how a newly enrolled roadmap with no embedded feedback obtains a valid ledger-processing state without being silently treated as migrated.

```text
Architecture: “Ledger-based candidate, review, promotion, and ordinary-feedback routes block with a migration-required result until that record exists”

Step 2 title: “Make root enrollment store feedback-free versions while blocking legacy feedback processing until explicit ledger migration”
```
  - Fix: Define distinct enrollment states for new feedback-free roadmaps and legacy roadmaps awaiting explicit import, then make every ledger route use that boundary consistently.
- MEDIUM `[candidate-discard-resolution]` [confidence: limited]: Steps 8 (`Bind candidate questions, answers, and automatic rejection resolution to the exact active-candidate batch`) and 10 (`Route selector-free feedback commands to the ledger lifecycle, retire the live-artifact overwrite, and preserve unenrolled legacy writers behind their existing fence`) provide no lifecycle or command route for the Architecture’s separate operator discard action. An active candidate that will not enter review therefore has no specified safe way to release the pointer while preserving its history.

```text
Architecture: “An operator may separately record a discard resolution for an active candidate that will not enter review.”
```
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): Provide a defined operator path to resolve and release an active candidate outside review without deleting its history.
  - Fix: Assign discard resolution to the candidate lifecycle and command workflow, define its preserved-history result, and add acceptance coverage alongside rejection and supersession.
