- CRITICAL `[candidate-admission-fixed-lineage]` [confidence: limited]: Step 1 routes every `--revise-feedback` call to `run_initial_candidate_proposal()`, but that function only ever admits one feedback item per roadmap for the roadmap's whole life, so every ordinary feedback update after the first one on a given roadmap gets refused, promoted or not. `plan_tool/roadmap_candidate_run.py`'s `CandidateProposalAdmission` class is documented as "the one fixed feedback lineage permitted for an enrolled roadmap," and `candidate_admission_path()` (its "roadmap-fixed lineage admission path") is keyed only by `plans_dir` and `slug`, never by the accepted-head version, so the same admission file is read on every call. When an admission already exists and a new call's feedback selector differs from the one on file, `run_initial_candidate_proposal()` returns "roadmap admission already binds different feedback" without building a candidate. `promote_review_seal()` never touches this admission file — it writes only the accepted-head selector — which `tests/test_roadmap_version_promotion.py::test_promoted_head_keeps_the_fixed_roadmap_admission_terminal_without_an_extra_member` confirms by asserting the admission bytes are unchanged after promotion. `ROADMAP_FORMAT.md` states the consequence directly: "a different feedback selector refuses before a model call, both before and after promotion." Step 1 has no route around this, so the plan's own Outcome ("Every ordinary roadmap feedback update creates an immutable successor revision from the accepted head... each later update starts from the previously promoted successor"), its acceptance criterion "A second ordinary-feedback proposal derives from the newly promoted accepted version," and the matching Testing bullet cannot hold — the second, differently-selected ordinary feedback update on any roadmap is refused forever. This is exactly the condition the plan's own seed names as a stop condition: "Stop if the existing candidate and promotion lifecycle cannot support successive ordinary feedback revisions without a parallel accepted-head authority."
  - Fix: Check this fixed, once-per-roadmap admission against `ROADMAP_FORMAT.md` and the cited promotion test with the user, and if confirmed, apply the seed's own stop clause — successive ordinary feedback revisions need a new per-generation admission or lineage mechanism, which the plan's own Non-goals rule out — instead of carrying the current single-admission design into `detail`.
- MEDIUM `[accepted-head-writer-exclusivity]` [confidence: limited]: Overview and Acceptance criteria both claim review-seal promotion is the only thing that can advance the accepted head, but a second writer already exists in the code. Overview says: "Only `--promote-review-seal` advances the accepted head, and later revisions build from that promoted successor without rewriting live top-level roadmap artifacts." Acceptance criteria repeats it: "Only existing review-seal promotion advances the accepted head, and it never rewrites live top-level roadmap artifacts." `ROADMAP_FORMAT.md` documents two guarded writers of `AcceptedRoadmapHead`: `promote_review_seal()` and `plan_tool/roadmap_decision_settlement_enrolled.py:run_enrolled_decision_settlement()`, which "changes it after rechecking the current accepted predecessor and storing its one new immutable settled version." The plan's own Architecture section already gets this right, calling `promote_review_seal()` "the only feedback-candidate writer that advances `AcceptedRoadmapHead`" — a claim decision settlement does not contradict, since it is not a feedback-candidate writer. Overview and Acceptance criteria drop that qualifier and read as a claim about every writer in the system, which is false.
  - Fix: Narrow the "only" wording in Overview and Acceptance criteria to match Architecture's existing "only feedback-candidate writer" framing, and name decision settlement as the system's other, untouched accepted-head writer.
- MEDIUM `[enrollment-module-path]` [confidence: limited]: Architecture names the wrong file for root enrollment: "Keep `plan_tool/roadmap_version_enrollment.py` and `--enroll-version` as the only explicit root-enrollment path." No file named `plan_tool/roadmap_version_enrollment.py` exists anywhere in the repository. Root enrollment is implemented in `plan_tool/roadmap.py`, where `enroll_roadmap_root()` and `ImmutableRootEnrollmentResult` are defined and from where `plan_tool/cli/roadmap_cmd.py` imports them. A reader using this plan to find or protect the enrollment code during step 1 will not find the named module and may miss that the real code sits inside the much larger `roadmap.py`.
  - Fix: Replace the Architecture section's file reference with `plan_tool/roadmap.py` (`enroll_roadmap_root`/`ImmutableRootEnrollmentResult`), where root enrollment actually lives.
