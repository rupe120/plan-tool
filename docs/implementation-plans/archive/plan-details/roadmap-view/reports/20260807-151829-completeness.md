- HIGH `[removal-feedback-ids-forward-render]`: Acceptance criterion 1 requires every one of the seventeen reference fields to take one of three stated dispositions, and explicitly names `RemovalRecord.feedback_ids` as disposition (b) — "rendered as an annotated literal id with the reason it cannot resolve" — the same disposition as `removed_id`. `removed_id` gets that treatment directly: it's the whole content of the tombstone label every view prints (step 1's `display_label` rule: "`RemovalRecord` → `.removed_id` and `.rationale` together"). `feedback_ids` does not: step 3's citation map only reads it to build a reverse-lookup key (querying one of the named feedback ids under `--mode review` surfaces the removal as a citer), and step 5's ledger detail file states outright that rendering a removal needs "no walk over `RemovalRecord.feedback_ids`" and "no second lookup." No step ever prints a removal's own `feedback_ids` values as literal, annotated text at the removal's own display site — every other one of the seventeen fields gets that direct, forward rendering somewhere (the walk, the ledger, or — for `removed_id` — the tombstone itself); this is the one field reachable only backwards, by a reader who already knows a feedback id to query.
- MEDIUM `[removal-id-collision]`: Step 1's `build_removal_index` (`01-roadmap-view-resolver-that-turns.md` § Implementation) is typed `Mapping[str, RemovalRecord]` — one record per key, "flattens each artifact's `.removals` tuple... keyed by `removed_id`" with no collision handling described or tested. Two distinct `RemovalRecord`s sharing the same `removed_id` — plausible on a hand-edited roadmap, since nothing in `roadmap_gates.py` enforces removal-id uniqueness the way `check_duplicate_row_ids` enforces it for live design rows — silently overwrites one with the other, with no marker. The plan puts heavy, repeated weight on making a colliding *design-row* id render as `⚠ ambiguous: <id>` naming every match rather than resolving to the first (§ Architecture, § Risks "The ambiguous id resolving silently," § Testing, § Acceptance criteria all call this out for `resolve_id`), but neither the plan body nor step 1's or step 5's detail file names or tests the same case for a colliding removal id, even though `build_removal_index` sits right beside `build_design_row_index` and is built the same way (a flat walk with no dedup).
- MEDIUM `[feedback-id-collision-ambiguity]`: Step 3's `resolve_citation_subject` and its full-map id-labeling have no defined outcome when a feedback id collides across artifacts — a state step 2's `feedback_index` deliberately preserves rather than drops (its own Input section: a hand-edited roadmap "can therefore carry the same feedback id in two different artifacts with nothing on disk having rejected it," and `test_feedback_index_preserves_both_rows_on_a_cross_artifact_id_collision` locks in keeping both rows). Step 3 labels a feedback-id key with "`display_label`'s result" — singular, one row — and its feedback branch just "checks `feedback_index` for the id," with no ambiguous-style handling the way a colliding design-row id gets via `Resolution.matches`. The plan's own acceptance criterion — "An id declared by two rows renders as ambiguous, naming both, in every view that resolves it" — names no row-kind restriction, so this is an unmet criterion for feedback ids, not just an untested edge case.
