## Why

Steps 3, 4, and 5 make rate-limit fallback backend switching scoped to the current batch invoke, streaming invoke, and parallel completeness-apply worker. The docs still describe `switch` in a way that can be read as a lasting backend change, which is risky for operators using `completeness-apply --jobs N` or other concurrent flows. This step makes the public contract explicit: fallback switching is recovery for the current retry path, not a mutation of the selected backend for sibling workers or later commands.

## Implementation

- **Foundational logic:** scoped rate-limit recovery documentation.

- **Document the public contract.** In `README.md:### Rate-limit recovery`, state that `switch` retries the current rate-limited operation on the fallback backend and restores the prior active backend when that invoke finishes. Keep `README.md:### Selecting a backend` focused on persistent defaults from `--backend` and `PLAN_TOOL_BACKEND`.

- **Make concurrency explicit where operators need it.** In `RUNBOOK.md:### backend rate-limit choice`, add the operator-facing check: under `--on-rate-limit switch`, a fallback selected by one invoke or one `completeness-apply --jobs N` worker must not become the backend for sibling workers or later commands. In `RUNBOOK.md:## Backends`, keep the quick reference short but include the same persistent-vs-retry distinction.

- **Keep maintainer guidance precise.** In `CLAUDE.md:Backend abstraction (backend.py)`, describe `backend.py` as the owner of the process-wide default plus scoped override helper behavior, without restating step 3 or step 4 internals. The important maintainer rule is that `get_active_backend()` may observe scoped retry state inside an invoke, while `set_active_backend` / startup selection still provide the process-wide fallback.

- **Update stale design-plan wording.** In `docs/design-plans/BACKEND_SELECTION.md:### 5. Failover on quota limit (shared helper + both retry loops)`, replace any wording that implies the retry helper permanently switches the backend. Prefer wording like “install the fallback for the retry scope” over “use backend” if the current text reads as global state.

If the docs update makes the current help misleading, tighten it to say that `switch` retries the current rate-limited invoke on the fallback backend.
