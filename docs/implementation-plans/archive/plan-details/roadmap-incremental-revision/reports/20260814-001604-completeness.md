- HIGH `[row-write-allowlist]`: Architecture’s planner allowlist, prose-block, merger, and downstream-request rules, steps 4 (`Reject invalid artifact-qualified feedback selections...`), 5 (`Parse and render... patches`), 6 (`Merge allowlisted patches...`), and 9 (`Run one bounded patch request...`), Testing, and Acceptance criteria do not define how an upstream fresh ID becomes an allowed endpoint in a downstream request, or require removal feedback to target the row being removed. `plan_tool/roadmap_gates:check_entity_component_coverage` requires a new entity to reach a component, while `check_design_row_continuity` accepts any cited local open feedback, so valid dependent additions can be rejected and an unrelated selected feedback row can authorize removal of an allowlisted endpoint.
  - Fix: Define one planner-owned map for fresh cross-collection endpoints and an exact feedback-to-removal authorization map, and require the context, parser, merger, gates, and tests to reject any unplanned relation or mismatched removal.
- CRITICAL `[baseline-conflict-detection]`: Architecture’s publication protocol, the Publication-blocking risk, Testing’s baseline/recovery-conflict cases, and the recovery Acceptance criterion promise never to overwrite an external conflicting edit, but a digest read “immediately before” `os.replace` is not a compare-and-replace operation. An external writer can replace a path after the digest check and before the publisher’s replacement, losing that edit despite the conflict guard.
  - Fix: Define an achievable external-writer boundary—either require writers to participate in an exclusive protocol or limit the guarantee to conflicts observed before replacement—and align recovery and acceptance language to it.
- MEDIUM `[seed-command-lock-lifetime]`: Architecture requires both `refresh_roadmap_seeds` and `_cmd_roadmap_materialize` to hold the per-roadmap lock, but `plan_tool/roadmap.py:refresh_roadmap_seeds` and `plan_tool/cli/roadmap_cmd.py:_cmd_roadmap_materialize` call `materialize_and_diff_one_plan`, which calls `materialize_plan_seed`, also named as a lock holder. The Architecture lock paragraph, Concurrency-blocking risk, Testing, and Acceptance criterion do not choose an outer-owner or re-entrant rule, so normal refresh/materialize paths can self-block on a non-reentrant file lock.
  - Fix: Define one composable lock ownership model for wrapper and nested seed operations, with inner helpers reusing the caller’s guard instead of acquiring a second lock.
- HIGH `[checkpoint-head-race]`: Architecture records the baseline `HEAD` but recovers a `checkpointing` marker only when the transaction checkpoint matches `HEAD`; step 7 (`Add clean-tree Git checkpoints...`) and step 8 (`Publish fenced recoverable revisions...`) use only a per-roadmap lock. An unrelated Git commit can advance `HEAD` after the revision checkpoint but before the marker update, causing recovery to restore candidate paths even though the revision commit exists, leaving history and the worktree inconsistent.
  - Fix: define checkpoint detection and recovery when `HEAD` advances during the marker window, preserving later commits while never rolling back a recorded transaction commit.
- MEDIUM `[removed-row-feedback-selection]`: Step 4 (`Reject invalid artifact-qualified feedback selections...`) accepts every open `target.kind: row` selector, while `plan_tool/roadmap.py:_check_predecessor_review_rows`, `plan_tool/roadmap_gates.check_feedback_integrity`, and `plan_tool/roadmap_view.resolve_feedback_target` allow that target to resolve through a removal record. Architecture’s row allowlist and prose-block map cover only existing design rows, and `add-row` may use only a fresh ID, so targeted revision has no defined result for feedback on an already removed row.
  - Fix: reject selectors whose target resolves only through a removal before backend invocation and direct them to broad `--from-stage`, with an acceptance case for that boundary.
- HIGH `[durable-publication-order]`: Architecture fsyncs preimages and the recovery directory before `prepared`, but does not require durable candidate files, destination-directory fsyncs after replacement, or durable phase transitions before the Git checkpoint. Step 8 (`Publish fenced recoverable revisions...`), the Publication-blocking risk, Testing, and Acceptance rely on crash recovery; `plan_tool/fileio.atomic_write_text`, used by `plan_tool.roadmap:_write_artifact`, is explicitly non-durable. A crash can therefore leave a recorded checkpoint or marker whose candidate bytes are absent, and the proposed recovery deliberately refuses that mismatch.
  - Fix: define a durable ordering for candidate staging, canonical replacements, marker transitions, and cleanup before checkpointing, with crash cases that prove either restoration or a complete published set
- MEDIUM `[fresh-id-slot-budget]`: Architecture, steps 3 (`Define revision collection names...`) and 4 (`Reject invalid artifact-qualified feedback selections...`), step 5 (`Parse and render... patches`), step 9 (`Run one bounded patch request...`), Testing, and the first acceptance criterion require planner-owned fresh-ID slots but never define the finite slot set or how an `add-row` identifies one. The backend therefore has no defined number of additions it may make, despite the plan promising bounded small patches and IDs allocated before the request.
  - Fix: define the planner’s finite fresh-slot allocation, operation reference form, exhaustion behavior, and recorded evidence for every collection request
- MEDIUM `[removed-plan-seed-state]`: Architecture says a successful revision changes every extant seed-state entry only to `invalidated` and records a removed plan ID “only” in the session record; Input says the sidecar changes status only; step 8, Testing, and Acceptance repeat those rules. A removed plan normally already has a sidecar entry, and `plan_tool.roadmap_seed_manifest:find_orphan_seed_records` treats a retained entry as an orphan, so the plan does not choose between deleting that entry and violating its status-only rule.
  - Fix: define the seed-state and untouched-draft treatment for a removed plan ID, then align the status-only statements, session record, orphan handling, tests, and acceptance criterion
