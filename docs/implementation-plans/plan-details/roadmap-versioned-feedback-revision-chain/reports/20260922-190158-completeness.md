- HIGH `[active-candidate-batch-policy]` [confidence: limited]: Step 3 (`Build one ordered root-and-active-candidate batch from every eligible open ledger item`) and step 5 (`Store batch responses with one root-and-active-candidate pointer while retaining superseded candidate history`) conflict on whether an ordinary new batch may replace an active candidate. Architecture says:

  ```
  The direct source is the accepted root when no active candidate exists, and the active candidate when one exists.
  ```

  It also says:

  ```
  Creating a successor from the active candidate replaces only the active-candidate pointer.
  ```

  But the same section says:

  ```
  only a new candidate batch waits until the active candidate is promoted, superseded, rejected, or discarded.
  ```

  The latter rule blocks the batch that the former rules need to create a superseding successor, leaving materially different behavior for feedback submitted while review is active.
  - Fix: Define whether ordinary batches may create a successor from an active candidate, or must wait for resolution, and make the source-selection, supersession, CLI, and acceptance rules use that one policy.
- MEDIUM `[ledger-item-closure-lifecycle]` [confidence: limited]: Step 1 (`Define the canonical feedback ledger, target fingerprints, and eligibility rules`) never defines how a closed item is represented or retained, while step 6 (`Add explicit idempotent legacy migration and guarded reviewer edits with predecessor-grouped history`) promises a close operation:

  ```
  Let reviewers submit, retarget, defer, close, or confirm reopening items without changing artifact versions
  ```

  Architecture defines `open`, `awaiting-review`, and `deferred` behavior, but not closure, and Testing covers reopening without defining whether closing preserves the stable item, its response/provenance, and its eligibility for reopening or retargeting. Implementers can therefore delete an item or retain a terminal state while both appearing to implement “close.”
  - Fix: Define closure as part of the ledger item lifecycle, including its retained history and allowed later operations, and add an acceptance criterion that distinguishes terminal retained items from deleted items.
- HIGH `[accepted-head-active-candidate-interlock]` [confidence: limited]: Step 7 (`Read enrolled decision-settlement evidence from the ledger while preserving its exact accepted-head replacement and leaving the ledger unchanged`) advances `AcceptedRoadmapHead`, but the plan does not say how it handles an active candidate bound to the former root. Leaving the pointer intact produces a root/active pair whose candidate ancestry no longer resolves to the current root; clearing or resolving it changes candidate history and proposal status. `plan_tool/roadmap_decision_settlement_enrolled.py:run_enrolled_decision_settlement` currently replaces only the accepted-head selector, so the plan needs an explicit safety route rather than relying on existing behavior.

```text
Architecture: “Processing reads only this pair: the accepted root and the active candidate, when present.”

Architecture: “Every candidate records both `root_version_id` and `source_revision_id`; validation walks source ancestry back to the declared root and refuses any disagreement.”

Step 7 intent: “Read enrolled decision-settlement evidence from the ledger while preserving its exact accepted-head replacement and leaving the ledger unchanged”
```
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): Define how accepted-head changes outside candidate promotion preserve or safely end an active candidate lifecycle.
  - Fix: Specify whether step 7 refuses while an active candidate exists or atomically records its terminal stale resolution, and add an acceptance criterion proving the resulting root/active pair remains valid.
- HIGH `[batch-ledger-edit-conflict]` [confidence: limited]: steps 3, 5, and 6 promise both immutable batch snapshots and ongoing reviewer edits, but do not define the storage result when an admitted item changes after the model call begins. Architecture says:

```text
“A candidate, review seal, or promotion cannot substitute items, responses, target fingerprints, or ledger bytes from a later edit.”

“Reviewer ledger edits remain allowed throughout”
```

Without a conflict result, candidate storage can overwrite the newer reviewer edit, or preserve it while storing a candidate whose recorded proposal no longer matches the ledger.
  - Fix: Define the exact conflict rule for a post-admission ledger edit, including whether candidate storage refuses or preserves the edit, and require the candidate, pointer, and ledger result to remain consistent.
