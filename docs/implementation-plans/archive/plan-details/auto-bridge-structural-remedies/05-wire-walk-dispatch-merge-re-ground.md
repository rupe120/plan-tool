# Step 5 — Route re-ground findings from the walk to the re-ground bridge by directive kind

## Summary

Wires the review/reconcile walk so applying a re-ground `granularity-merge` finding runs step 3's `reground_bridge` instead of falling to the "run it manually" notice. The change is two small pieces: a predicate in `plan_tool/review_walk.py` that recognizes a finding carrying step 4's machine directive as dispatchable, and a dispatch branch in `plan_tool/cli/review_actions.py` that reads the directive kind (step 4's `parse_merge_action`) and calls `reground_bridge` for a `reground` directive. The key design decision: dispatch is driven by the parsed directive **kind**, not the shared `granularity-merge` source token — so the walk never conflates a structural merge with a re-ground, and a (deferred) `merge`-kind directive never reaches a merge bridge from here. The re-ground bridge stays recommend-only by default (it owns its apply-or-recommend gate); the walk supplies only the opt-in token and forwards the confirm, exactly as `_dispatch_structural_escalation` does for split. A dedicated walk-level `--apply-structural` flag (parsed on the reconcile/review walk, forwarded by the walk caller into `_build_review_action_fn`) flips the structural gate on; because the re-ground finding is `info`-severity, the apply path is reachable only when `--include-info` is passed alongside it (the two-flag requirement — `--apply-structural` opts the walk in, `--include-info` keeps the `info` finding in the dispatch set). Absent either flag the finding is filtered out or stays recommend-only, and every unattended walk recommends only. On green, applying a re-ground finding runs the re-ground bridge, renders one status line, and the walk records `applied` only when the bridge actually mutated.

## Why

Steps 3 and 4 build the pieces but leave them unconnected. Step 4 makes the re-ground `granularity-merge` producer append a parseable `reground` directive to `suggested_action` (a marker with the target step ids). Step 3 ships `reground_bridge`, a gated actuator. But the walk still treats a `granularity-merge` finding as un-dispatchable: `plan_tool/review_walk.py:recognized_action` returns `None` (no `plan-tool detail --step` shape), `should_apply_as_finding` returns `False` (`granularity-merge` isn't in `_APPLY_AS_FINDING_SOURCES`), and `file_check_create_target` returns `None` — so `plan_tool/cli/review_actions.py:action` falls to the terminal "suggested action isn't a recognized reconcile or detail invocation; run it manually in another shell" notice. This step closes that last gap: it reads the directive and hands the finding to the re-ground bridge, so the operator actuates the re-ground straight from the walk instead of copying a command into another shell.

## Implementation

- **Foundational logic:** dispatch a `granularity-merge` finding by its directive kind. This plan wires only the `reground` kind; the discriminator is the parsed directive (step 4's kind), **not** the `granularity-merge` source — keying on the source can't tell a re-ground from the (deferred) merge remedy. Getting this wrong conflates a structural merge with a re-ground, the exact confusion the plan's risk section forbids.

- **Add the predicate in `plan_tool/review_walk.py`.** Add `merge_remedy_target(rec)` next to `file_check_create_target`, returning step 4's parsed directive object (`MergeAction`, from `parse_merge_action`) or `None`.
  - **Key on the parsed directive, not the source string.** Pass the whole rec: `return parse_merge_action(rec)` — step 4 ships `parse_merge_action(rec) -> Optional[MergeAction]` taking the `Recommendation`, source-guarding on `rec.source == granularity-merge` and anchoring on the exact `→ (merge|reground) steps:` marker internally, so a non-None result already means "this is a routable directive finding." The predicate adds no extra source check — the parser already enforces it.
  - **Confirm step 4's shipped arity + internal source-guard at HEAD before relying on the no-extra-check contract** (the same HEAD check the bridge keyword names get below). The predicate's correctness depends on `parse_merge_action` (a) taking the whole `Recommendation` and (b) source-guarding on `rec.source == granularity-merge` internally. If step 4 instead ships it taking only the `suggested_action` string, or not source-guarding, this predicate breaks: `parse_merge_action(rec)` fails on the wrong arg type, or any rec whose prose contains the `→ reground steps:` marker is treated as dispatchable. **Fallback if step 4's parser doesn't source-guard:** add the `rec.source == granularity-merge` guard in `merge_remedy_target` itself (`return parse_merge_action(...) if rec.source == "granularity-merge" else None`) so the predicate stays sound regardless of where the guard lives.
  - **Import from `review`, not `granularity`.** `review_walk.py` already imports from `plan_tool.review` (`Recommendation`, `AUDIT_FIX_SOURCES`). Step 4 places `parse_merge_action` in `review.py`, so add it to that same import — no new module edge, no cycle risk (`review` never imports `review_walk`).
  - **Extend `is_dispatchable`.** Add a fourth clause: `if merge_remedy_target(rec) is not None: return True`. This is what makes the walk call `action_fn` on apply for these findings (`walk_recommendations` / `_prompt_for_annotation` / `_auto_apply` all gate auto-dispatch on `is_dispatchable`).

- **Add the dispatch branch in `plan_tool/cli/review_actions.py`.** Add a `_dispatch_reground_remedy(rec)` closure inside `_build_review_action_fn` (a sibling of `_dispatch_structural_escalation` and `_dispatch_file_check_create`) and route to it from `action(rec)` before the `if not rec.suggested_action` terminal.
  - **Body-local imports, matching this leaf's style.** `_build_review_action_fn` already resolves `detail`, `launcher`, and `review` symbols through function-body imports to stay import-light. Add `from plan_tool.reground import reground_bridge`, and step 4's `parse_merge_action` plus the `MERGE_ACTION_REGROUND` kind constant from `plan_tool.review`. Do **not** import `merge_bridge` — the merge bridge is deferred (plan Deferred) and does not exist at HEAD. Call-time resolution also lets tests patch the bridge symbol on its owning module.
  - **Parse once, branch on kind.** Read the directive with `parse_merge_action(rec)` (step 4's parser takes the whole `Recommendation` and source-guards on `rec.source` internally). If it's `None` (a stray call — e.g. the walk's `r`/run key invokes `action_fn` even for non-dispatchable recs), return the same manual-run notice the terminal branch gives. If `kind == MERGE_ACTION_REGROUND` → call `reground_bridge`. Any other kind (`merge`, which no wired producer emits in this plan) also returns the manual-run notice — the merge dispatch branch ships with the deferred merge bridge follow-up, not here.
  - **Use a dedicated structural-remedy opt-in — do not overload `allow_split`.** The bridge owns the whole apply-or-recommend gate (opt-in + TTY confirm + safety check); the walk supplies only the opt-in token and the confirm, adding zero gate logic — the same contract `_dispatch_structural_escalation` follows. But the opt-in must be **its own** token, not `allow_split`: `allow_split` is set from `--split` in the `detail --reconcile` walk where it **defaults ON**, so reusing it would silently gate a *re-ground* — an inverse structural operation — on by default, with no re-ground-specific opt-in, violating the plan's explicit-`--apply`-opt-in gate principle. Add a dedicated `allow_structural_remedy` keyword param to `_build_review_action_fn`, **defaulting `False`**, and pass the bridge's opt-in argument as `allow_structural_remedy and not state.yes_to_all` with confirm-bypass `yes=False`. This mirrors `_dispatch_structural_escalation`'s fast-forward rule: a blanket `yes_to_all` must **not** auto-confirm an irreversible structure mutation, so the opt-in is forced off under fast-forward and the bridge falls back to a genuine TTY confirm.
  - **Which surface flips it — the reachable opt-in.** A dedicated walk-level `--apply-structural` flag is what flips `allow_structural_remedy` to `True`, so the re-ground apply path is invocable rather than only recommendable. Wire it as its own token: add `--apply-structural` (a `store_true`, gated exactly like the existing `--split`) to the reconcile/review walk subparser in `plan_tool/cli/parser.py`, and forward `getattr(args, "apply_structural", False)` into the walk's `_build_review_action_fn(..., allow_structural_remedy=...)` call(s) in `plan_tool/cli/reconcile.py`. The param **defaults `False`** on the `_build_review_action_fn` signature, so every unattended / no-flag walk still recommends only — the flag is the sole path that opts a walk in. Keep it a **shared structural opt-in**: one `--apply-structural` covers the re-ground bridge and, once the merge bridge lands, its dispatch too (per-remedy flags stay Deferred). Do **not** reuse `allow_split` — `--split` defaults ON in the `detail --reconcile` walk, so gating a *re-ground* (an inverse structural operation) on it would silently actuate it on by default; a split-named flag gating a re-ground actuation is the exact coupling this step exists to avoid.
  - **The re-ground finding is `info`-severity — the walk needs `--include-info` too.** `_reground_already_built_recommendation` emits at `info` severity, and the walk filters `info` findings out of the apply set by default. So the re-ground dispatch path is reachable only when **both** `--apply-structural` **and** `--include-info` are passed: `--apply-structural` flips the structural opt-in on, and `--include-info` keeps the `info`-severity finding in the walk's dispatch set. With either flag absent the finding is filtered out or stays recommend-only. State this two-flag requirement here and in acceptance; do not assume `--apply-structural` alone surfaces the finding.
  - **Forward the parsed step ids verbatim.** Pass the directive's step ids straight into `reground_bridge`'s step-ids argument — don't re-derive them from `rec.step_id` or the finding prose. `rec.step_id` is `None` for a re-ground finding, so it isn't the target set; the directive is the only place the complete set is readable (step 4 exists precisely because the id set isn't recoverable from the hashed rec id). Match the exact keyword name step 3 ships for that argument.
  - **`reground_bridge` is deterministic — pass nothing invoker-shaped.** Unlike scope-out's parent and the (deferred) merge bridge, `reground_bridge`'s actuator (`mark_steps_done`) is deterministic and has **no `invoker=` seam** — it flips `PENDING → DONE` on the target steps and spends no Claude on either the recommend or apply path. `_build_review_action_fn` / `_dispatch_reground_remedy` forwards `repo_root` and the plan path but nothing invoker-shaped to `reground_bridge`.

  - **No renumber guard in the re-ground-only walk — the stale-directive invariant is merge-specific.** Forwarding directive ids verbatim is only unsafe when an applied mutation *shifts step ids* underneath a later directive computed against the pre-mutation snapshot. That renumber hazard belongs to **merge alone**: `detail.py:merge_steps` renumbers survivors to contiguous `1..N`, so downstream ids shift down and a later merge directive points at shifted steps. **Re-ground does not renumber** — step 3's `mark_steps_done` keeps every step id (`Key contrast with merge and scope-out: mark-done keeps every step id … no downstream-orphan hazard`); it only flips `PENDING → DONE`, and that flip is idempotent, so an applied re-ground never shifts the ids a later re-ground directive names and a repeated directive is a harmless `noop`. Because this plan ships **re-ground only** (the merge bridge is deferred — plan Deferred), the walk carries **no renumber guard**: no halt-on-first-apply, no plan-stability key. That invalidation machinery lands with the deferred merge bridge follow-up, which introduces the id-shifting mutation that needs it.

- **Map each bridge outcome to one status line and set the annotation.** `reground_bridge` returns a frozen result whose `outcome` distinguishes what happened. Render one line per outcome (mirror the wording style of `_dispatch_structural_escalation`'s per-outcome messages), and set `state.apply_skip = True` for every outcome except `applied`.
  - **`applied`** — the bridge mutated the plan. Leave `state.apply_skip` at its default (`False`) so the walk records `applied` (the finding is resolved). Return e.g. `"re-grounded steps 3, 4, 5 to done"`.
  - **`recommended`** — default path, nothing mutated. Set `state.apply_skip = True` so the walk records `skip` (no edit landed → the finding isn't resolved), matching how `_dispatch_file_check_create` records `skip` when nothing moved. Return the runnable command the bridge recommends.
  - **every other outcome** (`unsafe` / `noop` / `step-missing` — use the exact outcome constants step 3 ships) — nothing mutated. Set `state.apply_skip = True` and return a short reason line. Read the actual outcome vocabulary off step 3 rather than assuming a fixed trio: step 3 adds a `noop` outcome for an already-satisfied re-ground, so handle the result's own full set.

- **Routing-table placement in `action(rec)`.** Add the re-ground branch after the `file_check_create_target` check and before `if not rec.suggested_action`. A `granularity-merge` finding isn't a `recognized_action`, isn't `should_apply_as_finding`, and isn't a file-check, so it reaches this new branch cleanly; guard the branch on `merge_remedy_target(rec) is not None` (or re-parse inline) so non-directive findings still fall through to the terminal notice.

- **Parallel consumer left as-is (Deferred).** `plan_tool/create.py:_granularity_split_hints` drops `granularity-merge` recs at the create stage (`granularity-merge recs are dropped`) — create's change-type review has no interactive re-ground actuator. This step does not add a create-side trigger; that mirrors how the create convergence loop still doesn't route through `escalate_to_split` (create-side trigger deferred, per CLAUDE.md's escalate-to-split note). See Deferred.

## Acceptance criteria

- Applying a `granularity-merge` finding with a `reground` directive calls `reground_bridge` with the directive's step ids and returns that bridge's outcome as a one-line status.
- The re-ground dispatch never routes to `plan-tool merge` or any merge bridge; a `merge`-kind directive (which no wired producer emits in this plan) falls through to the terminal manual-run notice.
- `is_dispatchable(rec)` returns `True` for a finding carrying a step 4 directive and `False` for a `granularity-merge` finding without one.
- The re-ground opt-in is a dedicated `allow_structural_remedy` param (default `False`), never `allow_split`; the bridge's opt-in argument is `False` whenever `state.yes_to_all` is `True` regardless of `allow_structural_remedy`, and `False` on any walk that does not pass `--apply-structural`.
- The re-ground dispatch path is reachable only when **both** `--apply-structural` **and** `--include-info` are passed (the finding is `info`-severity); with either absent the finding is filtered out or stays recommend-only.
- `state.apply_skip` is `False` only when the bridge outcome is `applied`; it is `True` for `recommended`, `unsafe`, `noop`, and `step-missing`.
- A `granularity-merge` finding with no directive marker still returns the existing "run it manually in another shell" notice.
- The re-ground-only walk needs no renumber/stale-directive guard: an applied re-ground keeps every step id (`mark_steps_done` never renumbers, only flips `PENDING → DONE` idempotently), so it cannot shift the ids a later directive names; the halt-on-first-apply / plan-stability-key invalidation is merge-specific and lands with the deferred merge bridge.
- All new tests in `tests/cli/test_review_actions.py` pass; the existing terminal-row tests in `TestActionMatrixTerminalRows` stay green.
