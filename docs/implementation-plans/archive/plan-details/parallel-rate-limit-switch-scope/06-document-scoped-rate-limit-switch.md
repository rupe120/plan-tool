## Why

The current docs describe `switch` as "switch to the fallback backend and retry," which is easy to read as a process-wide backend change. After steps 3, 4, and 5 land, the actual contract is narrower: a rate-limit switch is visible only to the current retry loop, then the original active backend remains in force for later calls, sibling workers, and the serial replay tail. Operators need that distinction before using `--on-rate-limit switch` in parallel completeness apply or long runs, and maintainers need it captured in the backend guidance so future edits do not reintroduce process-wide wording.

## Implementation

- **Foundational logic:** scoped rate-limit fallback documentation.

- **Document the behavior, not the mechanism.** Say that `--on-rate-limit switch` retries the current rate-limited backend call with the fallback backend, then restores the backend that was active before that call. Do not explain the context manager, token reset, or retry-loop internals from steps 3 and 4.

- **Keep persistent selection separate.** In `README.md:### Selecting a backend` and `RUNBOOK.md:## Backends`, keep `--backend` and `PLAN_TOOL_BACKEND` as the controls that choose the active backend for the process. In `README.md:### Rate-limit recovery` and `RUNBOOK.md:### backend rate-limit choice`, state that `--fallback-backend` and `PLAN_TOOL_FALLBACK_BACKEND` are recovery targets, not new defaults.

- **Name the parallel safety contract.** In the README and runbook rate-limit sections, include the observable result from step 5: parallel workers and later serial replay do not inherit a sibling worker's fallback backend. Keep this short and user-facing; the test detail belongs in the step 5 detail file, not in the docs.

- **Clarify interactive `ask`.** The `b` / backend-switch choice in `RUNBOOK.md:### backend rate-limit choice` should follow the same scoped rule as policy `switch`: it retries the current invoke with the chosen backend and then restores the prior active backend.

- **Update maintainer guidance.** In `CLAUDE.md:Backend abstraction (`backend.py`)`, preserve the current notes that `backend.py` is a stdlib-only leaf and that normal selection precedence is `--backend` > `PLAN_TOOL_BACKEND` > `claude`. Add one concise sentence that rate-limit fallback is scoped to the current batch or streaming invoke and must not be documented or implemented as a lasting global switch.

- **Repair the design-plan wording.** In `docs/design-plans/BACKEND_SELECTION.md:### 5. Failover on quota limit (shared helper + both retry loops)`, update wording like `use_backend(next)` and `switching to <backend>` so it describes a retry-scoped fallback. Keep the future design shape, but avoid saying a retry fallback writes the default backend for later work.

- **Touch parser help only if needed.** `plan_tool/cli/parser.py:make_base_parser` owns top-level help for `--on-rate-limit` and `--fallback-backend`. If those help strings read as a durable backend change, tighten them to something like "retry the current rate-limited call with --fallback-backend."
