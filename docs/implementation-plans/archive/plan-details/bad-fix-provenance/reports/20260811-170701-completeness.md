The Problem/Overview frame the earliest case as apply on one audit then recurrence on the next, but Architecture, Testing, and acceptance never state that two-pass histories stay silent even when identity and an intervening applied note are both present.
  - Fix: State in Architecture, step 3, acceptance criteria, and Testing that bad-fix inherits the sibling advisories’ minimum collapsed-pass count (default three same-stage finals) and stays silent below it, or document an explicit lower bar if two-pass detection is required.
- MEDIUM `[reuse-collapse-boundary]`: Bad-fix evaluates `build_collapsed_completeness_passes`, which merges adjacent completeness finals with identical finding-id sets into one `CompatiblePass` (`plan_tool/convergence_diagnosis.py:build_collapsed_completeness_passes`; `tests/test_convergence_diagnosis.py:test_adjacent_identical_id_sets_collapse`). The common reuse-audit path after `completeness-apply` keeps the same recommendation ids, so apply-then-reaudit collapses into a single pass and leaves no earlier pass in the window to pair with the recurrence. Architecture and Testing never name this silence case.
  - Fix: Add a Risk and Testing fixture for reuse-collapsed histories (applied note merged into the collapsed pass, no separate prior pass) and state that bad-fix fires only when a later final with a distinct collapsed pass still matches an earlier pass’s finding and annotation.
- MEDIUM `[newest-pass-eligibility]`: `classify_edit_drift` only considers new findings that are still open in the newest pass (`_edit_drift_eligible` skips findings with terminal annotations via `_is_resolved_in_run`), but step 3, Architecture, and acceptance only require same-issue identity plus a prior applied non-empty note — they never require the recurring finding to sit in the newest evaluation-window pass or to be unresolved there. A terminal decline or re-apply on the newest pass could still match an older remedy note and emit a misleading advisory.
  - Fix: Define bad-fix eligibility in Architecture, step 3, acceptance criteria, and Testing: evaluate findings in the newest collapsed pass in the window, and skip any finding already terminal (`applied` or deliberate `skip` with empty `halt_reason`) in that pass’s annotation map.
- MEDIUM `[record-saved-report-selection]`: Step 2 (`Add the completeness-record command for hand-applied findings`) and Architecture say the record CLI resolves a finding against “a saved completeness report” but never define which sidecar when several `*-completeness.json` files exist; `completeness-apply` at HEAD defaults to the newest completeness save and accepts `--id` (`plan_tool/cli/completeness_cmd.py:cmd_completeness_apply`). Without the same rule, a hand-record after re-audit can attach provenance to the wrong report.
  - Fix: Bind step 2 intent, Architecture, acceptance criteria, and Testing to the same newest-by-default / `--id` override selection contract `completeness-apply` uses. - INFO: [classifier-surface-wiring] Step 3 and acceptance name `plan-tool convergence` and `_emit_convergence_loop_advisories` but not the sibling wiring pattern at HEAD: a `classify_*` helper, a `ConvergenceDiagnosis` field, `_bad_fix_lines`, and explicit extension of `_convergence_loop_advisory_lines` (which today hand-picks impact-recurrence and edit-drift only — `plan_tool/cli/completeness_cmd.py:_convergence_loop_advisory_lines`). Nothing is wrong, but the bundle is not auditable for parity across both render paths without reading step 3’s file list. → fix: Add one acceptance bullet that bad-fix rides the same `diagnose_convergence` + `render_diagnosis` + `_convergence_loop_advisory_lines` pattern as the existing loop advisories.
