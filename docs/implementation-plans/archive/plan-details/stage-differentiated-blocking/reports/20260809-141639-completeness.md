- HIGH `[bare-bar-non-conceptual-findings]`: The bare bar is written only over the two conceptual axes — "Zero `plan-correctness` at any severity **and** zero HIGH completeness" — but the completeness loop's blocking signal is built from findings that carry neither source: `completeness_cmd._open_findings_now` returns `collect_deterministic_findings(...) + collect_self_consistency_findings(...)`. A HIGH `missing_on_disk` detail-coverage or `orphaned-deliverable` finding matches neither clause of the bare bar, so the bar would call that round clean and stop the loop with genuinely blocking well-formedness findings open; step 5 then propagates the same verdict into `--json has_blocking_findings`, which `_completeness_has_blocking_findings` returns True for today.
- HIGH `[is-bare-selector-partial-bundle]`: Step 4 (`Pick the bare or detail bar in the completeness iterate loop…`) selects the bar from `bundle_status.is_bare`, which `review.py:DetailBundleStatus.is_bare` defines as "True when at least one step has no detail file (partial or full)". - HIGH `[conceptual-findings-in-loop-state]`: Step 4's "feed it the conceptual audit findings" collides with how the loop's state is wired. `state.current_finding_ids` and `state.has_blocking_findings` are set from the same `_open_findings_now()` call, and that one id set also drives `converged`, `is_marginal`, and `stall_rounds`; the conceptual audit runs exactly once per invocation (the loop's own comment: "Conceptual audit runs ONCE, here"), and under the #85 read-only split the loop applies neither conceptual source. Adding a fixed, never-shrinking conceptual set to that id set means `converged` can never fire and `no_progress` fires after two rounds, so the bare bar's "keep iterating while correctness remains" produces extra rounds with nothing the loop can apply.
- HIGH `[clean-streak-sample-source]`: Step 3 (`Require a clean streak before should_continue stops on no_blocking_findings`) counts loop rounds, but the conceptual sample the streak is meant to confirm is produced once per invocation, so two consecutive rounds re-read the same `_audit_recs` — the second round confirms nothing. `review.audit_plan_until_stable` already implements consecutive-sample confirmation over genuine re-samples via `dry_rounds`, reporting `confirmation_kind` as `confirmed-dry` / `confirmed-low-yield`.
- HIGH `[should-continue-shared-callers]`: Step 3 edits `should_continue`, which `create.py`, `detail.py`, `cli/reconcile.py`, and `cli/completeness_cmd.py` all call, so a streak requirement on `no_blocking_findings` costs every one of those loops an extra round — while Deferred says "Selecting a stage bar inside the reconcile and create/detail iterate loops" is out of this plan's reach. The step also does not say how the streak interacts with the stops around it: `no_blocking_findings` already fires only at `iteration > 0`, `converged` and `max_iterations` are checked before it, and `max_stall_rounds` defaults to 2, so the extra round the streak forces will usually be relabeled `no_progress`.
- MEDIUM `[one-discriminator-vs-is-blocking-impact]`: Architecture claims "One discriminator owns both axes", but `convergence.py` already ships a second recommendation-level blocking predicate — `is_blocking_impact(rec, *, demote_low_impact_medium=…)` — which CLAUDE.md § "Convergence policy boundary" reserves for reconcile blocking-state refreshes and conceptual-audit `material_new`, and which the Input section never lists among the contracts this plan reads.
