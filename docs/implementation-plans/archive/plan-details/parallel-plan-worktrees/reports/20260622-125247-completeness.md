### Correctness (run these first)

_Verified: file paths resolve, dependencies are coherent, and the plan's stated concepts are internally sound._

- HIGH: ** `[prune-clone-discovery]` Step 4 (`destructive-worktree-remove-prune-verbs`) contradicts itself on whether `prune` discovers dead **clones**. Its implementation section commits to a `worktree_base` path-scan that classifies each child dir by kind and states "**dead clones are found too**" (and the Deferred reaffirms "Deregistered clones *under* `worktree_base` **are** now discovered"), but the later "Why prune covers only deregistered *worktrees*, not deregistered clones" subsection says a deregistered clone's path "can't be recomputed or discovered" and is "a **documented manual-cleanup limitation**," and the acceptance criterion says prune deletes worktrees "discovered via `worktree_list` scoped to `worktree_base`" — `worktree_list` is git's registry, which never lists clones. The path-scan decision (plan body + the impl section) is authoritative; the registry-based prose is stale from an earlier design.
- MEDIUM: ** `[prune-round-trip-filter]` Step 4's prune discovery claims the derived-path round-trip ("each dir name treated as a slug → `derive_worktree_path(...)` must round-trip to that path") ensures "an operator's *unrelated* dir under `base` is never a candidate." Since `derive_worktree_path(repo, slug)` is `base / slug`, every validly-named child dir of `base` round-trips trivially, so the check excludes nothing except path-traversal names — the real exclusion is the kind-classifier (skip-foreign) plus the clean-tree/confirm gate. An operator's own non-plan-tool worktree or clone of the repo parked under `worktree_base` would classify as a workspace, miss `registered`, and be swept as dead.
- MEDIUM: ** `[worktree-cmd-repo-root-from-inside-worktree]` The `worktree` group (step 3 `worktree-command-group-list-verbs-wire`, step 4) anchors all path math to `ctx.repo_root`, but repo-root resolution stops at the first `.git` entry and a worktree's `.git` is a gitlink *file*, so invoking `worktree list`/`prune`/`add` from a cwd *inside* a worktree resolves `repo_root` to the worktree and `worktree_base(repo_root)` mis-derives (e.g. `<main>.worktrees/<slug>.worktrees`). The verbs then scan/provision against the wrong base — `list`/`prune` silently find nothing; `add` provisions in the wrong place. The plan's own premise (operators `cd` into worktrees) makes this invocation likely.
- HIGH `[prune-clone-discovery]`: `worktree prune` (step 4) can `rm -rf` an operator's unrelated git repository. Its discovery is a `worktree_base` path-scan that classifies a dir as a *clone* by "a standalone repo dir whose `.git` is a directory" and deletes it when "no registered plan owns the path." That clone test matches **any** git repo, with no tie to this repo and no plan-tool provenance marker (step 2's derived scheme is bare `base / slug`, carrying no sentinel) — so a clean, slug-shaped git dir under the base that isn't a currently-registered plan is classified dead and deleted. Worktrees are safe (this repo's `git worktree list` registry is authoritative), but the body's claim "an operator's unrelated worktree/dir is never a candidate" is **false for clones**, which the plan itself calls the registry's blind spot.
- HIGH `[clone-remove-commit-loss]`: `worktree remove`/`prune` (step 4) `rm -rf` a clone dir, but a clone is an **independent repo whose objects aren't shared** — its branch and all commits live only in the clone's `.git`. The clean-tree gate (`_dirty_gate`, step 4) only refuses on *uncommitted* work, so a clean clone holding **committed-but-unmerged** commits is deleted with no protection, destroying the only copy. This contradicts the plan's own Out-of-scope claim that remove/prune "delete the working tree ... but not the branch ... leaves its branch behind" — true for worktrees (commits survive in the shared object store, branch ref orphaned-but-recoverable) but **false and data-losing for clones**. The plan repeatedly frames the dirty gate as the data-loss protection, hiding this asymmetry from an operator reasoning with the worktree mental model.
