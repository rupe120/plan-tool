- MEDIUM `[one-copy-content-criterion]` [confidence: limited]: The first acceptance criterion contradicts the resume file the plan adds in step 2 (resume-file module) and uses in step 3 (first stage run). The criterion says:

```
No command reads or writes the four stage artifacts' content outside
`.roadmap-versions/`; the feedback ledger, `seed-state.json`, `INDEX.md`,
the draft-seed directory, and the run-log resume file are the only other
roadmap files.
```

  The resume file holds the gate-clean stage results, which are artifact content, and the stage command writes and re-reads it under `.plan-tool/runs/<slug>/`. The criterion also calls it a "roadmap file", while the Architecture "One reader path" bullet says the file lives in the run-log directory and not in the roadmap folder. As written, the criterion is false the moment step 3 ships. Step 11's guard ("no production code reads ... the resume file outside the stage run") and the Testing bullet about `RoadmapStage.artifact_path` do not settle whether the stage run's own reads count. An implementer could read the criterion as banning the resume file or as exempting it.
  - Fix: Reword the criterion to say the one stored copy of accepted content is `.roadmap-versions/`, and that the resume file is a transient pre-publication holding area read and written only by the stage run. Say plainly that it is not a roadmap-folder file.
- MEDIUM `[legacy-folder-behavior]` [confidence: limited]: The plan does not say what happens to a legacy folder after the unversioned fallbacks go away. Step 3 refuses a stage run on a folder with no accepted head and top-level `0N-*.md` files, with a named error that "points at hand conversion". Step 11 removes the unversioned branches from the readers (`roadmap_view.py:load_roadmap` and the `--settle-decision` unenrolled branch). Two things are left open:
  - Neither step 11 nor the Architecture "One reader path" bullet names the outcome for `--view`, the seed routes, `--settle-decision`, and `--compare` on a no-head legacy folder. It could be a named refusal, a missing-file crash, or an empty view.
  - Step 12 lists what to document (the resume file, the post-head refusal, the `--compare` default, `INDEX.md`) but not the hand-conversion procedure the step 3 error points to. The plan therefore refers to a procedure that no step authors. Integration is the stated first user (see Out of scope: "Integration is converted by hand after this ships").
  - Fix: Define one named refusal for every accepted-roadmap reader on a folder with no accepted head, covering steps 3, 6, 7, 8, and 11. Add the hand-conversion pointer to step 12's documentation list, or state that the error text is the only guidance.
- MEDIUM `[checkpoint-removal-ownership]` [confidence: limited]: Step 3 (first stage run) and step 10 (legacy writer mode) both claim to retire the revision checkpoint. Step 3's title says "the revision checkpoint retired". Step 10 lists "the revision checkpoint and rollback" among the things it deletes, and the plan never says which step owns which half. A reader can't tell whether step 3 stops the stage run from writing the checkpoint while step 10 deletes the checkpoint and rollback code, or whether the two overlap. If step 10 deletes the code first or only partly, step 3 can leave a checkpoint write behind. A step can also mark the removal done while the other still has work. The earlier fix covered the `--from-stage` and stage-baseline split but not this one.
  - Fix: State the split once: step 3 only stops the stage run from creating or consulting a checkpoint, and step 10 deletes the checkpoint and rollback code and `--restore-revision`. Reword both step titles to match.
- MEDIUM `[stage-run-failure-resume-gap]` [confidence: limited]: Step 3 (first stage run) publishes the root version as one journaled generation: version members and ledger first, `accepted-head.json` last. The plan names two crash points, "before the head commits" (recovered by the no-head journal branch) and "after the head commits" (resume file deleted, `INDEX.md` healed). It does not say what a re-run does when a no-head journal is pending and a resume file is also present. The plan's wording is: "A crash before the head commits is recovered by the existing no-head branch of `recover_roadmap_publication`, which this plan keeps." That recovery finishes the old publish. The resume path would instead re-gate the held stages and rebuild a root version from them, so the two could publish two different roots, or recovery could publish a root from a brief that has since changed. The plan states no order between them and no rule for which wins. Testing covers the crash case only with "a re-run then publishes", and says nothing about a changed brief at that point.
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): The plan does not say how a pending root-publication recovery and a held resume file are ordered on re-run, so the first run could publish a root the operator did not intend.
  - Fix: State in the plan body that the stage run recovers any pending root-version journal before reading the resume file. Add a test where a crash left both a pending journal and a resume file, and a re-run publishes only the journaled root.
- MEDIUM `[reopen-route-replacement]` [confidence: limited]: Step 10 removes `--reopen-feedback` in favor of `--reopen-ledger-feedback`. The Route disposition lists the replacement only in a parenthetical. It is not listed under "Unchanged", and no step or criterion checks that the replacement covers what the removed route did. `--reopen-ledger-feedback` exists at HEAD (`plan_tool/cli/roadmap_cmd.py`), so this is a clarity gap only. Step 12's docs sweep should name the replacement when removing the old flag.
  - Fix: List `--reopen-ledger-feedback` under the Unchanged routes and have step 12 point docs that named `--reopen-feedback` at it.
