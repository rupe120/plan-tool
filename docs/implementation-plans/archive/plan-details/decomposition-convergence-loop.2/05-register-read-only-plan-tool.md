# Step 5 — Register read-only `plan-tool convergence` subcommand (cmd_status pattern, zero Claude, always exits 0)

## Summary

- Wire a new read-only `plan-tool convergence <name>` subcommand that loads a plan's saved report history, runs the step 1–4 diagnostic, and prints the rendered verdict. It spends no Claude and **always exits 0** — there is no `--fail-on-findings` and no `--min-runs` flag.
- Primary surfaces: a new `plan_tool/cli/convergence_cmd.py` (handler + `register`), plus the fixed multi-file registration fan-out across `plan_tool/cli/app.py`, `plan_tool/cli/parser.py`, `plan_tool/cli/__init__.py`, and the generated `docs/cli/` reference + help golden.
- **Key design decision:** model the handler on `plan_tool/cli/inspect.py:cmd_status` — `args`-only signature (no `invoker`, no `RunLogWriter`), `_load_context` → `resolve_plan_for_context` → engine → `print` → `return 0` — **not** on `cmd_validate`, because this step deliberately omits the `--fail-on-findings` rc-flip. The command is purely informational.
- On green: `plan-tool convergence <name>` prints the four-state headline + per-kind breakdown + (on `spinning`) the pre-filled `plan-tool split …` / `plan-tool create … --from-existing …` command that `render_diagnosis` builds, and exits 0 for every verdict; the package-surface, help-golden, and cli-reference drift tests stay green.

## Why

- Steps 1–4 build the whole diagnostic in `plan_tool/convergence_diagnosis.py` — `load_report_history` (step 1), `build_region_trends` (step 2), `diagnose_convergence` (step 3), and `classify_fork` + `render_diagnosis` (step 4) — but **nothing calls them from the CLI**. An operator cannot ask "is this plan's audit/apply loop converging, or spinning on a mis-decomposition?" without a registered command.
- This step is the one thin seam that wires the existing engine to a user-facing verb. It adds no new diagnostic logic — it resolves the plan, drives the step 1 → step 3 → step 4 chain, prints the step-4 render, and exits.
- It must inherit the repo's read-only safety guarantees: no Claude call, no mutation, no run-log entry, and the exit-code convention (a completed inspection exits 0 regardless of verdict). The deliberate omission of `--fail-on-findings`/`--min-runs` keeps this a pure "tell me the state" diagnostic, not a CI gate.

## Implementation

### Cross-step input contract (depends_on: 4)

This step consumes the step 1–4 engine in `plan_tool/convergence_diagnosis.py`. It calls exactly three entry points and reads nothing else; if a name differs, align in the producing step, not here:

- **`load_report_history(plan_path)`** (step 1) → `ReportHistory`. Returns an empty history when the plan's `reports/` dir is absent (no error).
- **`diagnose_convergence(history)`** (step 3) → `ConvergenceDiagnosis`. Carries the four-state headline, per-series verdicts, and `plan_slug` (set by step 1's `slug_from_filename`).
- **`render_diagnosis(diagnosis)`** (step 4) → `str`. Prints the headline, per-kind breakdown, and the pre-filled split/reseed command. It reads `diagnosis.plan_slug` itself, so the handler **must not recompute the slug**.

### `plan_tool/cli/convergence_cmd.py` (new)

- **`cmd_convergence(args: argparse.Namespace) -> int`** — mirror `plan_tool/cli/inspect.py:cmd_status` exactly:
  - Signature is `args`-only. **No `invoker`, no `claude_invoker`, no `RunLogWriter`** — this is a read-only verb and threading any backend seam would break the never-call-claude guarantee.
  - Body: `ctx = _load_context(args)` → `path = resolve_plan_for_context(ctx, args.name)` → `history = load_report_history(path)` → `diagnosis = diagnose_convergence(history)` → `print(render_diagnosis(diagnosis))` → `return 0`.
  - **Always returns 0.** Do not branch the exit code on the verdict. There is no `--fail-on-findings` arm (contrast `cmd_validate`'s `INVALID` → rc-1 arm) and no `--min-runs` floor. A plan that can't be located still surfaces a non-zero error from `resolve_plan_for_context` upstream — that path is unchanged.
- **Imports — top-level, not body-local.** `plan_tool/convergence_diagnosis.py` is a cycle-free leaf (its only `plan_tool` imports are `review_persistence`, `review`, `locator`, `convergence` — none import `plan_tool.cli`). Import the three functions at module top:
  - `from plan_tool.convergence_diagnosis import diagnose_convergence, load_report_history, render_diagnosis`
  - Also `from plan_tool.cli.context import _load_context`, `from plan_tool.cli.parser import Handler`, `from plan_tool.locator import resolve_plan_for_context` — matching `inspect.py`'s leaf-only import posture. Do **not** import `plan_tool.cli.app`.
- **`register(subparsers) -> dict[str, Handler]`** — copy `gates_cmd.py` / `inspect.py`'s single-command shape:
  - Build the `-y/--yes` parent locally (verbatim from `inspect.py:register`'s `yes_parent`). **Do not build a `fail_on_findings_parent`** — this command has no such flag.
  - `p = subparsers.add_parser("convergence", help="diagnose whether a plan's audit/apply loop is converging or spinning", parents=[yes_parent])`.
  - `p.add_argument("name", help="plan name — slug, filename stem (e.g. 1-my-feature), or filename.md")` (same `name` help string as `cmd_status`).
  - `return {"convergence": cmd_convergence}`.

### `plan_tool/cli/app.py` (edit)

- Add the **dual import** beside the other per-intent module imports (e.g. after the `gates_cmd` import block):
  - `from plan_tool.cli import convergence_cmd as _convergence_commands`
  - `from plan_tool.cli.convergence_cmd import cmd_convergence`
  - The second re-import is **required**: `plan_tool/cli/__init__.py` mirrors every module-level name of `app`, and `tests/cli/test_package_surface.py:test_every_subcommand_has_a_dispatch_handler` asserts `plan_tool.cli.cmd_convergence` resolves. Registering the module alone (without the `cmd_convergence` re-import) ships a command whose dispatch works but whose handler attribute is missing — a red package-surface test with no obvious cause.
  - Use the `from plan_tool.cli import convergence_cmd as …` form (not `import plan_tool.cli.convergence_cmd`), matching the existing imports' note about partially-initialized-package resolution.
- Append `_convergence_commands` to the `COMMAND_MODULES` tuple. Placement in the tuple does not affect `--help` order (that is `CANONICAL_COMMAND_ORDER`'s job); append after `_completeness_commands` to keep the registry grouped sensibly.

### `plan_tool/cli/parser.py` (edit)

- Insert `"convergence"` into `CANONICAL_COMMAND_ORDER`, **immediately after `"completeness-apply"`** (mid-tuple insert, not end-of-tuple append). A command absent from this tuple floats to the end of `--help` (`_canonical_index` returns `len(...)` for unknowns), so the explicit entry fixes its rendered position. The convergence diagnostic reads as a completeness-family verb (it judges the completeness audit/apply loop), so it sits beside `completeness-apply`.

### Foundational logic & shared locations

- **Foundational logic of this step:** a read-only inspection handler that resolves a plan, drives a no-Claude engine, prints its render, and exits 0.
- **Shared pattern (reuse, do not fork):** `plan_tool/cli/inspect.py:cmd_status` and `:cmd_validate` are the canonical read-only-handler shape; `cmd_convergence` copies `cmd_status`'s structure (no rc-flip) rather than `cmd_validate`'s (`--fail-on-findings` rc-flip). No new shared abstraction is warranted.
- **Deferred consolidation (not this step):** the `-y/--yes` and `--fail-on-findings` parents are minted per-handler-module across `inspect.py`, `gates_cmd.py`, and now `convergence_cmd.py`. Folding them into a shared `plan_tool/cli/parser.py` helper is a cross-module refactor `detail` can't mint — left to a reconcile pass (see Deferred).
