- MEDIUM `[stack-anchor-union-side-effects]` [confidence: limited]: Step 2 (stack gates, anchor union) adds stack ids to `_constraints_rows` in `plan_tool/roadmap_gates.py`. The plan calls this "the only components-side change" and says stack rows are decision anchors. But `_constraints_rows` is also the base of `_rows_of`, and `_rows_of` feeds more than the anchor union:
  - the undescribed-row gate, which refuses a row "inventoried in the frontmatter but never named in the prose";
  - `design_row_ids`;
  - `_constraints_identity_rows`, and through it feedback targets, id uniqueness and removal continuity.

  Hosting rows are kept out of `_constraints_rows` on purpose. They sit only in `_constraints_identity_rows`, and the plan's Problem statement says they are "never decision anchors or prose-inventory rows". The plan never says whether stack rows must be named in the constraints prose. If they must, step 4's prompt and the Integration-brief replay have to author that prose. If not, step 2 has to exempt them from the undescribed-row gate. Two implementers could land opposite behavior here, and an `open` stack row with no prose would either be refused or pass silently.
  - Fix: Decide once, in the plan body and step 2, whether stack rows are prose-inventory rows. Then align step 4's prompt, the replay fixture, and the step 8 doc example with that decision. Also state whether stack rows are exempt from `design_row_ids`.
- HIGH `[stack-feedback-target-ids]` [confidence: limited]: No step makes stack ids valid feedback targets in `plan_tool/roadmap_gates.py`. Step 3 (stack rows as feedback targets) never edits that file. Step 2 leaves `_constraints_identity_rows` unchanged and defers it to "the feedback and review steps".
  `feedback_target_ids` and `_continuity_rows` both read `_constraints_identity_rows`. They are used by feedback validation (`resolvable = feedback_target_ids(predecessor) | …`), `roadmap_revision.py`, and `roadmap_view.py`. So feedback naming a stack row would be refused as an unknown target. The acceptance criterion "a stack row can be targeted by feedback and revised through a candidate" fails.
  Removal continuity also would not see stack rows. That puts the "cannot remove a stack row" guarantee at risk.
  Stack ids are also absent from `_envelope_identity_rows`. `check_duplicate_row_ids` therefore misses a stack id that collides with a domain or constraint id. Step 2 plans to have the stack gate report that collision itself, but names no test for it.
  - Fix: Add the gates-side change to step 3's file list and intent. Stack ids join the feedback-target and continuity identity rows, and the global duplicate-id check covers them. Then add tests for feedback on a stack row, for a refused removal, and for a collision with another artifact's id.
