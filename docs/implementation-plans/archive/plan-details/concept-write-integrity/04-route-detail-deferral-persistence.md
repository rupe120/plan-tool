# Step 4 — Route detail's deferral persistence through synchronize_concepts

## Summary

Replace the direct `save_concepts` write at the tail of `plan_tool/detail.py:generate_detail` (the "publish the shared concept record exactly once" block) with a call to `plan_tool/concept_sync.py:synchronize_concepts`, and move the deferral-link preparation helper `plan_tool/detail.py:_replace_detail_deferrals` (with its reader `_concept_deferral_step_ids` and the `_DETAIL_DEFERRAL_STEPS_KEY` constant) into `plan_tool/concept_sync.py` as public symbols. The key design decision is a preparation/publication split that keeps `synchronize_concepts`'s signature frozen (step 1 pins it): detail prepares the reviewed tree with the moved helper, then hands original and reviewed trees to the synchronizer, which owns the fingerprint, the compare-and-swap guards, and publication. On green, detail's sidecar write flows through the guarded single writer — unchanged on-disk behavior for unsigned trees (sidecar only, plan untouched, via step 1's unsigned arm), and on signed trees the owned plan sections are re-rendered from the record so prose and record can no longer drift. Files: `plan_tool/detail.py`, `plan_tool/concept_sync.py`, `tests/test_detail.py`, `tests/test_concept_sync.py`.

## Why

`generate_detail`'s tail persists deferral-link updates by calling `save_concepts` directly (the `if concept_tree is not None and not dry_run:` block), hand-computing `plan_fingerprint` via `compute_plan_fingerprint` — the second of the three direct writers named in the plan's problem statement (gap 2). The direct write skips every validation and compare-and-swap guard `synchronize_concepts` runs, silently clobbers a sidecar another process rewrote mid-run, and on a signed tree leaves the plan's `## Deferred` / `## Out of scope` prose stale: the record changes but nothing re-renders the owned sections, which is exactly the record/prose divergence the plan exists to close. Step 1 made routing possible for the common case by teaching the synchronizer to handle unsigned trees without erasing scope prose; this step deletes the detail-side duplicate so that after step 3 (create) and before step 5 (scope-out plus the guard test), detail no longer writes `concepts.json` outside `concept_sync`.

## Input

- **Step 1's unsigned arm** (`plan_tool/concept_sync.py:synchronize_concepts`): a reviewed tree with no `review_state == "approved"` node publishes only the sidecar, leaves the plan file untouched, skips `refresh_plan_provenance`, and stores a fingerprint equal to `compute_plan_fingerprint(plan_path)`. The signature and `ConceptSyncResult` field set are frozen by step 1's acceptance criteria; mode detection is a predicate over the tree, never a caller flag.
- **`ConceptSyncResult` / `SyncStatus`** (`plan_tool/concept_sync.py`): `status`, `message`, `plan_fingerprint`, `rollback_error`, plus the `succeeded` property. On any failure the sync has already rolled back its own publication, so the on-disk sidecar (and its old deferral links) survive — the property detail's recovery messaging relies on.
- **Sidecar round-trip equality**: `plan_tool/concept_tree.py:save_concepts` writes `json.dumps(asdict(tree), indent=2, allow_nan=False) + "\n"`, and `synchronize_concepts` builds its `expected_sidecar` compare-and-swap value the same way. A tree loaded by `load_concepts` therefore serializes back to the exact bytes on disk — this is what lets the tree `generate_detail` loaded at the top of the run serve as `original_tree` at the tail.
- **Caller state at the tail**: `generate_detail` loads the tree once near its top (`load_concepts(plan_path, compute_plan_fingerprint(plan_path))`, raising `DetailError` on a stale record) and never mutates it — `_replace_detail_deferrals` deep-copies. Each successful step's `update_step_detail_field` has already round-tripped the plan through `parse_plan`/`write_plan`, so the on-disk plan at the tail carries the new `detail:` pointers. `DetailResult.deferrals` carries the parsed `DetailDeferral` tuples (each with a `concept_id`) for written steps.
- **Deferral-link contract** (persisted in `plan_tool/concept_tree.py:ConceptNode.source_metadata` under `detail_deferral_step_ids`): a compact JSON list of positive step ids; `plan_tool/review.py:_structured_concept_deferral_is_valid` and the completeness checks consume it, so the on-disk shape must not change.

## Files (creates vs edits)

- **New files:** none.
- **Existing files (edits only):**
  - `plan_tool/concept_sync.py` — receive the moved preparation helpers as public symbols: the `detail_deferral_step_ids` metadata key constant, the tolerant per-node step-id reader, and the ordered whole-step replacement function (today's `plan_tool/detail.py:_replace_detail_deferrals`).
  - `plan_tool/detail.py` — delete `_replace_detail_deferrals`, `_concept_deferral_step_ids`, and `_DETAIL_DEFERRAL_STEPS_KEY`; import the moved symbols from `plan_tool.concept_sync`; rewrite the tail block in `generate_detail` to prepare the reviewed tree and call `synchronize_concepts`; drop the `save_concepts` import and the tail's `compute_plan_fingerprint` computation.
  - `tests/test_detail.py` — add the pre-refactor characterization tests; re-target the one seam-coupled spy test; add the signed-tree divergence regression and the mid-run sidecar-rewrite refusal test.
  - `tests/test_concept_sync.py` — unit tests for the moved replacement helper and the load/serialize round-trip equality the compare-and-swap rests on.

## Implementation

**Move the preparation, keep the publication.** Move `_replace_detail_deferrals` intact into `plan_tool/concept_sync.py` (a public name like `replace_detail_deferrals`), together with `_concept_deferral_step_ids` and the key constant as public siblings. Its ordered whole-step semantics must not vary (the captured lesson pins them): include only successfully written steps, remove every affected step's old links before adding replacements, preserve unrelated `source_metadata` keys, encode retained ids as a compact JSON list (`separators=(",", ":")`), delete the key when empty, and process one prepared candidate in deterministic step order. One adjustment is required by the module boundary: the helper cannot keep its `DetailDeferral` parameter type — `concept_sync` importing `detail` would create a cycle (detail imports concept_sync after this step). Retype the replacements to plain concept-id sequences (e.g. `Sequence[tuple[int, Sequence[str]]]`) and have the caller map `result.deferrals` to ids; the helper only ever read `deferral.concept_id`. The rejected alternative — teaching `synchronize_concepts` itself to take replacements — would break the frozen signature step 1 pins and that step 3 already consumes.

**Route the tail.** In `generate_detail`'s tail block, keep the existing gates unchanged (`concept_tree is not None and not dry_run`, then `if replacements:`), and replace the body with roughly: prepare `reviewed_tree` via the moved helper; re-parse the plan fresh from disk; call `synchronize_concepts(plan_path, fresh_plan, concept_tree, reviewed_tree)`; on `not result.succeeded`, apply the same whole-batch flip the code does today (each written result becomes `written=False` with a reason built from `result.message`, noting the detail file is on disk and prior deferral links are retained). Constraints that are not free to vary:

- **`plan_snapshot` must be parsed fresh at the tail.** The `plan` parsed at the top of `generate_detail` predates every `update_step_detail_field` write; on a signed tree the sync re-renders frontmatter from the snapshot via `parser.py:render_plan_text`, so passing the stale snapshot would silently drop the just-written `detail:` pointers. (The auto-split arm already re-parses as `final_plan`; parsing once right before the sync call covers every arm.)
- **Remap concept owner step_ids when this run performed an auto-split (the part that is not free to vary — mirrors step 5).** Routing the signed path through `synchronize_concepts` newly makes the sync's `_mapped_scopes` guard consume each approved node's `source_metadata["step_id"]` owner mapping. Today's direct `save_concepts` write never touched those mappings, so a stale owner id was inert; the routed signed path is not — after `generate_detail`'s auto-split renumbers steps (`escalate_to_split`, the `final_plan` arm), an unremapped owner id either points at a step that no longer exists (`_mapped_scopes` refuses with `MAPPING_CONFLICT`, rolling back the whole persist) or — because renumbering keeps ids contiguous — points at a *different surviving step* and silently rewrites its scope. When the tail runs after an auto-split, remap the **candidate (reviewed) tree only** through the split's old→new id map before the sync consumes it (leave `original_tree` faithful to the on-disk sidecar for the compare-and-swap): a node whose `step_id` is a renumbered old id → rewrite to the new id; any other value → leave as-is. This is the exact owner-mapping remap step 5 applies for scope-out's narrow; the two share the shape, differing only in the id map's source (the split renumber here, `preview.renumber` there). A run with no auto-split leaves every owner mapping untouched. **Distinct from `detail_deferral_step_ids`** (the deferral-link field the moved helper rewrites): those links' renumber-awareness is a separate, pre-existing gap left in Deferred; the owner-mapping remap here is required because the signed sync path this step introduces is what first consumes it.
- **`original_tree` is the tree loaded at the top, unmutated.** Compare current durable state against the original snapshot, never the reviewed candidate — the loaded tree's serialization equals the on-disk sidecar bytes (round-trip equality above), which is the compare-and-swap precondition.
- **Delete only the caller's plan-fingerprint computation.** The line `updated_concepts.plan_fingerprint = compute_plan_fingerprint(plan_path)` goes away — the sync owns the fingerprint and overwrites it from the staged bytes. The nodes' existing concept fingerprints stay untouched; step 3 pinned the same split for create.
- **The sync must run whenever `replacements` is non-empty, even when links come out unchanged.** The fingerprint refresh is what keeps the sidecar loadable: detail files just changed the plan fingerprint, and the next `generate_detail` run's `load_concepts` raises `StaleConceptTreeError` if the stored fingerprint is stale. Both sync arms refresh it (unsigned arm: equal to `compute_plan_fingerprint(plan_path)`; signed arm: over the final staged plan+details), so on-disk freshness is preserved on every path.
- **Import the moved symbols and `synchronize_concepts` at module top in `detail.py`** so tests can monkeypatch `plan_tool.detail.synchronize_concepts` — the same patchability reasoning as the existing module-level `apply_finding` import comment. The edge is cycle-safe: `concept_sync` imports only `concept_tree`, `parser`, and `schema`, none of which import `detail`.
- **Pass `source_plan_text=None`** (default to current on-disk text). Detail authoring legitimately rewrote the plan since the top-of-run parse (detail pointers, possibly a split renumber), so a top-of-run source text would trip the plan-side divergence check on every run; with the default, the plan-side check trivially passes and the sidecar compare-and-swap remains the real guard.

**Inherited guards — enumerate, don't hand-wave.** Routing through the guarded writer gives this call site refusal paths the direct write never had:

- `SOURCE_DIVERGENCE` when the sidecar changed between the top-of-run load and the tail (e.g. a concurrent `scope-review`). Today's `save_concepts` blindly clobbers that concurrent write; the refusal is a deliberate behavior change — pin it with a test. The flip-to-`written=False` recovery messaging already fits (details are on disk; links retained).
- `MAPPING_CONFLICT` / the unknown-decision `INVALID_STATE` can only fire if the loaded record was already conflicted — the replacement helper never touches `decision`, `review_state`, or `step_id` metadata. A refusal there is strictly more correct than today's blind overwrite; no test needed beyond the sync's own.
- `_validate_tree(reviewed_tree)` cannot newly fail: the tree passed `load_concepts` validation and the helper only rewrites `source_metadata` string values.

**Signed-tree behavior change (deliberate, and the point).** When the tree has any approved node, the sync takes the signed path: it re-renders the owned `## Deferred` / `## Out of scope` sections from the record via `render_scope_decisions`, maps approved `step_id` scopes onto the fresh plan snapshot, publishes both artifacts, and calls `refresh_plan_provenance` — so a later `write_plan` in the same process doesn't raise `ConcurrentModificationError`. Frontmatter bytes stay stable because `render_plan_text` and `write_plan` share the same `yaml.safe_dump` serialization of `model_dump(exclude_defaults=True, exclude_none=True)`, and the plan on disk was last written by `write_plan`. This is the plan's divergence-regression requirement: after deferral persistence, prose and record agree.

**Shared-logic note.** The moved reader has two retained read-only consumers in `detail.py` — `_format_concept_scope_block` (prompt rendering) and `_included_deferral_step_ids` (the include-transition regen gate) — which switch to importing the public reader; their behavior is unchanged. `plan_tool/review.py:_structured_concept_deferral_is_valid` independently parses the same raw key with its own validation; consolidating it onto the moved reader touches a file outside this step and is listed in Deferred.

## Tests

### Test-creation order (refactor step)

Write these characterization tests **first**, against the current direct-write implementation, and require them to stay green unmodified after the routing:

- `tests/test_detail.py::TestStructuredDetailDeferrals` — the five existing flow tests are the core of the gate and already pass: `test_empty_envelope_is_not_written_without_concept_record`, `test_valid_deferral_persists_after_detail_write`, `test_unknown_concept_does_not_publish_detail`, `test_include_transition_regenerates_and_clears_link`, `test_failed_regeneration_retains_link_and_old_body`. They must pass byte-unmodified after the change.
- `test_unsigned_tree_persistence_leaves_plan_untouched` (new, `tests/test_detail.py`) — with an all-unreviewed tree, a successful run updates the sidecar's deferral links and leaves the plan file's bytes exactly as `update_step_detail_field` left them; passes today via the direct write and after via step 1's unsigned arm. This is the behavior-preservation pin for the unsigned case.
- `test_sidecar_fingerprint_fresh_after_persistence` (new, `tests/test_detail.py`) — after a successful run, `load_concepts(plan_path, compute_plan_fingerprint(plan_path))` returns the tree (no `StaleConceptTreeError`); pins the load-bearing fingerprint refresh both implementations must perform.
- One exception to "unmodified": `test_concurrent_deferrals_save_once_in_step_order` spies on `plan_tool.detail.save_concepts`, a seam this refactor removes. Before refactoring, add a seam-neutral sibling asserting the observable outcome (final sidecar carries both steps' links, deterministic order); after routing, re-target the old spy at the module-level `plan_tool.detail.synchronize_concepts` to keep the publish-exactly-once assertion. This is the only characterization edit, and it swaps the spy target, not the asserted behavior.

New tests landing with the change:

- `tests/test_concept_sync.py`:
  - `test_replace_detail_deferrals_replaces_links_in_step_order` — removal-before-add, compact JSON encoding, deterministic order across multiple steps.
  - `test_replace_detail_deferrals_deletes_empty_key_and_preserves_unrelated_metadata` — emptied link list drops the key; other `source_metadata` keys survive; input tree is not mutated.
  - `test_loaded_tree_serializes_to_exact_sidecar_bytes` — `save_concepts` → `load_concepts` → `json.dumps(asdict(...), indent=2, allow_nan=False) + "\n"` equals the on-disk bytes; pins the compare-and-swap precondition the routed call rests on.
- `tests/test_detail.py`:
  - `test_signed_tree_persistence_rerenders_owned_sections` — with an approved `defer` node, a successful run leaves the plan's `## Deferred` section matching the record's rendered decision and the sidecar fingerprint fresh (the plan-level divergence regression).
  - `test_concurrent_sidecar_rewrite_refuses_and_retains_links` — an invoker side-effect rewrites `concepts.json` mid-run; the tail sync refuses, every written result flips to `written=False` with a reason naming the retained links and on-disk detail files, and the concurrent sidecar bytes are not clobbered.
  - `test_stale_top_snapshot_not_used_for_signed_republish` — after a signed-tree run, the republished plan still carries every step's `detail:` pointer (guards the fresh-parse constraint).
- `test_signed_persist_after_autosplit_remaps_owner_step_ids` — a signed-tree run that performs an auto-split renumber persists without a `MAPPING_CONFLICT` refusal, and each approved node's `source_metadata["step_id"]` in the persisted sidecar is the renumbered new id (never a stale pre-split id, never silently mapped onto the wrong surviving step). Pairs a carved/renumbered owner against a surviving-unchanged owner so both remap arms are exercised.

## Acceptance criteria

- `grep -n "save_concepts" plan_tool/detail.py` returns nothing — the import and the call site are both gone.
- `grep -n "_replace_detail_deferrals\|_DETAIL_DEFERRAL_STEPS_KEY" plan_tool/detail.py` returns nothing; the replacement helper, reader, and key constant are public symbols in `plan_tool/concept_sync.py`, imported by `plan_tool/detail.py` at module top alongside `synchronize_concepts`.
- The tail of `generate_detail` no longer computes `compute_plan_fingerprint` — the sync owns the stored fingerprint; the top-of-run load-time use remains.
- The five unmodified `TestStructuredDetailDeferrals` characterization tests pass after the change; `test_concurrent_deferrals_save_once_in_step_order` passes with only its spy target changed.
- An all-unreviewed tree's deferral persistence leaves the plan file's bytes unchanged and stores a fingerprint equal to `compute_plan_fingerprint(plan_path)`.
- A signed tree's deferral persistence re-renders the owned sections from the record, retains all `detail:` pointers, and leaves `load_concepts(plan_path, compute_plan_fingerprint(plan_path))` succeeding.
- A sidecar rewritten between load and tail is not overwritten: the run reports the affected steps `written=False` with the retained-links recovery reason.
- A signed-tree persist that follows an auto-split renumber succeeds (no `MAPPING_CONFLICT`) and the persisted owner `source_metadata["step_id"]` values are the renumbered ids, never stale pre-split ids or ids mapped onto the wrong surviving step.
- `uv run pytest tests/test_detail.py tests/test_concept_sync.py -q` is green.
