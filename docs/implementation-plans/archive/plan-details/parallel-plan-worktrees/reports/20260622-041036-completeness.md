The default-off configuration (the project default) has no specified behavior for the bare command.
  - Address: `plan-tool completeness-apply parallel-plan-worktrees --anchor branch-awareness-off-default`
- MEDIUM `[prune-dirty-tree]`: step 4 (`prune`) "drops worktrees whose plan is archived/deregistered/whose path is gone; confirm, honor `-y`," but an archived/deregistered plan's worktree can still hold uncommitted work, and the dirty-tree data-loss gate is specified only for `remove --force` — not for `prune`. A blanket `prune -y` over a dirty dead worktree is the same uncommitted-work data loss the Risks section forbids.
  - Address: `plan-tool completeness-apply parallel-plan-worktrees --anchor prune-dirty-tree`

  - Address: `plan-tool completeness-apply parallel-plan-worktrees --anchor remove-current-worktree`

This bites clones hardest, since git's own worktree registry can't recover them.
  - Address: `plan-tool completeness-apply parallel-plan-worktrees --anchor derived-path-no-state`

### Correctness (run these first)

_Verified: file paths resolve, dependencies are coherent, and the plan's stated concepts are internally sound._

- HIGH `[branch-awareness-off-default]`: Architecture states "When branch-awareness is off (or for an explicit branch), accept a `--branch` argument," but acceptance criterion #1 and step 3 (`worktree add`) derive the branch "via branch-awareness, created from default when absent." Branch-awareness resolves to `false` by default in `project_config`, so the most common invocation — `plan-tool worktree add <plan>` with the default config and no `--branch` — has no defined branch concept to check out, leaving the default path undefined.
- MEDIUM `[stale-target-reuse]`: step 3's idempotent reuse ("reuse existing rather than failing") and step 2's "existing non-empty target dir → validate and fail clearly" overlap without a tiebreak: a derived path holding a stale/broken worktree (admin files pruned), or a foreign non-empty dir, satisfies both rules and which wins is unspecified, so re-running `worktree add` over a damaged path has undefined behavior.
- HIGH `[branch-checkout-in-worktree]`: Architecture says provisioning "creates/uses P's branch via `derive_branch`, `default_branch`, `create_and_checkout_branch` and checks it out in the new worktree," but `create_and_checkout_branch(repo_root, name)` at HEAD (`cli/gitcommit.py`) runs `git switch -c` against the **main** working tree — it checks the branch out in the main repo, not the worktree. Doing that then `git worktree add <path> <branch>` makes git refuse (a branch checked out in the main tree cannot also be checked out in a worktree), so the stated composition cannot provision the worktree on its branch. Branch creation+checkout must happen *inside* the worktree-add (`git worktree add -b <branch> <path> <start>`), which is step 1's `worktree_add` concern, not the main-tree helper.
