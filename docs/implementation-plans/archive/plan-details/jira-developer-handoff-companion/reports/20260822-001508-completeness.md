A key or mapping changed after capture can affect the story without appearing in the shared fingerprint, breaking the one-snapshot provenance promised by Architecture and Acceptance criteria.
  - Fix: Capture and fingerprint the existing story mapping or its absence before both renderers, and test that mapping changes regenerate matching outputs.
- HIGH `[binding-spirit-outcome]`: Steps 1 (`Capture companion-mode Jira inputs once without changing story-only detail tolerance`) and 3 (`Define the generated Jira developer-handoff format and lifecycle`) promise that every Plan path explains a step’s binding spirit and outcome, while `plan_tool.schema:Step.intent` is optional and Architecture permits selected detail only to enrich, not supply, that binding meaning. Architecture’s done fallback allows only the title and “any plan intent that is available,” and Testing plus Acceptance criteria repeat the universal explanation promise, so plans without an intent/outcome source can produce invented or incomplete binding prose.
  - Fix: Define the required binding source and visible refusal or fallback behavior when a step lacks stated spirit or outcome, including done steps, without promoting selected detail into plan authority.
- MEDIUM `[done-detail-validation]`: Steps 1 (`Capture companion-mode Jira inputs once without changing story-only detail tolerance`) and 3 (`Define the generated Jira developer-handoff format and lifecycle`) do not choose what happens when a done step has a selected detail file that is present but structurally invalid. Architecture requires valid selected detail only for non-done steps and defines fallback only for “no selected detail”; Testing and Acceptance criteria cover the missing-detail fallback only, while `plan_tool.jira:_build_jira_grade_detail_map` currently permits a missing done artifact but rejects a present invalid Jira-grade artifact.
  - Fix: State one done-step validation rule—missing detail uses the historical fallback, while malformed present detail either refuses or is explicitly treated as unavailable—and cover it in the companion tests.
- HIGH `[jira-key-identity]`: Architecture’s canonical covered-step-set rule, step 2 (`Prepare a companion-mode story renderer that keeps generated files current`), step 4 (`Publish synchronized story and handoff source files without overwriting human guidance`), Testing, and acceptance criterion 5 promise not to misassign human Jira keys, but covered step ids are local to a plan. At HEAD, `plan_tool.jira:_render_markdown_header` and `_render_json_payload` carry no source-plan identity, while `read_existing_export`, `_read_markdown_tickets`, and `_read_json_tickets` accept duplicate keys; an unrelated parseable export with the same step set, or one key on two different sets, can therefore reattach a key to the wrong regenerated story.
  - Fix: Require verifiable source-plan identity and one-to-one Jira-key ownership before reattachment, with an explicit refusal or migration rule for legacy exports that lack that proof.
- MEDIUM `[story-renderer-purity]`: Step 2 is marked `change_type: refactor` but combines a controlled renderer-boundary extraction with new companion behavior that regenerates current stories and preserves key metadata; Architecture and the per-step Testing strategy also depend on both behaviors. That prevents a behavior-preserving refactor from being independently tested and reviewed before the feature.
  - Fix: Split step 2 into a behavior-preserving renderer extraction and a dependent companion-rendering feature, then update step 4 dependencies and the two test strategies.
- MEDIUM `[handoff-output-mode-gate]`: `--handoff-output` has no defined behavior without `--developer-handoff`: Architecture defines it only inside companion mode, while step 5 (`Add an opt-in Jira companion CLI mode with explicit output behavior`), Testing, and acceptance criterion 6 cover only companion-mode precedence and lint/config rejection. An implementation can reasonably ignore the path and perform a story-only export or reject the command, giving operators materially different results.
  - Fix: Define whether `--handoff-output` without companion mode is rejected or ignored, and lock that choice in CLI tests and documentation.
