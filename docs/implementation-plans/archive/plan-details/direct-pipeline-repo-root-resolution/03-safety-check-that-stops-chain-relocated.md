# Step 3 — Add a safety check that stops the chain if the relocated repo has unrelated uncommitted changes

## Summary

Step 2 threads a post-create `created_repo_root` through `cmd_direct_jira`/`cmd_direct_run` in `plan_tool/cli/direct_cmd.py`, but only threads the value — it never checks whether that relocated root was safe to write into. This step closes that gap: it adds a helper to `plan_tool/cli/gitcommit.py` that reports which dirty paths in a repo fall outside a caller-supplied "expected" set, and wires a guard into both verbs that runs right after `created_repo_root` is derived and before `detail` starts. When `create` relocates to a different (disjoint) root than the one checked at chain start, and that root's dirty state is more than the writes `create` just made there — the plan file, manifest entry, concepts file, grounding-baseline sidecar, and (when a same-slug plan was replaced) the superseded plan's archive / manifest removal / renamed detail directory — the chain aborts with a message naming the offending paths instead of folding a stranger's uncommitted work into the first auto-generated commit. This guard only ever sees a **disjoint** relocated root: step 2's Architecture-decision-7 refuse-guard has already rejected any nested/ancestor relocation before this runs, so there is no embedded-repo `git status` collapse to reason about here. The key design point: the new helper must use `--untracked-files=all` so a brand-new `.plan-tool/` directory doesn't collapse into one porcelain line and hide an unrelated file sitting next to the expected one — a real gotcha already solved once in this codebase by `plan_tool/scenario_capture.py:working_tree_dirty`. On green, a relocated chain with unrelated dirty state in the destination repo aborts before `detail` runs; a relocated chain whose destination repo is dirty only from `create`'s own writes (including a collision-replace) proceeds unchanged; and a non-relocated chain never triggers this guard at all.

## Why

Step 0 of both `cmd_direct_jira` and `cmd_direct_run` checks `working_tree_dirty(repo_root)` before `create` runs — but `repo_root` there is the pre-create, cwd-derived root. When `create` relocates (a `--from-existing` seed whose files resolve under a different `.git` ancestor), the plan, its manifest entry, and possibly a concepts.json all land under a *different* root that step 0 never inspected. Once step 2 lands, every downstream stage — starting with `detail` — resolves and commits against that relocated root (`created_repo_root`) instead. Nothing today asks whether that relocated root was already dirty from something unrelated to this run. If it was, the first post-create `commit_all` call (stage 4, "Commit the authoring artifacts…") runs `git add -A` there and silently folds a stranger's uncommitted work into an auto-generated commit message that only claims to "author plan and detail." The plan's own Risks section names this directly: "today's code only 'works' because it never notices the relocation at all" — step 2 makes the relocation visible, and this step is what keeps that visibility from becoming a new way to commingle changes. This is a new guard, not a relaxation of an existing one: the non-relocated case already has step 0's precondition and needs nothing further.

## Input

This step builds on two things step 2 establishes, plus one existing contract it does not renegotiate:

- **`created_repo_root`** (step 2, `depends_on: 2`): the repo root `create` actually used, derived from `result.plan_path`'s owning `.git`/`.plan-tool` ancestor. Step 2 keeps this in a distinct local from the pre-create `repo_root`, specifically so this step can compare the two — read that comparison, don't re-derive either value. By the point this guard runs, step 2 has already **refused** any nested/ancestor relocation (Architecture decision 7) and committed the original root's dirt, so this guard only ever operates on a **disjoint** relocated root — read those as established preconditions, don't re-check them here.
- **`CreateResult`** (`plan_tool/create.py`): by the point `created_repo_root` exists, the split-proposal / `iteration_stage_failure` / size-gate guards have already run, so `result.plan_path` is guaranteed non-`None`. `result.manifest_path` is always populated. This step also reads the **collision-replace** fields `create` populates when a `--from-existing` seed replaced an existing same-slug plan: `result.replaced_archives` (`list[tuple[Path, Path]]` of `(original, archived)`), `result.replaced_manifest_entries` (`list[str]`), and `result.plan_details_renamed_to` (`Optional[Path]`) — each empty/`None` when no replacement happened. These are read-only inputs; this step does not change their shape.
- **`plan_tool/concept_tree.py:concepts_path(plan_path)`**: a pure function returning `plan-details/<slug>/concepts.json` beside a plan file — the deterministic location `create_plan` writes to when it defers a concept at create time (`_persist_or_clear_concepts`, `plan_tool/create.py`, which calls `plan_tool/concept_tree.py:save_concepts` on its non-empty branch). The file may or may not exist on disk; that's fine, since a nonexistent expected path simply never shows up in `git status` output.
- **`plan_tool/grounding.py:grounding_path(plan_path)`**: a pure function returning the grounding-baseline sidecar path beside a plan file. `cmd_create` (`plan_tool/cli/authoring.py`) unconditionally writes this file via `_stamp_grounding` right after every successful create — it is not conditional on a deferred concept the way `concepts_path`'s file is, so it is *always* present after a relocated create, not merely possible. It is git-tracked, not gitignored (confirmed by `git ls-files` on this very plan's own `plan-details/direct-pipeline-repo-root-resolution/grounding.json`), so it always shows up in `git status --untracked-files=all` on the relocated root and must be in the expected set alongside `concepts_path(plan_path)` — omitting it would make this step's guard misclassify a routine, always-present write as a stranger's dirt on every relocated create.
- **The existing `working_tree_dirty`/`commit_all` contracts** (`plan_tool/cli/gitcommit.py`): both already used by `plan_tool/cli/direct_cmd.py` and unchanged by this step. This step adds a new function alongside them, not a replacement.

## Implementation

**This guard is deliberately best-effort, with a safe failure mode — read this framing first.** `cmd_create` makes an *open-ended* set of writes under the root(s) it touches (plan file, manifest, concepts, grounding sidecar, seed archives, distilled artifact, collision replaced-archives, renamed detail directory, and the *deletion* of the pre-rename detail source), and `CreateResult` does **not** comprehensively enumerate them. So this guard's expected-path set — assembled below from the `CreateResult` fields that *are* exposed — cannot be proven exhaustive, and it isn't the design's goal that it be. The design contract is: **the failure mode of a missed `create` write is a *spurious abort* (the operator sees "unexpected dirt: `<path>`", inspects, commits or re-runs), never a corrupted commit or data loss.** That asymmetry is what makes best-effort acceptable — over-aborting is safe; the guard exists to stop a *stranger's* pre-existing dirt from being folded into `create`'s commit, and a false positive on one of `create`'s own writes only costs a re-run, not correctness. **Best-effort applies only to genuinely rare gaps, not the common path** — the writes create makes on *essentially every* create (the always-set above, including the whole `.plan-tool/` tool-state directory) and the ordinary collision-replace writes (both ends of `replaced_archives`, the renamed detail dir) are enumerated exactly, so the *supported* disjoint path never false-aborts. The residual best-effort gaps are stacked rarities: a seed physically under the relocated root (its archives land there), and a collision-replace that also `rmtree`s a *pre-rename* detail-dir source `CreateResult` doesn't expose. Those are documented in [Deferred](#deferred); the durable fix — having `create` report its complete touched-path set on `CreateResult` so this set can be exact — is **BACKLOG #150**. Do **not** keep growing this allowlist reactively past what `CreateResult` cleanly exposes; if a real workflow keeps tripping a spurious abort, that's the signal to land #150, not to enumerate one more path. (Two common-case omissions — the `.plan-tool/` directory and the deleted-original side of a collision-replace — were caught in code review *after* first authoring and folded into the always/collision sets above; they were bugs in the supported path, not acceptable best-effort gaps.)

**Add one function to `plan_tool/cli/gitcommit.py`** that answers "what's dirty in this repo that isn't accounted for by these expected paths?" A concrete shape: `unexpected_dirty_paths(repo_root: Path, expected: Sequence[Path]) -> list[str] | None` — matching the file's existing `str | None` return-type style (`current_branch`, `default_branch`) rather than `Optional[...]`.

- **Run `git status --porcelain --untracked-files=all`, not the bare `--porcelain` that `working_tree_dirty` uses.** This is the one constraint that isn't free to vary. Without `--untracked-files=all`, git collapses a wholly-new untracked directory into a single line (`?? .plan-tool/`) instead of listing its contents. On a relocated root where `create` is materializing `.plan-tool/plans.json` for the first time, that collapse means the reported path is `.plan-tool/` — not `.plan-tool/plans.json` — and a naive exact-match exclusion against the expected manifest path would wrongly flag the whole directory as unexpected. Worse, if an unrelated file also happened to sit inside that same brand-new directory, the collapsed line would hide it entirely, defeating the check in the other direction. `plan_tool/scenario_capture.py:working_tree_dirty` already solved this exact problem for a different reason (excluding its own scenario-corpus subpath) and its comment spells out why `-uall`/`--untracked-files=all` is required — treat that function as the template to generalize (a single hardcoded excluded prefix there; a caller-supplied list of expected paths here), not a novel design.
- **Fail closed on an unreadable repo.** When `git status` exits non-zero (not a work tree) **or the `subprocess.run` call itself raises `OSError`** (git binary absent from `PATH`, `repo_root` unreadable), return `None` rather than `[]` — mirrors `plan_tool/launcher.py:_git_changed_paths_or_none`'s documented `None`-means-"couldn't tell" contract. Wrap the `subprocess.run` in `try/except OSError` (as `scenario_capture.working_tree_dirty` does) so a missing git crashes nothing; without the guard a `FileNotFoundError` escapes and kills the chain instead of the documented graceful fail-closed abort. The caller in `direct_cmd.py` must treat `None` the same as a non-empty list (abort) — never let "couldn't determine" silently mean "proceed."
- **Parse each porcelain line the same way `plan_tool/scenario_capture.py:working_tree_dirty` does** — two status characters, a space, then the path (`line[3:]`). A stricter alternative exists if renamed/special-character paths matter here: `plan_tool/launcher.py:_git_changed_paths_or_none` uses `-z` NUL-delimited output and explicitly skips the origin-path field on `R`/`C` records. Either is defensible; pick based on how much the relocated-root scenario plausibly involves renames (likely rare, since the dirt being detected is pre-existing, not caused by this run).
- **Build the expected set by resolving and relativizing each caller-supplied path against `repo_root`.** For each path in `expected`, compute `path.resolve().relative_to(repo_root.resolve())` and compare `.as_posix()` against the reported paths; skip (don't raise) any expected path that isn't actually under `repo_root` — an explicit `--manifest` override pointing outside the repo is a real, if unusual, case (see `plan_tool/create.py`'s own note that `default_manifest_path` short-circuits on an explicit manifest path). A path that can't be under `repo_root` can't appear in that repo's `git status` output either, so skipping it is safe, not a gap.
- **Return the sorted list of reported paths not in that expected set.** Empty list means everything dirty is accounted for.

**Wire the guard into `plan_tool/cli/direct_cmd.py`, once per verb, sharing the actual check logic** (don't duplicate the expected-paths list and message-building between `cmd_direct_jira` and `cmd_direct_run` — mirror how `gate_create_result_size` and `_stage_namespace` are already shared rather than copy-pasted). A concrete shape:

- A small private helper — e.g. `_relocated_root_unexpected_dirt(created_repo_root, result) -> list[str] | None` — that builds the expected set from every write `cmd_create` is known to make under the relocated root and calls `unexpected_dirty_paths(created_repo_root, expected)`. The set is:
  - **Always:** `result.plan_path`, `result.manifest_path`, `concepts_path(result.plan_path)`, `grounding_path(result.plan_path)`, **and the whole `created_repo_root / ".plan-tool"` directory**. `grounding_path` (`plan_tool/grounding.py`) is unconditional — `cmd_create` writes it via `_stamp_grounding` after every successful create. The `.plan-tool/` directory is the crucial one: `create` writes tool-state scratch there on essentially *every* create — telemetry (`.plan-tool/telemetry/decisions.jsonl`), the initial-steps checkpoint (`.plan-tool/checkpoints/<slug>/…`), run logs (`.plan-tool/runs/…`) — and the relocated root, never subject to step 0's clean-tree check, **may not gitignore `.plan-tool/`**. Enumerating each file there is hopeless; instead pass the *directory* `created_repo_root / ".plan-tool"` as one expected entry (`unexpected_dirty_paths` treats a reported path as expected when it equals or is nested under any expected entry, so a directory covers everything beneath it). It is create's own tool state, never a stranger's source work. **Omitting `.plan-tool/` false-aborts the *common* supported disjoint path, not a rare edge** — this was a real bug caught in code review, distinct from the genuinely-rare best-effort gaps below.
  - **When `create` replaced a colliding same-slug plan** (the `should_replace` branch, `plan_tool/create.py` ~line 6218): the superseded plan's archived copies **and its deleted originals** — `result.replaced_archives` is a list of `(original, archived)` pairs, and `archive_existing_source` *unlinks* the original after copying it, so `git status` reports a ` D <original>` line the archived copy alone doesn't cover; include **both** ends of each pair. Also `result.replaced_manifest_entries` (the manifest is `result.manifest_path`, already in the always-set, but the removal is a real edit to it), and — when the collision carried provenance — `result.plan_details_renamed_to` (the renamed detail directory; a directory entry covers its contents). These are `create`'s own legitimate writes under the relocated root; omitting them would abort a `direct-*` run that both relocates *and* replaces a prior same-slug plan even though nothing is wrong. Read them off the `CreateResult` (per [Input](#input)) — do not re-derive them.
- In both `cmd_direct_jira` and `cmd_direct_run`, call it **only when `created_repo_root.resolve() != repo_root.resolve()`** — right after `created_repo_root` is computed and step 2's refuse-guard + original-root commit have run (so this guard only ever sees a **disjoint** relocated root; the nested/ancestor case was already refused in step 2 per the plan's Architecture decision 7), and **before** the "3. Detail" stage's `cmd_detail(detail_args)` call. **Ordering (load-bearing):** this relocated-root guard must run *after* step 2's original-root commit — if it aborted first, the original root's archived-seed dirt would never be committed, reintroducing the exact regression step 2's commit exists to prevent (the plan's Architecture decision 3 fixes this ordering explicitly). Firing before `detail` (not merely before the stage-4 commit) matters: it fails fast, before the chain spends a `detail` invocation — potentially a Claude round-trip — on a run that's going to abort anyway.
- When the result is `None` or non-empty, call `error(...)` (already imported from `plan_tool.style`) naming the verb and the offending paths, and `return 2` — matching the step-0 precondition's existing error shape and return code (`error(f"{verb} requires a clean working tree ...")`, `return 2`) so an operator sees a consistent failure mode whether the dirt was in the original repo or the relocated one.
- **Do not touch step 0's precondition or anything for the non-relocated case.** When `created_repo_root == repo_root`, skip the new helper call entirely — no new subprocess call, no new message, byte-for-byte the same behavior as before this step. This is what keeps the plan's "no-relocation case is behaviorally unchanged" acceptance criterion true.

**Constraints to respect:**

- The guard reads `created_repo_root` and `repo_root` — it does not compute either from scratch. Re-deriving `repo_root` a second time here (e.g. via another `_resolve_cmd_repo_root(args)` call) would be redundant per step 2's own Deferred note and risks drifting from the value step 0 actually checked.
- `concepts_path(result.plan_path)` may point to a file that doesn't exist; don't guard the call on existence — a nonexistent expected path is harmless to include. `grounding_path(result.plan_path)` does exist on every successful create, unconditionally — include it unconditionally too, not behind the same "may not exist" caveat.
- This step does not change `working_tree_dirty` or `commit_all`. It adds one new function to the same module.

## Acceptance criteria

- `plan_tool/cli/gitcommit.py` has a function that returns the dirty paths in a repo not covered by a caller-supplied expected-paths list, using `--untracked-files=all` so a brand-new directory doesn't hide an unrelated file inside it.
- That function returns `None` (not `[]`) when `git status` can't be read.
- In both `cmd_direct_jira` and `cmd_direct_run`, when `created_repo_root` differs from the pre-create `repo_root` and the (disjoint) relocated root has dirty content beyond the plan file, manifest entry, concepts file, grounding-baseline sidecar, and — when a same-slug plan was replaced — the collision-replace writes (`replaced_archives` / `replaced_manifest_entries` / `plan_details_renamed_to`) `create` is known to have written, the chain aborts with a non-zero exit and a message naming the offending path(s), before `cmd_detail` runs.
- When `created_repo_root` differs from `repo_root` but the relocated root's only dirty content is `create`'s own known writes — including a collision-replace's archives / manifest removal / renamed detail directory — the chain proceeds exactly as it would without this step.
- This guard runs only on a disjoint relocated root (step 2 already refused the nested/ancestor case) and only after step 2's original-root commit (so an abort here never orphans that commit).
- When `created_repo_root` equals `repo_root` (no relocation), this step's guard never fires — no new subprocess call, no new message.
- All new and existing tests in `tests/cli/test_gitcommit.py` and `tests/cli/test_direct_cmd.py` pass.

## Deferred

- End-to-end coverage driving a real narrower/broader seed-derived relocation through the full chain against a genuinely dirty destination repo — step 4's job; this step's tests stub the stage handlers and exercise the guard at the unit level, matching step 2's own scope.
- Fixing the same stale-manifest-path pattern in `plan_tool/cli/manifest.py`/`plan_tool/cli/inspect.py` — step 6's job, unrelated files and call sites.
- Any cleanliness check for standalone (non-`direct-*`) `detail`/`run` invocations — out of scope per the plan's Architecture decision 5; those resolve their own root fresh from cwd/`--repo-root` each time and have no stale in-process hand-off to guard against.
- **Known best-effort gap — seed physically under the relocated root.** When the `--from-existing` seed file lives under the relocated (disjoint sibling) root rather than the original, `cmd_create`'s seed-adjacent archives (source/provenance/distilled — see step 2's Input) land under `created_repo_root`, not `repo_root`. Step 2's original-root commit then no-ops (the original root is clean) and this guard's expected set doesn't include those archive paths (`CreateResult` doesn't expose them), so it would *spuriously abort* a valid relocated chain. Failure mode is a safe abort, not corruption; the exact fix (create reports its seed-archive paths) is **BACKLOG #150**. Callers hitting it can commit the archive in the relocated root and re-run.
- **Known best-effort gap — collision-replace deletes a rename-source detail dir.** On a same-slug collision-replace that reuses the prior detail bundle, `rename_plan_details_to_slug` (`plan_tool/create.py`) *deletes* the old-slug `plan-details/` at the rename **source** while `CreateResult.plan_details_renamed_to` exposes only the **destination**. When the source is under the relocated root, `git status --untracked-files=all` reports ` D plan-details/<old-slug>/…` lines the expected set can't cover (the source path isn't on `CreateResult`), so this guard would spuriously abort. Same safe failure mode; same durable fix (**BACKLOG #150** — expose the pre-rename source too). (Note: the *deleted plan file* of a collision-replace — distinct from this deleted detail *dir* — **is** now covered: both ends of `replaced_archives` are in the expected set.)
