- HIGH `[run-dirty-before-warning]` [confidence: limited]: Step 5 (`run --commit` footprint) promises a warning for a path that was already dirty before the step and then edited by it, but the only record it names cannot detect that case. From step 5 and the acceptance criteria:

  ```
  A path dirty before a `run` step and edited by it is left uncommitted and named in a warning.
  ```

  `git_state.changed_paths_or_none` returns only a `set[str]` of paths from `git status --porcelain -z`. A path that is dirty at the baseline and still dirty after the step appears in both sets, whether or not the step touched it. Set subtraction therefore cannot say "edited by the step". Two things go wrong:
  - The warning either fires for every path that was dirty before the step, or never fires.
  - If the footprint is baseline-delta by path name, the step's own edits to such a file are dropped without any signal.

  Step 5 also never says what happens when `changed_paths_or_none` returns `None` (git unreadable) at the baseline or after the step. Step 5 and the Architecture section ("A verb whose footprint cannot be enumerated without new bookkeeping is not converted") leave unchosen whether the commit is refused, falls back to the plan file only, or falls back to the whole tree. A whole-tree fallback would silently bring back the bug this plan fixes.
  - Plan-altitude restatement (delivered evidence, not a verdict on this finding): The plan promises that a file edited by a step but already dirty beforehand is reported rather than silently dropped, yet names no record that can tell "edited by the step" from "merely dirty before it". It also does not say what `run --commit` does when the git state cannot be read.
  - Fix: State how step 5 tells a pre-dirty path the step edited from one it did not touch, and keep that inside the "no new bookkeeping" fence. Either narrow the acceptance criterion and warning to "was dirty at the baseline and is dirty after", or add a one-time content check taken at the baseline. Then state the fail-closed behavior for an unreadable git state at either snapshot.
- MEDIUM `[footprint-rename-origin]` [confidence: limited]: Step 5 builds its footprint from `changed_paths_or_none`, which skips the origin field of a staged rename. A backend step that runs `git mv a b` puts only `b` in the delta, so `a`'s staged deletion is not in the footprint. The acceptance criterion reads:

  ```
  Deletes and renames inside the footprint stage.
  ```

  With `git commit -- <paths>`, the deletion of `a` stays staged but uncommitted. The post-commit clean check misses it because `a` is not a footprint entry. The commit then contains `b` as a new file and the tree is left half-staged. Step 1's tests cover renames only for caller-supplied paths, not for a footprint taken from the delta.
  - Fix: Require step 5's footprint to include both sides of a rename it takes from the baseline delta. Add a test where the step does a staged rename and both paths end up committed and clean.
