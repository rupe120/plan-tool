# Step 9 — Stop stage 4 from generating any seed body inline

## Summary

Retires the multi-fence bundle contract that lets stage 4's own backend call emit draft-seed bodies alongside `04-roadmap.md`: `RoadmapStage.side_output_seed_paths`, `ArtifactEnvelope.draft_seed_bundle`, `_StageOutcome.draft_seed_bundle`, `_plans_side_output_seed_paths`, `_lift_multi_fence_reply`, and `_write_stage_outputs`'s staged-seed-tree/atomic-swap branch all disappear from `plan_tool/roadmap.py`, so `04-roadmap.md` publishes on its own gates with no seed side output at all — every draft now materializes only through step 2's `materialize_plan_seed`. `plan_tool/roadmap_gates.py`'s `PLANS_GATES` drops `check_draft_seed_provenance` outright and keeps only the bundle-free basename-collision half of `check_draft_seed_bundle_alignment` (step 1's generalized gate). A new trigger replaces today's feedback-only invalidation: any stage-4 write that *replaces* an existing `04-roadmap.md` invalidates every tracked draft, with or without open feedback, and `_invalidate_roadmap_seeds` stops recomputing a draft's recorded digest when it fires — a hand-edited draft keeps the digest mismatch that marks it `digest-mismatched` rather than being laundered into plain `stale`. `plan_tool/prompts/roadmap-plans.md` stops asking the model for seed-fence output entirely, `plan_tool/cli/roadmap_cmd.py`'s `_create_handoff_lines` routes through step 3's `classify_draft_seeds` so it only hands out a `create --from-existing` line for a plan whose draft is actually `current`, and the copy-aside/invalidation/confirm wording across the CLI and `ROADMAP_FORMAT.md`/`CAPABILITIES.md`/`DATA_CONTRACT.md` sweeps the now-false "stage 4 emits seeds" and "invalidation means feedback" claims. On green, no code path writes a seed body except `materialize_plan_seed`, and `--from-stage 4` can never again silently wipe an independently materialized draft tree.

## Why

Every step from 1 through 8 in this plan builds a per-plan draft-seed lifecycle — one generation call (step 2), one classifier (step 3), one failure-isolated refresh (step 4), a targeted `--materialize` (step 5), a stricter promotion refusal (step 6), and two read-only views (steps 7–8) — but none of it is the *only* way a draft gets written until stage 4 stops writing one itself. Today `run_roadmap`'s stage-4 attempt asks the model, in the same call that authors `04-roadmap.md`, to also emit one fenced seed block per plan row (`plan_tool/prompts/roadmap-plans.md`'s "Output format (strict)" section), lifts that bundle in `_lift_multi_fence_reply`, gates it in-memory via `ArtifactEnvelope.draft_seed_bundle`, and writes it atomically alongside the primary artifact in `_write_stage_outputs`. As long as that path exists, an ordinary `--from-stage 4` re-entry with no open feedback still asks the model for a *fresh* seed bundle; step 2 already widens `preserve_existing_seeds` with a third condition (any plan already classifying `current`) so this window doesn't stay open for the whole stretch between step 2 landing and this step landing — this step's own job is removing the mechanism entirely, guard included, not closing the window for the first time. This step is what finally makes stage 4 a plans-only writer, so the rest of the plan's materialization surfaces are the *only* place a seed body is ever generated.

The `_confirm_invalidated_roadmap_seed` and `--materialize`/`digest-mismatched`-accept surfaces steps 3/5/6/10 build depend on invalidation firing whenever the ground truth (`04-roadmap.md`) changes underneath a draft — not only when a reviewer answered feedback. An ordinary revision with no feedback is common (a `--from-stage 4` re-entry to fix a typo, or upstream stages 1–3 changing and stage 4 re-deriving its plan list) and today leaves every stale draft's sidecar entry reading `"current"`, which is exactly the mistracked-drift case step 3's classifier exists to catch. Closing that gap without breaking the existing feedback-triggered path or the digest fidelity `digest-mismatched` depends on is this step's other half.

### 2. The new stage-4-replace invalidation trigger

`run_roadmap`'s stage loop today has two seed-lifecycle branches after a write: `if feedback_applied:` (invalidate — keep, unmodified) and `elif stage.side_output_seed_paths is not None:` (either invalidate, if seeds were already stale, or call the now-deleted `_mark_roadmap_seeds_current`). Replace the `elif` arm with the new trigger: **any stage-4 write that replaces an existing `04-roadmap.md`** — regardless of `feedback_applied` — invalidates every tracked draft. A fresh (non-replacing) stage-4 write invalidates nothing, because there is nothing tracked yet for a row step 2 hasn't materialized.

- `test_loop_never_branches_on_stage_identity` forbids `stage.number ==` / `stage.name ==` anywhere in this file. The loop already has a data-driven idiom for "this is the plans artifact" — `isinstance(reloaded.artifact, PlansArtifact)`, used a few lines above in the `feedback_applied` branch. Reuse it (paired with `replaced`) rather than reintroducing a stage-number check; that keeps the new branch honest with the same test the old one already had to satisfy.
- `_mark_roadmap_seeds_current` has exactly one definition and one caller (this branch) at HEAD — delete it outright per the plan's Step intent; nothing else calls it.
- `_invalidate_roadmap_seeds` currently recomputes each entry's `digest` from the live file (`if source.is_file(): digest = digest_text(source.read_text(...))`) before flipping `status` to `"invalidated"`. Drop that recompute — leave `digest = old.get("digest")` as the final value, unconditionally. This applies to *both* callers of `_invalidate_roadmap_seeds` (the existing feedback-triggered one and this new one): a hand-edited draft's digest mismatch is what step 6's promotion refusal and step 10's accept action key on to distinguish `digest-mismatched` from plain `stale`, and recomputing here would silently launder that signal away the moment any stage 1–4 write invalidates the tracked set.

## Applicable guardrails

- **The plan's "Out of scope" list** binds this step's CLI/docs sweep: nothing here may auto-promote a draft, auto-accept feedback, add a correctness gate on seed style/length/model agreement, or regenerate every seed on an ordinary revision. The new invalidation trigger marks drafts stale; it never writes a replacement — that stays step 2/5's job on explicit request.
- **The Step intent's digest-preservation rule** is a hard constraint on `_invalidate_roadmap_seeds`, not a recommendation: both its existing feedback-triggered caller and this step's new replace-triggered caller must leave a pre-existing `digest` untouched. Recomputing it from the live file — even "just for the new caller" — silently converts a `digest-mismatched` draft into a `stale` one and costs it step 10's accept eligibility.
- **The Step intent's additive-trigger rule**: the new any-stage-4-replace invalidation is additive to, not a replacement for, the existing per-stage (1–4) feedback-triggered invalidation that already fires the moment a stage writes with open feedback in its predecessor. Do not remove or merge that branch — an interrupted run that answered feedback at an earlier stage but never reached stage 4 still needs it.
- **The Architecture doctrine "a stage is a row in a table, not a branch in the loop"** (module docstring; enforced by `test_loop_never_branches_on_stage_identity`) binds the new invalidation trigger's implementation: key it off the parsed artifact's type (the existing `isinstance(reloaded.artifact, PlansArtifact)` idiom) or another data-carried field, never a hardcoded stage number or name.
