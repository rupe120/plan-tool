- HIGH `[legacy-migration-approval]`: Step 3 (`Migrate valid legacy deferrals into non-delivery records`) says to “Preserve the signed legacy meaning by setting the migrated record’s review state to `approved`,” but step 5 (`Review and approve non-delivery records explicitly`) says “only a TTY-confirmed review can approve a new or changed non-delivery record” and classifies synthesized `origin_ref` as approval-sensitive. Legacy concept sign-off never reviewed that newly created origin or full record, so migration fabricates record approval through an unattended publication flow.
- HIGH `[pending-include-intent]`: Step 6 (`Persist pending include regeneration requests`) displays and reviews an exact destination and artifact, yet states that the request “has no independent `review_state`, rationale, or sign-off marker.” An approved node decision proves only `include` intent; it cannot prove which request mapping the operator approved, so a changed but semantically valid destination can be resumed by step 7 as reviewed authority.
- MEDIUM `[legacy-committed-owner-migration]`: Step 3 (`Migrate valid legacy deferrals into non-delivery records`) permits migration when “the linked step [is] one of those owners” without restricting its scope and sets the resulting record to `approved`, but step 4 (`Reject invalid accounting before concept publication`) says “An approved non-delivery record cannot coexist with an owner for the same concept on a committed step.” A legacy link to a committed exact owner is therefore accepted as migratable by step 3 and rejected as contradictory by step 4; step 3 also lacks authority to park that owner atomically.
- HIGH `[legacy-detail-publication-transaction]`: Step 3 (`Migrate valid legacy deferrals into non-delivery records`) directs `generate_detail()` to “call `save_concepts()` once” after processing `DetailResult` objects whose `written` value is already true, while the plan’s Architecture requires every durable multi-file update to use the prerequisite transaction API. A sidecar failure can therefore leave newly written detail paired with the old legacy accounting—the mixed generation the prerequisite explicitly eliminates.
- HIGH `[pending-destination-scope]`: Step 7 (`Resume include regeneration and publish it as one transaction`) commits each requested destination and closes requests connected by shared concepts or destination steps, but steps 6–7 never include an approved parked concept routed through that destination when it has no include request. Committing the whole step then gives that other concept effective delivery alongside approved non-delivery, so step 4’s validator must reject the transition and the reviewed request cannot complete.
