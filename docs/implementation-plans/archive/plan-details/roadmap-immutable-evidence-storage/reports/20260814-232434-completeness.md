- HIGH `[post-link-recovery]`: Step 1 (`Add confined immutable evidence publishing and delete only owned staging files`) makes incompatible recovery promises: Architecture says a publisher “may reclaim” stale staging, requires an existing final to have “link count one,” and says any post-link failure later resolves as `existing`. The staging/durability Risks, Testing’s post-link failure injection, and the lock/result acceptance criteria depend on this, but failed staging cleanup leaves `nlink=2` and a failed directory sync has not established the required durability boundary ([Linux `fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html)); after a crash, a retry may need to create anew or return non-success.
  - Fix: Define one required locked recovery sequence that returns `existing` only after a safe final reaches the sync boundary, otherwise safely republishes exclusively or returns a non-success result, and align the risks, tests, and criteria to it.
- MEDIUM `[interruption-recovery]`: Step 1 (`Add confined immutable evidence publishing and delete only owned staging files`) defines `interrupted` in Architecture as best-effort cleanup with no success result, and acceptance criterion 2 repeats that outcome, but Testing names only crashes, write failures, and generic failure injection. It never requires injected interruptions at cleanup or post-link boundaries followed by a retry, so an implementation can leave a link-count-two final or map interruption as ordinary I/O failure without a failing test.
  - Fix: require deterministic interruption-and-retry cases that prove the `interrupted` result and recoverable final state at every publication boundary.
- HIGH `[staging-inode-publication]`: Step 1 (`Add confined immutable evidence publishing and delete only owned staging files`) promises to hard-link the tracked staging inode, but Architecture’s capability, staging, and publication paragraphs establish descriptor/device/inode tracking without a link-time identity guarantee. Python’s [`os.link`](https://docs.python.org/3.13/library/os.html#os.link) still links a named source even when its directories are descriptor-relative, so a replacement between validation and linking can publish different regular bytes; `O_NOFOLLOW` and a final link count of one do not detect that. Testing’s “replaced staging entry,” Risks “A safe final name follows…,” and acceptance criteria 2–3 therefore cannot prove the promised source identity.
  - Fix: define the supported-platform ownership and link-time identity rule that prevents a replaced staging name from becoming a final record, with an unsafe-storage/no-final outcome when it cannot be proven.
- MEDIUM `[scan-publication-consistency]`: Step 2 (`Add deterministic final-only evidence scanning without reading unsafe entries`) does not define how a scan interacts with a publisher: Architecture locks only publishers, then links the final before removing staging, while its scanning paragraph accepts bytes only from link-count-one files. Architecture’s lock, publication, and scanning paragraphs; Risk “Staging contaminates a view”; Testing’s creator and scan cases; and acceptance criteria 3 and 5 allow a scan to omit, wait for, or report a valid in-flight final as `unsafe-entry`.
  - Fix: choose and test one shared-lock or concurrent-visibility rule so scans have one defined result during publication and recovery.
