- HIGH `[decision-anchor-no-retarget-scope]`: The Architecture matrix's `edit-row` row states the no-retarget rule only for `PlansArtifact`: "On `PlansArtifact`, it cannot retarget an existing `AssumptionRow.consuming_plan_ids` or `DecisionRow.anchor`... this vocabulary does not rewrite existing plan-internal relations regardless of decision state," and the matching acceptance-criteria bullet repeats the same "plan-internal relation" scope. But `DecisionRow` (with its `anchor` field) is not Plans-specific — `plan_tool/roadmap_artifacts.py` defines it once and every one of the four artifact types (`DomainArtifact`, `ConstraintsArtifact`, `ComponentsArtifact`, `PlansArtifact`) carries a `decisions: tuple[DecisionRow, ...]` field. The gate this rule was added to compensate for, `check_settled_decisions` (`roadmap_gates.py:1606`), only protects a decision's `anchor` when its predecessor `status` is `SETTLED`; a `PENDING` decision's anchor is unguarded by any gate (`check_decision_records` only checks the anchor resolves to *some* valid id, and `check_design_row_continuity`'s `pinned_by_anchor` set is built only from `SETTLED` predecessor decisions). That is exactly the gap the round-5 fix closed for Plans. Scoping the fix to "On `PlansArtifact`" leaves the identical, unguarded case live on `01-domain.md`, `02-constraints.md`, and `03-components.md`: an `edit-row` there can silently retarget a still-`PENDING` decision's `anchor` to a different row, with no gate rejecting it, during exactly the kind of automated bounded revision this plan exists to make safe from untouched-content drift. `AssumptionRow` genuinely is Plans-only (no other artifact type declares an `assumptions` field), so that half of the sentence is correctly scoped; only the `DecisionRow.anchor` half is under-scoped.
  - Fix: restate the no-retarget rule so it protects `DecisionRow.anchor` on every artifact type that carries decisions (Domain, Constraints, Components, and Plans), not only `PlansArtifact`, and widen the matching acceptance-criteria bullet and the step 1/3 testing coverage description to match.
- MEDIUM `[feedback-free-outcome-scope]`: Step 4 requires a feedback-free stage's successful re-gate to report "its own terminal outcome — distinct from a merged-and-gated completion and from a retry-exhausted stage" and never filed "under either existing result type" (Architecture; Acceptance criteria: "naming the stage, zero attempts, and a successful exit"). At HEAD, `roadmap.py`'s `OUTCOMES` tuple is a deliberately closed two-member set (`OUTCOME_COMPLETED`, `OUTCOME_STAGE_EXHAUSTED`), with a comment stating it has exactly two members, and `roadmap_cmd.py` renders it with a strict two-way branch (`_print_completed` vs `_print_exhausted`). The plan never says whether the new outcome adds a third member to that closed vocabulary and a new CLI branch, or instead stays a per-stage run-log/summary line inside the existing "completed" rendering while the run-level field stays two-valued. The two readings carry real, different weight: widening the vocabulary means touching every place that currently treats it as exhaustively two-valued; leaving it alone risks a multi-stage run where every selected stage was a feedback-free skip rendering as an ordinary "completed" run with nothing at the top level telling an operator or CI that nothing was merged — the exact confusion the acceptance criterion ("never mistaken for a merged completion") means to rule out.
  - Fix: state whether the feedback-free terminal outcome extends the run-level closed outcome vocabulary or is scoped to per-stage reporting only, and add an acceptance criterion covering the case where every selected stage in a run is a feedback-free skip.
- HIGH `[hand-edit-reconciliation-boundary]`: Step 4's hand-edit check can't actually tell a fixable hand edit from an unfixable one, even though the Acceptance criteria and Testing section both require it to. The check parses the predecessor, renders it back out, and compares that rendering to the raw non-feedback bytes. On a match, it proceeds. On a mismatch, Architecture says: "A mismatch triggers hand-edit reconciliation... the canonical parsed form... becomes the working artifact," immediately followed by: "If the parse/render round trip cannot reproduce that non-feedback content losslessly, reconciliation refuses." Both sentences describe the same parse→render→compare operation, so the condition that triggers reconciliation (a mismatch) and the condition that makes it refuse ("cannot reproduce... losslessly") read as the same event — meaning every hand edit that reaches reconciliation would also fail the refusal check, and the success path the Acceptance criteria requires ("A hand edit... is detected and reconciled to its canonical form...") and the Testing section requires ("a predecessor with a non-feedback hand edit that round-trips losslessly is reconciled to its canonical form before any operation is authorized") never actually happens. Every existing round-trip check in this codebase treats a mismatch as one unconditional refusal with no partial-success tier: `roadmap_revision.preflight_feedback_revision`'s `RenderCanonicalMismatch`, `roadmap_structural_revision_run._preflight_is_canonical` (`render-canonical-rejected`), and the byte compare in `roadmap_escalation_selection.py`. None of them separate a recoverable mismatch from an unrecoverable one, so nothing in this codebase already does what step 4 asks for.
  - Fix: name the actual second check that tells a reconcilable hand edit from an irreconcilable one — for example, whether reconciliation means re-parsing the edited (not the old canonical) text and accepting it only when a second, independent round trip of that edited text is self-consistent — and make the Architecture, Acceptance criteria, and Testing sections describe that one mechanism instead of reusing the same compare for both the trigger and the refusal.
