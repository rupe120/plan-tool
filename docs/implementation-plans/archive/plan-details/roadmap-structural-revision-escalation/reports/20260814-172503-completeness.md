- HIGH `[escalation-selector-eligibility]`: Step 1 (`Separate feedback selection from local revision eligibility while preserving seed invalidation and one-artifact replacement`) leaves the escalation selector’s accepted and rejected states undefined. Architecture names “unknown, duplicate, closed, or stale selector,” Testing and Acceptance criteria add “removed” and “cross-artifact-invalid,” but `plan_tool.roadmap_artifacts:FeedbackState` has only `open`, `awaiting-review`, and `deferred`, and `FeedbackTarget` has no target-artifact field; `plan_tool.roadmap_revision:parse_feedback_selector` and `preflight_feedback_revision` therefore cannot supply those meanings. Different implementations can disagree about deferred, artifact-targeted, removed-target, and stale-report rows while claiming the same strict selector.
  - Fix: Define one escalation selector eligibility and rejection vocabulary that maps feedback state, target resolution, artifact qualification, and report freshness to observable results while retaining the intended local-ineligible cases.
- MEDIUM `[escalation-reason-vocabulary]`: Step 3 (`Define deterministic escalation reports with safe paths, bounded context, digest checks, and owner-stage routing`) promises both a classification and an operator-selected reason, but Architecture says only that reasons “cover prose, row or collection structure, relationship or decision semantics, and cross-artifact impact.” It never defines the closed values, whether each paired phrase is one or two reasons, or the mapping from reason and target kind to classification and routing; Step 6’s CLI and the Testing/Acceptance requirements for deterministic classification consequently have no single contract to implement.
  - Fix: Specify the closed escalation-reason vocabulary and the deterministic mapping from each reason and target condition to report classification and routing outcome.
- HIGH `[relation-closure-owner-stage]`: Architecture records “directly declared relation neighbors” but bases context on the “declared relation closure,” without defining the edge set, direction, traversal depth, cycle handling, deterministic order, or how a multi-artifact closure chooses an owner stage for `--from-stage`. Steps 2 (`Extract stable roadmap relation edges without changing existing views`), 3, and 6 consume this rule; `plan_tool.roadmap_view:build_citation_map` is only a partial reverse-reference map, while `plan_tool.roadmap:STAGES` supplies artifact numbers but no closure-to-route rule. Reports can therefore remain bounded yet disagree about affected artifacts, context accounting, and the broad command the plan must not recommend heuristically.
  - Fix: Define one ordered relation-edge and closure contract, including refusal cases and the rule that converts a resolved artifact set into either one safe `--from-stage` recommendation or a schema/ownership-decision result.
- HIGH `[escalation-report-identity-freshness]`: Architecture says “One report covers one selected feedback row and is immutable by convention,” while step 5 (`Write only new immutable escalation reports`) requires repeated writes and step 6 (`Wire --escalate-feedback and --view escalations to report-only writes and log-free reads`) must inspect them. Testing and Acceptance criteria require unchanged runs to produce the same semantic report and stale reports to be rejected, but no identity, path, collision, duplicate-run, or view-selection rule identifies which immutable report is checked; nor does the plan say that stale/current is recomputed rather than persisted into an immutable file.
  - Fix: Define report identity and creation policy, report-view selection/listing, and a derived freshness check from recorded input digests that withholds routing for every stale report.
- HIGH `[snapshot-consistency]`: Architecture, Input, the stale-evidence risk, steps 3, 5, and 6, Testing, and acceptance criteria 1 and 6–7 require a report’s named artifacts and digests to describe one current revision, but they do not say what happens if a roadmap writer changes an artifact while the report reads its closure. The report can otherwise contain individually current digests from different roadmap states, then be marked current even though its context never existed together.
  - Fix: define one concurrent-read rule that verifies all named inputs still match the collected snapshot before report publication and before a view gives routing advice.
- HIGH `[escalation-mode-exclusivity]`: Step 6 (`Wire --escalate-feedback and --view escalations…`) adds a command mode but never defines its behavior with `--from-stage`, `--apply`, `--refresh-seeds`, `--accept-seed`, `--materialize`, `--view`, `--from-existing`, `-y`, `--mode`, or `--id`. `plan_tool.cli.roadmap_cmd:register` already has a broad-mode group, while Architecture forbids escalation from invoking `--from-stage`; without a stated conflict policy, a combined invocation can ignore options or reach a broad writer.
  - Fix: define escalation as an exclusive command mode with one preflight-rejection result for every conflicting option, preserving report-only writes and observability.
- MEDIUM `[escalation-run-log-contract]`: Step 4 (`Add escalation run-log results…`) promises no reviewer prose, while Architecture requires command start, result, or failure with selector, report digest, and stale/current outcome; step 5 consumes those lifecycle results. Testing and acceptance criteria do not define the event fields, closed outcomes, nullability when no report exists, or proof that emitted events omit feedback request and report/context prose. `plan_tool.run_log:RoadmapLocalRevisionPreflight` and `RoadmapLocalRevisionAttempt` show that this log uses closed event contracts rather than free-form error text.
  - Fix: define a redacted escalation event matrix for selector rejection, report creation, report-read freshness, write failure, and interruption, with tests that assert both required fields and absent reviewer prose.
- HIGH `[relation-membership-staleness]`: Architecture treats digests of “every named artifact” as sufficient freshness evidence, but step 2’s relation inventory can gain a new incoming relation from an artifact absent from the old closure. `plan_tool.roadmap_view:build_citation_map` derives citations from domain, constraints, components, and plans artifacts, so an unlisted artifact can become relevant without changing any stored report digest; Testing and acceptance criterion 6 cover only already-named artifacts.
  - Fix: bind freshness to both relation-closure membership and the listed artifacts, so a new relevant relation cannot leave an old route marked current.
- MEDIUM `[broad-route-source-prerequisite]`: Step 3 and acceptance criterion 9 treat an unambiguous owner stage as sufficient to recommend `--from-stage`, but `plan_tool.roadmap:_resolve_brief_path` rejects that command when no recorded `source.json` exists unless the operator supplies `--from-existing PATH`. Architecture, Input, step 6, and Testing do not include source availability in routing evidence, so the stated next action can fail before it reaches the owner stage.
  - Fix: make route recommendations account for the recorded-brief prerequisite and state the safe alternative when it is absent.

Coverage gaps in the plan's own ideas are reported for visibility in this bare-plan audit. Apply actions for this axis are withheld until a complete detail bundle exists, so these findings are informational for now.

- HIGH `[snapshot-consistency]`: The revision-bound digest contract lacks a concurrent-snapshot rule. Architecture, Risks, Testing, and Acceptance criteria require current digests and stale-routing rejection across named artifacts, and steps 3, 5, and 6 build, persist, and render that evidence; `plan_tool.roadmap_revision_publish:roadmap_writer_guard` already coordinates canonical writers, but the plan never says how report collection avoids reading a mix of artifacts during a broad stage rewrite. A mixed snapshot can briefly appear current and recommend a route for a roadmap revision that never existed as one state.
  - Fix: Define a coherent report-snapshot rule that detects or excludes concurrent canonical changes, emits stale/no-route evidence on interference, and adds an interleaving acceptance test.
- MEDIUM `[escalation-documentation-contract]`: Step 7 (`Document the escalation report, stale-routing rule, and no-write boundary`) promises discoverability and the non-fifth-artifact boundary, but no acceptance criterion requires a documented report schema, stale-routing rule, command form, or canonical-artifact distinction. The Testing section only says step 7 has “verification appropriate to the artifacts.”
  - Fix: add an acceptance criterion that names the documentation contract operators must be able to find and verify.
