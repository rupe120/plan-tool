- HIGH `[nested-repo-dirty-precondition]`: Step 4 (`04-end-end-tests-direct-jira-direct-run.md`)'s "narrower (inside)" fixture — "create a nested directory under the original root's tree, `git init` it there too" — makes the *original* cwd-derived root appear dirty to git before `create` ever runs. Git treats an un-gitignored nested `.git` checkout as an opaque embedded repository and reports it as a single collapsed `?? nested/` line in `git status --porcelain`; I verified empirically that `--untracked-files=all` does **not** expand or suppress that line (that flag only fixes the plain-untracked-directory collapse step 3 targets — an embedded-repo boundary collapses regardless of it). Architecture decision 3 states the step-0 clean-tree precondition ("`working_tree_dirty` before `create` runs") is deliberately left unchanged and checks only the pre-relocation cwd root — but that untouched precondition rejects `direct-jira`/`direct-run` with "requires a clean working tree" the instant a nested repo exists anywhere under the original root's tree, before `create` and the relocation logic ever run. This makes step 4's own `test_direct_jira_narrower_relocation_end_to_end`, `test_direct_run_narrower_relocation_end_to_end`, and both fixture-sanity tests unsatisfiable as literally specified, and it defeats the real "narrower (nested repo)" use case the plan's Architecture and Testing sections target for any operator whose cwd tree holds an un-gitignored nested checkout.
- HIGH `[original-root-commit-embeds-nested-repo]`: Step 2's Architecture decision 3 has the original-root commit run `commit_all(repo_root, ...)` (`git add -A`) to capture the archived-seed write, but under a narrower relocation the nested `created_repo_root` sits inside `repo_root`'s own tree, and `git add -A` silently stages that entire nested repo as an embedded gitlink the instant it has any commit — confirmed empirically ("warning: adding embedded git repository", `new file mode 160000`). This corrupts the "small, clearly-named commit covering only that known side effect" step 2's own Implementation promises, embedding a stray submodule-style reference nobody intends to track into the original root's history.
- HIGH `[relocated-root-collision-replace-dirt]`: `find_umbrella_root`'s case 1 (`plan_tool/locator.py`) can return a directory that is a strict ancestor of the original `repo_root` (e.g. a seed referencing a file under the outer project while cwd is itself a nested sub-repo), and `cmd_create`'s relation-string check (`umbrella.resolve()).startswith(repo_root.resolve())`) mislabels that ancestor case "broader (outside)" — the same bucket as an unrelated sibling. Step 4's own "broader" fixture deliberately builds only the true-sibling sub-case ("a sibling directory not under the original root"), never the ancestor one. In the ancestor sub-case `repo_root` becomes nested inside `created_repo_root`, so its own state — including step 2's archived-seed commit — collapses to a single opaque embedded-repo entry in `created_repo_root`'s `git status`, which step 3's expected set (`{plan_path, manifest_path, concepts_path, grounding_path}`) never accounts for, so step 3's guard aborts the chain even when everything is properly committed.
- MEDIUM `[relocated-root-expected-dirt-set]`: Step 4's Input section still restates step 3's guard contract as `{result.plan_path, result.manifest_path, concepts_path(result.plan_path)}` ("a relocated root with dirty content outside {plan_path, manifest_path, concepts_path(plan_path)} aborts the chain"), omitting `grounding_path(plan_path)` — even though step 3's own Input, Implementation, and dedicated test (`test_direct_jira_relocated_root_grounding_sidecar_not_flagged`) all correctly include it as a fourth, unconditional expected path. A step-4 test author following step 4's own Input section literally could build a dirty-abort scenario that wrongly treats the grounding sidecar as unexpected dirt.
