- HIGH `[depends-on-notes-renumbering]`: Step 2's Architecture fan-out/fan-in table only covers what happens to a note when its *own* edge is the one being split, merged, or carved — it never covers the far more common case where a step's `depends_on` ids merely shift because a split/merge/scope-out happened to a *different* step elsewhere in the plan. `_apply_step_split`'s `remap`, `_apply_step_merge`'s `renumber`, and `scope_out.py:compute_narrow`'s `old_to_new` all renumber `depends_on` for every survivor via `step.model_copy(update={"depends_on": new_deps, ...})`, which leaves every other field — including `depends_on_notes` — untouched. A step with a note on an edge that isn't itself being transformed keeps its pre-renumber key after any split/merge/carve anywhere else in the plan; step 1's existence-only validator then either rejects the whole plan (stale key no longer in the remapped `depends_on`) or, if the stale key coincidentally still validates, silently attaches the note to the wrong antecedent — the exact "quietly false carry-over" this plan's own Architecture says a note must never become.
  - Fix: add a rule to the fan-out/fan-in table (and the Testing bullet and acceptance criterion that restate it) requiring every split/merge/scope-out to thread `depends_on_notes` keys through the same old-id→new-id map already computed for `depends_on`, for every survivor — not only the steps named directly in the transform.
- MEDIUM `[dependency-rationale-overlap]`: The Problem statement frames `depends_on` as having no accompanying why anywhere in the codebase ("nothing asks why step 4 depends on step 1"), but `completeness_report.py` already has a related, unmentioned mechanism from BACKLOG #238: `SoftEdge`/`PlanMass.soft_edges` scans a step's detail-body prose for markers like "ordering-only"/"test-only" naming a specific `depends_on_id`, and records the matched sentence as that edge's `note` (see `DATA_CONTRACT.md`'s `SoftEdge` row). It answers a narrower question (is this edge load-bearing) than `depends_on_notes` (what does this edge deliver), and it's reporting-only like this field, but the plan never says how the two relate, so a reader ends up with two different, unlinked ways to annotate a `depends_on` edge's meaning.
  - Fix: add a sentence to the Architecture or Problem section naming `soft_edges`/`SoftEdge` and stating the relationship — e.g. that `depends_on_notes` is deliberately separate from and does not replace the free-prose soft-edge heuristic, or that a later change could let `_find_soft_edges` read `depends_on_notes` instead of scanning detail prose.
- MEDIUM `[manual-wizard-note-gap]`: The Architecture section explicitly scopes out one Claude-free `depends_on` authoring path (`canonical.py`'s `extract_canonical_steps`, "This is not a gap step 3 closes") but never mentions the other Claude-free path: `create.py`'s `prompt_steps`/`_prompt_one_step` manual wizard, which runs when both canonical extraction and the Claude proposal return no steps and `--yes` is not set. That wizard already asks the operator for `depends_on` via `_ask_int_list` but has no matching prompt for a per-edge note, so a plan authored through this fallback can never carry a note on any edge — an unscoped accident, not a deliberate carve-out like the canonical path gets.
  - Fix: add one sentence to the Architecture "Authoring" paragraph deciding whether `_prompt_one_step`'s manual wizard also collects a per-edge note (mirroring step 3's Claude-proposal prompt) or is deliberately excluded like the canonical path, and say why.
- MEDIUM `[step4-review-render-untested]`: Step 4 ("Show each proposed step's `depends_on` ids and their notes in create's interactive step review") is the only step with no acceptance-criterion bullet and no Testing-section bullet locking in its own behavior — the six acceptance criteria and the Testing section's bullets each name steps 1, 2, 3, 5, or 6 by mechanism, but none says the interactive review must render `depends_on` ids and notes together. Nothing stated would fail if the shipped review rendered only notes, or only rendered a note when one exists, instead of showing every edge alongside any note it carries.
  - Fix: add an acceptance criterion and a Testing-section bullet stating that create's interactive step review renders every proposed step's `depends_on` ids together with any note, for edges with and without one.
- MEDIUM `[merge-inbound-note-collapse]`: Step 2's Architecture merge row only states a rule for the merged step's own outbound edges — "keep a collapsed edge's note only when every merging member's edge to that same antecedent carried the identical note text … otherwise clear it" — but `create.py:_apply_step_merge` also folds edges the *other* direction: its `_remap_external` helper repoints every surviving step that depended on **any** merge-set member onto the one survivor id, deduping with `dict.fromkeys` (comment: "a step that depended on two members keeps a single edge"). A step S with `depends_on = [3, 4]` and `depends_on_notes = {3: "...", 4: "..."}`, where 3 and 4 are both being merged, ends up with `depends_on = [<survivor id>]` — one key, but two possibly-conflicting note texts that must be reconciled into it. The plan gives step 2 no rule for this inbound-collapse direction, so the implementation has to invent one — exactly what step 2's own intent says to avoid ("never let a note silently become false when an edge doesn't survive one-to-one").
  - Fix: add a second bullet to the merge row covering the opposite direction — when an external dependent's several edges into the merge set collapse onto one survivor id, keep that dependent's note only if every collapsing edge carried identical note text, otherwise clear it, mirroring the rule already stated for the outbound case.
