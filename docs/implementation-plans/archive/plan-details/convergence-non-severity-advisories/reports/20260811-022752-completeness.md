At bare stage, `is_blocking_finding` only counts a `plan-completeness` finding as blocking when it's high/critical — a medium `plan-completeness` finding does not block. Because the compatible-window rule already requires every pass in a window to share one persisted `audit_stage`, that same stage is available to gate materiality the same way.   - Fix: define edit-drift materiality as the same stage-aware bar `_open_medium_plus`/`is_blocking_finding` already use (`is_blocking_finding(rec, stage=<the window's persisted audit_stage>, classify_domain=...)`) instead of plain `is_blocking(severity)`, and correct every place the plan currently names `is_blocking` for this purpose — the Architecture "Edit-drift binary observable" paragraph and the References bullet on `plan_tool/convergence.py`.

  - Fix: relabel step 1's change_type from refactor to feature to match what the step does.

CLAUDE.md's "Convergence policy boundary" section explicitly asks to keep `is_blocking`, `is_blocking_impact`, and `is_blocking_finding` — and their callers — clearly separated; reusing "material" for a third, cross-invocation concept invites exactly that conflation.
  - Fix: give edit-drift's finding filter a name distinct from "material"/`material_new` (e.g. "counted" or "edit-drift-eligible"), or add one sentence stating explicitly that it's a different concept from `material_new`/`is_blocking_impact`, everywhere the plan currently uses the bare word "Material" for this filter (the Architecture paragraph and the matching acceptance criterion bullet).
