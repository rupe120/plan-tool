- HIGH `[add-row-collection-selection]`: The `add-row` operation's Architecture-matrix row states its rule once, generically — "Adds one typed design row to the current artifact with a new valid id" — and only becomes concrete for one of the four target artifacts: "In `PlansArtifact`, it admits a `PlanRow`, `AssumptionRow`, or `DecisionRow`; only a `PlanRow` also appends its one matching `ordering` entry." At HEAD, `plan_tool/roadmap_artifacts.py` shows every other artifact type carries several distinct typed row collections that an "artifact"-targeted add could plausibly mean: `DomainArtifact` has `entities` (`EntityRow`), `business_rules` (`BusinessRuleRow`), `workflows` (`WorkflowRow`), and `decisions` (`DecisionRow`); `ConstraintsArtifact` has `dispositions` (`AttributeDispositionRow`), `constraints` (`ConstraintRow`), `decisions`, and `hosting` (`HostingRow`); `ComponentsArtifact` has `system_patterns`, `component_patterns` (both `PatternRow`), `components` (`ComponentRow`), `decisions`, and `stores` (`StoreRow`). Because `add-row`'s only eligible feedback target is `artifact` (the whole artifact, not an existing row), nothing in the operation signals which of these several row types a given `add-row` call is meant to create for Domain, Constraints, or Components — unlike `edit-row`/`remove-row-with-record`, whose `row` target already fixes the collection by resolving an existing id. The Testing section only ever exercises `add-row` at "stage 4," enumerating `PlanRow`, `AssumptionRow`, and `DecisionRow` and their ordering companion — it never states or tests what `add-row` creates on `01-domain.md`, `02-constraints.md`, or `03-components.md`. The Acceptance criteria bullet on `add-row` is likewise scoped only to `PlansArtifact` ("On `PlansArtifact`, `add-row` admits a plan, assumption, or decision..."). This leaves genuinely open, materially different readings for the other three stages — is `add-row` authorized there at all, restricted to one specific collection per artifact, or expected to carry a type discriminator the plan never names — and the ambiguity lands squarely on stage 1 (`01-domain.md`), the exact stage whose 70 KB whole-artifact revision failure motivated this plan's Overview and Problem statement.
  - Fix: in the Architecture matrix's `add-row` row, name which row-type collection(s) `add-row` may target on `DomainArtifact`, `ConstraintsArtifact`, and `ComponentsArtifact` (or state that `add-row` is scoped to `PlansArtifact` only, if that is the intent), and widen the Testing section and the `add-row` acceptance-criteria bullet to cover whichever scope is chosen for all four artifact types, not only Plans.
- HIGH `[feedback-free-regate-failure-outcome]`: Step 4 says a feedback-free stage's failed re-gate "halts the run without a backend call or write for the skipped stage, reports the stage and its gate violations," but only the success case gets a named outcome ("a re-gate success is a genuine third member of the run-level outcome vocabulary"). The acceptance criteria and Testing section describe the failure's observable behavior (stop before a call/write, name the violation, keep the earlier merge) but never state its `RoadmapResult.outcome`. This is concrete, not academic: the only existing machinery shaped like "stop mid-run, report a stage and its violations" is `OUTCOME_STAGE_EXHAUSTED` (`roadmap.py`), which `cli/roadmap_cmd.py:_print_exhausted` renders as "stage {N} exhausted its retry budget ({kind} failure)." A feedback-free stage that fails its re-gate made zero backend attempts, so reusing that path unmodified would report a retry-budget exhaustion that never happened.
  - Fix: state which outcome a feedback-free stage's failed re-gate reports (reused `OUTCOME_STAGE_EXHAUSTED` with a distinct `failure_kind`, or a new one) and require its rendering to say the stage was never invoked, not that it exhausted retries.
- MEDIUM `[revision-route-hand-edit-policy]`: Step 4's hand-edit preflight treats any non-feedback predecessor mismatch as always safe to silently fix and continue: "Any mismatch unconditionally reprocesses the predecessor... with no safe/unsafe distinction." The sibling local-revision route answers the same underlying question the opposite way: `roadmap_revision.py:preflight_feedback_revision` raises `RenderCanonicalMismatch` and refuses outright whenever `render_artifact(artifact) != artifact_text` — any non-canonical predecessor, not only one touched outside feedback. Both routes ask "the on-disk artifact doesn't exactly match what our renderer would produce — proceed or refuse?" over the same artifact types, and land on opposite answers, with no stated reason. A reviewer used to the local route's hard refusal has no reason to expect the new stage route to instead reprocess and proceed.
  - Fix: state in the Architecture section why the stage-envelope route reprocesses-and-logs while the local route keeps refusing outright, so the two routes' safety guarantees read as a deliberate choice.
- MEDIUM `[stage-gate-vocabulary-miscount]`: The Architecture section says a merged candidate is judged by "the existing id-continuity, settled-decision, feedback-integrity, and design-row-continuity gates" — four names — but only three such gates exist. `ROADMAP_FORMAT.md` says so directly: "The three revision gates — `check_design_row_continuity`, `check_feedback_integrity`, and `check_settled_decisions` — judge the artifact under check against its own prior version." `roadmap_gates.py` defines no function named or acting as an "id-continuity" check; the plan's "id-continuity" item most likely double-counts `check_design_row_continuity` (whose own name is already the fourth item in the same list) rather than naming a real fourth gate. The same four-item phrase already appears in `BACKLOG.md`'s #297 entry, so this predates the plan, but the plan is where it becomes load-bearing prose about what actually protects a merged candidate.
  - Fix: correct the Architecture section to name exactly the three existing gates, dropping the separate "id-continuity" item — or, if a distinct id-stability property is genuinely intended beyond what those three (plus `check_duplicate_row_ids`) already provide, name the gate that provides it.
- HIGH `[skipped-stage-upstream-propagation]`: Step 4 requires that when a feedback-free stage is skipped mid-run, a later re-entered stage still sees "the skipped stage's preflight-loaded predecessor as its upstream value" (Architecture), and the acceptance criteria repeat this as "a later selected stage with open feedback still follows the bounded route using a green skipped predecessor as upstream input." No part of the plan names the route that delivers this. At HEAD, `roadmap.py:_run_roadmap` builds every stage's upstream context from one list (`loaded`), seeded only with the artifacts below `from_stage` (`_load_and_regate_below`) and extended in exactly one other place: right after a stage's artifact is written and re-read back from disk. A feedback-free skip, by this same step's own design, "makes no backend request, artifact write, artifact reload... merely because an earlier selected stage existed" — precisely the write-then-reread step that is the only thing currently adding a stage's artifact to `loaded` for anything at or above `from_stage`. Nothing in the plan says the skip path instead folds the skipped stage's own predecessor artifact into `loaded`/upstream despite performing no write or reread. Left unaddressed, a run mixing a skip with a later bounded merge — the exact scenario the plan's own acceptance criteria and testing section call for — would render the later stage's prompt and build its gate envelope with that upstream artifact silently absent.
  - Fix: state that a feedback-free skip still contributes its preflight-loaded predecessor artifact to the upstream set that later stages in the same run consume, even though it performs no write or reread, so the existing per-stage upstream construction stays complete across a skip.
