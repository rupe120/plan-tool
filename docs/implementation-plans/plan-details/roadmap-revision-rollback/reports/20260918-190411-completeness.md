That filter is wrong: `recover_roadmap_publication` (`plan_tool/roadmap_revision_publish.py`) is shared by every roadmap writer under the same `pending_generation_path` journal, and two of those writers — `enroll_roadmap_root` (`kind="root-enrollment"`, built by `build_root_enrollment_generation` in `plan_tool/roadmap_versions.py:400-449`) and review-seal promotion (`kind="review-seal-promotion"`, `plan_tool/roadmap_version_promotion.py:91`) — publish members that live entirely under `.roadmap-versions/` (the stored version record, brief, artifacts, and the accepted-head selector), none of which are among the checkpoint's ten tracked files. Step 1's own contract for `with_last_written` is to `raise RoadmapRevisionCheckpointError` for exactly this case ("Raise... if `relative_path` does not match any tracked entry — this is what catches a step-2 wiring mistake"), pinned by `test_with_last_written_rejects_a_relative_path_outside_the_tracked_inventory`. So a crashed `enroll_roadmap_root`/review-seal-promotion call — reachable any time after an earlier, unrelated stage-run failure already left a checkpoint behind (enrollment is not blocked by a checkpoint's presence) — leaves a dangling non-`revision-restore` journal that both reconciliation sites will try to fold in, and `with_last_written` raises. For an ordinary continuing stage run (step 2), nothing catches `RoadmapRevisionCheckpointError` (a `ValueError` subclass) — the capture/continue/reconcile wrapping only catches `OSError` — so it propagates uncaught out of `cmd_roadmap` as a raw traceback instead of a clean exit code, exactly in the "resume after something already went wrong" path this plan exists to make robust. For restore invoked via the CLI (step 4's `except (RoadmapWriterGuardError, ValueError)`), it is caught but surfaces as an unmodeled generic usage error rather than one of the plan's five matrix rows, and any reconciliation already persisted before hitting the untracked path leaves the checkpoint partially rewritten. Neither step 2's nor step 3's test rosters cover a peeked `root-enrollment`, `review-seal-promotion`, or `baseline-enrollment` journal — every reconciliation test uses a `stage-publication` or `revision-restore` journal only.
  - Fix: In both step 2's capture-or-continue and step 3's restore reconciliation, scope the fold-in to a peeked journal whose members are entirely drawn from the checkpoint's own tracked inventory (e.g. restrict to `kind in {"stage-publication", "feedback-publication", "confirmed-feedback-reopen", "structural-feedback-publication", "baseline-enrollment"}`, or check each member's relative path against the checkpoint's tracked entries and skip any journal that names one outside it) instead of merely excluding `"revision-restore"`, and add a test to each step proving a dangling `root-enrollment`/`review-seal-promotion` journal is left unreconciled (no raise, checkpoint untouched) rather than folded in.
- MEDIUM `[checkpoint-relative-path-derivation]` [confidence: limited]: Step 1 (`docs/implementation-plans/plan-details/roadmap-revision-rollback/01-roadmap-revision-checkpoint-file-that.md`) defines `tracked_paths(plans_dir, slug) -> tuple[Path, ...]` returning ten *absolute* paths, and `CheckpointEntry.relative_path: str`, and its own Input section states the requirement plainly:

  ```
  its own per-entry relative-path convention (see Implementation) must
  match `GenerationMember.relative_path`'s convention exactly — root-relative,
  forward-slash, no leading `./` — or step 3's conversion breaks silently on
  the first hand-off.
  ```

  But nowhere in step 1's Implementation, References, or Tests does it name the mechanism that turns each absolute `tracked_paths()` entry into that relative-path string. The codebase already has exactly this helper, `roadmap_relative_stage_path` (`plan_tool/roadmap_artifacts.py:115-131`, `.resolve()` on both root and candidate before `.relative_to()`/`.as_posix()`), and step 2 explicitly imports it for the identical purpose ("It is not currently imported into `plan_tool/roadmap.py`; this step adds it..."), but step 1's own References section for `tracked_paths` lists only `roadmap_dir`, `domain_path`/`constraints_path`/`components_path`/`plans_path`, `brief_source_path` — never `roadmap_relative_stage_path`. An implementer of `capture_checkpoint` is left to invent this conversion, and a plausible but different implementation (e.g. `Path(p).relative_to(roadmap_dir(plans_dir, slug)).as_posix()` without first calling `.resolve()` on both sides) can diverge from `GenerationMember`'s convention under a symlinked temp directory (a real risk on macOS, where `/tmp` resolves to `/private/tmp`) even though it would pass step 1's own fixture-only tests, which never compare against `roadmap_relative_stage_path`'s output.
  - Fix: Name `roadmap_relative_stage_path` explicitly in step 1's Implementation and References as the function `capture_checkpoint` uses to derive each `CheckpointEntry.relative_path`, and add a test asserting the checkpoint's captured relative paths equal `roadmap_relative_stage_path`'s output for each of the ten tracked files.
