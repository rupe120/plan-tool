# Scope Out Executor

## Overview

Adds `plan-tool scope-out <plan> --step N`, the actuating half of the structural-remedy work carved out of `structural-remedy-vocabulary` (whose advisory arms — the convergence scope-out recommendation, the reconcile finding, the docs — land first). When a region of a plan is spinning (recurs + no-shrinkage at `last_severity ≥ high` with a non-decreasing first→last severity trend — the "patches backfire" signature `convergence` detects), scope-out carves that region out so the rest converges. It performs two mutations **seed-first**: emit a `create --from-existing` forward-seed for the carved step under `plan-seeds/<plan>-carved-<slug>.md`, then narrow the plan. The actuating path is `--apply` plus either interactive confirm `yes` or the explicit second opt-in `-y/--yes`; every path lacking that apply authorization recommends only, spends no Claude, mutates nothing.

## Problem statement

Today the scope-out remedy exists only as prose: the convergence diagnostic recommends carving a spinning region but there is no runnable command to do it. The carve needs **new code + resolved design** rather than composing existing executors — its narrowing half has no precedent: no existing executor *drops* a step. `split_step` is one→many; `merge_steps` folds many→**one survivor** and repoints dependents to it (`create._apply_step_merge`). A deep audit of the combined plan put almost every HIGH/structural finding on this executor because it touches hard plan-graph mechanics (dependency edges, run cursor, detail-file lifecycle) and the run-state "carry" has a real mechanism subtlety. Its practical reach is a **dependency-leaf / end-of-plan step with no surviving inbound dependent** (the safe-carve envelope in steps 2–3 refuses a carve whose id a surviving step `depends_on`): for such a step, scope-out carves it out to somewhere durable and re-plannable instead of patching it in place. The **common mid-plan spinning CURRENT step** — which typically has a surviving downstream step that `depends_on` it — is **out of this executor's single-step reach**; its resolution is the Deferred multi-step / multi-region sub-tree carve (carving the whole dependent sub-tree together), and until then that case stays on the structural re-seed path.

## Architecture

**Seed-first atomicity contract.** A crash after the seed write leaves a harmless re-runnable orphan seed; a crash before it leaves the plan untouched. A post-seed `apply_narrow` exception is likewise outside the returned `ScopeOutResult` outcome contract: the exception propagates, no result is returned, and the already-written orphan seed remains on disk while `apply_narrow` rolls back the plan/detail changes it can. Because step 3 writes the seed seed-first and `_carved_seed_path` suffixes a fresh `-2`/`-3` on each collision, **retries after a failed `apply_narrow` accumulate near-duplicate orphan seeds** under `plan-seeds/` — scope-out neither reuses nor cleans the prior attempt's seed. This accumulation is **accepted, not de-duped**: the stale orphans are harmless (the same disposition as the single post-crash orphan) and left for the operator to prune by hand.

**Run-state "carry" = done-context PROSE, not a live-status round-trip.** The carved step typically has run state (it is the spinning, often CURRENT step). But `create --from-existing` re-decomposes into fresh PENDING steps and cannot round-trip live `status`, and `schema.Step` has **no `progress` field** (only `status: StepStatus` and the ephemeral `status_note`). So the seed carries the carved step's detail/frontmatter as the region to re-plan, while prose carries the run-state context — but the framing splits on whether that state is genuinely complete. The carved step is "the spinning, often CURRENT step", i.e. typically non-DONE: its own `status`/`status_note` render as **attempted/partial context to account for**, kept distinct from the "already implemented — do not re-plan" done-context framing (reserved for genuinely-complete upstream context and explicitly known completed work), exactly as `annotate_render.render_create_seed`'s done-context block frames context for the whole-plan path. Labeling a non-DONE carved step's partial `status_note` as done-context would risk the re-plan treating the half-built carved work as complete-and-skip — the inverse over*claim* of the resumability over*claim* this decision already guards. So the carved step's detail/frontmatter stays in re-plan scope even when its status reads as in-progress; the attempted-context prose says what was left half-done, and the re-plan *accounts for* that context without resuming the in-progress step verbatim. Do **not** reuse the PENDING-only safety gate verbatim (`merge_steps`/`split_step`/`escalate_to_split` refuse a run-started target) — that would forbid the exact case scope-out exists for. (fixes `progress-source-undefined`, `runstate-resume-overclaim`)

**The narrow is a NEW primitive with its OWN drop-renumber — not a reuse of `merge`.** `_apply_step_merge`'s renumber is private inline fold-logic (collapses members onto a survivor), not a callable unit and not shaped for a drop (which has no survivor). The narrow writes its **own** small drop-renumber: shift survivors after the hole down by one and rebuild the `depends_on` edges. It also owns an explicit downstream detail-file journal for every rename/archive side effect; do not call `detail._migrate_downstream_details_after_merge` unless its whole side-effect surface is wrapped in a snapshot/restore rollback wrapper. Do not claim reuse of merge's renumber, and do not fold an extract-shared-helper refactor into this step (that would make it a refactor+feature mixed step). (fixes `narrow-drop-primitive`, `narrow-renumber-reuse-feasibility`, `narrow-detail-helper-rollback`)

**Carved step's `features:` tags — carry to seed + prune from the narrowed registry.** A drop has no survivor to fold tags onto, unlike `merge_steps` (`merged_features = _dedup([f for s in member_steps for f in s.features])`), so a carved step that is the sole implementer of a registry feature would otherwise leave that feature registered-but-unimplemented in the narrowed plan while the seed loses the tags. Step 1's `render_carved_seed` carries the carved step's `features` tags into the seed as re-plan scope so the re-planned successor re-registers them; step 2's narrow prunes from the narrowed plan's `features:` registry any feature left with no implementing step after the drop, preserving the step→feature ownership invariant (no dangling tag). Do not drop the `features` dimension silently. (fixes `carved-step-features-disposition`)

**Carved step's `scope` disposition — note it in the seed, never resurrect parked work as committed.** `scope-out` accepts an arbitrary `--step N`, so the carved step may be `deferred` or `wont_do` (`schema.Step.scope: StepScope`), not just the `committed` step the convergence recommender ever fires on. Step 1's `render_carved_seed` reads the carved step's `scope` and renders its disposition in the seed: a `committed` step is re-plan scope as usual, while a `deferred`/`wont_do` step carries an explicit disposition note so `create --from-existing` does not silently resurrect parked/abandoned work as committed re-plan scope (and a `deferred` carve does not lose its gated disposition). Do not drop the `scope` dimension silently. (fixes `carved-step-scope-disposition`)

**Dependency-graph integrity across the drop (the central correctness gap).** The carved step has edges in both directions and both must be handled explicitly — a silent id reuse corrupts the graph with no validation crash. **Inbound** (a surviving step `depends_on` the carved step): after drop+renumber that id is reused by a different step. `_apply_step_merge` repoints dependents to the survivor; scope-out has **no survivor to repoint to**, so it must **refuse** (recommend-only) when a surviving step depends on the carved step — unless the whole dependent sub-tree is carved together (Deferred). **Outbound** (the carved step `depends_on` surviving upstream steps): only upstream dependencies whose status is `done` are captured in the seed as done-context so `create --from-existing` re-establishes that assumption; non-DONE upstream dependencies are rendered as explicit external prerequisites with their current status, not as already-done context, so a PENDING carved target cannot tell the re-plan to assume incomplete upstream work already exists. (fixes `carved-step-dependents`, `carved-step-upstream-deps`)

**Carved step's own detail file → archive.** The narrow migrates downstream detail files (`id > survivor`); the carved step's own detail file would be left orphaned. Resolve the carved detail from `schema.Step.detail` first (`repo_root / step.detail`), falling back to the canonical `detail.derive_detail_path(...)` only when the step has no `detail:` pointer but the canonical file exists. Archive that resolved file (mirror `merge_steps`, which archives folded-away files), since its body is already captured in the seed. Treat no carved detail as a clean no-op, but treat a failed archive of an existing carved detail as an apply failure that raises and triggers rollback. A **pointed-but-missing** carved detail (a step whose `detail:` pointer is set but whose file is absent — moved/deleted/slug-drifted) is a third, explicit case distinct from both the no-pointer no-op and the happy resolved-file path: `compute_narrow` does **not** block on it (blocking would forbid carving a step merely because its detail file drifted) and has nothing to archive (the clean no-op), but it flags the absent body to step 1's renderer so the seed emits a **missing-detail warning** rather than the "never detailed" note — so the lost carved body is reported, not silently mislabeled as a step that was never detailed. **Step 2's archive resolution (inside `compute_narrow`) and step 3's seed-body resolution must target the identical carved-detail file — preferably step 3 reads the body from the preview's already-resolved `preview.archive_detail` rather than re-resolving independently in `_resolve_carved_detail_path`**, so the path has a single source of truth; where step 3 must resolve on its own, a shared resolver helper or an explicit parity contract pinned by a test enforces that it lands on the same file. The file archived from disk is then exactly the body the seed captured; if the two reads ever diverged, the seed and the archive would refer to different files, silently losing the carved body (orphaning it under the dropped step's slug) or archiving an unrelated one. (fixes `carved-detail-file-disposition`, `carved-detail-pointed-but-missing`)

**Saved report sidecars across the drop — accept staleness, mirroring `merge`/`split`.** The narrow migrates/archives downstream **detail files** but does **not** remap or purge the saved completeness/reconcile **report sidecars** under `plan_reports_dir` — `review_persistence.save_review` keys them by `step_id` and `convergence_diagnosis.load_report_history`/`recurring_regions` group them into regions by `step{step_id}` / `step<N>` anchor tokens. After a drop+renumber shifts survivors down by one, those sidecars retain the pre-carve numbering, so the next `plan-tool convergence` read can mis-attribute the carved step's spin trend to whatever survivor now holds its renumbered id (and could re-recommend `scope-out` on that innocent renumbered survivor). This staleness is **accepted, not repaired** — the same frontmatter-is-source-of-truth disposition `merge`/`split` already take for the stale prose body `write_plan` preserves byte-for-byte. Recorded consequence: cross-run report history is re-grounded the normal way — a fresh completeness/reconcile pass over the narrowed plan after the carved region is re-planned — not by the narrow rewriting historical sidecars; `compute_narrow`/`apply_narrow` neither read nor mutate `plan_reports_dir`. (fixes `carved-report-sidecar-staleness`)

**Re-establish a run cursor in the narrowed plan — only when the drop removes the plan's sole CURRENT.** Scope-out's CLI accepts an arbitrary `--step N`, so the carved step is not always the run cursor. The narrow promotes a survivor to CURRENT **only when** the dropped step was the plan's sole CURRENT and a post-drop runnable PENDING survivor remains — promoting the first committed pending survivor whose dependencies are all done, matching `Plan.next_runnable_step()`. Carving a PENDING/DONE step while a different survivor is already CURRENT must leave that CURRENT untouched: force-promoting would yield two CURRENT steps, an invalid single-cursor plan that nothing downstream repairs (`create._seed_initial_step_status` no-ops once any step is non-PENDING). When no post-drop runnable pending survivor exists, leave no CURRENT rather than promoting blocked or parked work before its prerequisites; if the committed survivor set is all DONE, also set the top-level plan status to `completed` so the narrowed no-cursor plan satisfies existing completion semantics. (fixes `narrowed-plan-current-pointer`)

**Intra-narrow atomicity + the safety gate (mirror `escalate_to_split`).** The narrow is multi-step (drop + renumber + repoint depends_on + migrate/archive detail files + set cursor); compute the full new-plan + file-op plan in memory (a dry-run preview, as `merge_steps(dry_run=True)` does), validate, then apply all-or-nothing with rollback — never a partial on-disk state from an in-process apply failure (a real process crash mid-apply still relies on seed-first re-runnability, not the rollback). Detail-file renames and archives must be driven from the preview's explicit journal, with destination-collision checks and inverse operations recorded before any later write can fail; helper calls with hidden best-effort side effects are allowed only behind a snapshot/restore wrapper that treats every side effect as rollback-managed. The mutation applies only when **safe** (canonical contiguous step ids; no inbound dependent on the carved step; no downstream non-PENDING step orphaned by renumber) **+ `--apply` + either interactive confirm `yes` or explicit `-y/--yes`**; every other returned path (unattended without `-y`, unsafe, non-TTY without `-y`, declined, empty-plan) recommends only, spends no Claude, mutates nothing. The `unsafe` refusal — like `empty-plan` — redirects the operator to a next action rather than dead-ending on a bare blocker list, naming the next `plan-tool create --from-existing` re-seed command form (whose `<seed.md>` is a placeholder path the operator hand-authors, matching `convergence_diagnosis.py:_reseed_command`), not a copy-paste-runnable line (see the *Recommend↔carve reach asymmetry* decision, which owns why the common convergence-recommended case carves as `unsafe` and why the refusal is a designed branch). `compute_narrow` refuses non-canonical numbering before preview/apply with a `non-canonical-numbering` blocker that step 3 maps to `unsafe`, writing nothing. Return a frozen `EscalateResult`-style value for non-exceptional paths (`outcome` ∈ `applied` / `recommended` / `unsafe` / `step-missing` / `empty-plan`; only the returned `applied` outcome mutates); post-seed `apply_narrow` exceptions propagate outside this result contract with the orphan-seed caveat above; re-parse the plan from disk on entry. `apply_narrow` persists the narrowed plan via `parser.py:write_plan`, which rewrites only frontmatter and preserves the human prose body byte-for-byte — so after a carve the narrowed plan's prose (`## Steps`, Overview/Risks/Acceptance bullets) still narrates the now-removed step; this stale carved-step narrative is expected, not a defect, under the frontmatter-is-source-of-truth convention (mirroring `merge`/`split`). (fixes `narrow-atomicity`, `narrow-detail-helper-rollback`)

**Empty-plan guard — keyed on the committed survivors, not the total count.** Carving the plan's only surviving step would produce a `steps: []` plan — the rot the forward-seed disposition exists to avoid. But a `steps: []` result is not the only dead-plan shape: `schema.Plan` carries a `scope` dimension (`committed`/`deferred`/`wont_do`), so carving the last **committed** survivor while **parked** (`deferred`/`wont_do`) steps remain leaves a plan that satisfies `min_length=1` yet has no committed step — no promotable CURRENT, `all_steps_done` returns `False`, `new_plan_status` stays `in_progress` — equally dead. The guard fires whenever the post-drop survivor set has no committed step (`committed_steps` empty), covering both shapes, and never builds a committed-empty narrowed plan. Refuse (outcome `empty-plan`) with a message pointing at a full re-seed (`create --from-existing`). (fixes `scope-out-last-step-empty-plan`)

**Carved-region seed emitter — adapt, don't force-reuse.** `annotate_render.render_create_seed(annotation: PlanAnnotation, *, report_path)` consumes a whole-plan `PlanAnnotation` (from `annotate.classify_plan_implementation`, a Claude pass) and writes beside the source — wrong contract for a carved single-step subset under `plan-seeds/`. Build a focused, deterministic carved-region renderer (no Claude) that serializes the carved `Step` + its detail body as re-plan scope, plus the done-context prose and captured upstream-dep context, splitting upstream dependencies so only DONE prerequisites become assumed done-context and non-DONE prerequisites render as external prerequisites. (fixes `scope-out-seed-emission-reuse`)

**Dependency on the advisory plan (single-step only).** This plan depends on `structural-remedy-vocabulary` landing first and flips its scope-out recommendation from prose-only to a runnable command — but only for the single-step case. `plan-tool scope-out --step N` needs one resolved step id; non-single-step or unresolvable evidence remains `FORK_STRUCTURAL` and renders the existing `plan-tool create --from-existing <seed.md>` re-seed path. `render_diagnosis` renders the runnable `--step N` command only when `classify_fork` returns `FORK_SCOPE_OUT` with a single resolved step; a defensive empty `FORK_SCOPE_OUT.command` falls back to prose-only so it never emits a `--step` line with no id. A resolved single step is **not** a carvability guarantee, and `render_diagnosis` frames the printed `--step N` line as a **preview the executor may refuse** rather than a guaranteed carve, paired with the `plan-tool create --from-existing` fallback — the *Recommend↔carve reach asymmetry* decision owns the rationale (why the recommender recommends optimistically without the live graph and why a refusal is a designed branch, not a dead end). (fixes `scope-out-arm-step-focus`)

**Recommend↔carve reach asymmetry — the recommender recommends optimistically; the executor's `unsafe` refusal is a designed, actuating branch of the *same* remedy.** The convergence diagnostic's `FORK_SCOPE_OUT` arm and this executor's step-3 safety gate read **different information by design**: `convergence` sees only the persisted report subset (recurrence + severity trend keyed by `step{id}` tokens) and **cannot re-derive the live plan graph**, while the gate reads the on-disk `depends_on`/run-state to decide carvability. So the recommender *cannot* know whether a resolved spinning step has a surviving inbound dependent — and the common mid-plan spinning CURRENT step usually does, which the gate rejects as `unsafe`. **Resolution: the recommender recommends optimistically and the executor refuses safely; this is one remedy traversed across two commands, not a recommendation contradicting its executor.** Three rulings make that contract explicit: (1) **`convergence` does not gate the `--step N` recommendation on carvability it cannot see** — suppressing the line whenever a dependent *might* exist would violate *always surface the more-correct plan* (`MISSION.md`) and would hide the cheaper single-step carve in exactly the cases where it *is* safe (a true dependency-leaf / end-of-plan step). The printed line is contractually a **preview the gate may refuse**, rendered together with its paired fallback so the operator sees both before running. (2) **The executor's `unsafe` outcome is a designed branch, not a failure** — it exits 0 (a refusal is not a failure-to-complete, per the exit-code convention), spends no Claude, mutates nothing, and its message **names the next `plan-tool create --from-existing` re-seed command form** (the `FORK_STRUCTURAL` remedy the carved case "stays" on, whose `<seed.md>` is a placeholder path the operator hand-authors — matching `convergence_diagnosis.py:_reseed_command`), mirroring `empty-plan` — so the recommend→refuse→re-seed chain lands the operator on a next action, never a bare blocker list (the `scope-out-refusal-fallback` dead-end). The convergence `--step N` recommendation end is copy-paste-runnable; the refuse end gives the command form whose seed the operator authors before running. (3) **The executor does *not* emit a single-step forward-seed on the inbound-dependent refusal**, even though seed emission is deterministic and Claude-free: the correct carve for a step with a surviving dependent is the *whole dependent sub-tree* (the Deferred multi-step carve), so a single-step seed would carve the wrong region and mislabel the dependent as already-replanned — refuse and redirect to re-seed instead. The asymmetry is therefore **accepted and bounded**: occasional recommend-then-refuse-then-reseed is the deliberate price of not gating recommendation on information the recommender structurally lacks, and the multi-step carve that would widen the executor's reach to match the recommender's trigger is Deferred. (fixes `trigger-reach-asymmetry`, `scope-out-refusal-fallback`)

## Out of scope

- A new split/merge algorithm for the **step** altitude — reuse `split_step` / `merge_steps`.
- **Multi-step / multi-region carve** — Deferred; this executor is single-step (`--step N`); non-single-step evidence stays on the structural re-seed path, while only a defensive empty `FORK_SCOPE_OUT.command` renders prose-only.
- **Auto-mutating structure without explicit apply authorization** — every actuating path requires `--apply` plus either interactive confirm or `-y/--yes`; default recommends only, spends no Claude.
- A **BACKLOG.md writer** or an **in-plan `DEFERRED`** disposition — the carved part is a forward-seed (settled in the vocabulary plan).
- The **advisory arms themselves** — those ship in `structural-remedy-vocabulary`.

## Risks

- **Silent graph corruption** — a dropped step's id is reused by renumber with no validation crash. Mitigation: the inbound-dependent refusal + explicit `depends_on` repair (decision 3); test a surviving step depending on the carved step.
- **Run-state overclaim** — carrying live status would falsely claim a resumable in-progress step. Mitigation: carry as done-context prose, not a live-status round-trip (decision 1); the AC tests assert prose content + re-plan accounting, not a non-existent field.
- **Partial on-disk state** — an in-process apply failure mid-narrow could leave inconsistent frontmatter/detail files. Mitigation: dry-run-preview-then-apply + rollback (decision 6) is an **in-memory** journal that owns downstream detail renames/archives explicitly (or snapshot/restores any helper side effects) and unwinds only on an in-process **exception**, not a hard crash; a real process crash (SIGKILL/power loss) between the detail-file renames and the final non-atomic `write_plan` runs no rollback and can leave renamed detail files under a stale plan. That crash window is **hand-recoverable, not crash-atomic** — the forward-seed is already on disk (seed-first ordering), so the operator re-runs scope-out (or cleans up the renamed detail files) from the harmless orphan seed; nothing recovers it automatically.
- **Lost run cursor** — the narrowed plan could have no CURRENT to resume from. Mitigation: re-establish CURRENT in the narrowed plan (decision 5).
- **Doc double-write** — this plan and the vocabulary plan both touch RUNBOOK/CLAUDE docs. Mitigation: sequence so a watched-file drift guard does not halt mid-run.

## Testing

## Acceptance criteria

- `plan-tool scope-out <plan> --step N --apply` plus interactive confirm, or `plan-tool scope-out <plan> --step N --apply -y`, on a safe plan emits a `create --from-existing` forward-seed carrying the carved step detail/frontmatter as re-plan scope plus done-context prose for status/status_note and upstream context that marks DONE dependencies as assumed done and non-DONE dependencies as explicit external prerequisites, then narrows the plan — seed-first, never dropping the carved work.
- The emitted `plan-seeds/<plan>-carved-<slug>.md` is read and accepted by `create --from-existing`'s wiring without error; an integration test feeds it back with `create`'s Claude invoker stubbed (no real decomposition) and asserts that narrower deterministic guarantee — the seed file is ingested without raising — rather than implying the deterministic pre-Claude path validates the carved-scope seed shape.
- The carved step's run state is captured as narrative prose (status + status_note rendered as narrative) — not a claimed live-status round-trip, and not refused or silently discarded. A non-DONE (in-progress/CURRENT) carved step's status renders as attempted/partial context to account for, kept distinct from the "already implemented — do not re-plan" done-context framing reserved for genuinely-complete context, and its detail body stays in re-plan scope; an AC test asserts the prose content and that an IN_PROGRESS carved step's body remains re-plan scope (not mislabeled complete-and-skip), not a non-existent `progress` field.
- The narrow refuses non-canonical step numbering before preview/apply and writes nothing; it repairs `depends_on`: a surviving step that depends on the carved step causes a refusal (recommend-only), never a silent id-reuse; the carved step's own detail file is resolved from `Step.detail` first with canonical fallback and archived; a carved step whose `detail:` pointer is set but whose file is absent emits a missing-detail warning in the seed (distinct from the never-detailed note) and is a clean no-op archive, never an apply failure; a CURRENT cursor is re-established; an all-DONE no-cursor narrowed plan is marked `completed`.
- A carved step that is the sole implementer of a plan-level `features:` tag has that tag carried into the seed as re-plan scope (so the re-planned successor re-registers it) **and** pruned from the narrowed plan's `features:` registry, leaving no dangling registered-but-unimplemented tag; an AC test asserts both halves (seed carry + registry prune) — guards the step→feature ownership invariant the *Carved step's `features:` tags* decision exists to preserve.
- Carving a non-committed step does not resurrect parked work as committed: `render_carved_seed` notes the carved step's `scope` so a `deferred`/`wont_do` carve renders with an explicit disposition note rather than as plain committed re-plan scope; an AC test asserts a `wont_do` carved step's seed carries that disposition note and a `committed` carved step does not — guards `carved-step-scope-disposition`.
- The narrow is atomic against in-process apply **exceptions** (dry-run preview + in-memory apply-or-rollback); a real process crash mid-apply is **not** crash-atomic and is **hand-recoverable** from the already-on-disk forward-seed (seed-first ordering), not recovered automatically.
- Carving the plan's only surviving step — or the last committed survivor while only parked (`deferred`/`wont_do`) steps remain, so no committed-empty narrowed plan is produced — is refused (`empty-plan`) with a re-seed hint; the default / unattended without `-y` / unsafe / non-TTY without `-y` / declined paths recommend only, spend no Claude, and mutate nothing — a frozen `EscalateResult`-style value where only the returned `applied` outcome mutates. A post-seed `apply_narrow` exception returns no result, leaves the orphan seed on disk, and relies on `apply_narrow` rollback for plan/detail changes.
- The `unsafe` refusal (like `empty-plan`) is not a dead end: its message redirects the operator to the structural re-seed / Deferred multi-step sub-tree path (`plan-tool create --from-existing`), the path the plan body names as where the refused case "stays" — so the common convergence-recommended case (a spinning CURRENT step with a surviving inbound dependent, which carves as `unsafe`) lands on a next action, not a bare blocker list.
- `plan-tool convergence` renders the runnable `plan-tool scope-out … --step N` only when the localized fork resolves a single step; non-single-step evidence remains the structural `plan-tool create --from-existing <seed.md>` re-seed path, while only a defensive empty `FORK_SCOPE_OUT.command` renders prose-only — never a `--step` line with no resolvable id. The printed line is framed as a preview the executor may refuse (the step-3 safety gate, not `convergence`, decides carvability), so a resolved-but-uncarvable step is never presented as a guaranteed carve; convergence frames the line only as a preview that may return `unsafe` and does not itself name the re-seed path — the `plan-tool create --from-existing` pointer for the refused case is owned by the executor's `unsafe`/`empty-plan` message, not the convergence render.

## Deferred

- **Multi-step / multi-region carve** — this executor is single-step (`--step N`); non-single-step evidence remains `FORK_STRUCTURAL` with the re-seed command, while only a defensive empty `FORK_SCOPE_OUT.command` falls back to prose-only. Deferred because resolving a multi-region carve (e.g. carving a whole dependent sub-tree together) requires handling inbound dependents that are themselves carved, beyond this plan's single-step scope.
