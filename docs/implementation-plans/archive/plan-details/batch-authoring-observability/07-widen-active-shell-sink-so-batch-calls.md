# Step 7 — Widen the shared runner's observability hook so batch calls get spawn/stream/progress/stall/termination, and redact tool-input summaries for real

## Summary

Two things land together. First, `plan_tool/backend_runner.py:run_streaming_once`'s `run_logger` parameter, today a plain `Optional[RunLogWriter]` the pump/heartbeat closures call directly, widens into a small observer contract covering all five in-flight signals — spawn, stream-event, progress, stall, termination — plus a sixth, interrupt, that only a caller-built observer provides; a bare `RunLogWriter`/`None` (what `run`'s `shell_invoker` still passes, unedited) keeps working via an internal fallback that adds spawn/termination for free but not interrupt. `plan_tool/shell.py:claude_invoke` becomes the first caller to build the fuller kind, from the writer step 5 already exposes through `get_active_run_logger()`, and flips `redaction_ready` to `True` now that `plan_tool/backend.py:_summarize_tool_input` does real redact-then-truncate scrubbing instead of a blank suppression. Because the runner now emits `backend_spawn`/`backend_termination` itself, using the precise seven-value termination reason step 4 tracks, `claude_invoke`'s own coarser step 5/6 bracket around the same call is retired to avoid emitting both. `roadmap.py` and `cli/review_cmd.py`'s existing audit/reconcile calls pick up the richer signal automatically, with no edit to either file. Green when a batch call with a bound writer produces the same five-plus-one signal `run` already gets, a bad observer callback can't kill the pump/heartbeat threads or the silence kill, and `-v` batch output shows a genuinely redacted summary instead of `[OMITTED]`.

## Why

As of step 6, `claude_invoke`'s `_run_once_seam` calls `backend_runner.run_streaming_once(...)` but passes no `run_logger` at all — so every one of `claude_invoke`'s seven callers (`roadmap`, `create`, `review`, `detail`, `jira`, `lessons`, `annotate`) gets the silence kill and configured-timeout protection, but none of the in-flight signal `run` has had since the runner existed: no `claude_stream_event` per tool use, no `claude_call_progress` heartbeat, no `claude_call_stall_suspected` marker. For `roadmap` — the plan's named initial rollout target — a stage call that runs for minutes looks identical in the JSONL to one that's silently wedged until the 900-second silence kill fires, which is the exact ambiguity this whole plan exists to close.

Separately, nothing today records *why* a child process ended for any caller with the precision `plan_tool/backend_runner.py:get_last_termination_reason()` (step 4) already computes internally. `claude_invoke`'s own step 5/6 bracket in `shell.py` approximates this with a four-branch local classifier (`_classify_batch_termination_reason`) built before `spawn_failure`/`operator_interrupt` were reachable batch outcomes — step 6 named this as a known precision gap it left unresolved. Once the runner can call an observer directly, it has the exact answer already tracked; keeping both the runner's own bracket and `shell.py`'s external one would double-emit `backend_spawn`/`backend_termination` for every batch attempt, so this step has to resolve, not just note, the gap step 6 flagged.

Finally, step 6 made `-v`-verbosity batch output print the literal `[OMITTED]` for every tool-use summary as a deliberate fail-closed stopgap — safe, but useless to an operator watching a long `roadmap` stage. `plan_tool/backend.py:_summarize_tool_input` still returns whatever `Bash`'s `command` or `Edit`'s `file_path` field contains verbatim, truncated but not scrubbed; flipping `redaction_ready` back to `True` without first building the real redaction rule would leak credentials embedded in a tool argument to the terminal and the run log the moment this step lands.

## Implementation

### The observer contract, and the parameter it widens

`run_streaming_once`'s `run_logger` parameter keeps its name — `launcher.py`'s wrapper and every existing test that passes a bare `RunLogWriter`/`None` keeps compiling with no edits — but its accepted shape widens from "a `RunLogWriter`" to "a `RunLogWriter`, or an object providing the same handful of observer methods." One way to shape this, modeled directly on `plan_tool/progress.py:SupportsNotice`/`_ClaudeCallStartSink` (a structural `Protocol` kept specifically so a lower module stays decoupled from a concrete writer type and tests can pass a recording fake with no subclassing): define a small `Protocol` in `plan_tool/run_log.py` — call it, say, `RunnerObserver` — with methods roughly `on_spawn(phase, attempt, backend, transport, child_pid, effective_timeout_ms, prompt_bytes)`, `on_stream_event(phase, attempt, **event_kwargs)`, `on_progress(phase, attempt, elapsed_ms, silent_ms, last_tool, last_activity_kind)`, `on_stall(phase, attempt, silent_ms, threshold_ms, last_tool)`, `on_termination(phase, attempt, backend, reason, duration_ms, signal_or_timeout, silent_ms)`, and `on_interrupted(phase, attempt, source)`. The spawn and termination signatures carry step 5's full field sets — this bracket is the one production emitter that survives the plan, and it is the only place the four spawn-side fields and two termination-side fields are actually known: the runner computes `transport` as a safe descriptor from the transport parameter it was handed (never the `PromptTransport` object itself), `child_pid` from `proc.pid` once `Popen()` returns, `effective_timeout_ms` from `enforce_configured_timeout`/`configured_timeout_s` and the effective silence threshold under Architecture's earlier-of-the-two precedence rule (never `None` from this bracket — every spawn has at least the silence threshold), `prompt_bytes` from the encoded prompt length, `signal_or_timeout` from which kill mechanism fired (when one did), and `silent_ms` from the monitor's own silence clock at termination. `RunLogWriter` need not subclass it — a `Protocol` is satisfied structurally, and `RunLogWriter` already has all six matching methods once step 5 lands (`claude_stream_event`, `claude_call_progress`, `claude_call_stall_suspected`, `backend_spawn`, `backend_termination`, `run_interrupted`), just under different names. Whether `backend_runner.py` adapts a raw `RunLogWriter`'s differently-named methods into the observer shape via a small internal wrapper, or the `Protocol`'s method names are chosen to match `RunLogWriter`'s existing ones directly (so a `RunLogWriter` satisfies it with zero adaptation), is the implementer's call — either closes the gap; name and exact method signatures are not fixed by this step, only that the six capabilities exist somewhere reachable from `backend_runner.py` without a new import (`run_log.py` is already an allowed import).

**Backward compatibility is the runner's own job, not the caller's.** When `run_logger` is a bare `RunLogWriter` (what `run`'s `shell_invoker` passes, unedited by this step) or `None`, `run_streaming_once` resolves it internally into a small default observer that reuses `RunLogWriter`'s existing methods for spawn and termination but has no interrupt handling — a `KeyboardInterrupt` caught during `proc.wait()`/`Popen()` still classifies `operator_interrupt` and calls the termination hook with that reason (step 4's classification is untouched), but no `run_interrupted` fires for this fallback path. `claude_invoke` is the one caller in this step that builds and passes a fuller observer with interrupt handling included — see below. A later step (8, per the plan's own step-6 Input note) is expected to give `run` the same interrupt richness through `run_step`'s own adapter; this step does not build that adapter and does not touch `plan_tool/launcher.py`.

**Every observer call the runner makes is wrapped so a bad callback can't take down the pump or heartbeat thread, or disable the silence kill.** The stdout pump already wraps its `run_logger.claude_stream_event(...)` call in `except (RunLogLineTooLarge, OSError)`, and the heartbeat wraps its progress/stall pair the same narrow way — both print one line to stderr and keep going rather than let a run-log write kill the thread. This step broadens that same pattern to every observer call this step adds (spawn, termination, interrupted) and widens the exception clause from the two known `RunLogWriter` failure modes to a general `except Exception`, because the object being called is no longer only `RunLogWriter` — it can be a caller-authored observer (like `claude_invoke`'s), and a bug there must not be able to defeat the silence kill or leave the pump thread dead mid-response. `except Exception`, not `except BaseException`, is deliberate and safe here: the pump and heartbeat run on background threads, and `KeyboardInterrupt` only ever lands on the main thread (the same fact steps 3/4's own `except BaseException` blocks around `Popen()`/`proc.wait()` rely on) — it structurally cannot originate from inside one of these callback calls. On catch, print one line naming which callback and exception type failed and continue; do not write to the JSONL, since the run-log sink is plausibly the thing that just failed.

**Where the new calls land.** Spawn fires once `Popen()` returns successfully — after step 4's own `Popen()` try/except, on the success path only, before the pump/heartbeat threads start; firing it earlier would pair a "spawned" event with a call that never actually produced a child on the `spawn_failure` path. Termination fires at every one of the function's existing exit points — the normal end (before the final `return`), and both of step 4's `except` arms (Popen's and `proc.wait()`'s), immediately before each re-raises — reading `get_last_termination_reason()` at that same point, which step 4's own classification already sets first. On the `proc.wait()` exception arm specifically, when the caught exception is a `KeyboardInterrupt`, call the observer's interrupt hook with `source="proc_wait"` in addition to (not instead of) the termination call — mirroring step 5's `backend_recovery_wait`/`run_interrupted` pairing, where the termination reason and the interrupt marker are two separate, complementary facts about the same event.

### `claude_invoke`'s wiring

Inside `claude_invoke`, read `get_active_run_logger()` once (not once per retry attempt — `run_streaming_once`'s own `phase=`/`attempt=` parameters, already passed per attempt since step 6, are what make the events per-attempt-correct; the observer object itself can be built once and reused across every attempt `_run_once_seam` drives). When the writer is `None`, pass `None` through unchanged — behavior stays exactly what step 6 shipped. When it's a real writer, build the fuller observer (spawn, stream-event, progress, stall, termination, *and* interrupted — the shape `run`'s call sites don't get until step 8) and pass that as `run_logger=` to `backend_runner.run_streaming_once`, alongside flipping `redaction_ready` from `False` to `True`.

**Retire, don't adapt, `_run_once_seam`'s own `backend_spawn`/`backend_termination` bracket.** With the runner now emitting both events itself — using the precise reason `get_last_termination_reason()` tracks, not the coarser four-branch guess `_classify_batch_termination_reason` made before `spawn_failure`/`operator_interrupt` were reachable — leaving both brackets in place double-emits one `backend_spawn` and one `backend_termination` row per batch attempt. Delete the calls step 5 added and step 6 adapted, and delete `_classify_batch_termination_reason` itself, which has no other caller once they're gone. This is a real behavior change from step 6's landed shape, not a revert: the replacement source is more precise, not merely relocated.

### `plan_tool/backend.py`: redact-then-truncate

Rewrite `_summarize_tool_input` so every one of its five return sites — the non-dict `inp` catch-all, the `Edit`/`Write`/`Read`/`NotebookEdit` → `file_path` branch, the `Bash` → `command` branch, the `Grep`/`Glob` → `pattern [in path]` branch, and the unmatched-`tool_name` JSON-preview catch-all — runs its scrubbing pass on the branch's own untruncated candidate string *before* the existing `[:_TOOL_INPUT_SUMMARY_CAP]` slice, not after. Truncating first and redacting second would leak a secret's leading bytes for anything long enough to straddle the 200-character cutoff, which is the one failure mode this rule exists to close.

The scrub replaces two shapes with a fixed `[REDACTED]` placeholder, each occurrence independently:

- A known secret-prefix token: the existing `Authorization:`/`Bearer `-prefixed shapes `claude_errors.py` already recognizes, plus a bare token starting with `sk-`, `ghp_`, `gho_`, `AKIA`, or `xox`.
- Any other contiguous run of 20+ alphanumeric/`-`/`_` characters containing at least two of the three character classes (uppercase, lowercase, digit) — a length/character-class heuristic, not real entropy scoring.

Over-redaction (a commit SHA, hash, or UUID losing its value in a diagnostic line) is accepted; under-redaction is not, since this pattern list is the plan's actual enforcement point for the credential guarantee here, not a best-effort nicety. No existing pattern-matching utility in this codebase does this today; write it fresh rather than searching for something to reuse.

**Suppress, don't redact, the two remaining producers.** `_codex_tool_use_summary` (called from `_codex_parse_stream_line`'s `item.started` branch) and `_cursor_tool_use_summary` (called from `_cursor_parse_stream_line`'s `tool_call`/`subtype == "started"` branch) never call `_summarize_tool_input` and hand back their own pre-formatted `(tool_name, summary)` pair. Real redaction for these two is step 10's declared work, extending the same rule to a differently-shaped input rather than reinventing it. Until then, replace whatever these two return with the literal string `"[OMITTED]"` at their call sites before it's placed into the `tool_input_summary` field of the `tool_use` event dict — the same suppression shape step 6 already used for the `redaction_ready=False` case, now scoped permanently to these two backends' native tool-call producers rather than to every batch call. `_cursor_parse_assistant_blocks`'s *other* `tool_use` branch (the claude-shaped blocks cursor also emits, going through `_summarize_tool_input` directly) gets real redaction from this step, same as claude's — only cursor's own native `tool_call` shape is suppressed.

### Zero-diff callers

`roadmap.py:shell_roadmap_invoker` delegates straight to `claude_invoke`, and stage execution (the `bind_shell_sink(phase=phase, attempt=attempt)` call bracketing `invoker(prompt)`) already sets `_active_run_logger` for that scope via step 5's extension of `bind_shell_sink`. `cli/review_cmd.py:_audit_sink` does the same thing through the identical `bind_shell_sink` call for every audit handler (`cmd_review`, `cmd_review_all`, `cmd_verify`). Neither module needs an edit: once `claude_invoke` builds an observer from whatever writer is currently bound, both automatically start producing the fuller signal for their existing claude calls — this is the "roll out by command class" behavior the plan's own Out of scope section already credits to the shared-runner mechanics, not something this step has to wire per caller. `apply_finding`'s own dispatch (in `review_actions.py`/`reconcile.py`'s walk paths) is a different call path that never binds `_active_run_logger`, per the plan's Out of scope — nothing here changes that.

## Acceptance criteria
