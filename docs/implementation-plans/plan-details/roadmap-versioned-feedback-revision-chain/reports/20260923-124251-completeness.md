- HIGH `[decision-settlement-evidence]` [confidence: limited]: Step 7 (`Gate enrolled decision settlement behind an atomic active-candidate confirmation`) replaces the current artifact-coupled evidence lookup with a ledger-item lookup but does not require the item’s submitted-against source and target fingerprint to match the accepted source being settled. Step 1 Implementation defines eligibility as:

```
it accepts only an `open` item whose submitted-against predecessor is the processing source and whose current target fingerprint exactly matches the target in that source.
```

Step 7 Implementation instead requires only an item id, a row target naming the decision, and nonblank request text. At HEAD, `plan_tool/roadmap_decision_settlement.py:build_decision_settlement_candidate` gets evidence from the current accepted artifact, so its feedback row cannot silently refer to an older target. The proposed ledger branch could settle a changed current decision using a stale ledger item, violating the target-provenance safety promised by steps 1 and 7. Sites: Architecture’s target-fingerprint rule; step 1 Implementation, Tests, and Acceptance criteria; step 7 Input, Implementation, Tests, and Acceptance criteria; `plan_tool/roadmap_decision_settlement.py:build_decision_settlement_candidate`; and `plan_tool/roadmap_decision_settlement_enrolled.py:run_enrolled_decision_settlement`.
  - Fix: Define enrolled settlement evidence as valid only when its ledger item still proves the selected decision target against the exact accepted source, and align the ledger branch, its receipt/currentness checks, and tests to that rule.
- HIGH `[settlement-confirmation-cli]` [confidence: limited]: Step 7 requires a two-call, bound confirmation handshake, but no step defines how the CLI can make the request and return its exact binding for a later response. Architecture promises:

```
A CLI or web frontend submits a separate affirmative or negative response; on affirmation the writer guard rechecks that exact pair and then atomically publishes the settlement and records the active candidate as stale-resolved.
```

At HEAD, `plan_tool/cli/roadmap_cmd.py:_decision_settlement_has_conflict` requires `--confirm-decision-settlement` on every settlement invocation, and `_cmd_roadmap_decision_settlement` passes that one value directly to `run_enrolled_decision_settlement`. Step 7 changes the runner but not the CLI; step 10 says to preserve settlement while its lifecycle conflict rule rejects confirmation companions; step 11 requires parser-grounded documentation without defining the request/response syntax. A CLI operator therefore has no specified way to request the durable binding first and submit it later. Sites: Architecture’s settlement handshake; step 7 Implementation, Tests, and Acceptance criteria; step 10 Input, Implementation, Tests, and Acceptance criteria; step 11 Implementation and Tests; `plan_tool/cli/roadmap_cmd.py:_decision_settlement_has_conflict`; `plan_tool/cli/roadmap_cmd.py:_cmd_roadmap_decision_settlement`; and `plan_tool/roadmap_decision_settlement_enrolled.py:run_enrolled_decision_settlement`.
  - Fix: Specify and test the CLI’s two-call settlement request and bound-response interface, while retaining the existing no-active-candidate settlement behavior and documenting the exact operator workflow.
- HIGH `[active-candidate-reentry]` [confidence: limited]: Step 5 (`Store batch responses with one root-and-active-candidate pointer...`) makes an unchanged active processing pair replay its stored candidate without a backend call, but the plan requires a selector-free ordinary run to batch from that active candidate whenever work exists. Since step 10 removes the selector and no request identity distinguishes retry from a new ordinary run, new eligible feedback or current derived context cannot reliably produce the promised superseding successor. Sites: Architecture; Testing; Acceptance criteria; step 5 Implementation, Tests, and Acceptance criteria; and step 10 Input and Implementation.


```text
Step 5 Tests: “`test_reentry_loads_the_current_active_candidate_without_backend_call` — asserts an unchanged current processing pair returns its stored active candidate and makes no model call.”
```
  - Fix: Define how selector-free proposal requests distinguish an idempotent retry from a new batch run, so active-candidate reentry replays only the original request while later eligible input can create a successor.
- MEDIUM `[migration-processing-fence]` [confidence: limited]: Step 1 (`Define the canonical mutable feedback ledger, target fingerprints, and eligibility rules`) promises that steps 3, 5, 6, 8, and 9 all use `check_ledger_processing_ready`, but steps 8 (`Bind candidate questions, answers, rejection, and discard resolution to the exact active-candidate batch`) and 9 (`Promote only the exact active candidate for the current root and keep promotion from reading or rewriting the live ledger`) explicitly decline an independent migration check. This contradicts the Architecture and acceptance guarantee that ledger-based candidate, review, and promotion routes return `migration-required` for migration-pending roadmaps, leaving those routes with different refusal behavior. Sites: Architecture legacy-migration paragraph; acceptance criterion “New feedback-free enrollment is ledger-native…”; step 1 Implementation and acceptance criteria; step 8 Input “No independent migration check”; and step 9 Input “No independent migration check.”
  - Fix: Choose and state one migration-required boundary for every ledger lifecycle route, then align the shared readiness contract and steps 8–9 refusal behavior to it.
