## Conceptual completeness — reported, not auto-applied

Coverage gaps in the plan's own ideas are reported for visibility in this bare-plan audit. Apply actions are withheld until a complete detail bundle exists, so these findings are informational for now.

- HIGH `[grounding-floor-verdicts]`: step 4 (`Add grounding-floor guard`) says low grounding should “suppress confident IMPLEMENTED/PARTIAL verdicts,” while `plan_tool.annotate:AnnotationStatus` and `plan_tool.annotate_render:render_create_seed` currently drive seed scope directly from section status. The plan never defines whether low-grounding IMPLEMENTED/PARTIAL sections become low-confidence statuses, `NEEDS-REVIEW`, excluded seed entries, or carried work, so the guard could either over-claim completion or create false carryover work.
- MEDIUM `[needs-review-rollup]`: P1 introduces `NEEDS-REVIEW`, but step 8 (`Add list --status rollup`) and the acceptance criterion for `plan-tool list --status` list only IMPLEMENTED/PARTIAL/NOT-IMPLEMENTED counts. A stale backlog sweep could produce review-required sections that disappear from the rollup, undermining the operator status view.
- MEDIUM `[batch-exit-status]`: step 7 (`Add batch form`) requires continuing past per-file failures and the Testing section mentions “aggregate exit status,” but Architecture and Acceptance criteria never define the exit-code policy for all-success, partial-success, zero-match, and total-failure batch runs. Scripts cannot reliably drain a backlog unattended without knowing whether a partially failed batch exits 0, 1, or 2.
- MEDIUM `[jira-lint-input]`: step 9 (`Extend jira AC lint ... + add jira --lint flag`) names `jira --lint`, but the current `plan_tool.cli.jira_cmd:cmd_jira` treats `jira` as a plan-generation command whose positional `name` is normally required. The plan does not say whether `--lint` validates the generated stories in the current run, an existing `jira-stories.md/json` artifact, an explicit `--output` path, or stdin.
- MEDIUM `[last-annotated-date]`: step 8 (`Add list --status rollup`) promises “last annotated date” from cached `*.annotated.md`, but `plan_tool.annotate_render:render_annotated_report` currently records `source`, `repo_root`, and `grounded_files` with no annotation timestamp. The plan does not say whether `list --status` should trust file mtime or a report metadata field, so the date can be inconsistent across copies, checkouts, and archive moves.
- MEDIUM `[batch-output-collisions]`: step 7 (`Add batch form`) defines `annotate <dir-or-glob> --seed-dir/--report-dir`, but does not define what happens when two matched plans from different directories share the same stem and would derive the same seed/report filenames. An unattended batch could overwrite artifacts or fail mid-sweep without a planned policy.
- MEDIUM `[needs-review-seed-exclusion]`: step 3 (`Degrade gracefully on a contradictory section`) and Architecture say `NEEDS-REVIEW` sections are excluded from the carryover seed, but Acceptance criteria only require the report/seed to be written and the section marked `NEEDS-REVIEW`. The core unattended-safety behavior is not locked by a criterion.
- MEDIUM `[batch-directory-scope]`: step 7 (`Add batch form`) defines `annotate <dir-or-glob>` expansion but never says whether directory/glob matches exclude `archive/`, `plan-details/`, generated `*.annotated.md`, and seed files. A backlog sweep could reprocess archived plans, detail specs, or generated artifacts as fresh source plans.
