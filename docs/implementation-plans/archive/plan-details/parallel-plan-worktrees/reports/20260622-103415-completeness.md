### Correctness (run these first)

_Verified: file paths resolve, dependencies are coherent, and the plan's stated concepts are internally sound._

- MEDIUM `[start-point-ref-resolvability]`: Step 1 (`worktree_add`/`clone_repo` primitives) resolves `start_point` to "the resolved default branch's HEAD when `default_branch` resolves," but `gitcommit.py:default_branch` returns the *bare name* (it strips the `origin/` prefix off `refs/remotes/origin/HEAD`, yielding e.g. `main`). A bare `main` resolves as a worktree-add start-point only when a *local* `refs/heads/main` exists; in a clone that checked out a different branch (git creates a local branch only for the checked-out branch, others stay `origin/*` remote-tracking) the name resolves to nothing and `git worktree add -b plan/x <path> main` — and `clone_repo`'s `git -C <path> switch -c <branch> main` — fails cryptically. The plan reasons carefully about the `None`→`HEAD` fallback but assumes the resolved name is a usable committish.
- INFO: INFO: [clone-start-point-in-clone] `clone_repo` (step 1) resolves `start_point` against the **source** repo (default-branch HEAD, else source `HEAD`) but then runs `git -C <clone> switch -c <branch> <start_point>` **inside the clone**, whose refs are independent. When `default_branch` resolves to a name like `main` the clone has a local `main` and it works; when it falls back to the literal `HEAD`, the clone's HEAD is whatever `git clone` checked out, which matches the source HEAD only by `git clone`'s default-branch behavior — an implicit coupling the plan never states.
- MEDIUM `[prune-foreign-worktree-discrimination]`: `worktree prune` claims to find *deregistered* plans' worktrees "via git's own registry (`git worktree list --porcelain`)," but that registry lists **every** git worktree of the repo, including ones a user created by hand. Once a plan is deregistered its slug is gone from the manifest, so prune has no slug→path mapping to confirm a registered worktree is one plan-tool provisioned — yet prune is destructive. The plan never states the discrimination rule (e.g. "only worktrees physically under `worktree_base` are prune candidates"), so as written prune could target an operator's unrelated worktree.
- MEDIUM `[worktree-base-inside-repo-guard]`: Architecture mandates the worktree base live "never inside it [the repo] — a worktree inside the main working tree pollutes the tree and confuses git," but makes `worktree_base` overridable via `.plan-tool/config.json`/flag with no step validating the override. The default is safe; a misconfigured override placing the base inside the working tree reintroduces exactly the pollution the design forbids, with no guard in step 2 (path/config resolution) or step 3 (`add`).
