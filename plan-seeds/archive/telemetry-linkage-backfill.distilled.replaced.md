## Overview

Phase 2 of the decision/outcome telemetry effort (BACKLOG #72) fills the telemetry producers so new `DecisionEvent`s actually carry the join keys a phase-3 resolver will correlate on. Phase 1 gave the base event a *place* to carry `decision_id`/`run_id`/`plan_fingerprint`/`code_fingerprint`/`anchor`; this plan makes producers *populate* them. Two coordinated parts: **Part A** threads caller-computed fingerprints into six existing recorder call sites, and **Part B** adds three new per-kind recorders (drift-gate, `apply_finding` verdicts, escalate-to-split outcomes) in `telemetry.py` plus one call site each. Everything is purely additive and best-effort: telemetry is observational and must never change a command's control flow, exit code, or output. It ships **no** new consumer — the resolver/analysis surface and outcome-verdict derivation remain phase 3.

## Problem statement

The spike's empirical finding over 347 real events: the recorders that carry the good join keys (fingerprints, outcome actions) are exactly the ones that haven't fired, and 81% of events are ownerless prompt-budget checks — no post-hoc join logic recovers linkage the events don't carry. Phase 1 gave the event a place to carry `plan_fingerprint`/`code_fingerprint`/`anchor`, but every authoring-time recorder call site verified at HEAD still passes nothing for them (relies on the `""`/`{}` defaults), so new events remain unjoinable on the renumber-proof fingerprint anchor. And three of the highest-leverage heuristic decisions the backlog names — the reconcile/`--refresh` drift-gate, per-finding `apply_finding` verdicts, and escalate-to-split outcomes — emit no decision event at all. Until the producers carry the keys, phase 3's resolver has nothing to correlate and its smoke test (spike §7) cannot run.

## Architecture

**Part A — backfill fingerprints onto existing recorders' call sites.** The recorders already accept `plan_fingerprint`/`code_fingerprint` (defaulted); their callers just don't pass them. Thread the caller-computed digests (`review_persistence.compute_plan_fingerprint`, `fingerprint.compute_code_fingerprint`) into each site that has a plan in hand: `plan_tool/create.py` — `record_create_granularity_assessment` (~3504) and the `record_create_step_outcome` wrapper `_record_step_outcome` (~3539); `plan_tool/review.py` — `record_code_reveals_split` (~3457, reconcile lane); `plan_tool/cli/completeness_phases.py` — `record_granularity` (~664) and `record_audit_coverage` (~816) (both modules already import the compute helpers); `plan_tool/cli/convergence_cmd.py` — `record_convergence` (~119). `record_prompt_budget` stays fingerprint-less by design (ownerless pre-send backstop, no plan context, spike §3). `run_id` needs no backfill: it auto-flows from the `telemetry`-owned `_active_run_id` ContextVar, which phase 1 binds only at the two `run` entrypoints; these are authoring-time commands (`create`/`completeness`/`convergence`), not runs, so `run_id=""` is correct. `anchor` is carried only where a decision is about one specific finding — no Part-A site is (they're plan-/step-wide), so Part A adds fingerprints, not anchors.

**Part B — add recorders + call sites for the three un-wired decision families.** New per-kind convenience recorders in `telemetry.py`, each a thin wrapper over `record_decision` taking primitives (so the module stays a stdlib-only leaf), each with a new `kind`/`decision` literal exported as a module constant (the contract downstream aggregation keys on), plus one call site each: (1) **reconcile / `--refresh` drift-gate** (`plan_tool/refresh.py:refresh_plan`) — record the gate verdict per refresh (`no-baseline` first stamp / `no-drift` fast no-op / `drifted` reconcile ran), the drifted-file count, and findings count; `refresh_plan` already computes `current_code_fp = compute_code_fingerprint(...)` and imports `compute_plan_fingerprint`, so both fingerprints are in hand — this decision is about code-vs-plan drift, so it carries `code_fingerprint`. (2) **`apply_finding` verdicts** (`plan_tool/launcher.py`, where `parse_apply_verdict`'s result is consumed) — record the per-finding verdict (`APPLIED`/`NOT-APPLICABLE`/`BLOCKED`/`BLOCKED-STRUCTURAL`) with the finding `anchor` slug + its `step_id` (folded into `decision_id` so per-step verdicts sharing a second-precision `ts` don't collide) + `plan_fingerprint`. (3) **escalate-to-split outcomes** (`plan_tool/launcher.py:escalate_to_split`, or its three callers on the frozen `EscalateResult`) — record `EscalateResult.outcome` (`applied`/`recommended`/`unsafe`/`proposal-unusable`/`step-missing`) with the target `step_id` + `plan_fingerprint`.

**Ground rules.** (1) `telemetry.py` stays a stdlib-only leaf — new recorders take primitives (verdict strings, ids, counts, already-computed fingerprint strings/dicts) exactly as existing wrappers do; callers import and run the compute helpers, the leaf never imports `review_persistence`/`fingerprint`. (2) Best-effort and control-flow-neutral everywhere — `record_decision` already swallows errors; each new call site additionally wraps its fingerprint-compute + record in a local `try/except` that returns/continues on failure (mirroring create.py's `_record_*` helpers), so a fingerprint error never fails an apply/refresh/escalate; no new non-zero exit path, no new operator-visible stdout. (3) Carry `plan_fingerprint` on every backfilled/new site (short digest, renumber-proof anchor); carry the full `code_fingerprint` path→hash map only where the decision is *about* code state (the drift-gate, and Part-A recorders that already have it cheaply) — the per-finding apply-verdict site carries `plan_fingerprint` only, because dozens of per-finding lines each carrying a ~45 KB map is wasteful volume (phase 1's `_MAX_LINE_BYTES` lesson); make this per-site choice explicit with the line-volume rationale. (4) Hoist fingerprint computation above per-item loops — `apply_finding` verdicts fire once per finding and escalate can fire per structural finding, and `compute_plan_fingerprint` reads the plan file while `compute_code_fingerprint` hashes the footprint; compute the plan-state fingerprint once per apply/reconcile pass and reuse it across per-finding records, never recomputing inside the loop.

## Out of scope

- **The resolver / `plan-tool telemetry` analysis-and-recommend surface** — no consumer of the keys ships here; nothing reads the backfilled fingerprints (phase 3).
- **Deriving outcome verdicts** (`acted-on`/`no-op`/`reverted`/`still-open`) — phase 3 correlates decision→outcome; phase 2 only makes the keys exist.
- **Backfilling historical events** — existing events stay as-is; only new events carry the enriched producers. No migration of old data.
- **A `TELEMETRY_SCHEMA_VERSION` bump** — phase 2 adds no base field; the tolerant reader already accepts new `kind` values. Do not bump.
- **Binding `run_id` at non-run commands** — `run_id` means "the run this happened in"; create/detail/completeness/convergence are not runs, so leaving `run_id=""` there is correct, not a gap.
- **Changing `telemetry.py`'s leaf status** — it stays stdlib-only.

## Risks

- **Leaf-purity regression** — the seductive wrong move is importing a fingerprint producer into `telemetry.py`. Severity: high (breaks the module's contract). Mitigation: fingerprints are caller-supplied; keep the stdlib-only import test green (`grep -E '^(from|import) plan_tool' plan_tool/telemetry.py` stays empty).
- **Control-flow / exit-code perturbation** — a recorder or fingerprint-compute throwing at the apply/refresh/escalate site must not fail that operation. Severity: high. Mitigation: best-effort try/except at every new site plus the existing swallow in `record_decision`; a test that a raising `compute_*`/record leaves the host command's rc and output unchanged.
- **Line-volume / cost at hot sites** — per-finding apply verdicts × a big `code_fingerprint` map would bloat the log and re-hash the footprint each finding. Severity: medium. Mitigation: `plan_fingerprint`-only on the per-finding site + hoist the compute above the loop (design decisions 3–4).
- **Silent schema drift** — DATA_CONTRACT + drift guard must move with the new `kind` families' context shapes. Severity: medium. Mitigation: update `DATA_CONTRACT.md` and `tests/test_data_contract.py` together.
- **`decision_id` collision on per-step verdicts** — many `apply_finding` verdicts can share a second-precision `ts`. Severity: medium. Mitigation: fold `step_id` into the hash (as `create-step-outcome` already does) so distinct per-step verdicts stay distinguishable.

## Testing

Follow the project's unit-first convention (mirror `plan_tool/X.py` → `tests/test_X.py`; add `@pytest.mark.integration` only for cross-module CLI/orchestrator drives). Coverage the plan must land:
- **Part A backfill** — tests assert the fingerprints now land on recorded events at each of the six call sites (create ×2, code-reveals-split, granularity[completeness], audit-coverage, convergence), and that `record_prompt_budget` stays fingerprint-less.
- **Drift-gate recorder** — each of `no-baseline` / `no-drift` / `drifted` records the right verdict + both fingerprints + drifted-file/findings counts.
- **Apply-verdict recorder** — tests over the four verdict tokens (`APPLIED`/`NOT-APPLICABLE`/`BLOCKED`/`BLOCKED-STRUCTURAL`) asserting anchor + step_id + `plan_fingerprint` land and no full `code_fingerprint` map is carried; a test that distinct per-step verdicts sharing a `ts` stay distinguishable via the folded `step_id`.
- **Escalate-to-split recorder** — tests over the five outcomes (`applied`/`recommended`/`unsafe`/`proposal-unusable`/`step-missing`) asserting outcome + step_id + `plan_fingerprint`.
- **Best-effort invariant** — a forced failure in `compute_*`/`record_*` leaves the host command's exit code and stdout unchanged (test-proven for at least the apply and refresh sites).
- **Leaf purity** — the stdlib-only import test for `telemetry.py` stays green.
- **Drift guard** — `tests/test_data_contract.py` stays green with the three new `kind` families documented.

## Acceptance criteria

- A newly recorded event at each of the six backfilled call sites (create ×2, code-reveals-split, granularity[completeness], audit-coverage, convergence) carries a non-empty `plan_fingerprint` (and `code_fingerprint` where the site already had it); `record_prompt_budget` stays fingerprint-less.
- Three new decision families record: a drift-gate verdict (`no-baseline`/`no-drift`/`drifted`) with both fingerprints + counts; a per-finding apply verdict (`APPLIED`/`NOT-APPLICABLE`/`BLOCKED`/`BLOCKED-STRUCTURAL`) with anchor + step_id + `plan_fingerprint`; and an escalate-to-split outcome (`applied`/`recommended`/`unsafe`/`proposal-unusable`/`step-missing`) with step_id + `plan_fingerprint`.
- Every new/changed call site is best-effort: a forced failure in `compute_*`/`record_*` leaves the host command's exit code and stdout unchanged (test-proven for at least the apply and refresh sites).
- `telemetry.py` imports nothing first-party (leaf test green); no `TELEMETRY_SCHEMA_VERSION` bump; the per-finding apply site carries no full `code_fingerprint` map; fingerprint compute is hoisted above per-finding loops.
- `DATA_CONTRACT.md` documents the three new `kind` families with the drift guard green; the change ships no resolver/analysis/read surface.
- **BACKLOG #72 is updated** in the plan's final step: phase-2 backfill + new sites marked shipped, phase 3 (resolver + `plan-tool telemetry` surface + outcome-verdict derivation) left as remaining scope, spike reference (`.tmp/72-telemetry-linkage.spike.md`) retained.
