# Per-aspect backend selection + short-rate-limit failover

Design for choosing a **different backend per aspect** of plan-tool processing,
and for **failing over** to another backend when the active one hits a
recoverable short rate limit instead of blocking until its retry window resets.

Status: **unimplemented proposal for aspect routing and automatic failover**.
The project-default and model-selection overlap is **superseded by Project
Model Selection** (2026-11-12): [the shipped contract](../BACKENDS.md#project-configuration)
uses `default_backend` and `backends.<name>.commands.<command>.model`, with
explicit invocation overrides. It does not add named tiers, aspect routing,
cooldown chains, or configuration writers. The proposed `default`, `aspects`,
and `failover` keys below remain inert. Existing explicit rate-limit recovery
(`--on-rate-limit switch` with a fallback backend) is a separate shipped feature.

The remaining sections describe proposed behavior, not the current contract.
Provenance: research pass, 2026-06-10.

> **Scope split.** This doc covers backend *selection/routing* — which backend
> runs which aspect, and failover. Its sibling
> [the pluggable-backend implementation plan covers backend *definition* —
> what a backend is and how it's declared/tuned. They share **one** per-project
> config file, `.plan-tool/backends.json`: this doc owns its `default`,
> `aspects`, and `failover` keys; the definition doc owns the `backends.<name>`
> per-backend overrides.

## Why

plan-tool drives one subprocess CLI (`claude` or `codex`) for every step of
processing. Today there is **one** process-wide active backend, chosen once in
`cli/app.py` (explicit `--backend` flag > recognized `--model` family >
`PLAN_TOOL_BACKEND` env > project `default_backend` > `claude`) and read everywhere via
`backend.get_active_backend()`. Two gaps:

1. **No per-aspect selection.** `docs/evidence/backend-recommendations.md` (generated by
   `plan-tool bench`) shows different backends win different *aspects* of
   processing — `implementation` and `reconcile` favor `codex`; `proposal`,
   `detail`, `apply` favor `claude`. There is no way to act on that: every
   aspect uses the single selected backend.
2. **No failover on recoverable short rate limits.** When a backend hits an
   ordinary short rate limit, the retry path may wait until its reset epoch and
   retry the **same** backend. If another backend is authenticated and idle,
   the run could continue on it instead of blocking for up to an hour. A
   confirmed monthly plan quota is terminal and remains outside automatic
   failover.

## Aspects

The "aspects" are exactly the 5 benchmark task families, which map 1:1 to
production entrypoints — all already decorated with `@spawn_cwd_from_repo_root`
(`backend.py:711`), the precedent for the per-aspect scoping decorator below:

| Aspect | Entrypoint | File | Recommended (current analysis) |
|---|---|---|---|
| `proposal` | `create_plan` | `create.py:4165` | claude |
| `detail` | `generate_detail` | `detail.py:1145` | claude |
| `reconcile` | `review_plan_full` | `review.py:3935` | codex |
| `implementation` | `run_step` (only `mode="run"`) | `launcher.py:1469` | codex |
| `apply` | `apply_finding` | `launcher.py:2094` | claude |

Operations outside these families (review-class run modes — check/optimize/
test/security/lint; jira) fall through to the global default backend.

## Design

### 1. Scope the active backend per call (`backend.py`)

Convert the `_active_backend` module global into a `ContextVar`, mirroring the
existing `_active_spawn_cwd` pattern (`backend.py:671`):

- `set_active_backend(...)` keeps setting the **default** (the ContextVar's
  base value), so existing callers and precedence are unchanged.
- Add `use_backend(backend) -> contextmanager` (parallel to `spawn_cwd`) that
  scopes the active backend for a block, save/restore via a token.
- `get_active_backend()` reads the ContextVar — every existing consumer
  (`shell.py`, `launcher.py`, `claude_errors.py`, `review.py`, `bench.py`) is
  untouched.

### 2. The backend plan (new module `plan_tool/backend_plan.py`)

A small process-wide object resolved once at CLI startup, mirroring how
`claude_errors.get/set_default_wait_on_rate_limit` is a process-wide setting
set by `cli.main`:

```python
@dataclass(frozen=True)
class BackendPlan:
    default: CliBackend                  # global selection (today's behavior)
    per_aspect: dict[str, CliBackend]    # aspect -> backend (subset of the 5)
    failover_enabled: bool
    failover_order: tuple[CliBackend, ...]   # chain to try on a short rate limit

    def for_aspect(self, aspect: str | None) -> CliBackend: ...
```

- `ASPECTS = ("proposal", "detail", "reconcile", "implementation", "apply")` —
  the canonical key set (validated on config load).
- `get_active_plan() / set_active_plan()` — module-level, set once by
  `cli.app.main`.
- Resolution per aspect, highest precedence first:
  1. `--backend-<aspect>` CLI flag
  2. `PLAN_TOOL_BACKEND_<ASPECT>` env
  3. `.plan-tool/backends.json` → `aspects[aspect]`
  4. global `--backend` flag
  5. global `PLAN_TOOL_BACKEND` env
  6. `.plan-tool/backends.json` → `default`
  7. `"claude"`

### 3. Shared per-project config `.plan-tool/backends.json`

Direct-edit-friendly JSON, loaded like `jira_config.py` / `locator.py`'s
`plans.json`, found at `<repo-root>/.plan-tool/backends.json`. This is the
**single shared** per-project backend config; this proposal would read `default`,
`aspects`, and `failover`, while [the pluggable-backend implementation plan
reads the `backends.<name>` block (per-backend model/flags):

```json
{
  "default": "claude",
  "aspects": { "implementation": "codex", "reconcile": "codex" },
  "failover": { "enabled": true, "order": ["claude", "codex"] },
  "backends": {
    "codex": { "model": "gpt-5-codex", "extra_streaming_argv": ["--reasoning", "high"] }
  }
}
```

- New `backend_config.py` owns the whole file; `BackendConfigError`
  (verbatim-surfaced) on malformed JSON, unknown aspect key, or unknown backend
  name (lists `resolve_backend`'s registered names).
- All keys optional; an absent file = today's behavior (default `claude`, no
  per-aspect map, failover off). Each design tolerates the other's keys.

### 4. Wire selection into entrypoints

Add a decorator `with_aspect_backend(aspect_or_resolver)` in `backend_plan.py`,
parallel to `spawn_cwd_from_repo_root`: it reads the bound args, resolves the
aspect's backend from the active plan, and wraps the body in `use_backend(...)`.
Apply to the 5 entrypoints:

- `create_plan`, `generate_detail`, `review_plan_full`, `apply_finding` →
  static aspect string.
- `run_step` → a resolver: `mode == "run"` → `"implementation"`, else `None`
  (review-class modes use the default). Uses `MUTATING_MODES` (`launcher.py:147`).

Stacks cleanly with the existing `@spawn_cwd_from_repo_root` (both are
ContextVar-scoped, save/restore safe under nesting — e.g. `apply_finding`
reached from inside an iterating `create`).

### 5. Failover on recoverable short rate limits (shared helper + both retry loops)

The two loops — `shell.claude_invoke` (`shell.py:191`) and
`launcher.shell_invoker` (`launcher.py:421`) — have identical RATE_LIMIT
branches that wait until `failure.reset_epoch` then retry. Factor the failover
decision into a shared helper in `backend_plan.py`:

```python
def next_failover_backend(current, reset_epoch) -> CliBackend | None
```

A per-process cooldown registry (`{backend_name: reset_epoch}`, a ContextVar so
it's test-isolated) records each recoverably limited backend's reset. On a
recoverable `RATE_LIMIT`, when `plan.failover_enabled`:

1. Record `current_backend -> reset_epoch` (or `now + FALLBACK` if unknown).
2. Pick the next backend in `failover_order` that is **not** in cooldown and
   **passes `shutil.which`** (skip uninstalled).
3. If found → retry the current limited call with `next`, print a
   `retrying current call with <backend>` hint, then restore the previously
   active backend after that retry scope; `continue` the loop (no wait).
4. If none available → existing behavior: wait until the **soonest** cooldown
   reset, clear cooldowns, retry.

The confirmed Cursor `PLAN_QUOTA` classification is terminal, so it never
enters this failover branch or receives a fallback policy. Failover off (the
default) preserves ordinary short-limit wait-then-retry behavior exactly.

### 6. CLI surface

- `parser.py`: add `--backend-<aspect>` for the 5 aspects and
  `--failover` / `--no-failover` global flags (alongside `--backend`).
- `app.py`: after resolving the global backend (unchanged block at
  `app.py:378-388`), build and `set_active_plan(...)` from flags + env + config.
  Preflight `shutil.which` for every distinct backend the plan can select
  (extend the existing explicit-backend check at `app.py:396`).
- New `backends` subcommand group (`cli/backends_cmd.py`, registered in
  `COMMAND_MODULES`), no claude calls:
  - `plan-tool backends show` — print the resolved plan (aspect → backend,
    failover chain), with the source of each choice.
  - `plan-tool backends adopt-recommended` — parse
    `docs/evidence/backend-recommendations.md` and write the `aspects` map into
    `.plan-tool/backends.json`. Reuse `bench.RECOMMENDATIONS_REL`
    (`bench.py:2083`); add a `parse_recommendations(text) -> dict[aspect,name]`
    reader next to the writer in `bench.py` (parses `## <family>` +
    ``**Recommended backend:** `x` `` lines). Refuses if the doc's corpus hash
    is stale vs current (the doc already records both) unless `--force`.
  - `plan-tool backends set <aspect> <backend>` / `unset <aspect>` — edit the
    config file (sorted-keys, stable-indent writer like `jira_config`).

## Open questions

1. **Failover order default** — when `failover.order` is omitted but
   `failover.enabled` is true, default to "every other registered backend in
   registration order," or require an explicit order? Recommendation: default
   to all-others, so enabling failover needs one key.
2. **Per-aspect failover** — should the failover chain be global (as designed)
   or per-aspect (e.g. `implementation` fails over codex→claude but `detail`
   does not)? Recommendation: global for v1; the cooldown registry already
   makes a later per-aspect refinement additive.
3. **Cooldown persistence** — keep cooldowns in-process (reset each invocation)
   or persist to `.plan-tool/` so a fresh `plan-tool run` knows a backend is
   still limited? Recommendation: in-process for v1; revisit if users chain
   many short invocations during one quota window.
