- MEDIUM `[structural-request-routing]`: Architecture and the Scope-blocking risk promise that structural feedback is rejected “before a backend call,” while Testing and Acceptance only require an `add-row`, `remove-row`, or relation-endpoint attempt to fail before publication. Steps 4 (`Reject invalid live-row feedback selections...`), 5 (`Enroll full-stage artifacts...`), 6 (`Merge allowlisted existing-row modifications...`), and 9 (`Run one bounded patch request...`) have no deterministic pre-call signal for that distinction: at HEAD, `plan_tool/roadmap_artifacts:FeedbackRow` carries only `id`, `target`, free-text `request`, `state`, and `proposed_response`, so a row-target request to remove a row is indistinguishable from a routine edit until backend output is parsed.
  - Fix: Choose a deterministic structural-request boundary or limit rejection to after the bounded reply and before publication, then align the Architecture, risk, steps 4–6 and 9, Testing, and Acceptance criteria.
- HIGH `[recovery-marker-directory-durability]`: Step 8 (`Publish fenced recoverable revisions...`), the Architecture publication protocol, Publication-blocking risk, Testing, and recovery acceptance promise crash recovery from durable `prepared`, `replacing`, `checkpointing`, and `checkpointed` markers, but the protocol fsyncs private directories before `prepared` and destination directories after replacement without requiring the marker’s parent directory to be fsynced after each marker write or replacement. `plan_tool/fileio:durable_write_text` currently fsyncs its temporary file before `os.replace` but not the parent directory, so it does not supply that guarantee; a crash can retain canonical replacements while losing the marker entry needed to recover them.
  - Fix: Define every phase-marker transition as durable only after both marker contents and its directory entry are synced, and cover crashes immediately after each transition.
- HIGH `[patch-operation-identities]`: The Architecture’s per-collection allowlist contains live design-row targets and relation endpoints, then says `respond-feedback` may name an allowlisted ID, while selectors use `artifact:<feedback id>` and the acceptance criterion requires exactly one response for every selected feedback row. `roadmap_artifacts.FeedbackRow` keeps `id` and `target.row_id` as distinct identities; Steps 3, 5, 6, and 9 never say which identity a response operation carries. Two selected feedback rows may target one design row, so a target-keyed response cannot prove the required one-response-per-selection rule.
  - Fix: define separate operation identity rules for design-row modifications/prose and selected feedback responses, including the exact duplicate and unknown-response failures.
- HIGH `[published-session-checkpoint-order]`: The Architecture’s publication and session-record paragraphs require the durable published record to include checkpoint outcome, require checkpoint failure recovery to restore that record, and create the Git checkpoint before the `checkpointed` marker; Steps 3, 7, 8, and 9, Testing, and the successful-session criterion all consume that contract. The plan never establishes whether the session record is staged before the checkpoint, finalized after it, or committed separately: before the checkpoint it cannot report its actual outcome, while after it it is absent from the checkpointed candidate set.
  - Fix: define one ordered record-finalization and recovery protocol that states which fields are pre-checkpoint, how the final checkpoint result is recorded, and which commit/recovery boundary owns the record.
- MEDIUM `[targeted-patch-retry-policy]`: Step 9 (`Run one bounded patch request per dependent collection...`) and the Architecture say one bounded request advances only after upstream validation, while the Publication-blocking risk and Testing require exhausted retries and every attempt outcome. The plan does not define whether “one” is one backend call or one logical collection with retries, the retry budget, or which failed collection is retried before downstream work stops.
  - Fix: state the targeted-request retry budget, correction scope, downstream-stop rule, and matching attempt-record behavior.
- MEDIUM `[load-roadmap-lock-snapshot]`: The Architecture says `load_roadmap` takes the transaction guard “briefly to recover an abandoned session before loading artifacts,” while Input, Step 11 (`Show the latest published...`), Testing, and the lock acceptance criterion require read-only views to recover before rendering. It does not say whether an active writer makes a view wait or fail, or whether the guard remains held across all four reads; `roadmap_view.load_roadmap` currently reads those paths independently, so releasing after recovery permits a mixed revision view.
  - Fix: define active-writer view behavior and the lock window that gives `load_roadmap` one recovered, internally consistent artifact set.
- MEDIUM `[deferred-downstream-publication]`: Step 9 promises one request per dependent collection and publication only of a complete gate-valid result, but the Architecture session-record paragraphs and Deferred section require a published session to record “deliberately deferred downstream work.” The plan never says what may be deferred or whether deferral cancels publication, so one implementation can skip an affected collection while another must fail the session.
  - Fix: define the trigger, record shape, and publication rule for deferred work, including whether an affected collection may ever be omitted
