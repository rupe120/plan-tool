- HIGH `[semantic-receipt-id]`: Step 2 (`Define immutable, redacted escalation receipts for one selected artifact`) cannot compute the Architecture receipt identity as written: the receipt records a “semantic receipt id,” yet that id “covers every redacted receipt field except creation time,” which includes itself. The same impossible identity drives the `<semantic-id>.json` path, `--view escalations` validation, Testing’s identity/reuse/collision cases, and acceptance criteria 1 and 3.
  - Fix: define a canonical semantic-id preimage that excludes both `creation_time` and the derived `semantic_id`, then use that one definition for storage, validation, reuse, collision checks, and tests.
- HIGH `[receipt-artifact-path-boundary]`: Step 2’s stored selected-artifact path and step 4 (`Wire exclusive escalation creation and log-free receipt views`) leave `--view escalations` without a rule that binds that path to the selector’s fixed roadmap artifact. Architecture says views recompute freshness from the stored receipt, while Input forbids consuming repository code; a self-consistent forged receipt can carry a valid public semantic id and an arbitrary path unless the view derives and verifies it. `plan_tool/roadmap.py:STAGES` and `plan_tool/roadmap_view.py:load_roadmap` already resolve artifacts from the selector and roadmap directory rather than arbitrary stored paths.
  - Fix: make the selector-derived stage path authoritative for receipt creation and views, reject any stored-path mismatch before reading it, and test that a validly re-identified substituted path cannot cause a read or handoff.
- MEDIUM `[creation-telemetry-terminal]`: Step 3 (`Create receipts atomically with redacted escalation lifecycle evidence`) has no valid event matrix for rejected creation commands: Architecture requires “exactly one” preflight event and terminal result event, but `mode-rejected`, `selector-rejected`, and `reason-rejected` exist only as preflight verdicts while terminal outcomes allow only `created`, `reused`, `write-failed`, and `interrupted`. Testing’s telemetry-nullability promise and acceptance criterion 2 therefore cannot verify a closed lifecycle for a rejected command.
  - Fix: define whether rejected preflight emits a closed terminal result or has no result event, then align event counts, terminal vocabulary, nullability, and tests with that choice.
- MEDIUM `[receipt-schema-version]`: Receipt versioning is undefined: Architecture calls the receipt “versioned” but its closed “records only” field list contains no schema version, while the view contract must identify an “unsupported” receipt. Step 2’s schema, step 4’s view, Testing’s schema validation, and acceptance criteria 1 and 4 cannot distinguish supported from unsupported data.
  - Fix: Add an explicit schema-version field to the closed receipt and semantic-identity contract, with supported and unsupported view outcomes.
- HIGH `[creation-telemetry-redaction]`: Creation telemetry’s redaction rule does not cover generic run-log metadata. Architecture says events never contain reviewer content, and Risks, Testing, and acceptance criterion 5 require absence tests, but step 3’s `plan_tool.run_log.py` integration has no rule for `RunLogWriter.start`, which records raw `argv`; an invalid `--escalation-reason` can itself contain feedback prose before it becomes `reason-rejected`.
  - Fix: Define redaction for the complete creation-log envelope, including run-start and error paths, so it stores only validated closed values and permitted selector facts.
- MEDIUM `[artifact-canonicality]`: Architecture names `artifact-not-canonical` as a selector verdict and Input requires a selected canonical artifact, but step 1 (`Define strict escalation-receipt selection and reason capture independently of local revision eligibility`) never defines canonicality for receipt creation. `plan_tool.roadmap_revision:preflight_feedback_revision` currently uses exact parse/render byte equality, so implementers can reasonably preserve that rule or accept edited source bytes.
  - Fix: Define the canonical-artifact test for receipt selection and require its verdict, telemetry, and tests to use that one rule.
- MEDIUM `[receipt-selection-extraction]`: Step 1 combines sharing or extracting existing selector logic from `plan_tool.roadmap_revision.py` into `plan_tool.roadmap_feedback.py` with new receipt behavior: artifact-target acceptance, new selector verdicts, and reason capture. Its refactor classification therefore mixes behavior-preserving reorganization with feature work, making regressions in the existing local writer hard to isolate.
  - Fix: Split the behavior-preserving selector extraction from the new escalation selection and reason feature, with the feature step depending on the extracted contract.
- MEDIUM `[receipt-creation-race]`: Architecture requires an identical `<semantic-id>.json` receipt to reuse and a nonidentical collision to fail without overwrite, but step 3’s atomic-creation contract, Testing, and acceptance criterion 3 define no concurrent-create rule. Two creators can both observe no file and then race to publish the same path, defeating either reuse or collision handling.
  - Fix: define a concurrent exclusive-create and re-read rule that preserves one immutable receipt, treats a losing identical creator as reuse, and rejects a nonidentical collision

## Conceptual completeness — reported, not auto-applied

Coverage gaps in the plan's own ideas are reported for visibility in this bare-plan audit. Apply actions for this axis are withheld until a complete detail bundle exists, so these findings are informational for now.

- MEDIUM `[receipt-creation-race]`: The immutable receipt contract has no concurrent-create rule. Architecture requires one `<semantic-id>.json` to reuse identical evidence without a write and reject a nonidentical collision, but Testing and acceptance criterion 3 cover only ordinary failure and interruption; `plan_tool/fileio.py:atomic_write_text` uses overwrite-capable `os.replace`, so two creators that both observe no receipt can overwrite the first receipt and both report `created`.
  - Fix: add a concurrent receipt-creation acceptance case and tests requiring one durable creator, reuse only after matching durable evidence, collision rejection otherwise, and no overwrite or partial receipt.
- MEDIUM `[receipt-view-source-unavailable]`: Step 4’s view must recompute freshness, but Architecture only defines malformed, unsupported, mismatched, and stale *receipts*; it does not define the visible no-route result when the selected artifact is missing, unreadable, or unparsable. The stale-evidence Risk, Testing’s live-freshness coverage, and acceptance criterion 4 cover changed bytes, not an unavailable source, so an implementation can fail the view instead of preserving invalid evidence without a handoff.
  - Fix: add a source-unavailable freshness result that keeps the receipt visible, suppresses the handoff and run log, and is covered by an acceptance criterion and view tests
